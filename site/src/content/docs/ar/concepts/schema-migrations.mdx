عندما تغيّر ملف مخطط، يجب أن تتبعه قاعدة البيانات: السمة الجديدة تحتاج إلى عمود، و
العلاقة الجديدة إلى جدول ربط. يحسب Verdin هذا الترحيل نيابةً عنك، ويعرضه قبل تنفيذه،
ولا يحذف البيانات أبدًا دون أن يُطلب منه ذلك. تشرح هذه الصفحة كيف.

## من المخطط إلى الخطة

لا يطلب منك Verdin أبدًا كتابة ترحيل. إنه يقارن بين نموذجين لقاعدة البيانات:

1. **المرغوب**: مشتق من ملفات `schema/*.json`، مع كل جدول وعمود وفهرس
   تحتاجه (بما في ذلك جداول الربط وجداول Verdin الخاصة).
2. **الحالي**: النموذج الذي تركه آخر ترحيل، مخزّن في قاعدة البيانات كلقطة (snapshot).

الفرق هو **خطة**: قائمة خطوات، لكل منها SQL الخاص بقاعدة بياناتك ومستوى
مخاطر. لأن الخطة تأتي من اللقطة المخزّنة لا من فحص قاعدة
البيانات، فهي حتمية ومتطابقة في كل لهجة SQL. التغييرات التي تنتج SQL نفسه
على قاعدة بياناتك، مثل `integer` إلى `biginteger` على SQLite، لا تنتج أي خطوة.

يطبعها `verdin migrate plan`. هنا أُعيدت تسمية السمة `excerpt` في المدونة إلى
`summary` في `article.json`:

```text title="Terminal"
$ verdin migrate plan
  1. [safe] add column articles.summary
       ALTER TABLE "articles" ADD COLUMN "summary" text
  2. [destructive] drop column articles.excerpt
       ALTER TABLE "articles" DROP COLUMN "excerpt"

requires: verdin migrate apply --allow destructive

possible renames (pass them to keep the data):
  --rename-column articles.excerpt=summary
```

## مستويات المخاطر

| المخاطرة | الخطوات | السبب |
| --- | --- | --- |
| **safe** (آمن) | إنشاء جدول، وإضافة عمود، وإضافة فهرس غير فريد أو حذفه، وإعادة تسمية جدول أو عمود. | لا يمكن أن تفقد بيانات أو تفشل على الصفوف الموجودة. |
| **risky** (محفوف بالمخاطر) | تغيير نوع عمود، وإضافة فهرس فريد إلى جدول موجود، وإعادة بناء جدول SQLite (لا يستطيع SQLite تعديل الأعمدة في مكانها). | قد تفشل على البيانات الموجودة (تكرارات، أو قيم لا تتحوّل)، أو تعيد كتابتها. |
| **destructive** (مُدمِّر) | حذف عمود أو جدول. | تحذف بيانات. |

كل عمود سمة يقبل القيمة الفارغة (يُتحقق من `required` عند النشر)، لذا فإن إضافة
سمات، مطلوبة أو لا، آمنة دائمًا. إضافة `"unique": true` إلى عنوان المقالة في المدونة
محفوفة بالمخاطر، لأن العناوين الموجودة قد تتكرر:

```text title="Terminal"
$ verdin migrate plan
  1. [risky] create unique index articles_title_uq
       CREATE UNIQUE INDEX "articles_title_uq" ON "articles" ("title", "locale", "publication_state")

requires: verdin migrate apply --allow risky
```

قبل تنفيذ أول تعليمة، يجري Verdin فحصًا لكل خطوة محفوفة بالمخاطر يمكن أن تفشل، مثل
البحث عن التكرارات قبل إنشاء فهرس فريد، ويتوقف برسالة إذا وجد أحد الفحوص
مشكلة. لم يتغير شيء عند تلك النقطة.

## تطبيق خطة

ينفّذ `verdin migrate apply` الخطوات المعلّقة. ويأخذ أعلى مستوى مخاطر تقبله:

```sh title="Terminal"
verdin migrate apply                        # الخطوات الآمنة فقط (الافتراضي)
verdin migrate apply --allow risky          # وأيضًا تغييرات الأنواع والفهارس الفريدة
verdin migrate apply --allow destructive    # وأيضًا عمليات الحذف
```

إذا كانت أي خطوة فوق مستوى المخاطر المسموح به، فلا يُنفَّذ شيء:

```text title="Terminal"
$ verdin migrate apply
Error: these steps need explicit approval:
  create unique index articles_title_uq (risky)
```

يأخذ الترحيل قفلًا، فلا تُرحِّل نسختان في الوقت نفسه أبدًا. على PostgreSQL وSQLite
تُنفَّذ الخطة كاملة في معاملة واحدة: أي إخفاق يتراجع عن كل شيء. أما MySQL وMariaDB
فتعتمدان كل تعليمة DDL بمفردها، لذا يسجّل Verdin تقدّمه خطوة بخطوة في
سجل (journal). بعد الإخفاق، أصلح السبب وشغّل `verdin migrate apply` من جديد: يستأنف من
الخطوة الفاشلة إذا لم تتغير الخطة، ويرفض إذا تغيّر المخطط في الأثناء.

## إعادة التسمية

السمة المحذوفة والسمة الجديدة تبدوان كحذف وإضافة، ما سيُفقد بيانات
العمود. لا يخمّن Verdin إعادة التسمية أبدًا. يقترحها عندما يختفي عمود ويظهر عمود من
النوع نفسه في الجدول نفسه (أو يختفي جدول ويظهر آخر بالأعمدة نفسها)،
وتؤكدها أنت صراحةً:

```text title="Terminal"
$ verdin migrate apply --rename-column articles.excerpt=summary
applied 1 step
```

- يعيد `--rename-column TABLE.OLD=NEW` تسمية عمود؛ و`TABLE` هو جدول نوع المحتوى
  (`collectionName` الخاص به).
- يعيد `--rename-table OLD=NEW` تسمية جدول. وتُعاد تسمية جداول الربط الخاصة بالنوع معه.
- مرّر الخيارات نفسها إلى `migrate plan` لمعاينة النتيجة.

إعادات التسمية خطوات آمنة. ويقدّم منشئ أنواع المحتوى الاقتراحات نفسها في نافذة الحوار الخاصة به.

## `verdin dev` و`verdin start`

| | `verdin dev` | `verdin start` |
| --- | --- | --- |
| عند بدء التشغيل | يطبّق الخطوات الآمنة المعلّقة. ويتوقف إذا كانت هناك خطوات أخرى معلّقة. | يرفض البدء ما دامت أي خطوة معلّقة، إلا إذا مرّرت `--migrate`، الذي يطبّق الخطوات الآمنة أولًا. |
| تغييرات المخطط أثناء التشغيل | يعرض **منشئ أنواع المحتوى** الخطة مع مخاطرها واقتراحات إعادة التسمية، ويطبّقها عند تأكيدك، بما في ذلك الخطوات الأكثر خطورة. التعديلات اليدوية (أو `git pull`) يلتقطها مراقب ملفات: تُطبَّق الخطط الآمنة ويُعاد تحميل التطبيق؛ وتُسجَّل الأخرى ويبقى التطبيق العامل كما كان. | المخطط للقراءة فقط. انشر الملفات الجديدة ثم رحِّل. |

يرحّل المنشئ قاعدة البيانات أولًا، ثم يكتب ملفات المخطط، ثم يعيد تحميل
API المحتوى وAPI الإدارة وGraphQL ومستند OpenAPI دون إعادة تشغيل. إذا فشل
الترحيل، تبقى الملفات والتطبيق العامل كما كانا.

في الإنتاج، شغّل `verdin migrate plan` على نسخة من قاعدة البيانات، ثم
`verdin migrate apply` بمستوى المخاطر الذي تقبله، قبل تشغيل الإصدار الجديد. راجع
[الترقية](/ar/migrate/upgrading/) و[النسخ الاحتياطية](/ar/deploy/backups/).

## مقارنة مع Strapi

يزامن Strapi قاعدة البيانات مع المخطط عند بدء التشغيل، دون أن يعرض ما
سيفعله. أما Verdin فيخطط أولًا، ويعرض الـ SQL، ولا يطبّق دون طلب إلا الخطوات الآمنة، و
يتطلب `--allow` لأي شيء قد يفشل أو يحذف بيانات.

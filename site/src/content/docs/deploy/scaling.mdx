Verdin keeps its state in the database, so you can run several instances of the same
project behind a load balancer for availability or load. This page lists what the
instances share, what each one keeps to itself, and the settings that matter.

## Checklist

- **A shared database.** PostgreSQL, MySQL or MariaDB. SQLite is a file on one machine
  and does not work with several instances.
- **The same configuration everywhere.** Every instance uses the same `verdin.toml`,
  schema files and secrets (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). With different secrets, sessions and API tokens made on
  one instance are refused by the others.
- **Production mode.** Run `verdin start`, not `verdin dev`. Change the schema in
  development, commit it, and migrate once per deploy.
- **Shared media storage.** Use the S3 provider (`[upload] provider = { name = "s3", … }`),
  or mount the same volume on every instance for the local provider.
- **Health checks.** Point the load balancer at `GET /_ready`, which answers `503` when
  the database cannot be reached. `GET /_health` only says the process is up; use it for
  liveness.
- **The shared event bus.** Set `[cluster].bus = "database"` on every instance, so that
  realtime events, presence, cache invalidation and search updates reach all of them (see
  [Shared event bus](#shared-event-bus)).
- **Plugin jobs on one instance.** Set `[plugins].run_jobs = false` on every instance but
  one; otherwise each instance runs the scheduled jobs.
- **Metrics per instance.** With `[metrics].enabled = true`, each instance serves its own
  `/_metrics`; scrape each one.

## Migrations with several instances

`verdin start --migrate` is safe to run on every instance at once. Each migration run
holds a lock in the database (an advisory lock on PostgreSQL, `GET_LOCK` on MySQL and
MariaDB, waiting up to 60 seconds), so the first instance applies the steps and the
others find the database up to date.

During a rolling deploy, instances of the old version keep running against the
migrated database for a while. Safe steps create tables, add nullable or defaulted
columns and indexes, widen text columns or add enum values, which the old version
does not notice. Apply risky or destructive steps (`verdin migrate apply --allow
risky|destructive`) in a separate deploy, once no instance of the old schema needs the
data. See [Schema migrations](/concepts/schema-migrations/).

## What is shared

| What | How |
| --- | --- |
| Admin sessions, API tokens, permissions | In the database; no sticky sessions needed. |
| Feature switches, plugin switches, locales, review workflows | In the database. Each instance reads them again every `[server].sync_interval_secs` (10 s), so a change made on one instance reaches the others within that delay. |
| Webhook deliveries | A queue in the database. An instance claims a delivery before sending it, so each goes out once. |
| Scheduled releases | Claimed in the database before they run, so each runs once. |
| Daily digest | Each day's run is claimed in the database, so admins get one email. |
| Passkey challenges | Spent challenges are recorded in the database, so each is answered once across instances. |
| Audit log pruning | Runs on every instance; deleting old rows twice is harmless. |
| Plugin key-value store | In the database. |
| Realtime events, presence and soft locks | With the [event bus](#shared-event-bus): a client connected to any instance receives the events of all of them and sees every admin on an entry. |
| The anonymous response cache | With the event bus, a write on any instance empties the cache of every instance. |
| The search index | With the event bus, every instance re-reads and indexes the entries the others change. |
| Transformed images | With the event bus, a changed or deleted file leaves every instance's transform cache. |

## What stays on each instance

- **Rate limits** are counted by each instance. With `n` instances, a client can make
  up to `n` times `[api].public_rate_limit` requests per minute. Enforce a global limit
  at the load balancer if you need one.
- **Without the event bus** (`[cluster].bus = "none"`, the default), realtime events and
  presence are those of the instance a client is connected to (use sticky sessions for
  the event streams), a write empties only its own instance's response cache (keep
  `[api].cache_ttl_secs` to a few seconds, or `0`), and the search index follows only
  the writes its instance makes.
- **The search index** (`[search]`) lives on each instance's disk. With the event bus,
  instances index each other's changes as they happen; an instance that starts with an
  empty index directory builds it from the database. Changes made while an instance was
  down reach its index when the index is rebuilt: delete the directory before starting
  it, or rebuild after a deploy.
- **Image transformations** (`[upload.transforms]`) are cached per instance under
  `cache_dir`. Put a CDN in front of `/uploads` to share them.
- **Scheduled plugin jobs**: see `run_jobs` above.

## Shared event bus

Some things happen in memory: the realtime streams, who is editing which entry, the
anonymous response cache, the search index. The event bus carries them from the
instance where they happen to the others.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Or `VERDIN_CLUSTER__BUS=database`, on every instance. The bus uses the project's
database, so it needs no other service:

- **PostgreSQL**: an instance writes each event to the `vd_cluster_events` table and
  wakes the others with `NOTIFY`. Each instance keeps one of its pool connections for
  `LISTEN`. The notification only names the sender, so events of any size stay
  under PostgreSQL's 8000-byte limit. If the connection drops, the instance reconnects
  and reads the table to catch up. It also reads the table every 30 seconds in case a
  notification is lost.
- **MySQL, MariaDB and SQLite**: each instance reads new rows of `vd_cluster_events`
  every `poll_interval_ms` (1000 by default). The query uses the primary key, so reading
  an empty table costs little. Lower the interval for faster updates; one instance's
  change reaches the others within the interval.

What travels: content writes (to the realtime streams, the response cache and the search
index, which reads the changed entry again), media changes (streams, cache, transform
cache), presence heartbeats and comment and task notices for the admin. Each instance
ignores its own events. Webhooks, CDN purges, history, audit logs and plugin hooks do
not travel: the instance that made the change runs them once.

Rows are deleted after 10 minutes. A new instance starts with the next event, not the
earlier ones. An instance that cannot keep up, or loses its database connection, drops
events rather than holding a write. The `verdin_cluster_events_total` metric counts
events sent, received and dropped (see [Monitoring](/deploy/monitoring/#prometheus-metrics)).

Each instance names itself on the bus with a random id at each start, or with
`[cluster].instance_id` if you set it (a pod name, for example). The id only
tells instances apart; nothing else depends on it.

With one instance, leave `bus` at `none`: events stay in memory and nothing is written.

Redis and NATS backends are not available yet. The database bus covers every supported
database with nothing else to run.

## Settings

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Set `run_jobs` per instance with `VERDIN_PLUGINS__RUN_JOBS=false`.

## Database connections

Each instance opens up to `[database].pool_max` connections (10 by default). Keep
`instances × pool_max` below the server's limit, with room for migrations, backups and
maintenance. PostgreSQL's default limit is 100 connections. On PostgreSQL, the event bus
keeps one of each instance's connections for `LISTEN`.

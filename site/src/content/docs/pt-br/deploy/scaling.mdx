O Verdin mantém o seu estado no banco de dados, então você pode rodar várias instâncias do
mesmo projeto atrás de um load balancer para ter disponibilidade ou dar conta da carga. Esta
página lista o que as instâncias compartilham, o que cada uma guarda para si e as configurações
que importam.

## Checklist

- **Um banco de dados compartilhado.** PostgreSQL, MySQL ou MariaDB. O SQLite é um arquivo em
  uma máquina e não funciona com várias instâncias.
- **A mesma configuração em todo lugar.** Todas as instâncias usam o mesmo `verdin.toml`, os
  mesmos arquivos de schema e os mesmos segredos (`VERDIN_ADMIN_JWT_SECRET`,
  `VERDIN_TOKEN_PEPPER`, `VERDIN_SSO_<ID>_SECRET`…). Com segredos diferentes, as sessões e os
  tokens de API criados em uma instância são recusados pelas outras.
- **Modo de produção.** Rode `verdin start`, não `verdin dev`. Altere o schema em
  desenvolvimento, commite-o e migre uma vez por deploy.
- **Armazenamento de mídia compartilhado.** Use o provedor S3
  (`[upload] provider = { name = "s3", … }`), ou monte o mesmo volume em todas as instâncias
  para o provedor local.
- **Health checks.** Aponte o load balancer para `GET /_ready`, que responde `503` quando o
  banco de dados não pode ser alcançado. `GET /_health` só diz que o processo está de pé;
  use-o para liveness.
- **O barramento de eventos compartilhado.** Defina `[cluster].bus = "database"` em todas as
  instâncias, para que eventos de tempo real, presença, invalidação de cache e atualizações da
  busca cheguem a todas elas (veja [Barramento de eventos compartilhado](#barramento-de-eventos-compartilhado)).
- **Jobs de plugins em uma única instância.** Defina `[plugins].run_jobs = false` em todas as
  instâncias menos uma; caso contrário, cada instância roda os jobs agendados.
- **Métricas por instância.** Com `[metrics].enabled = true`, cada instância serve o seu próprio
  `/_metrics`; faça o scrape de cada uma.

## Migrações com várias instâncias

`verdin start --migrate` pode rodar em todas as instâncias ao mesmo tempo com segurança. Cada
execução de migração mantém um lock no banco de dados (um advisory lock no PostgreSQL,
`GET_LOCK` no MySQL e no MariaDB, esperando até 60 segundos), então a primeira instância aplica
os passos e as outras encontram o banco de dados já atualizado.

Durante um rolling deploy, as instâncias da versão antiga continuam rodando contra o banco de
dados migrado por um tempo. Os passos seguros criam tabelas, adicionam colunas que aceitam nulo
ou têm valor padrão e índices, ampliam colunas de texto ou adicionam valores de enum, o que a
versão antiga não percebe. Aplique os passos arriscados ou destrutivos (`verdin migrate apply
--allow risky|destructive`) em um deploy separado, quando nenhuma instância do schema antigo
precisar mais dos dados. Veja [Migrações de schema](/pt-br/concepts/schema-migrations/).

## O que é compartilhado

| O quê | Como |
| --- | --- |
| Sessões de administração, tokens de API, permissões | No banco de dados; não é preciso sticky sessions. |
| Interruptores de recursos, interruptores de plugins, idiomas, fluxos de revisão | No banco de dados. Cada instância os relê a cada `[server].sync_interval_secs` (10 s), então uma alteração feita em uma instância chega às outras dentro desse intervalo. |
| Envios de webhooks | Uma fila no banco de dados. Uma instância reserva um envio antes de mandá-lo, então cada um sai uma única vez. |
| Lançamentos agendados | Reservados no banco de dados antes de rodar, então cada um roda uma única vez. |
| Resumo diário | A execução de cada dia é reservada no banco de dados, então os administradores recebem um único e-mail. |
| Desafios de chaves de acesso | Os desafios usados são registrados no banco de dados, então cada um é respondido uma única vez entre as instâncias. |
| Limpeza do log de auditoria | Roda em todas as instâncias; apagar linhas antigas duas vezes não causa problema. |
| Armazenamento chave-valor dos plugins | No banco de dados. |
| Eventos de tempo real, presença e soft locks | Com o [barramento de eventos](#barramento-de-eventos-compartilhado): um cliente conectado a qualquer instância recebe os eventos de todas e vê todos os administradores em uma entrada. |
| O cache de respostas anônimas | Com o barramento de eventos, uma escrita em qualquer instância esvazia o cache de todas. |
| O índice de busca | Com o barramento de eventos, cada instância relê e indexa as entradas que as outras alteram. |
| Imagens transformadas | Com o barramento de eventos, um arquivo alterado ou apagado sai do cache de transformações de todas as instâncias. |

## O que fica em cada instância

- **Os limites de taxa** são contados por cada instância. Com `n` instâncias, um cliente pode
  fazer até `n` vezes `[api].public_rate_limit` requisições por minuto. Imponha um limite
  global no load balancer se precisar de um.
- **Sem o barramento de eventos** (`[cluster].bus = "none"`, o padrão), os eventos de tempo
  real e a presença são os da instância à qual o cliente está conectado (use sticky sessions
  para os streams de eventos), uma escrita esvazia apenas o cache de respostas da sua própria
  instância (mantenha `[api].cache_ttl_secs` em poucos segundos, ou em `0`) e o índice de
  busca acompanha apenas as escritas da sua instância.
- **O índice de busca** (`[search]`) fica no disco de cada instância. Com o barramento de
  eventos, as instâncias indexam as alterações umas das outras à medida que acontecem; uma
  instância que inicia com um diretório de índice vazio o constrói a partir do banco de dados.
  As alterações feitas enquanto uma instância estava fora do ar chegam ao seu índice quando ele
  é reconstruído: apague o diretório antes de iniciá-la, ou reconstrua depois de um deploy.
- **As transformações de imagens** (`[upload.transforms]`) ficam em cache por instância em
  `cache_dir`. Coloque uma CDN na frente de `/uploads` para compartilhá-las.
- **Os jobs agendados de plugins**: veja `run_jobs` acima.

## Barramento de eventos compartilhado

Algumas coisas acontecem em memória: os streams de tempo real, quem está editando qual
entrada, o cache de respostas anônimas, o índice de busca. O barramento de eventos as leva da
instância em que acontecem para as outras.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Ou `VERDIN_CLUSTER__BUS=database`, em todas as instâncias. O barramento usa o banco de dados do
projeto, então não precisa de nenhum outro serviço:

- **PostgreSQL**: uma instância grava cada evento na tabela `vd_cluster_events` e acorda as
  outras com `NOTIFY`. Cada instância reserva uma das conexões do seu pool para `LISTEN`. A
  notificação só informa o remetente, então eventos de qualquer tamanho ficam abaixo do limite
  de 8000 bytes do PostgreSQL. Se a conexão cair, a instância reconecta e lê a tabela para
  se atualizar. Ela também lê a tabela a cada 30 segundos, caso uma notificação se perca.
- **MySQL, MariaDB e SQLite**: cada instância lê as novas linhas de `vd_cluster_events` a cada
  `poll_interval_ms` (1000 por padrão). A consulta usa a chave primária, então ler uma tabela
  vazia custa pouco. Diminua o intervalo para atualizações mais rápidas; a alteração de uma
  instância chega às outras dentro do intervalo.

O que viaja: escritas de conteúdo (para os streams de tempo real, o cache de respostas e o
índice de busca, que relê a entrada alterada), alterações de mídia (streams, cache, cache de
transformações), batimentos de presença e avisos de comentários e tarefas para a administração.
Cada instância ignora os seus próprios eventos. Webhooks, purgas de CDN, histórico, logs de
auditoria e hooks de plugins não viajam: a instância que fez a alteração os executa uma única
vez.

As linhas são apagadas após 10 minutos. Uma nova instância começa com o próximo evento, não com
os anteriores. Uma instância que não consegue acompanhar, ou que perde a conexão com o banco de
dados, descarta eventos em vez de segurar uma escrita. A métrica `verdin_cluster_events_total`
conta os eventos enviados, recebidos e descartados (veja
[Monitoramento](/pt-br/deploy/monitoring/#métricas-prometheus)).

Cada instância se identifica no barramento com um id aleatório a cada início, ou com
`[cluster].instance_id`, se você o definir (o nome de um pod, por exemplo). O id só serve para
distinguir as instâncias; nada mais depende dele.

Com uma única instância, deixe `bus` em `none`: os eventos ficam em memória e nada é gravado.

Os backends Redis e NATS ainda não estão disponíveis. O barramento de banco de dados cobre todos
os bancos de dados compatíveis sem nada mais para rodar.

## Configurações

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Defina `run_jobs` por instância com `VERDIN_PLUGINS__RUN_JOBS=false`.

## Conexões com o banco de dados

Cada instância abre até `[database].pool_max` conexões (10 por padrão). Mantenha
`instâncias × pool_max` abaixo do limite do servidor, com folga para migrações, backups e
manutenção. O limite padrão do PostgreSQL é de 100 conexões. No PostgreSQL, o barramento de eventos
reserva uma das conexões de cada instância para `LISTEN`.

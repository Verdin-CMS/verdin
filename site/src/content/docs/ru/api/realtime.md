Verdin передаёт изменения контента и медиа по мере их фиксации через
[Server-Sent Events](https://developer.mozilla.org/docs/Web/API/Server-sent_events) (SSE).
Каждый подписчик получает только события о том, что ему разрешено читать. На этой странице
описан протокол; как использовать его во фронтенде, см. в разделе
[Обновления в реальном времени](/ru/guides/frontend/realtime/).

## Включение

По умолчанию функция выключена. Включите её в **Настройки → Функции → Реальное время**
(разрешение `features.manage`). Пока она выключена, эндпоинты отвечают `404`.

## Поток контента

```
GET /api/_events
GET /api/_events?types=api::article,api::category
```

| Параметр | Описание |
| --- | --- |
| `types` | Необязательный список UID типов содержимого через запятую; `plugin::upload` — это медиатека. Форма Strapi `api::article.article` тоже работает. Без параметра вы получаете события всех типов, которые вам разрешено читать. |

Аутентификация такая же, как в REST API: API-токен или JWT конечного пользователя в
`Authorization: Bearer …` либо отсутствие заголовка для публичного доступа. На недействительный
токен сервер отвечает `401` ещё до открытия потока.

```sh title="Terminal"
curl -N -H "Authorization: Bearer $VERDIN_TOKEN" \
  'https://cms.example.com/api/_events?types=api::article'
```

```text
event: ready
data: {}

event: entry.publish
data: {"event":"entry.publish","uid":"api::article","documentId":"k2m7q4dx8n5t1v3b9c0e6a2wfr","locale":"en"}

event: media.create
data: {"event":"media.create","uid":"plugin::upload","documentId":"v3k9…","fileId":5}
```

## Сообщения

Первое событие — всегда `ready`. Дальше каждое изменение приходит как SSE-событие с его
именем, а `data` содержит JSON-объект:

| Поле | Когда есть | Описание |
| --- | --- | --- |
| `event` | всегда | Имя события, как в строке SSE `event:`. |
| `uid` | всегда | UID типа содержимого или `plugin::upload` для медиа. |
| `documentId` | всегда | Изменённый документ или файл. |
| `locale` | локализованные типы | Локаль изменённой версии. |
| `fileId` | события медиа | Числовой id файла, который используется в медиаполях. |
| `actorId` | поток админки | Администратор, который внёс изменение, если его внёс администратор. |

| События | Отправляются, когда | Кто их получает |
| --- | --- | --- |
| `entry.create`, `entry.update`, `entry.discard-draft` | Документ создан, сохранён или его черновик отменён | Для типов с черновиками и публикацией — клиенты с `readDrafts` (эти события меняют только черновики). Для остальных типов — клиенты с `find` или `findOne`. |
| `entry.publish`, `entry.unpublish`, `entry.delete` | Документ опубликован, снят с публикации или удалён | Клиенты с `find` или `findOne` для типа |
| `media.create`, `media.update`, `media.delete` | Файл загружен, изменён или удалён | Клиенты с `find` или `findOne` для медиатеки |

События содержат id, а не контент. Чтобы прочитать документ или файл, запросите его через
REST или GraphQL API с обычными разрешениями клиента. События приходят из всех API: REST,
GraphQL, админ-панели, релизов и плагинов.

## Время жизни соединения

- Каждые 15 секунд сервер отправляет комментарий keep-alive.
- Поток контента завершается через час. Переподключитесь (`EventSource` в браузерах делает
  это сам) — при этом токен проверяется заново.
- Событие `lagged` с `data: {"missed": 12}` означает, что клиент читал слишком медленно и
  указанное число событий было потеряно. Заново запросите то, что показывает клиент.
- Повторной отправки нет: события, которые произошли, пока клиент был отключён, позже не
  отправляются.

`EventSource` в браузерах не умеет отправлять заголовок `Authorization`. Для публичного
доступа он работает как есть; с токеном используйте `fetch` с потоковым чтением тела или
SSE-клиент с поддержкой заголовков.

## Поток админки

Админ-панель открывает собственный поток с токеном доступа администратора:

```
GET /admin/api/events?types=api::article
```

В нём те же события контента и медиа для типов, которые администратор может читать (с
`content.read` и `media.read`), включая черновики, а также:

- `actorId` в изменениях, сделанных администраторами;
- события `presence` (см. ниже);
- `comment.create`, `comment.update`, `comment.delete`, `comment.resolve`,
  `comment.reopen`, `task.create`, `task.update` и `task.delete` с `uid`,
  `documentId` и `locale` записи.

Поток админки завершается через 15 минут — это время жизни токена доступа: переподключитесь
с новым токеном.

### Присутствие

Редактор записи сообщает серверу, кто сейчас в записи:

```
POST /admin/api/presence
{ "uid": "api::article", "documentId": "k2m7q4…", "locale": "en", "editing": true }
```

- Отправляйте его примерно каждые 20 секунд, пока редактор открыт. `editing: true` означает,
  что у администратора есть несохранённые изменения. При закрытии редактора отправьте
  `"leave": true`.
- Присутствие истекает через 45 секунд после последнего heartbeat.
- Ответ перечисляет, кто находится в записи: `{ "data": [{ "userId": 3, "name": "Ada Lovelace", "editing": true, "holdsLock": true }] }`.
- `GET /admin/api/presence?uid=&documentId=&locale=` читает тот же список.
- Когда список меняется, потоки админки получают событие `presence` с `uid`, `documentId` и
  `locale` записи и списком в `presence`.

Первый администратор, который всё ещё редактирует запись, держит мягкую блокировку
(`holdsLock`). Редактор показывает её остальным, но не мешает им сохранять. Для чтения
присутствия нужно `content.read` для типа.

## Несколько экземпляров

События и присутствие относятся к тому экземпляру, к которому подключён клиент. За
балансировщиком нагрузки направляйте `/api/_events` и `/admin/api/events` с липкими сессиями
(sticky sessions) или подключайте realtime-клиентов к одному экземпляру. См.
[Масштабирование](/ru/deploy/scaling/).

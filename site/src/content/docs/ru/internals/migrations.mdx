На этой странице объясняется, как `verdin-migrate` приводит базу данных в соответствие со схемой: как он вычисляет разницу, как оценивает каждый шаг и как применяет план так, чтобы сбой никогда не оставлял вас в неведении. Повседневная работа (`verdin migrate plan`, `--allow`, переименования) описана в разделе [миграции схемы](/ru/concepts/schema-migrations/) — прочитайте его сначала; флаги команд — в [справочнике по CLI](/ru/reference/cli/).

1. `verdin-schema` разбирает и проверяет файлы, получая `Schema`.
2. `derive_model` (`derive.rs`) превращает её в `DbModel`: все таблицы, колонки, индексы и внешние ключи, которые нужны схеме, включая таблицы связей и [таблицы платформы](/ru/internals/storage/#таблицы-платформы).
3. Последняя применённая модель читается из `vd_schema_snapshots`.
4. `diff` (`diff.rs`) сравнивает две модели и возвращает список `Change` вместе с подсказками о переименованиях.
5. `build_plan` (`plan.rs`) превращает каждое изменение в SQL для подключённого варианта СУБД, оценивает его и при необходимости добавляет предпроверку.
6. `apply` (`apply.rs`) выполняет план, а затем сохраняет желаемую модель как новый снимок.

**Снимок хранит физическую модель, а не схему.** Когда более поздняя версия Verdin выводит из той же схемы больше таблиц (таблицы связей для новой функции, новую таблицу платформы), diff создаёт их без каких-либо изменений схемы.

**Diff сравнивает со снимком, а не с живой базой данных.** Это делает его детерминированным и позволяет не зависеть от того, как каждая СУБД сообщает о собственной структуре. Verdin не анализирует базу данных, поэтому ручные изменения таблиц (дрейф) не обнаруживаются.

Изменения, которые в диалекте дают тот же DDL, не порождают шагов. Например, `string` → `text` — это изменение типа в PostgreSQL и MySQL, но в SQLite оба типа — `text`, поэтому для SQLite шага нет.

## Категории изменений

У каждого шага есть уровень риска (`Risk` в `diff.rs`). `apply` выполняет только шаги до разрешённого вами уровня и отклоняет весь план ещё до выполнения, если какой-то шаг его превышает.

| Риск | Изменения |
|---|---|
| **Безопасно** | Создать таблицу; добавить колонку, допускающую NULL или со значением по умолчанию; ослабить колонку (разрешить NULL при том же типе и значении по умолчанию); создать неуникальный индекс или уникальный индекс на новой таблице; удалить индекс; переименовать таблицу или колонку |
| **Рискованно** | Добавить колонку `NOT NULL` без значения по умолчанию; иначе изменить тип колонки, допустимость NULL или значение по умолчанию; добавить уникальный индекс на существующую таблицу; пересобрать таблицу SQLite без удаления колонок |
| **Разрушительно** | Удалить колонку; удалить таблицу; пересобрать таблицу SQLite с удалением колонок |

Поскольку все колонки атрибутов допускают NULL (см. [хранение](/ru/internals/storage/#системные-колонки)), добавление атрибутов, в том числе обязательных, всегда безопасно. Значения `enumeration` проверяет приложение, а не колонка, поэтому добавление или удаление значения вообще не меняет DDL.

**Предпроверки** выполняются до первого оператора плана, поэтому рискованный шаг, который не может выполниться успешно, останавливает прогон, пока база данных ещё не тронута:

| Шаг | Предпроверка |
|---|---|
| Уникальный индекс на существующей таблице | В индексируемых колонках нет повторяющихся значений, отличных от NULL |
| Колонка `NOT NULL` без значения по умолчанию | В таблице нет строк |
| Колонка становится `NOT NULL` | В колонке нет NULL |

**Переименования.** Удалённая колонка плюс добавленная колонка того же типа в той же таблице *предлагается* как переименование: `verdin migrate plan` выводит подсказку вроде `--rename-column articles.title=headline`, а конструктор типов содержимого предлагает её принять. Переименование никогда не выводится молча; без флага план удаляет старую колонку и добавляет новую. Удалённая таблица плюс созданная таблица с теми же колонками так же получает подсказку `--rename-table old=new`. Переименования — безопасные шаги, и переименованная таблица забирает с собой свои таблицы связей.

**Пересборка в SQLite.** SQLite не умеет изменять колонку, поэтому, если в таблице есть хоть одно изменение колонки, планировщик заменяет все изменения колонок и индексов этой таблицы одной пересборкой: создать новую структуру под временным именем, скопировать сохраняемые колонки, удалить старую таблицу, переименовать новую, заново создать индексы.

## Режимы

| Команда | Что происходит |
|---|---|
| `verdin start` | Ожидающие шаги останавливают запуск с сообщением, которое отсылает к `verdin migrate plan`. Файлы схемы доступны только для чтения. |
| `verdin start --migrate` | Ожидающие **безопасные** шаги применяются до запуска сервера; всё более рискованное останавливает запуск. |
| `verdin dev` | Безопасные шаги применяются при запуске. Наблюдатель за файлами в `schema/` перезагружает приложение при каждом изменении: безопасные миграции применяются, и приложение подменяется на месте; более рискованные изменения записываются в лог, а работающее приложение остаётся как было. |
| Конструктор типов содержимого (только `verdin dev`) | `POST /schema/plan` показывает шаги, их риск, SQL и подсказки о переименованиях. `POST /schema/apply` выполняет их с уровнем риска, подтверждённым пользователем. |
| `verdin migrate plan` | Выводит каждый шаг с риском и точным SQL для подключённого диалекта, нужный плану уровень `--allow` и подсказки о переименованиях. |
| `verdin migrate apply` | Выполняет план. Если в плане есть соответствующие шаги, нужен `--allow risky` или `--allow destructive`. |

Когда конструктор применяет изменение, он сначала выполняет миграцию, затем записывает `schema/*.json`, затем подменяет приложение. Если миграция не удалась, файлы и работающее приложение остаются как были. Поскольку результат работы конструктора — файлы, процесс заканчивается коммитом в git.

## Выполнение, которое переживает нетранзакционный DDL

PostgreSQL и SQLite выполняют DDL внутри транзакций. MySQL и MariaDB неявно фиксируют изменения при каждом DDL-операторе, поэтому сбой посреди плана оставил бы базу данных между двумя состояниями. `apply` учитывает оба случая.

**Во всех СУБД:**

1. Взять блокировку миграции на одном выделенном соединении: `pg_advisory_lock` в PostgreSQL; `GET_LOCK('verdin_migrate:<database>')` в MySQL и MariaDB с ожиданием до 60 секунд; в SQLite `BEGIN IMMEDIATE` упорядочивает пишущих. В SQLite движок также отключает `foreign_keys` на время прогона, чтобы пересборка таблиц не каскадировала в таблицы связей.
2. Заново вычислить план по снимку и проверить разрешённый риск.
3. Выполнить все предпроверки до первого DDL-оператора.

**В PostgreSQL и SQLite** весь план, новый снимок и строка журнала `completed` выполняются в одной транзакции. Сбой откатывает всё.

**В MySQL и MariaDB** каждый шаг — один оператор, а прогресс записывается по шагам:

1. Записать план в `vd_migrations_journal` (хеш плана и его шаги) со статусом `running`.
2. Выполнить каждый шаг и после каждого записать число завершённых шагов.
3. Если шаг не удался, журнал сохраняет ошибку и остаётся в статусе `running`. Тогда `verdin migrate plan` сообщает о прерванном прогоне, числе применённых шагов и последней ошибке.
4. Следующий `apply` заново вычисляет план. Если его хеш совпадает с журналом, он **продолжает** с упавшего шага: одиночные DDL-операторы в этих СУБД атомарны, поэтому упавший шаг выполняется снова. При продолжении предпроверки пропускаются, потому что предыдущие шаги уже изменили базу данных.
5. Если за это время схема изменилась, хеши различаются, и `apply` отказывается, прося восстановить схему, по которой был построен план.
6. Когда последний шаг выполнен успешно, новый снимок и статус журнала `completed` записываются вместе в одной транзакции.

Хеш плана учитывает вариант СУБД и каждый оператор, поэтому продолженный прогон выполняет ровно тот SQL, который был запланирован.

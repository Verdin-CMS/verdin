На этой странице описаны таблицы, которые Verdin выводит из вашей схемы, и то, как хранится каждый вид атрибута. Прочитайте её, прежде чем что-либо менять в `crates/verdin-migrate/src/derive.rs` или в Document Service, или когда нужно обращаться к базе данных напрямую. Что принимает каждый тип атрибута, см. в разделе [типы атрибутов](/ru/reference/attribute-types/).

Вы никогда не пишете эти таблицы вручную: [движок миграций](/ru/internals/migrations/) создаёт и развивает их по схеме.

## Соглашения об именах

| Объект | Имя |
|---|---|
| Таблица типа содержимого | `collectionName`, по умолчанию — `pluralName` с дефисами, заменёнными на подчёркивания (`blog-posts` → `blog_posts`) |
| Колонка | Имя атрибута в snake_case (`metaTitle` → `meta_title`) |
| Ссылки связей | `{table}_{column}_lnk` |
| Ссылки полиморфных связей | `{table}_{column}_mph` |
| Ссылки медиа | `{table}_{column}_mda` |
| Индекс | `{table}_{part}_uq` для уникальных индексов, `{table}_{part}_idx` для остальных |
| Таблица платформы | Префикс `vd_` (`vd_admin_users`, `vd_schema_snapshots`…) |

Правила, которые проверяет валидатор схемы (`crates/verdin-schema/src/naming.rs` и `validate.rs`):

- `collectionName` соответствует `^[a-z][a-z0-9_]*$`, не длиннее 50 символов и не может начинаться с `vd_`.
- `singularName` и `pluralName` записываются в kebab-case (`^[a-z][a-z0-9-]*$`, без дефисов в начале, в конце и сдвоенных). `upload`, `uploads`, `auth`, `users` и `connect` зарезервированы, потому что эти маршруты использует content API.
- Имена атрибутов начинаются с буквы и продолжаются буквами, цифрами или подчёркиваниями (правило Strapi) и не длиннее 50 символов.
- В типах содержимого зарезервированы `id`, `documentId`, `locale`, `publicationState`, `publishedAt`, `createdAt`, `updatedAt`, `createdBy` и `updatedBy`, а также любые имена, чей snake_case с ними совпадает. В компонентах зарезервирован `id`.
- Сгенерированные идентификаторы ограничены 60 символами (PostgreSQL допускает 63, MySQL — 64). Более длинное имя обрезается и получает 8-символьный хеш полного имени, поэтому разные длинные имена остаются разными, а результат детерминирован.

В сгенерированном SQL каждый идентификатор заключается в кавычки, поэтому зарезервированные слова SQL допустимы как имена атрибутов.

## Системные колонки

Каждая таблица типа содержимого начинается с этих колонок:

```sql
id                 BIGINT       primary key, auto-increment
document_id        CHAR(26)     NOT NULL           -- ULID, shared by every version of a document
locale             VARCHAR(16)  NOT NULL DEFAULT '' -- '' for types that are not localized
publication_state  SMALLINT     NOT NULL           -- 0 = draft, 1 = published
published_at       <datetime>   NULL
created_at         <datetime>   NOT NULL
updated_at         <datetime>   NOT NULL
created_by_id      BIGINT       NULL               -- vd_admin_users.id
updated_by_id      BIGINT       NULL
UNIQUE (document_id, locale, publication_state)
INDEX  (publication_state, locale)
```

- `document_id` — ULID в нижнем регистре, генерируемый при создании. Он одинаков у черновика, опубликованной версии и всех локалей.
- Нелокализованные типы используют `locale = ''` вместо `NULL`, потому что значения NULL ни в одной СУБД не конфликтуют в уникальных индексах, и это сломало бы ограничение `(document_id, locale, publication_state)`.
- Колонка состояния называется `publication_state`, а не `state`, потому что `state` — распространённое имя атрибута.

Дальше идут колонки атрибутов, по одной на скалярный атрибут. **Все колонки атрибутов допускают NULL.** Как и в Strapi v5, черновики могут быть неполными, поэтому `required` проверяется при публикации версии (или при каждой записи в типы без черновиков и публикации), а не базой данных. Это также делает добавление обязательного атрибута безопасной миграцией.

Атрибуты `unique` и все `uid` получают уникальный индекс по `(column, locale, publication_state)`. Черновик и его опубликованная версия могут иметь одинаковое значение, два опубликованных документа — нет, и база данных обеспечивает это без гонок. Нарушение сообщается как `ValidationError` для этого поля.

## Черновики и публикация

Verdin следует модели Strapi v5. Взгляд со стороны пользователя описан в разделе [черновики и публикация](/ru/concepts/draft-and-publish/); здесь — что происходит в таблице.

- У документа не больше одной черновой строки (`publication_state = 0`) и одной опубликованной строки (`publication_state = 1`) на локаль.
- Запись из админ-панели идёт в черновую строку.
- **Опубликовать** проверяет в черновике атрибуты `required` и правила валидации, затем копирует значения атрибутов черновика в опубликованную строку (обновляя её или вставляя в первый раз) в одной транзакции. Вместе с ними копируются ссылки черновика на связи и медиа.
- **Снять с публикации** удаляет опубликованную строку. Её ссылки удаляются вместе с ней через `ON DELETE CASCADE`.
- **Отмена черновика** перезаписывает черновик значениями и ссылками опубликованной строки.
- У типов содержимого без черновиков и публикации есть только опубликованная строка.
- В локализованных типах нелокализуемые атрибуты общие: публикация одной локали копирует их в опубликованные строки других локалей.

## Связи: ссылка по id документа

**Это главное отличие от хранения в Strapi.** Strapi связывает строки по id строки и должен перезаписывать ссылки при публикации. Verdin хранит связь как *исходная строка → целевой документ*:

```sql
-- articles_category_lnk
id                  BIGINT   primary key, auto-increment
source_id           BIGINT   NOT NULL REFERENCES articles(id) ON DELETE CASCADE
target_document_id  CHAR(26) NOT NULL
position            DOUBLE   NOT NULL   -- 1..n, rewritten on every write
UNIQUE (source_id, target_document_id)
UNIQUE (source_id)                      -- to-one kinds only
INDEX  (target_document_id)
```

- Целевая строка выбирается при чтении, в читаемой версии: опубликованная статья видит опубликованные категории, черновик — черновики. Если категорию снять с публикации, она исчезает из опубликованных статей без изменения каких-либо ссылок.
- Публикация копирует только собственные ссылки исходной строки.
- Таблица связей есть только у **владеющей** стороны (атрибут с `inversedBy` или односторонняя связь). Обратная сторона (`mappedBy`) читает ту же таблицу в обратном направлении и доступна только для чтения: запись в неё — ошибка валидации, в которой указан владеющий атрибут.
- «Не больше одной цели» (`oneToOne`, `manyToOne`, `oneWay`) — это уникальный индекс по `source_id`. «Цель принадлежит одному исходному документу» (`oneToOne`, `oneToMany`) нельзя выразить индексом, потому что черновик и его опубликованная версия законно делят цели. Document Service обеспечивает это *перемещением* цели: связывание удаляет ссылки на неё, которые держат другие документы в том же состоянии, — так ведёт себя и Strapi.
- Внешнего ключа на `target_document_id` нет, потому что `document_id` не уникален в целевой таблице. Document Service отклоняет ссылки на несуществующие документы и при удалении последней версии документа в той же транзакции удаляет ссылки на него.
- Строки ссылок сохраняют первичный ключ `id`, поэтому для движка миграций и пересборки таблиц SQLite таблицы связей выглядят как любые другие.
- Переименование таблицы переименовывает и её таблицы связей. Миграции выполняются с выключенным `foreign_keys` в SQLite, поэтому пересборка таблицы не каскадирует в её таблицы связей.

**Полиморфные связи** (`morphToOne`, `morphToMany`) связывают документы любого типа содержимого. Их ссылки хранятся в `{table}_{column}_mph` с `source_id`, `target_type` (UID цели), `target_document_id` и `position`, уникальным `(source_id, target_type, target_document_id)` и, для `morphToOne`, уникальным `source_id`. У обратных сторон (`morphOne`, `morphMany`) таблицы нет: они читают ссылки владельца, которые указывают на них, и доступны только для чтения. Удаление документа удаляет полиморфные ссылки на него. Что с ними можно и нельзя делать, см. в разделе [связи](/ru/concepts/relations/).

## Компоненты и динамические зоны: колонка JSON

Атрибут-компонент или динамическая зона — это **одна JSON-колонка** в строке документа (`jsonb` в PostgreSQL, `json` в MySQL и MariaDB, `text` в SQLite). Strapi хранит каждый компонент в отдельной таблице с полиморфными таблицами соединения; колонка избавляет от этих JOIN и превращает публикацию и историю в простое копирование.

```json
// "seo" column (a single component)
{ "id": 1, "metaTitle": "…", "metaDescription": "…" }

// "blocks" column (a dynamic zone)
[
  { "id": 1, "__component": "blocks.hero", "title": "…" },
  { "id": 2, "__component": "blocks.quote", "text": "…", "author": "…" }
]
```

- У каждого элемента компонента есть целочисленный `id`, уникальный в пределах атрибута. Новые элементы получают следующий свободный номер.
- Данные проверяются по схеме компонента при каждой записи.
- Публикация и отмена копируют JSON как есть.
- **Связи и медиа внутри компонентов** хранятся прямо в JSON: `documentId` для связей (там разрешены только `oneWay` и `manyWay`) и id файлов для медиа. Они проверяются при записи и разрешаются пакетными запросами, когда компонент подгружается. Полиморфные связи и атрибуты `password` не могут находиться внутри компонентов.
- **Фильтрация** требует JSON-функций конкретного диалекта. Скалярные поля одиночных компонентов читаются через JSON-путь (`#>>` в PostgreSQL, `JSON_VALUE` в MySQL и MariaDB, `json_extract` в SQLite). Повторяемые компоненты используют `EXISTS` по элементам массива (`jsonb_array_elements`, `JSON_TABLE`, `json_each`). Динамические зоны можно фильтровать только по `__component`, потому что у их элементов разные поля.

Сторона моделирования описана в разделе [компоненты и динамические зоны](/ru/concepts/components-and-dynamic-zones/).

## Таблицы платформы

Таблицы платформы входят в каждую выведенную модель, поэтому движок миграций создаёт и развивает их точно так же, как таблицы контента; в `verdin migrate plan` они появляются как безопасные шаги. Они определены в `crates/verdin-migrate/src/system.rs`.

| Область | Таблицы |
|---|---|
| Миграции | `vd_schema_snapshots`, `vd_migrations_journal` (принадлежат движку миграций, создаются при первом использовании) |
| Администраторы | `vd_admin_users`, `vd_admin_roles`, `vd_admin_user_roles`, `vd_admin_permissions`, `vd_sessions` (refresh-токены), `vd_admin_tokens` (ссылки приглашения и сброса), `vd_admin_two_factor`, `vd_admin_passkeys`, `vd_spent_challenges` |
| Доступ к content API | `vd_api_tokens`, `vd_api_token_permissions`, `vd_public_permissions` |
| Конечные пользователи | `vd_users`, `vd_user_roles`, `vd_user_role_permissions`, `vd_end_user_sessions` |
| Экземпляр | `vd_settings` (переключатели функций, раскладки представлений редактирования, разовые маркеры обновлений), `vd_locales`, `vd_cluster_events` (общая шина событий, см. [Несколько экземпляров](/ru/deploy/scaling/)) |
| Медиа | `vd_files`, `vd_folders` |
| Работа с контентом | `vd_history_versions`, `vd_releases`, `vd_release_actions`, `vd_workflows`, `vd_workflow_stages`, `vd_document_stages` |
| Совместная работа | `vd_comments`, `vd_tasks`, `vd_document_views`, `vd_document_votes`, `vd_polls`, `vd_poll_votes` |
| Интеграции | `vd_webhooks`, `vd_webhook_deliveries`, `vd_deploy_targets`, `vd_deployments`, `vd_plugin_kv`, `vd_audit_logs` |
| Функции сайта | `vd_redirects`, `vd_menus`, `vd_forms`, `vd_form_submissions` |

## Таблицы медиа

Файлы — это строки `vd_files` в формате Strapi (`name`, `alternative_text`, `caption`, `width`, `height`, `formats`, `hash`, `ext`, `mime`, `size`, `url`, `provider`…), плюс `focal_point`, `folder_id` и `folder_path`. Папки (`vd_folders`) сохраняют `path` из значений `path_id`, как в Strapi, например `/1/4`.

Медиа-атрибут — это таблица связей `{table}_{column}_mda` с `source_id` (строка контента), `file_id` (строка `vd_files`) и `position`. У неё уникальный `(source_id, file_id)` и, если атрибут не `multiple`, уникальный `source_id`. Обе колонки — внешние ключи с `ON DELETE CASCADE`, поэтому удаление файла или строки удаляет их ссылки. Ссылки на медиа подчиняются тем же правилам черновиков и публикации, что и ссылки связей: у каждой версии свои ссылки, а публикация копирует их.

Как работают загрузки, форматы и провайдеры хранилища, описано в разделе [медиа](/ru/concepts/media/).

Verdin управляет доступом двух аудиторий по отдельности: **администраторов**, которые входят
в админ-панель, и **клиентов content API**, которые читают и записывают контент с ваших сайтов
и из приложений. На этой странице объясняется, как авторизуется каждая аудитория и как всё
это связано. Полный список действий — в [справочнике по разрешениям](/ru/reference/permissions/).

| Кто | Аутентифицируется через | Откуда разрешения | Где действуют |
| --- | --- | --- | --- |
| Администратор | Email и пароль (плюс второй фактор или SSO) | Его [роли](#роли-администраторов) | Админ-панель и [admin API](/ru/api/admin/) |
| Анонимный клиент | Без заголовка `Authorization` | [Публичный доступ](#публичный-доступ) | REST, GraphQL, realtime |
| Сервер или сборка | `Authorization: Bearer vd_…` | Тип [API-токена](#api-токены) | REST, GraphQL, realtime |
| Вошедший конечный пользователь | `Authorization: Bearer <JWT>` | Его [роль конечного пользователя](#конечные-пользователи) | REST, GraphQL, realtime |

По умолчанию всё закрыто: content API отвечает `403`, пока вы не выдадите доступ, а
администратор может делать только то, что разрешают его роли.

## Роли администраторов

У администратора одна или несколько ролей; их разрешения складываются. Встроенных ролей три:

| Роль | Может |
| --- | --- |
| **Super Admin** | Всё, включая пользователей, роли и API-токены. Эту роль нельзя изменить. |
| **Editor** | Читать, создавать, обновлять, удалять и публиковать весь контент; пользоваться медиатекой; запускать деплои; управлять SEO, редиректами, меню и формами. |
| **Author** | Создавать контент, а читать, обновлять и удалять только созданные им записи. Не может публиковать. Загружает файлы и редактирует или удаляет только свои. |

Другие роли создаются в **Настройки → Роли** (разрешение `roles.manage`). Последнего
активного Super Admin нельзя деактивировать, удалить или понизить, поэтому экземпляр никогда
не заблокирует сам себя. Роль также может требовать от участников настроить
[двухфакторную аутентификацию](/ru/guides/auth/two-factor/): пока они этого не сделают, им
доступен только их профиль.

### Что такое разрешение

Разрешение — это **действие**, **объект** (для действий с контентом) и необязательные
**условия**:

- **Действия с контентом**: `content.read`, `content.create`, `content.update`,
  `content.delete` и `content.publish` для одного типа содержимого (`api::article`) или для
  всех (`*`).
- **Действия с медиа**: `media.read`, `media.create`, `media.update` и `media.delete` для
  медиатеки.
- **Действия с настройками**, например `users.manage`, `tokens.manage`, `webhooks.manage` или
  `features.manage`, которые открывают соответствующие страницы **Настроек**.
- **Условия**: `is-creator` ограничивает разрешение на контент или медиа тем, что создал сам
  администратор. Так работает роль Author.

Условия становятся частью запроса к базе данных: список с фильтром `is-creator` правильно
считает записи и страницы, а не скрывает строки задним числом.

### Разрешения на поля и локали

Разрешения на контент можно сузить ещё больше:

- **Поля.** `content.read`, `content.create` и `content.update` могут перечислять атрибуты,
  на которые они распространяются. Поля вне списка скрыты при чтении (включая поиск,
  фильтры, сортировку и связанные записи) и отклоняются при записи.
- **Локали.** Для [локализованных типов](/ru/concepts/internationalization/) разрешения на
  контент могут перечислять локали, на которые они распространяются. Версии в других локалях
  нельзя прочитать или изменить.

И то и другое задаётся для каждого типа содержимого в редакторе роли, в разделах **Поля** и
**Языки**.

## Content API

Клиенты content API проверяются по правам: **действие** над **объектом**.

| Действие | Разрешает |
| --- | --- |
| `find` | Получать список документов (`GET /api/articles`) или читать одиночный тип. |
| `findOne` | Читать один документ (`GET /api/articles/{documentId}`). |
| `create` | `POST` |
| `update` | `PUT` |
| `delete` | `DELETE` |
| `publish` | Маршруты `actions/publish`, `actions/unpublish` и `actions/discard-draft`. |
| `readDrafts` | Чтение с `status=draft`. |

Объекты — это типы содержимого, медиатека (`plugin::upload`) и учётные записи конечных
пользователей (`plugin::users-permissions.user`), когда включены
[конечные пользователи](/ru/guides/auth/end-users/).

Несколько правил действуют для всех клиентов:

- Для чтения черновиков помимо `find` или `findOne` нужно `readDrafts`. Право, которое читает
  контент вашего сайта, не может случайно прочитать неопубликованную работу.
- Для populate, фильтрации или сортировки через связь нужен доступ на чтение к её целевому
  типу.
- Поля `private` никогда не возвращаются, какие бы права ни были.
- Запись возвращает записанный документ даже без `find`, как в Strapi.
- Те же права действуют для [GraphQL](/ru/api/graphql/) и для
  [потока реального времени](/ru/api/realtime/).

### Публичный доступ

Запросы без заголовка `Authorization` получают права из **Настройки → Публичный доступ**. По
умолчанию ничего не разрешено. Обычно разрешают `find` и `findOne` для типов, которые
показывает ваш сайт.

### API-токены

API-токены предназначены для серверов, шагов сборки и скриптов. Создавайте их в
**Настройки → API-токены** (разрешение `tokens.manage`):

| Тип | Права |
| --- | --- |
| **Только чтение** | `find` и `findOne` для всех типов. Никогда — черновики. |
| **Полный доступ** | Все действия для всех типов, включая черновики. |
| **Настраиваемый** | Выбранные вами права, как у публичного доступа. |

- Токен начинается с `vd_`. Его секрет показывается один раз — при создании или
  перегенерации; Verdin хранит только его хеш с ключом.
- У токенов может быть срок действия. Неизвестный, просроченный или некорректный токен даёт
  `401`: публичный доступ в этом случае никогда не используется.
- Любой действительный токен может читать документ OpenAPI по адресу `/api/_openapi.json`,
  если вы не сделали документацию публичной.

Как создавать и ротировать токены, см. в разделе [API-токены](/ru/guides/auth/api-tokens/).

### Конечные пользователи

Конечные пользователи — это люди, которые входят на ваш сайт или в приложение, как с
плагином users-permissions в Strapi. По умолчанию функция выключена. У каждой учётной записи
одна роль:

- **Public** — роль запросов без токена: её права — это права из
  **Настройки → Публичный доступ**.
- **Authenticated** по умолчанию выдаётся новым учётным записям.
- Пользовательские роли содержат любой набор прав с теми же действиями, что и выше.

Конечный пользователь отправляет JWT, полученный при входе, как `Authorization: Bearer <jwt>`.
Verdin отличает его от API-токенов по префиксу `vd_`. См.
[Конечные пользователи](/ru/guides/auth/end-users/).

## Сравнение со Strapi

Модель повторяет Strapi v5: RBAC администраторов с условиями `is-creator` и content API с
публичным доступом, API-токенами и ролями users-permissions. Отличия:

- Все функции доступны каждому проекту: пользовательские роли, разрешения на поля и локали,
  [SSO](/ru/guides/auth/sso/) и [журналы аудита](/ru/guides/content/audit-logs/).
- Чтение черновиков через content API — отдельное право, `readDrafts`.
- Публикация через REST — отдельное право, `publish`, со своими маршрутами.

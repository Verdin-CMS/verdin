Модель контента — это набор типов содержимого и компонентов, которые определяет ваш проект.
Всё остальное Verdin выводит из неё: таблицы базы данных, REST и GraphQL API, документ
OpenAPI, валидацию и формы админ-панели. На этой странице описаны составные части модели и
правила, которые к ним применяются.

## Типы содержимого

Тип содержимого описывает один вид документов, например статью или главную страницу. У него
есть `kind`:

| Вид | Содержит | Маршруты REST (пример блога) |
| --- | --- | --- |
| `collectionType` | Любое число документов | `/api/articles`, `/api/articles/{documentId}` |
| `singleType` | Не больше одного документа | `/api/homepage` |

Типы-коллекции доступны по их `pluralName`, одиночные типы — по `singularName`. Первый `PUT`
к одиночному типу создаёт его документ. Все маршруты описаны в [REST API](/ru/api/rest/).

У каждого типа содержимого есть UID вида `api::<singularName>` (`api::article`). Strapi
записывает тот же UID как `api::article.article`; Verdin принимает эту форму в файлах схемы и
в импортёре и приводит её к `api::article`.

У каждого документа есть системные поля, которые вы не объявляете: `id`, `documentId`
(26-символьный ULID в нижнем регистре, одинаковый для черновиков, опубликованных версий и
локалей), `createdAt`, `updatedAt`, `publishedAt`, а также `locale` у
[локализованных типов](/ru/concepts/internationalization/).

## Файлы схемы

Типы содержимого и компоненты — это JSON-файлы в каталоге `schema/` вашего проекта
(`[schema].path` в `verdin.toml`). Вы храните их в git, как код.

```
schema/
├── content-types/
│   ├── article.json
│   ├── category.json
│   ├── tag.json
│   └── homepage.json
└── components/
    ├── blocks/
    │   ├── hero.json
    │   └── quote.json
    └── shared/
        └── seo.json
```

Формат — это `schema.json` из Strapi, поэтому большинство схем Strapi загружаются без
изменений. Вот тип статьи из
[примера блога](https://github.com/Verdin-CMS/verdin/tree/main/examples/blog):

```json title="schema/content-types/article.json"
{
  "kind": "collectionType",
  "singularName": "article",
  "pluralName": "articles",
  "displayName": "Article",
  "options": { "draftAndPublish": true },
  "attributes": {
    "title": { "type": "string", "required": true, "maxLength": 200 },
    "slug": { "type": "uid", "targetField": "title", "required": true },
    "excerpt": { "type": "text", "maxLength": 500 },
    "body": { "type": "richtext" },
    "readingTime": { "type": "integer", "min": 0 },
    "featured": { "type": "boolean", "default": false },
    "category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
    "tags": { "type": "relation", "relation": "manyToMany", "target": "tag" },
    "seo": { "type": "component", "component": "shared.seo" },
    "blocks": { "type": "dynamiczone", "components": ["blocks.hero", "blocks.quote"] }
  }
}
```

| Ключ | Обязательный | Описание |
| --- | --- | --- |
| `kind` | да | `collectionType` или `singleType`. |
| `singularName` | да | Kebab-case. Должен совпадать с именем файла (`article.json`). |
| `pluralName` | да | Kebab-case, отличается от `singularName`. |
| `displayName` | да | Имя, которое показывает админ-панель. |
| `description` | нет | Показывается в админ-панели. |
| `collectionName` | нет | Имя таблицы. По умолчанию — `pluralName` в snake_case. |
| `options.draftAndPublish` | нет | Хранить черновик и опубликованную версию каждого документа. По умолчанию `false`. См. [Черновики и публикация](/ru/concepts/draft-and-publish/). |
| `pluginOptions.i18n.localized` | нет | Отдельная версия для каждой локали. По умолчанию `false`. См. [Интернационализация](/ru/concepts/internationalization/). |
| `attributes` | нет | Поля в том порядке, в котором их возвращает API. |
| `validations` | нет | Правила, связывающие несколько полей; см. [ниже](#проверки-между-полями). |

Схемы строгие: неизвестный ключ, параметр, который тип не поддерживает, или ссылка на
несуществующий тип или компонент — это ошибка с указанием файла и пути, и сервер не
запускается. Запустите `verdin schema check`, чтобы проверить файлы без запуска сервера.

Некоторые имена заняты:

- Имена атрибутов начинаются с буквы, дальше идут буквы, цифры и подчёркивания, не больше 50
  символов. Они превращаются в колонки в snake_case (`metaTitle` → `meta_title`).
- `id`, `documentId`, `locale`, `publicationState`, `publishedAt`, `createdAt`,
  `updatedAt`, `createdBy` и `updatedBy` зарезервированы в типах содержимого, а `id` — внутри
  компонентов.
- `upload`, `uploads`, `auth`, `users` и `connect` не могут быть `singularName` или
  `pluralName`: эти маршруты принадлежат API.
- У типа содержимого не больше 60 атрибутов `string`, `email`, `uid` и `enumeration` — так
  строки укладываются в ограничение MySQL на размер строки. Для части из них используйте
  `text`.

Файлы редактируются в **Конструкторе типов содержимого** админки, который доступен, пока
сервер работает в режиме `verdin dev`, или вручную. В любом случае изменение становится
[миграцией схемы](/ru/concepts/schema-migrations/). Раскладка редактора (порядок полей,
ширина, подписи) не входит в схему: администраторы настраивают её в панели, и она хранится в
базе данных.

## Компоненты

Компонент — это повторно используемая группа полей, например `shared.seo` (мета-заголовок и
мета-описание). Его UID имеет вид `<category>.<name>` и берётся из пути:
`schema/components/shared/seo.json` — это `shared.seo`. В файле компонента есть
`displayName`, необязательные `description` и `icon`, а также `attributes`.

Динамическая зона — это список, в котором смешаны несколько компонентов, например тело статьи
из блоков hero и цитат. И то и другое хранится внутри документа в JSON; см.
[Компоненты и динамические зоны](/ru/concepts/components-and-dynamic-zones/).

## Атрибуты

У каждого атрибута есть `type` и параметры, которые от него зависят. Полный список типов, их
параметров и типов колонок в каждой базе данных — в
[справочнике по типам атрибутов](/ru/reference/attribute-types/).

| Категория | Типы |
| --- | --- |
| Текст | `string`, `text`, `richtext` (Markdown), `blocks` (структурированный rich text Strapi), `email`, `uid`, `password`, `enumeration` |
| Числа | `integer`, `biginteger`, `float`, `decimal` |
| Даты | `date`, `time`, `datetime` |
| Другие скалярные | `boolean`, `json` |
| Ссылки | `relation` (см. [Связи](/ru/concepts/relations/)), `media` (см. [Медиа](/ru/concepts/media/)) |
| Структура | `component`, `dynamiczone` |

Общие параметры:

| Параметр | Действие |
| --- | --- |
| `required` | Значение должно быть задано при публикации версии (или при каждой записи — для типов без черновиков и публикации). Черновики могут быть неполными. |
| `private` | Content API никогда не возвращает такое поле, не фильтрует, не сортирует и не подгружает по нему. Атрибуты `password` всегда private. |
| `default` | Значение, которое используется, если в новом документе поле не передано. Проверяется по правилам самого атрибута. |
| `unique` | Никакие два документа не могут иметь одинаковое значение в рамках локали и версии. Доступно для типов `string`, `email`, числовых типов, дат и времени; `uid` уникален всегда. |
| `configurable` | `false` блокирует атрибут в конструкторе типов содержимого: там его нельзя изменить, переименовать или удалить. |
| `pluginOptions.i18n.localized` | `false` делает значение общим для всех локалей. |

Все колонки атрибутов в базе данных допускают NULL. Как и в Strapi v5, `required` проверяет
Verdin при публикации, а не ограничение `NOT NULL`, поэтому добавление обязательного атрибута
в тип, где уже есть строки, — безопасное изменение.

## Валидация

Каждая запись проверяется по схеме до того, как что-то попадёт в базу данных:

- **Типы и ограничения** — при каждой записи: типы значений, `minLength`/`maxLength`,
  `min`/`max`, `regex`, значения `enum`, число элементов в повторяемых компонентах и
  динамических зонах, типы компонентов, которые разрешает динамическая зона, и типы файлов,
  которые принимает медиаполе. Неизвестные ключи и системные поля во входных данных — ошибки.
- **Обязательные поля и правила между полями** — при публикации версии и при каждой записи в
  типы без черновиков и публикации. Они действуют и внутри компонентов и динамических зон.
- **Уникальность** — через уникальные индексы в базе данных, поэтому две одновременные записи
  не могут обе пройти успешно.

Неудачная проверка возвращает `400` с `ValidationError`, в `details.errors` которой
перечислены все проблемы с путями, например `["seo", "metaTitle"]` или
`["blocks", 2, "text"]`. См. [Ошибки](/ru/api/rest/#ошибки).

### Проверки между полями

Тип содержимого может объявить правила, которые сравнивают его собственные поля. Они
записываются на [JSON Logic](https://jsonlogic.com). Этот тип события требует, чтобы дата
окончания была не раньше даты начала, и ограничивает число проданных билетов числом мест:

```json title="schema/content-types/event.json"
{
  "kind": "collectionType",
  "singularName": "event",
  "pluralName": "events",
  "displayName": "Event",
  "attributes": {
    "startDate": { "type": "date", "required": true },
    "endDate": { "type": "date" },
    "seats": { "type": "integer", "min": 0 },
    "sold": { "type": "integer", "min": 0 }
  },
  "validations": [
    {
      "rule": { "or": [{ "!": { "var": "endDate" } }, { "<=": [{ "var": "startDate" }, { "var": "endDate" }] }] },
      "message": "must be after the start date",
      "field": "endDate"
    },
    { "rule": { "<=": [{ "var": "sold" }, { "var": "seats" }] }, "message": "more tickets sold than seats" }
  ]
}
```

- Невыполненное правило — это ошибка валидации с `message`, привязанная к `field`, если он
  указан, или к документу (`path: []`).
- Правила проверяются тогда же, когда `required`: при публикации и при каждой записи в типы
  без черновиков и публикации. Черновики могут их нарушать.
- `var` читает собственные поля документа, в компоненты можно заходить через пути с точками.
  Связи и медиа в правилах недоступны.
- Сравнение числовое, если обе стороны — числа, и текстовое, если обе — строки, поэтому даты,
  время и дата-время в ISO сравниваются правильно. Пустое поле — это `null`: учитывайте
  необязательные поля, как это делает первое правило.
- Разрешённые операторы: `var`, `==`, `!=`, `===`, `!==`, `<`, `>`, `<=`, `>=`, `!`, `!!`,
  `and`, `or`, `in`, `if`, `?:`, `+`, `-`, `*`, `/`, `%`, `min`, `max`, `cat`. Неизвестный
  оператор, неизвестный `field` или пустой `message` — ошибка схемы.

Правила проверяет сервер; если публикация не удалась, админ-панель показывает их сообщения у
указанных полей. В Strapi аналога нет. Условные поля Strapi (`conditions`) принимаются в
файлах схемы и сохраняются, но пока не применяются.

Когда вы меняете файл схемы, база данных должна последовать за ним: новому атрибуту нужна
колонка, новой связи — таблица связей. Verdin вычисляет эту миграцию за вас, показывает её до
выполнения и никогда не удаляет данные без явного указания. На этой странице объясняется, как
это работает.

## От схемы к плану

Verdin никогда не просит вас писать миграцию. Он сравнивает две модели базы данных:

1. **Желаемую**: выведенную из ваших файлов `schema/*.json`, со всеми нужными им таблицами,
   колонками и индексами (включая таблицы связей и собственные таблицы Verdin).
2. **Текущую**: модель, которую оставила последняя миграция; она хранится в базе данных в виде
   снимка.

Разница между ними — это **план**: список шагов, у каждого из которых есть SQL для вашей базы
данных и уровень риска. Поскольку план строится по сохранённому снимку, а не по анализу базы
данных, он детерминирован и одинаков для всех диалектов. Изменения, которые дают тот же SQL в
вашей базе данных, например `integer` → `biginteger` в SQLite, не порождают шагов.

`verdin migrate plan` выводит его. Здесь атрибут `excerpt` блога был переименован в `summary`
в `article.json`:

```text title="Terminal"
$ verdin migrate plan
  1. [safe] add column articles.summary
       ALTER TABLE "articles" ADD COLUMN "summary" text
  2. [destructive] drop column articles.excerpt
       ALTER TABLE "articles" DROP COLUMN "excerpt"

requires: verdin migrate apply --allow destructive

possible renames (pass them to keep the data):
  --rename-column articles.excerpt=summary
```

## Уровни риска

| Риск | Шаги | Почему |
| --- | --- | --- |
| **Безопасно** (`safe`) | Создать таблицу, добавить колонку, добавить или удалить неуникальный индекс, переименовать таблицу или колонку. | Не может потерять данные или упасть на существующих строках. |
| **Рискованно** (`risky`) | Изменить тип колонки, добавить уникальный индекс в существующую таблицу, пересобрать таблицу SQLite (SQLite не умеет изменять колонки на месте). | Может упасть на существующих данных (дубликаты, значения, которые не конвертируются) или переписать их. |
| **Разрушительно** (`destructive`) | Удалить колонку или таблицу. | Удаляет данные. |

Все колонки атрибутов допускают NULL (`required` проверяется при публикации), поэтому
добавление атрибутов, обязательных или нет, всегда безопасно. Добавление `"unique": true` к
заголовку статьи блога рискованно, потому что существующие заголовки могут повторяться:

```text title="Terminal"
$ verdin migrate plan
  1. [risky] create unique index articles_title_uq
       CREATE UNIQUE INDEX "articles_title_uq" ON "articles" ("title", "locale", "publication_state")

requires: verdin migrate apply --allow risky
```

Перед выполнением первого оператора Verdin запускает проверку для каждого рискованного шага,
который может упасть, например ищет дубликаты перед созданием уникального индекса, и
останавливается с сообщением, если проверка находит проблему. К этому моменту ничего ещё не
изменено.

## Применение плана

`verdin migrate apply` выполняет ожидающие шаги. Команда принимает максимальный риск, на
который вы согласны:

```sh title="Terminal"
verdin migrate apply                        # только безопасные шаги (по умолчанию)
verdin migrate apply --allow risky          # также изменения типов и уникальные индексы
verdin migrate apply --allow destructive    # также удаления
```

Если хотя бы один шаг выше разрешённого риска, ничего не выполняется:

```text title="Terminal"
$ verdin migrate apply
Error: these steps need explicit approval:
  create unique index articles_title_uq (risky)
```

Миграция берёт блокировку, поэтому два экземпляра никогда не мигрируют одновременно. В
PostgreSQL и SQLite весь план выполняется в одной транзакции: сбой откатывает всё. MySQL и
MariaDB фиксируют каждый DDL-оператор отдельно, поэтому Verdin записывает прогресс по шагам в
журнал. После сбоя устраните причину и снова запустите `verdin migrate apply`: команда
продолжит с упавшего шага, если план не изменился, и откажется, если схема за это время
поменялась.

## Переименования

Удалённый атрибут и новый выглядят как удаление и добавление, при которых данные колонки были
бы потеряны. Verdin никогда не угадывает переименования. Он предлагает переименование, когда
колонка исчезает, а колонка того же типа появляется в той же таблице (или исчезает таблица и
появляется таблица с теми же колонками), и вы подтверждаете его явно:

```text title="Terminal"
$ verdin migrate apply --rename-column articles.excerpt=summary
applied 1 step
```

- `--rename-column TABLE.OLD=NEW` переименовывает колонку; `TABLE` — таблица типа
  содержимого (его `collectionName`).
- `--rename-table OLD=NEW` переименовывает таблицу. Таблицы связей типа переименовываются
  вместе с ней.
- Передайте те же флаги в `migrate plan`, чтобы заранее посмотреть результат.

Переименования — безопасные шаги. Конструктор типов содержимого предлагает те же варианты в
своём диалоге.

## `verdin dev` и `verdin start`

| | `verdin dev` | `verdin start` |
| --- | --- | --- |
| При запуске | Применяет ожидающие безопасные шаги. Останавливается, если ожидают другие шаги. | Не запускается, пока есть ожидающие шаги, если не передать `--migrate`, который сначала применяет безопасные шаги. |
| Изменения схемы во время работы | **Конструктор типов содержимого** показывает план с рисками и предложениями переименований и применяет его после подтверждения, включая более рискованные шаги. Ручные правки (или `git pull`) отслеживаются наблюдателем за файлами: безопасные планы применяются, и приложение перезагружается; остальные записываются в лог, а работающее приложение остаётся как было. | Схема доступна только для чтения. Разверните новые файлы и выполните миграцию. |

Конструктор сначала мигрирует базу данных, затем записывает файлы схемы, затем перезагружает
content API, admin API, GraphQL и документ OpenAPI без перезапуска. Если миграция не удалась,
файлы и работающее приложение остаются как были.

В продакшене запустите `verdin migrate plan` на копии базы данных, затем
`verdin migrate apply` с допустимым для вас риском — до запуска новой версии. См.
[Обновление](/ru/migrate/upgrading/) и [Резервные копии](/ru/deploy/backups/).

## Сравнение со Strapi

Strapi синхронизирует базу данных со схемой при запуске, не показывая, что собирается
сделать. Verdin сначала строит план, показывает SQL, без запроса применяет только безопасные
шаги и требует `--allow` для всего, что может упасть или удалить данные.

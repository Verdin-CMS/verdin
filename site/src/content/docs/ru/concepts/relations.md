Связь соединяет документы двух типов содержимого, например статью и её категорию. На этой
странице описаны виды связей, то, как ссылки хранятся и разрешаются, и правила их записи,
упорядочивания и чтения. Синтаксис запросов описан в [REST API](/ru/api/rest/#запись-данных).

## Виды

Связь — это атрибут с `type: "relation"`, видом `relation` и целевым типом содержимого
`target`:

| Вид | Документ ссылается на | На цель ссылается | Обратная сторона |
| --- | --- | --- | --- |
| `oneWay` | одну цель | любое число документов | нет |
| `manyWay` | много целей | любое число документов | нет |
| `manyToOne` | одну цель | любое число документов | `oneToMany` |
| `oneToMany` | много целей | один документ | `manyToOne` |
| `oneToOne` | одну цель | один документ | `oneToOne` |
| `manyToMany` | много целей | любое число документов | `manyToMany` |

В примере блога статьи связаны с категорией (с обратной стороной) и с тегами (без неё):

```json title="schema/content-types/article.json (excerpt)"
"category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
"tags": { "type": "relation", "relation": "manyToMany", "target": "tag" }
```

```json title="schema/content-types/category.json (excerpt)"
"articles": { "type": "relation", "relation": "oneToMany", "target": "article", "mappedBy": "category" }
```

- Сторона с `inversedBy` (или без обоих ключей) — **владеющая**: она хранит ссылки, и именно
  в неё выполняется запись.
- Сторона с `mappedBy` — **обратная**: она читает ссылки владельца в обратном направлении и
  доступна только для чтения. Запись в неё — ошибка валидации, в которой указан владеющий
  атрибут.
- Стороны должны быть согласованы: `mappedBy` указывает атрибут цели, который ссылается
  обратно через `inversedBy`, с соответствующим обратным видом из таблицы.
- У `oneWay` и `manyWay` никогда нет обратной стороны.

Конструктор типов содержимого сам создаёт обратный атрибут в целевом типе.

## Связь по документу, а не по строке

У документа несколько строк: черновик и опубликованная версия, и по одной такой паре на
каждую локаль. Verdin хранит связь как ссылку от исходной **строки** на целевой **документ**
(его `documentId`) в таблице связей с именем `{table}_{field}_lnk`. Целевая строка
выбирается при чтении связи:

- Опубликованная статья видит опубликованную версию своей категории, а её черновик — черновик
  категории. У типов без черновиков и публикации одна версия, которую видят все.
- Если цель тоже локализована, при чтении она разрешается в той же локали. Нелокализованный
  целевой тип общий для всех локалей.
- Снятие категории с публикации скрывает её из опубликованных статей, не трогая ни одной
  ссылки; повторная публикация возвращает её.
- Публикация статьи копирует в опубликованную версию только её собственные ссылки.

Strapi вместо этого связывает id строк, поэтому ему приходится перезаписывать ссылки при
каждой публикации черновика. Verdin этого никогда не делает, и публикация остаётся простым
копированием строки черновика.

Целостность обеспечивает Verdin, а не внешние ключи: ссылка на несуществующий документ —
ошибка валидации, а удаление документа в той же транзакции удаляет ссылки на него.

### Один документ на цель

Для `oneToOne` и `oneToMany` цель принадлежит не более чем одному исходному документу.
Связывание цели, которую держит другой документ, **перемещает** её: ссылка другого документа
удаляется в той же записи. Так ведёт себя и Strapi. Правило действует в рамках версии:
черновик и его опубликованная версия могут держать одну и ту же цель.

## Запись

На владеющей стороне `data` принимает `documentId`, список таких значений или объект,
описывающий изменение:

| Входные данные | Результат |
| --- | --- |
| `"k2m…"` или `{ "documentId": "k2m…" }` | Связать одну цель (связи «к одному»). |
| `["k2m…", "p9x…"]` | Заменить все ссылки, в этом порядке. |
| `null` или `[]` | Удалить все ссылки. |
| `{ "set": ["k2m…"] }` | Заменить все ссылки. |
| `{ "connect": [...], "disconnect": [...] }` | Добавить и удалить ссылки, сохранив остальные. |

Подключение новой цели к связи «к одному» заменяет предыдущую. `set` нельзя сочетать с
`connect` или `disconnect`.

В админ-панели поле связи показывает связанные записи. **Связать запись** (или **Связать
записи** для связей «ко многим») открывает диалог, который ищет записи целевого типа по их
текстовым полям, а если цель локализована — в локали текущей записи. Выберите одну запись или
отметьте несколько и добавьте их; уже связанные записи помечены.

## Порядок

Связи «ко многим» сохраняют порядок ссылок. Список или `set` сохраняют переданный порядок.
Элементы `connect` могут указывать своё место:

```json
{
  "data": {
    "tags": {
      "connect": [
        { "documentId": "k2m…", "position": { "before": "p9x…" } },
        { "documentId": "a7c…", "position": { "end": true } }
      ]
    }
  }
}
```

`position` — это `{ "before": documentId }`, `{ "after": documentId }`, `{ "start": true }` или
`{ "end": true }`. Позиции перенумеровываются при каждой записи. При чтении связанные
документы возвращаются в порядке ссылок, если populate не запрашивает `sort`.

## Чтение

Связи возвращаются, только если их подгрузить через populate:

```http
GET /api/articles?populate[category][fields][0]=name&populate[tags][sort]=label:asc
```

Связь «к одному» — это объект или `null`; связь «ко многим» — массив. Каждая подгружаемая
связь может принимать собственные `fields`, `filters`, `sort`, `populate` и `count`, до пяти
уровней вглубь. Каждый уровень — это один пакетный запрос на связь (`WHERE … IN (…)`), а не
JOIN, поэтому глубокий populate не размножает строки. На документ и связь возвращается не
больше 1000 связанных документов; `count` даёт точное число.

Фильтровать через связи можно с любой стороны (`filters[category][name][$eq]=News`), а
сортировать — по полю связи «к одному» (`sort=category.name:asc`). Populate, фильтрация или
сортировка через связь с типом, который клиент не может читать, отклоняются (`populate=*`
такую связь пропускает), поэтому связи никогда не раскрывают контент, скрытый
[разрешениями](/ru/concepts/permissions/) клиента.

## Связи внутри компонентов

[Компонент](/ru/concepts/components-and-dynamic-zones/) может содержать связи, но только
`oneWay` и `manyWay`:

```json title="schema/components/shared/related.json"
{
  "displayName": "Related",
  "attributes": {
    "label": { "type": "string" },
    "articles": { "type": "relation", "relation": "manyWay", "target": "article" }
  }
}
```

JSON компонента хранит сами значения `documentId`: строку для `oneWay` и массив для
`manyWay`. Поэтому другие виды там не разрешены:

- Обратной стороне пришлось бы просматривать JSON каждого документа, чтобы найти, кто на неё
  ссылается.
- Правило «один документ на цель» (`oneToOne`, `oneToMany`) тоже нельзя обеспечить без такого
  поиска.

Внутри компонентов порядок списка `manyWay` — это порядок массива. Ссылки проверяются при
записи и разрешаются, когда компонент подгружается, в статусе и локали документа; цели,
которых больше нет, пропускаются. Фильтровать по ним нельзя.

## Полиморфные связи

`morphToOne` и `morphToMany` связывают документы любого типа содержимого. Их ссылки хранят
тип цели рядом с её `documentId`, и при записи указываются оба:

```json
{ "data": { "related": [{ "__type": "api::article", "documentId": "k2m…" }, { "__type": "api::page", "documentId": "p9x…" }] } }
```

Подгруженные элементы — это целевые документы со своим `__type`, прочитанные в статусе и
локали запроса. Обратные стороны `morphOne` и `morphMany` указывают тип владельца (`target`) и
его атрибут (`morphBy`) и доступны только для чтения. Полиморфные связи нельзя фильтровать и
сортировать, и они не могут находиться внутри компонентов.

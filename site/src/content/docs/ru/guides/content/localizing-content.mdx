Локализованный тип содержимого хранит по одной версии каждой записи на локаль. В этом
руководстве вы добавите локали, в которых публикуете контент, включите локализацию для типа,
переведёте записи в админ-панели и будете читать и записывать каждую локаль через API.
Модель, которая за этим стоит (общие поля, связи между локализованными типами), описана в
разделе [Интернационализация](/ru/concepts/internationalization/).

Локализация входит в ядро: отдельную функцию включать не нужно. Она работает как плагин i18n
в Strapi v5 и принимает тот же параметр `locale`.

## Перед началом

- Чтобы добавлять, переименовывать или удалять локали, нужно **Управление языками**
  (`locales.manage`).
- Чтобы сделать тип локализованным, нужно отредактировать его схему в **Конструкторе типов
  содержимого** (`verdin dev`) или в `schema/content-types/<name>.json`.
- Какие разрешения на контент нужны редакторам, см. в разделе
  [Разрешения](/ru/reference/permissions/).

## Добавьте локали

При первом запуске создаётся английский (`en`) как локаль по умолчанию. Запросы без указания
локали используют её, и новые записи создаются в ней.

<Steps>

1. Откройте **Настройки → Интернационализация** и выберите **Добавить язык**.
2. Введите **Код**: код языка строчными буквами, при необходимости с регионом или
   письменностью, например `fr`, `pt-BR` или `zh-Hans`. Название заполняется автоматически, и
   его можно изменить.
3. Отметьте **Сделать языком по умолчанию**, если запросы без локали должны использовать эту
   локаль, затем сохраните.

</Steps>

Чтобы потом сменить локаль по умолчанию, выберите **Сделать языком по умолчанию** у другой
локали. Локаль по умолчанию удалить нельзя.

<Aside type="caution" title="Удаление локали удаляет её записи">
Удаление локали безвозвратно удаляет все записи на ней во всех типах содержимого, включая
опубликованные версии. Для подтверждения диалог просит ввести код локали.
</Aside>

## Сделайте тип содержимого локализованным

В **Конструкторе типов содержимого** откройте тип и включите **Локализовано** в его
настройках. Затем решите для каждого поля, какие значения отличаются по локалям: поле с
выключенным **Локализовано** хранит одно значение, общее для всех локалей.

То же самое в файле схемы для типа `article` из примера:

```json title="schema/content-types/article.json" {6,9}
{
  "kind": "collectionType",
  "singularName": "article",
  "pluralName": "articles",
  "displayName": "Article",
  "pluginOptions": { "i18n": { "localized": true } },
  "attributes": {
    "title": { "type": "string", "required": true },
    "readingTime": { "type": "integer", "pluginOptions": { "i18n": { "localized": false } } }
  }
}
```

Как ведут себя общие поля:

- Сохранение общего поля в одной локали записывает его в черновики всех локалей.
- Публикация локали копирует её общие поля в опубликованные версии других локалей.
- Связи и медиаполя тоже могут быть общими.

Типы без `pluginOptions.i18n.localized` не локализованы и игнорируют параметры `locale`.
Изменение локализации типа — это изменение схемы: проверьте миграцию через
`verdin migrate plan` перед деплоем.

## Переведите запись в админ-панели

<Steps>

1. Откройте запись и выберите целевой язык в переключателе **Язык** вверху редактора. У
   локалей без версии отображается **Ещё не создано**.
2. Редактор сообщает, что у записи ещё нет версии на этой локали и что сохранение её создаст.
   Общие поля уже показывают свои значения.
3. Чтобы начать с существующего перевода, выберите в этом уведомлении **Заполнить из другого
   языка**. Выберите источник в **Копировать из** и нажмите **Скопировать поля**. Локализуемые
   поля, включая связи и медиа, копируются в форму. Пока ничего не сохраняется.
4. Отредактируйте поля, затем **Сохранить черновик** или **Опубликовать**. У каждой локали свой
   черновик и своя опубликованная версия.

</Steps>

В списке есть такой же переключатель **Язык**: он показывает версии в одной локали за раз.
Удаление из редактора удаляет только версию в текущей локали; остальные локали сохраняются.

Если включена функция **Действия ИИ**, редактор также может переводить текстовые поля из
черновика другой локали. См. [Действия ИИ](/ru/guides/integrations/ai-actions/).

## Ограничьте редакторов частью локалей

Разрешения роли на контент могут распространяться только на некоторые локали. В
**Настройки → Роли** откройте роль, найдите тип содержимого и выберите **Языки**. Выберите
**Только эти языки** и отметьте нужные. Администраторы с этой ролью не могут читать или
менять версии в других локалях; переключатель **Язык** показывает такие локали с пометкой
«(нет доступа)».

## Чтение и запись локалей через API

Добавьте `locale` к любому REST-запросу или передайте его как аргумент в GraphQL. Без него
используется локаль по умолчанию. Неизвестная локаль — ошибка `400`.

<Tabs syncKey="api">
<TabItem label="REST">

```sh title="Terminal"
# Прочитать французские версии
curl 'http://localhost:1337/api/articles?locale=fr'

# Создать или обновить французскую версию документа
curl -X PUT 'http://localhost:1337/api/articles/<documentId>?locale=fr' \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"data":{"title":"Bonjour"}}'

# Удалить только французскую версию
curl -X DELETE 'http://localhost:1337/api/articles/<documentId>?locale=fr' \
  -H "Authorization: Bearer $TOKEN"
```

</TabItem>
<TabItem label="GraphQL">

```graphql
query {
  articles(locale: "fr") {
    documentId
    title
    locale
  }
}
```

</TabItem>
<TabItem label="TypeScript">

```ts
const { data } = await verdin.collection('articles').find({ locale: 'fr' });
```

</TabItem>
</Tabs>

Чего ожидать:

- `PUT` с `locale` создаёт версию этой локали, если у документа её ещё нет.
- Ответы для локализованных типов содержат `locale`. У всех версий общий `documentId`.
- `DELETE` удаляет только версию в запрошенной локали (в локали по умолчанию, если локаль не
  указана). Ссылки на документ удаляются, когда у него не остаётся ни одной локали.
- Когда локализованный тип ссылается на другой локализованный тип, при чтении цель
  разрешается в той же локали, и фильтры через связи работают так же. Нелокализованные цели
  общие для всех локалей.
- Полезная нагрузка вебхуков и версии истории записывают локаль.

В отличие от Strapi, у content API нет маршрута `/api/i18n/locales`. Локали перечисляются в
admin API по адресу `GET /admin/api/i18n/locales` и управляются через `POST`,
`PUT /admin/api/i18n/locales/{code}` и `DELETE /admin/api/i18n/locales/{code}`
(`locales.manage`).

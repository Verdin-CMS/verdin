Процесс проверки — это упорядоченный список этапов, например *To do*, *In review* и *Ready*,
через которые проходят записи некоторых типов содержимого перед публикацией. В этом
руководстве вы настроите процесс, будете перемещать и назначать записи и познакомитесь с
соответствующим admin API.

В Strapi процессы проверки — функция Enterprise. В Verdin они входят в открытое ядро.

## Перед началом

- Включите **Настройки → Функции → Процессы проверки**. По умолчанию функция выключена.
- Для настройки процессов нужно **Управление процессами проверки** (`workflows.manage`).
- Для перемещения и назначения записи нужен доступ на её изменение. См.
  [Разрешения](/ru/reference/permissions/).

## Создайте процесс

<Steps>

1. Откройте **Настройки → Процессы проверки** и выберите **Новый процесс**.
2. Задайте ему **Название**.
3. В разделе **Типы содержимого** выберите типы, записи которых следуют этому процессу. Тип
   может следовать не более чем одному процессу.
4. В разделе **Этапы** перечислите этапы по порядку. У каждого есть **Название этапа** и
   **Цвет**. Добавляйте этапы кнопкой **Добавить этап**, а порядок меняйте кнопками со
   стрелками. Новые записи начинают с первого этапа.
5. При желании выберите для этапа **Роли, которые могут перемещать записи на этот этап**. Если
   роли не выбраны, это может любой, кто может изменять запись.
6. При желании задайте **Этап, необходимый для публикации**. Тогда записи можно публиковать,
   только пока они на этом этапе. **Любой этап** не ограничивает публикацию.
7. Сохраните.

</Steps>

Записи, которые существовали до подключения их типа к процессу, находятся на первом этапе.

Если потом изменить процесс:

- Удаление этапа возвращает его записи на первый этап.
- Исключение типа содержимого из процесса сбрасывает этапы его записей.
- Удаление процесса сбрасывает этапы и ответственных его записей.

## Перемещение и назначение записей

Редактор записи показывает панель **Проверка** с полями **Этап** и **Ответственный**.

- Выберите другой **Этап**, чтобы переместить запись. Этапы, зарезервированные для других
  ролей, выбрать нельзя, и панель об этом сообщает. Администраторы с **Управление процессами
  проверки** всегда могут перемещать записи.
- Выберите **Ответственного** из активных администраторов, которые могут читать тип
  содержимого, или выберите **Убрать ответственного**. Назначить запись может любой, кто может
  её изменять.
- Если в процессе есть обязательный этап, панель сообщает, какого этапа должна достичь запись,
  прежде чем сработает **Опубликовать**.

В списке есть столбец **Этап**, а главная страница показывает назначенные вам записи в разделе
**Назначено мне**. Локализованные типы хранят этап отдельно для каждой локали.

## Что блокирует этап публикации

Обязательный этап действует для всех способов публикации: админ-панели, REST, GraphQL,
релизов и плагинов. Публикация записи, которая не на этом этапе, завершается ошибкой `400`:

```text
the entry must be in the review stage `Ready` to be published
```

В Strapi требование этапа действует только в админ-панели. Роли этапов тоже работают иначе: в
Verdin они ограничивают, кто перемещает записи *на* этап.

## Журналы аудита и вебхуки

- Смена этапов и назначения записываются в [журналы аудита](/ru/guides/content/audit-logs/)
  как `entry.stage` и `entry.assign`.
- Вебхуки могут подписаться на **Этап записи изменён** (`review-workflows.updateEntryStage`).
  См. [Вебхуки](/ru/guides/integrations/webhooks/).

## Admin API

Все маршруты находятся под `/admin/api` и принимают токен доступа администратора.

| Маршрут | Разрешение | Что делает |
| --- | --- | --- |
| `GET /review-workflows`, `GET /review-workflows/{id}` | `workflows.manage` | Процессы с их этапами. |
| `POST /review-workflows`, `PUT /review-workflows/{id}` | `workflows.manage` | Создать или заменить процесс (тело ниже). |
| `DELETE /review-workflows/{id}` | `workflows.manage` | Записи его типов теряют этапы. |
| `GET /content/{uid}/{documentId}/review?locale=` | чтение записи | Этап, ответственный и этапы, на которые вы можете переместить запись (`canMoveTo`). |
| `PUT /content/{uid}/{documentId}/review?locale=` | изменение записи | `{ "stageId": 3, "assigneeId": 7 }`. Оба поля необязательны; `"assigneeId": null` убирает ответственного. |
| `GET /content/{uid}/review?documentIds=a,b` | чтение типа | Этапы до 200 записей, процесс — в `meta.workflow`. |
| `GET /review/assigned` | выполнен вход | Записи, назначенные вам. |
| `GET /review/assignees?uid=` | изменение типа | Активные администраторы, которые могут читать тип. |
| `GET /review/roles` | `workflows.manage` | Коды и названия ролей для ролей этапов. |

Процесс в том виде, в каком его отправляют в `POST` и `PUT`:

```json
{
  "name": "Editorial",
  "contentTypes": ["api::article"],
  "stages": [
    { "id": 1, "name": "To do", "color": "#4945ff" },
    { "id": 2, "name": "In review", "color": "#ff8800" },
    { "name": "Ready", "color": "#2f9e44", "roles": ["editor"] }
  ],
  "publishStage": "Ready"
}
```

- В процессе от 1 до 50 этапов с уникальными названиями и цветами `#rrggbb`.
- `publishStage` указывает один из этапов; не передавайте его, если этап не нужен.
- Передавайте существующие этапы с их `id`, чтобы записи на них остались на месте. Этапы без
  `id` считаются новыми.

<Aside type="note">
Выключение функции скрывает этапы и перестаёт требовать этап публикации. Процессы и этапы
записей сохраняются до повторного включения.
</Aside>

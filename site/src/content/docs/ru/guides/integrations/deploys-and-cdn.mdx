Два инструмента для сайтов, которые кешируют то, что отдаёт Verdin:

- **Деплои** добавляют кнопку **Деплой** в шапку админки. Она вызывает хук сборки вашего
  сайта (Netlify, Vercel, Cloudflare Pages или любой CI), а провайдер сообщает, как идёт
  сборка.
- **Очистка CDN** помечает ответы content API тегами по типам содержимого и очищает эти теги
  в Cloudflare, Fastly или на вашем собственном эндпоинте, когда контент меняется публично.

Оба инструмента входят в ядро: отдельного переключателя функции нет. Деплои настраиваются в
**Настройки → Деплои**, CDN — в `verdin.toml`.

### Добавьте цель

<Steps>

1. У провайдера создайте хук сборки для сайта и скопируйте его URL (Netlify: **Build
   hooks**; Vercel: **Deploy Hooks**; Cloudflare Pages: **Deploy hooks**; CI: любой URL,
   который запускает пайплайн по `POST`).
2. В Verdin перейдите в **Настройки → Деплои** и выберите **Добавить цель**.
3. Задайте **Название** (например, **Продакшен-сайт**) и вставьте **URL хука сборки**.
4. Сохраните. URL хука — это секрет: дальше показывается только его хост. Чтобы направить
   цель на другой хук, используйте **Заменить URL**.

</Steps>

Администраторы, которые могут деплоить, теперь видят **Деплой** в шапке. При нескольких
целях кнопка открывает меню **Деплой в**. После подтверждения Verdin отправляет:

```http
POST <build hook URL>
content-type: application/json

{ "trigger": "verdin", "triggeredBy": "editor@example.com" }
```

Цель деплоится не чаще раза в 10 секунд, поэтому двойной щелчок не запускает две сборки.
Запрос прерывается через 15 секунд и не следует редиректам. Хук, который отвечает не `2xx`,
записывается как **Отклонён**.

### Передавайте состояния сборки обратно

Без обратного вызова деплой остаётся в состоянии **Запущен**. Чтобы видеть в админке
**Сборка**, **Готов** и **Ошибка** и ссылку на задеплоенный сайт, передайте провайдеру URL
обратного вызова цели: нажмите кнопку **URL обратного вызова** цели и скопируйте его.

<Tabs syncKey="deploy-provider">
<TabItem label="Netlify">

В **Site configuration → Build & deploy → Deploy notifications** добавьте исходящий вебхук
для **Deploy started**, **Deploy succeeded** и **Deploy failed** с URL обратного вызова.

</TabItem>
<TabItem label="Vercel">

В **Team settings → Webhooks** создайте вебхук для событий `deployment.created`,
`deployment.succeeded` и `deployment.error` с URL обратного вызова.

</TabItem>
<TabItem label="Другой CI">

Отправьте `POST` с JSON, содержащим `status` (`building`, `ready` или `error`) и, при
желании, `url` задеплоенного сайта и `message`:

```sh title="Terminal"
curl -X POST "$VERDIN_CALLBACK_URL" -H 'content-type: application/json' \
  -d '{ "status": "ready", "url": "https://www.example.com" }'
```

</TabItem>
</Tabs>

Verdin понимает `state` от Netlify, `type` от Vercel и обычный `status` и обновляет последний
деплой цели. Он отвечает `204` или `404`, если URL неверный. URL обратного вызова имеет вид
`{public_url}{admin path}/api/deploy/callback/{id}/{secret}`, поэтому задайте в
[`[server].public_url`](/ru/reference/configuration/) адрес, доступный провайдерам.

<Aside type="caution">
URL обратного вызова содержит секрет: любой, у кого он есть, может сообщать состояния деплоя
для этой цели. Запускать деплои или что-либо читать с его помощью нельзя.
</Aside>

**История деплоев** показывает последние 50 деплоев, новые сверху, с целью, временем начала,
статусом, HTTP-статусом хука и сообщением провайдера. Удаление цели удаляет её историю, но не
хук сборки.

### Разрешения

| Разрешение | Разрешает |
| --- | --- |
| **Запуск деплоев** (`deploy.trigger`) | Кнопку **Деплой** в шапке. Оно есть у встроенной роли Editor. |
| **Управление целями деплоя и CDN** (`deploy.manage`) | **Настройки → Деплои**: цели, URL обратного вызова и очистку CDN. |

См. [Разрешения](/ru/reference/permissions/). URL хуков сборки подчиняются тем же правилам
адресов, что и [вебхуки](/ru/guides/integrations/webhooks/): при `verdin start` они не могут
указывать на частные сети, если это не разрешено
[`[webhooks].allow_private_networks`](/ru/reference/configuration/).

### Деплой при каждом изменении

Кнопка подходит сайтам, которые пересобираются по требованию. Чтобы пересобирать сайт при
каждой публикации, создайте [вебхук](/ru/guides/integrations/webhooks/) для `entry.publish` и
`entry.unpublish` с хуком сборки в качестве URL. Для запланированного пакета изменений
публикуйте их [релизом](/ru/guides/content/releases/) и подпишите вебхук на
`releases.publish`.

## Очистка CDN

Когда CDN кеширует content API, он отдаёт устаревший контент, пока не истечёт кеш. С
настроенным `[cdn]` Verdin помечает свои ответы тегами и очищает нужные теги по мере
изменения контента, поэтому кешировать можно надолго.

### Как работают теги

Каждый успешный `GET` к content API содержит `vd` (всё), `vd-<singularName>` (тип
содержимого) и тег каждого типа, который могут подгрузить его документы: цели связей, в том
числе внутри компонентов и динамических зон, с переходом по их собственным связям. Для
статей примера блога в обоих форматах заголовков:

```http
Cache-Tag: vd,vd-article,vd-category,vd-tag
Surrogate-Key: vd vd-article vd-category vd-tag
```

Тип с полиморфной связью может дотянуться до любого типа, поэтому его ответы содержат теги
всех типов.

Cloudflare читает `Cache-Tag`, Fastly — `Surrogate-Key`. Когда контент меняется публично,
Verdin очищает тег типа:

- при публикации, снятии с публикации или удалении записи;
- при любой записи в тип без черновиков и публикации (его записи сразу публичны).

Сохранение черновика ничего не очищает, поскольку черновики публично не отдаются. Изменения в
пределах секунды (`debounce_ms`) собираются в одну очистку, а неудачная очистка повторяется
дважды.

### Настройка

<Tabs syncKey="cdn">
<TabItem label="Cloudflare">

```toml title="verdin.toml"
[cdn]
provider = "cloudflare"
zone_id = "023e105f4ecef8ad9ca31a8372d0c353"
```

`VERDIN_CDN_TOKEN` — API-токен с разрешением **Cache Purge** для зоны.

</TabItem>
<TabItem label="Fastly">

```toml title="verdin.toml"
[cdn]
provider = "fastly"
service_id = "SU1Z0isxPaozGVKXdv0eY"
```

`VERDIN_CDN_TOKEN` — API-токен Fastly с правом очищать сервис.

</TabItem>
<TabItem label="Вебхук">

```toml title="verdin.toml"
[cdn]
provider = "webhook"
url = "https://purge.example.com/verdin"
```

Verdin отправляет `POST { "tags": ["vd-article"] }` с `Authorization: Bearer <VERDIN_CDN_TOKEN>`,
если токен задан. Используйте это для другого CDN, обратного прокси или API ревалидации
вашего фреймворка.

</TabItem>
</Tabs>

```sh title="Terminal"
export VERDIN_CDN_TOKEN=...
```

Verdin проверяет раздел при запуске и не работает без `zone_id`, `service_id`, `url` или
токена, которые нужны провайдеру. См. [`[cdn]`](/ru/reference/configuration/).

Что кешировать, по-прежнему решает ваш CDN: настройте правило кеширования для путей API
(например, `/api/*` для анонимных `GET`) с долгим TTL на edge. Не кешируйте
аутентифицированные запросы, чтение для предпросмотра и `/api/_events`.

### Проверка и ручная очистка

Раздел **CDN** в **Настройки → Деплои** показывает провайдера и **Недавние очистки**
(**Очищено** или **Ошибка**, с тегами). **Очистить всё** сбрасывает все ответы с тегом `vd`.

Поскольку ответы содержат теги типов, которые они могут подгрузить, переименование категории
также очищает закешированные списки статей, в которые она могла попасть, независимо от того,
запрашивал ли запрос `populate`.

Собственный кеш Verdin в памяти ([`[api].cache_ttl_secs`](/ru/reference/configuration/))
работает отдельно: он очищается при каждом изменении.

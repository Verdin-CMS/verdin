Администраторы могут входить через любого провайдера OpenID Connect: Microsoft Entra ID,
Google Workspace, Okta, Auth0, Keycloak, Authentik, GitLab и других. Для каждого провайдера на
странице входа появляется кнопка, а вход по паролю продолжает работать рядом с ней. В этом
руководстве вы зарегистрируете приложение, настроите провайдера в Verdin и сопоставите группы
с ролями.

В Strapi SSO — функция Enterprise. В Verdin она входит в открытое ядро. Для конечных
пользователей ваших сайтов см. [вход через OAuth для конечных пользователей](/ru/guides/auth/end-users/).

## Перед началом

- Для настройки SSO нужно **Управление функциями** (`features.manage`).
- Задайте `[server].public_url` — адрес, по которому администраторы открывают Verdin,
  например `https://cms.example.com`. Из него строится URI перенаправления.

## Настройка

<Steps>

1. **Зарегистрируйте приложение** (клиент типа «web») у провайдера с таким URI
   перенаправления:

   ```text
   https://cms.example.com/admin/api/auth/sso/<id>/callback
   ```

   `<id>` — id провайдера, который вы выберете на шаге 3, например `corp`. Путь админки
   следует `[admin].path`.

2. **Задайте секрет клиента в окружении** и перезапустите Verdin:

   ```sh title=".env"
   VERDIN_SSO_CORP_SECRET=…
   ```

   Переменная называется `VERDIN_SSO_<ID>_SECRET`, где id записан заглавными буквами, а
   дефисы заменены подчёркиваниями. Публичным клиентам (только PKCE, без секрета) переменная
   не нужна.

3. **Добавьте провайдера.** Включите **Настройки → Функции → Единый вход**, выберите
   **Настроить провайдеров**, затем **Добавить провайдера** и заполните:

   - **ID**: строчные буквы, цифры и дефисы, не больше 32 символов.
   - **Текст кнопки**: показывается на странице входа как «Продолжить через …».
   - **URL издателя**: Verdin читает `/.well-known/openid-configuration` по этому адресу.
     Должен использовать `https`, кроме `localhost`.
   - **ID клиента** и **Области (scopes)** (по умолчанию `openid email profile`; `openid`
     обязателен).

   Диалог показывает **URI перенаправления для регистрации у провайдера** и имя переменной
   секрета. Сохраните.

4. **Проверьте** в приватном окне: на странице входа появится **Продолжить через Corp
   account**.

</Steps>

## Кто может входить и с какими ролями

| Настройка | Ключ JSON | Действие |
| --- | --- | --- |
| **Разрешённые домены эл. почты** | `allowedDomains` | Входить могут только адреса с этими доменами. Пусто — любые. |
| **Создавать аккаунты при первом входе** | `autoCreate` | Создавать учётную запись администратора при первом входе. Без этого входить могут только адреса, у которых уже есть учётная запись. |
| **Роли по умолчанию** | `defaultRoles` | Коды ролей созданных учётных записей, если сопоставление ролей ничего не дало. |
| **Claim роли** | `roleClaim` | Claim ID-токена со списком групп пользователя, например `groups` или `roles`. |
| **Сопоставление ролей** | `roleMap` | Какой код роли даёт каждое значение claim. |
| **Доверять неподтверждённым адресам** | `trustUnverifiedEmail` | Принимать адреса, которые провайдер не помечает как подтверждённые. |
| **Провайдер требует MFA** | `providerMfa` | Не спрашивать у администраторов второй фактор Verdin после входа через этого провайдера. |

- Провайдеру, который создаёт учётные записи, нужны роли по умолчанию или сопоставление ролей.
- Ни то, ни другое не может выдать роль Super Admin; повышайте администраторов вручную в
  **Настройки → Пользователи**.
- Роли задаются только при создании учётной записи. Потом управляйте ими в
  **Настройки → Пользователи**.
- Имя и фамилия созданной учётной записи берутся из claims `given_name` и `family_name`.

Тот же провайдер в JSON, как его хранит функция (`PUT /admin/api/features/sso`):

```json
{
  "enabled": true,
  "settings": {
    "providers": [
      {
        "id": "corp",
        "name": "Corp account",
        "issuer": "https://login.microsoftonline.com/<tenant>/v2.0",
        "clientId": "…",
        "scopes": ["openid", "email", "profile"],
        "autoCreate": true,
        "defaultRoles": ["author"],
        "roleClaim": "groups",
        "roleMap": { "<editors group id>": "editor" },
        "allowedDomains": ["corp.example"],
        "trustUnverifiedEmail": true,
        "providerMfa": true
      }
    ]
  }
}
```

## Замечания о провайдерах

- **Microsoft Entra ID** не включает `email_verified` в свои ID-токены: включите для него
  **Доверять неподтверждённым адресам**. Чтобы сопоставлять группы, добавьте claim `groups` в
  настройках токенов приложения; его значения — это id групп.
- **Google Workspace**: издатель — `https://accounts.google.com`. Ограничьте вход своим
  доменом через **Разрешённые домены эл. почты**.
- **Keycloak**: издатель — URL realm, `https://<host>/realms/<realm>`.

## Двухфакторная аутентификация

По умолчанию у администратора, у которого есть [второй фактор](/ru/guides/auth/two-factor/)
Verdin, его спрашивают после возврата от провайдера. Если провайдер уже требует MFA, включите
**Провайдер требует MFA**, чтобы его не спрашивали дважды.

## Как это работает

<Diagram
  caption="Вход через SSO"
  code={`sequenceDiagram
  participant B as Браузер
  participant V as Verdin
  participant P as Провайдер
  B->>V: GET /admin/api/auth/sso/corp
  V-->>B: редирект со state и PKCE challenge
  B->>P: вход
  P-->>B: редирект на callback с code
  B->>V: GET /admin/api/auth/sso/corp/callback
  V->>P: обмен code (TLS)
  V-->>B: cookie сессии, редирект на /admin/`}
/>

- Verdin использует authorization code flow с PKCE (S256). `state` подписывается и
  привязывается к короткоживущей cookie `HttpOnly`, а `nonce` выводится из него.
- Verdin проверяет издателя, аудиторию (и `azp`, если их несколько), срок действия и nonce
  ID-токена. Нужен claim `email` с `email_verified: true`, если не включено **Доверять
  неподтверждённым адресам**.
- Эндпоинты провайдера должны использовать `https`.
- Каждый вход через SSO записывается в [журналы аудита](/ru/guides/content/audit-logs/) как
  `admin.login` с указанием провайдера.

Если вход не удался, браузер возвращается на страницу входа с причиной ("Single sign-on
failed"), и причина записывается в лог сервера. Частые причины:

| Причина | Решение |
| --- | --- |
| the provider did not verify the email | Включите **Доверять неподтверждённым адресам** или исправьте claim у провайдера. |
| this email domain may not sign in | Добавьте домен в **Разрешённые домены эл. почты**. |
| no admin account for this identity | Включите **Создавать аккаунты при первом входе** или сначала создайте администратора. |
| the sign-in request expired or was not started here | Начните заново со страницы входа в том же браузере. |

<Aside type="note">
Деактивированный администратор не может войти и через SSO.
</Aside>

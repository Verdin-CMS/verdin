Конечные пользователи — это люди, которые входят на ваш сайт или в приложение, а не в
админ-панель. Verdin даёт им регистрацию, вход, подтверждение email, сброс пароля, провайдеров
OAuth и роли, которые определяют, что они могут делать в content API. Маршруты и полезная
нагрузка — как у плагина users-permissions в Strapi v5, поэтому существующие фронтенды
продолжают работать.

## Перед началом

<Steps>

1. Включите **Настройки → Функции → Пользователи и права** (по умолчанию выключено) или
   включите **Конечные пользователи** в **Настройки → Конечные пользователи → Настройки**.
2. Настройте `[email]`, если используете подтверждение email или сброс пароля:

   ```toml title="verdin.toml"
   [email]
   provider = "smtp"          # log (default), smtp, resend or postmark
   from = "My site <no-reply@example.com>"

   [email.smtp]
   host = "smtp.example.com"
   port = 587
   username = "apikey"        # password in VERDIN_EMAIL_SMTP_PASSWORD
   ```

   Resend и Postmark читают свой ключ из `VERDIN_EMAIL_API_KEY`. В
   **Настройки → Функции → Эл. почта** есть **Отправить тестовое письмо**. Для локальной
   работы `docker/compose.dev.yml` включает Mailpit (SMTP на порту 1025, почтовый ящик на
   `http://localhost:8025`).

3. Задайте `[server].public_url`: его используют ссылки в письмах и callback OAuth.

</Steps>

Для управления учётными записями и ролями нужно **Управление конечными пользователями**
(`endusers.manage`). Для изменения вкладки настроек (регистрация, провайдеры, шаблоны) нужно
**Управление функциями** (`features.manage`).

## Настройте регистрацию и сессии

В **Настройки → Конечные пользователи → Настройки**, в разделе **Регистрация и сессии**:

| Настройка | По умолчанию | Действие |
| --- | --- | --- |
| **Разрешить регистрацию** | включено | Любой может создать учётную запись через content API. Выключено: `register` отвечает `400`. |
| **Подтверждать адреса эл. почты** | выключено | Новые пользователи должны открыть ссылку из письма, прежде чем смогут войти. |
| **Роль по умолчанию** | Authenticated | Роль новых учётных записей. |
| **Сессии** | Один долгоживущий токен | **Один долгоживущий токен** (устаревший режим Strapi) или **Короткие токены с обновлением**. |
| **Длительность сессии (дней)** | 30 | Время жизни долгоживущего токена. |
| **Срок действия токена доступа (в минутах)**, **Срок действия refresh-токена (в днях)** | 30, 30 | С refresh-токенами. |

В разделе **Страницы вашего приложения** задайте **После подтверждения эл. почты** (куда
попадают пользователи после подтверждения адреса) и **Страница сброса пароля** (ваша
страница, которая получает `?code=` и просит новый пароль). Для сброса пароля нужна страница
сброса.

## Настройте роли

Каждый запрос выполняется от имени одной из ролей:

- **Public**: запросы без токена. Её разрешения — это разрешения из **Настройки → Публичный
  доступ**.
- **Authenticated**: встроенная роль, которая выдаётся новым учётным записям. Её нельзя
  удалить.
- **Пользовательские роли**: создавайте их в **Настройки → Конечные пользователи → Роли**
  кнопкой **Создать роль**.

**Разрешения** роли используют ту же матрицу, что публичный доступ и API-токены: **Найти**,
**Найти одну**, **Создать**, **Изменить**, **Удалить**, **Опубликовать** и **Читать
черновики** для каждого типа содержимого, **Медиатеки** и **Пользователей** (маршруты
`/api/users`). Вошедший пользователь получает только разрешения своей роли, а не ещё и
публичный доступ: если вошедшим пользователям нужно публичное чтение, выдайте его и роли.
При удалении роли её пользователи переходят в Authenticated.

Чтобы действовать от имени пользователя, фронтенд отправляет его JWT как
`Authorization: Bearer <jwt>`. API-токены начинаются с `vd_` — так Verdin их различает.

## Регистрация и вход

<Tabs>
<TabItem label="Регистрация">

```sh title="Terminal"
curl -X POST http://localhost:1337/api/auth/local/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"ana","email":"ana@example.com","password":"a long password"}'
# → { "jwt": "…", "user": { "id": 1, "username": "ana", … } }
#   или { "user": … }, если включено подтверждение email
```

</TabItem>
<TabItem label="Вход">

```sh title="Terminal"
curl -X POST http://localhost:1337/api/auth/local \
  -H 'Content-Type: application/json' \
  -d '{"identifier":"ana@example.com","password":"a long password"}'
# → { "jwt": "…", "user": {…} }
```

`identifier` — это email или имя пользователя.

</TabItem>
<TabItem label="Чтение от имени пользователя">

```sh title="Terminal"
curl -H "Authorization: Bearer $JWT" http://localhost:1337/api/users/me
curl -H "Authorization: Bearer $JWT" http://localhost:1337/api/articles
```

</TabItem>
</Tabs>

Вход отклоняется для заблокированных пользователей ("Your account has been blocked by an
administrator") и, при включённом подтверждении, для неподтверждённых ("Your account email is
not confirmed").

## Токены и сессии

- **Один долгоживущий токен** (`jwtManagement: "legacy-support"`): JWT действует
  **Длительность сессии (дней)**.
- **Короткие токены с обновлением** (`jwtManagement: "refresh"`, как в Strapi 5): JWT
  действует **Срок действия токена доступа (в минутах)**, а ответы на вход дополнительно
  содержат `refreshToken`. Вызовите `POST /api/auth/refresh` с `{ refreshToken }`, чтобы
  получить новую пару. Каждый refresh-токен срабатывает один раз; предъявление уже
  использованного завершает всю сессию. `POST /api/auth/logout` с `{ refreshToken }`
  завершает её намеренно.
- Смена или сброс пароля отзывает прежние токены пользователя, как и его блокировка.
- Запросы входа, регистрации и сброса ограничены 20 в минуту на IP клиента.
- Пароли хранятся в Argon2id. Учётные записи, импортированные из Strapi, сохраняют хеш bcrypt
  до следующего входа, когда он пересчитывается.

## Подтверждение адресов email и сброс паролей

При включённом **Подтверждать адреса эл. почты** регистрация отправляет по почте ссылку на
`/api/auth/email-confirmation?confirmation=…`. Открытие ссылки подтверждает учётную запись и
перенаправляет на **После подтверждения эл. почты**. `POST /api/auth/send-email-confirmation`
с `{ email }` отправляет новую ссылку.

Если пароль забыт:

<Steps>

1. Ваше приложение вызывает `POST /api/auth/forgot-password` с `{ email }`. Ответ одинаковый,
   существует учётная запись или нет.
2. Пользователь получает письмо со ссылкой на вашу **Страницу сброса пароля** с `?code=…`. Код
   действует один час.
3. Ваша страница вызывает `POST /api/auth/reset-password` с
   `{ code, password, passwordConfirmation }` и получает `{ jwt, user }`.

</Steps>

Вошедшие пользователи меняют пароль через `POST /api/auth/change-password`
(`{ currentPassword, password, passwordConfirmation }`).

Письма редактируются в **Настройки → Конечные пользователи → Настройки → Шаблоны писем**:
**Тема**, **Сообщение** и необязательное **HTML-тело (необязательно)** для **Подтверждение
эл. почты** и **Сброс пароля**. В них можно использовать подстановки `{{username}}`,
`{{email}}` и `{{url}}`; в HTML-теле значения экранируются.

## Вход через провайдеров OAuth

Есть встроенные пресеты для GitHub, Google, Microsoft, Discord, Facebook, GitLab и LinkedIn.
Любое другое имя — это обобщённый провайдер OAuth 2, которому нужны **URL авторизации**,
**URL токена** и **URL информации о пользователе**: так работают Keycloak, Auth0 и Okta с URL
вашего realm или tenant. Вход через Apple не поддерживается.

<Steps>

1. В **Настройки → Конечные пользователи → Настройки → Провайдеры входа** выберите
   **Добавить GitHub** (или другой пресет, или **Добавить провайдера OAuth 2**).
2. У провайдера зарегистрируйте **URL обратного вызова для регистрации у провайдера**,
   показанный в диалоге: `https://cms.example.com/api/connect/github/callback`.
3. Введите **ID клиента**, необязательные **Области доступа** и **Перенаправление в ваше
   приложение** — страницу фронтенда, которая получает `?access_token=` после входа.
   Включите **Включён**.
4. Задайте секрет клиента в окружении сервера и перезапустите его:

   ```sh title=".env"
   VERDIN_OAUTH_GITHUB_SECRET=…
   ```

   Переменная называется `VERDIN_OAUTH_<PROVIDER>_SECRET`. Секреты никогда не хранятся в базе
   данных.

</Steps>

Вход идёт по той же схеме, что в Strapi:

<Diagram
  caption="Вход конечных пользователей через OAuth"
  code={`sequenceDiagram
  participant B as Браузер
  participant V as Verdin
  participant P as Провайдер
  B->>V: GET /api/connect/github
  V-->>B: редирект к провайдеру
  B->>P: согласие
  P-->>B: редирект на /api/connect/github/callback
  B->>V: callback
  V-->>B: редирект на вашу страницу ?access_token=…
  B->>V: GET /api/auth/github/callback?access_token=…
  V-->>B: { jwt, user }`}
/>

`state` OAuth подписывается и привязывается к браузеру через cookie. Учётные записи
сопоставляются по email; email, который уже использует другой провайдер или учётная запись с
email и паролем, отклоняется ("Email is already taken.").

## Управление учётными записями в админ-панели

**Настройки → Конечные пользователи → Пользователи** показывает учётные записи с поиском по
имени пользователя или email. Можно **Добавить пользователя**, отредактировать учётную запись
(имя пользователя, email, пароль, роль, **Подтверждён**, **Заблокирован**),
**Заблокировать** или **Разблокировать** её и удалить.

## Маршруты

Маршруты находятся под префиксом content API, по умолчанию `/api`. Формат запросов и ответов
повторяет Strapi v5.

| Маршрут | Что делает |
| --- | --- |
| `POST /auth/local/register` | `{ username, email, password }` → `{ jwt, user }` или `{ user }` при включённом подтверждении email. |
| `POST /auth/local` | `{ identifier, password }` → `{ jwt, user }`. |
| `GET /auth/email-confirmation?confirmation=` | Подтверждает email, затем перенаправляет или возвращает пользователя. |
| `POST /auth/send-email-confirmation` | `{ email }`: новая ссылка подтверждения. |
| `POST /auth/forgot-password` | `{ email }`: отправляет ссылку для сброса. |
| `POST /auth/reset-password` | `{ code, password, passwordConfirmation }` → `{ jwt, user }`. |
| `POST /auth/change-password` | Требует входа. `{ currentPassword, password, passwordConfirmation }` → `{ jwt, user }`. |
| `POST /auth/refresh`, `POST /auth/logout` | Только в режиме обновления: `{ refreshToken }`. |
| `GET /users/me` | Вошедший пользователь. |
| `GET /users`, `GET /users/count`, `GET /users/{id}` | Нужно Найти / Найти одну для Пользователей. Обычный JSON без обёртки `data`, как в Strapi. `populate=role` добавляет роль, `_q=` ищет по именам пользователей и email, `pagination[page]` и `pagination[pageSize]` (не больше 100) листают страницы. |
| `POST /users`, `PUT /users/{id}`, `DELETE /users/{id}` | Нужно Создать / Изменить / Удалить для Пользователей. `{ username, email, password, confirmed, blocked, role }`, где `role` — id роли. |
| `GET /connect/{provider}` | Начинает вход через OAuth. |
| `GET /auth/{provider}/callback?access_token=` | Обменивает токен провайдера на `{ jwt, user }`. |

`verdin import strapi` переносит конечных пользователей с их паролями, пользовательские роли и
разрешения ролей public, authenticated и пользовательских. См.
[Миграция со Strapi](/ru/migrate/from-strapi/).

<Aside type="caution">
Роль с правами Создать, Изменить или Удалить для **Пользователей** позволяет её участникам
управлять всеми учётными записями конечных пользователей. Выдавайте её только доверенным
ролям или API-токенам.
</Aside>

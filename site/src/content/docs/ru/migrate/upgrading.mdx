На этой странице объясняется, как перевести проект на более новую версию Verdin, и
перечислено, что менялось между минорными версиями. Verdin следует
[семантическому версионированию](https://semver.org/) с поправкой на 0.x: до 1.0 **минорный**
релиз (0.8 → 0.9) может менять поведение, а **патч**-релиз (0.9.0 → 0.9.1) только исправляет
ошибки и укрепляет защиту.

## Перед обновлением

1. **Прочитайте журнал изменений** от вашей версии до новой:
   [журнал изменений](/ru/project/changelog/) перечисляет все изменения, а
   [заметки ниже](#заметки-об-обновлении) кратко описывают те, что требуют действий.
2. **Сделайте резервную копию** базы данных и хранилища медиа (см.
   [Резервные копии](/ru/deploy/backups/)). Возврат к старой версии означает восстановление
   этой копии: старые версии не отменяют таблицы и колонки, добавленные новой.
3. **Попробуйте на копии** продакшена, если в заметках упоминается поведение, на которое
   полагаются ваш фронтенд или редакторы.

Версии можно пропускать. Миграции вычисляются по разнице между базой данных и тем, что
ожидает новая версия, а не проигрываются релиз за релизом, поэтому 0.6 → 0.9 мигрирует за один
прогон. Прочитайте заметки всех промежуточных версий.

## Обновление

<Tabs syncKey="install">
<TabItem label="Docker">

<Steps>

1. Измените тег образа в файле Compose, манифесте или `Dockerfile`, например
   `ghcr.io/verdin-cms/verdin:0.10` → `ghcr.io/verdin-cms/verdin:0.11`. Минорный тег (`0.10`)
   следует за своими патч-релизами; зафиксируйте полную версию (`0.10.0`), чтобы самим решать,
   когда их получать.

2. Скачайте образ и перезапустите:

   ```sh frame="terminal"
   docker compose pull verdin
   docker compose up -d verdin
   docker compose logs -f verdin
   ```

   Команда образа по умолчанию, `start --migrate`, применяет миграции новой версии до начала
   обслуживания запросов. Ищите в логах `applied migrations` и `verdin listening`.

</Steps>

</TabItem>
<TabItem label="Binary">

<Steps>

1. Скачайте архив для своей платформы со
   [страницы релизов](https://github.com/Verdin-CMS/verdin/releases), например
   `verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz`, и сверьте его с `SHA256SUMS` релиза:

   ```sh frame="terminal"
   sha256sum --ignore-missing -c SHA256SUMS
   tar xzf verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz
   ```

2. Остановите сервер, замените бинарник `verdin` и проверьте версию:

   ```sh frame="terminal"
   verdin version
   ```

3. Проверьте и примените миграции из каталога проекта:

   ```sh frame="terminal"
   verdin migrate plan
   verdin migrate apply
   ```

   Или запустите `verdin start --migrate`, который сначала применяет безопасные шаги.

4. Запустите сервер как обычно (`verdin start`).

</Steps>

## Миграции при запуске

Новая версия часто добавляет собственные таблицы или колонки (сессии, настройки, новые
функции). `verdin start` сравнивает базу данных с тем, что нужно схеме и новой версии:

- Если они совпадают, сервер запускается.
- Если есть ожидающие шаги, он не запускается и предлагает выполнить `verdin migrate plan` и
  `verdin migrate apply` или запустить сервер с `--migrate`.
- `--migrate` применяет только **безопасные** шаги. Если шаг рискованный или разрушительный,
  запуск завершается ошибкой, и вы применяете его сами через
  `verdin migrate apply --allow risky` (или `destructive`), прочитав план.
- В MySQL и MariaDB, где изменения схемы нельзя выполнить в транзакции, прерванная миграция
  продолжается с упавшего шага при следующем `verdin migrate apply`.

При нескольких экземплярах работает постепенное обновление: первый новый экземпляр берёт
блокировку миграции и выполняет её, остальные ждут и обнаруживают, что делать уже нечего. См.
[Запуск нескольких экземпляров](/ru/deploy/scaling/).

<Aside type="caution">
Переводите весь проект на одну версию. Не держите одновременно запущенными экземпляры двух
минорных версий дольше, чем длится постепенный деплой.
</Aside>

## Заметки об обновлении

Заметные и ломающие изменения по версиям, от новых к старым. Полный список — в
[журнале изменений](/ru/project/changelog/).

### 0.10 → 0.11

Миграция, которая выполняется при запуске, добавляет одну таблицу, `vd_cluster_events`; она
используется только при `[cluster] bus = "database"`.

- **Decimal**: целые значения `decimal` возвращаются как целые числа JSON (`25`, а не
  `25.0`), как это делает Strapi. Клиенты со строгой проверкой типа JSON могут это заметить;
  `[api] decimal_as_string` не изменился. В SQLite `sort` и `$gt`/`$lt`/`$between` по decimal
  теперь сравнивают числа, а не текст, поэтому результаты, зависевшие от прежнего
  (неправильного) порядка, меняются.
- **`populate=*` в локализованных типах** теперь возвращает и `localizations` — остальные
  языковые версии документа, как в Strapi v5. Атрибут схемы с именем `localizations`
  сохраняет своё значение.
- **Плагины**: хуки «после», вызванные собственными записями плагина, выполняются, когда его
  вызов вернулся, а не внутри записи, а хуки, которые пишут, вкладываются не глубже 4
  уровней. Функции хоста останавливаются на лимите времени вызова.
- **Несколько экземпляров**: задайте `[cluster] bus = "database"` на каждом экземпляре, чтобы
  потоки реального времени, присутствие, кеш ответов и поисковый индекс следовали за
  изменениями, сделанными на остальных (см. [Масштабирование](/ru/deploy/scaling/)).
- **Скрипты, читающие списки admin API**: `GET /admin/api/users`, `/roles`, `/api-tokens`,
  `/webhooks`, `/releases`, `/site/redirects`, `/site/menus`, `/site/forms` и
  `/deploy/targets` возвращают 25 строк, если не передать `pageSize` (не больше 100), с
  `meta.pagination`, как и списки, которые уже разбивались на страницы. Обходите страницы
  через `?page=`, пока `page` не достигнет `meta.pagination.pageCount`. `/deploy/deployments`
  разбивается так же, вместо того чтобы возвращать последние 50; `limit` по-прежнему
  работает как устаревший псевдоним `pageSize`. См. [Списки](/ru/api/admin/#списки).

### 0.9.1 → 0.10

Миграции базы данных нет. Документация переехала из `docs/` на этот сайт.

- **Получатели вебхуков `review-workflows.updateEntryStage`**: `model` теперь содержит имя в
  единственном числе (`article`), как в событиях записей, а uid переехал в `uid`. Читайте
  `uid` там, где использовали `model`.
- **Пересоздайте типы TypeScript** командой `verdin types`: `Collections` и `Singles` теперь
  псевдонимы типов, которые нужны `createClient<VerdinSchema>`.
- **Docker**: образ хранит кеш трансформаций и поисковый индекс в `/data` и связывает
  `/app/public/uploads` с `/data/uploads`. Если вы задавали
  `VERDIN_UPLOAD__TRANSFORMS__CACHE_DIR` или `VERDIN_SEARCH__DIR` только чтобы обойти
  доступный только для чтения `/app`, их можно убрать. У образа есть `HEALTHCHECK`.
- **CDN**: ответы содержат теги типов, которые они могут подгрузить, поэтому очистка обновляет
  большую часть кеша, чем раньше; менять ничего не нужно.
- Поля связей в админ-панели связывают записи через диалог (**Связать запись**) вместо
  встроенного поля поиска.

### 0.9.0 → 0.9.1

Релиз с укреплением защиты; обновиться рекомендуется всем установкам. Его миграция (одна
новая таблица, две новые колонки) выполняется при запуске.

- **За обратным прокси задайте `[server].trusted_proxies`.** Для адреса клиента используется
  `X-Forwarded-For` только от перечисленных прокси; иначе все клиенты за прокси делят один
  адрес для ограничений частоты и журналов аудита.
- **Браузерным фронтендам на другом origin нужен `[api].cors_origins`.** 0.9.1 добавляет CORS
  в content API и GraphQL; раньше поддержки CORS не было.
- **Чтение через связи учитывает разрешения.** `populate`, фильтры и сортировка по связям
  достигают только тех типов и полей, которые клиент может читать, во всех API. Публичные
  запросы и запросы с токеном, которые подгружали типы без права `find`, теперь получают
  меньше данных: выдайте недостающие разрешения.
- **SSO стал строже.** Для его настроек нужен Super Admin; `defaultRoles` и `roleMap` не могут
  выдавать Super Admin; claim `email_verified` провайдера должен быть true (если не задан
  `trustUnverifiedEmail`); второй фактор администраторов действует, если провайдеру не
  доверена эта проверка (`providerMfa`); издатель и эндпоинт токена должны быть публичными
  URL `https`. После обновления проверьте входы через SSO.
- **Super Admin** может создавать, редактировать, удалять, повторно приглашать или
  сбрасывать только другой Super Admin.
- **Учётные записи конечных пользователей блокируются** после повторных неверных паролей,
  как учётные записи администраторов.
- Подгруженные связи возвращают не больше 1000 записей на запись и связь.
- Поисковые индексы перестраиваются при первом запуске (приватные поля компонентов больше не
  индексируются).

### 0.8 → 0.9

- Поле поиска в списке админки ищет по всем текстовым полям (`_q`), а не по заголовку.
- Новые разрешения администраторов `deploy.manage`, `deploy.trigger` и `site.manage`;
  Editor получает `deploy.trigger` и `site.manage`.
- Новые необязательные функции (реальное время, комментарии и задачи, действия ИИ, SEO и
  карта сайта, редиректы, меню, формы) выключены, пока вы их не включите. Метрикам нужен
  `[metrics].enabled = true`.

### 0.7 → 0.8

- **Условные поля применяются**: поле, скрытое своими `conditions`, больше не обязательно.
  Контент, который полагался на обязательность такого поля, теперь может сохраняться без
  него.
- Новый тип атрибута `password`; `verdin import strapi` теперь импортирует поля паролей
  Strapi.

### 0.7.0 → 0.7.1

- Среда выполнения плагинов переходит на Wasmtime 48. Существующие плагины продолжают
  работать без пересборки.
- Для сборки из исходников нужен Rust 1.95 или новее.

### 0.6 → 0.7

- **Несколько экземпляров**: каждый экземпляр перечитывает настройки, изменённые другими,
  каждые `[server].sync_interval_secs` (10 с). Если вы запускаете больше одного, задайте
  `[plugins].run_jobs = false` на всех, кроме одного.
- Контент, который плагины записывают через хост, теперь проходит проверки платформы перед
  записью, например этапы процессов проверки. Собственные хуки «до записи» плагинов для таких
  записей по-прежнему пропускаются, чтобы плагин не мог запустить сам себя.

### 0.5 → 0.6

- **Журналы аудита** по умолчанию включены и хранят записи `[audit].retention_days` (90).
  Если они вам не нужны, выключите функцию в **Настройки → Функции**.

### 0.4 → 0.5

- Ничего менять не нужно. Плагины загружаются из `[plugins].path` (`plugins/`) и остаются
  выключенными, пока их не включат.

### 0.3 → 0.4

- **`auth`, `users` и `connect` — зарезервированные имена маршрутов**, наряду с `upload` и
  `uploads`: перед обновлением переименуйте типы содержимого, имя API которых совпадает с
  одним из них.

### 0.2 → 0.3

- Имена атрибутов следуют правилу Strapi (буква, затем буквы, цифры и подчёркивания), а не
  только camelCase. Два имени, соответствующие одной колонке, отклоняются.
- Параметры `regex` принимают шаблоны в стиле JavaScript.

### 0.1 → 0.2

- Ограничения размера тела и тайм-ауты применяются для каждого роутера API; у загрузок свои
  ограничения (`[upload].max_file_size`).
- Встроенные роли существующих установок один раз получают новые разрешения.

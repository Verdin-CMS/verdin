Пройдитесь по этому списку, прежде чем выпускать проект Verdin к реальным пользователям.
Каждый пункт ссылается на страницу с объяснением. Страницы платформ
([Docker](/ru/deploy/docker/), [Fly.io](/ru/deploy/fly/), [Render](/ru/deploy/render/),
[Railway](/ru/deploy/railway/), [Kubernetes](/ru/deploy/kubernetes/)) по возможности
применяют эти настройки за вас.

## Запускайте продакшен-сервер

- [ ] **Используйте `verdin start`, а не `verdin dev`.** `dev` позволяет конструктору типов
      содержимого переписывать файлы схемы, применяет миграции при каждом изменении и
      ослабляет правила для cookie и вебхуков ради локальной работы. Меняйте схему при
      разработке, коммитьте файлы и разворачивайте их.
- [ ] **Применяйте миграции при деплое.** `verdin start` не запускается, пока база данных
      отстаёт от схемы. `verdin start --migrate` сначала применяет ожидающие *безопасные*
      шаги (это команда образа Docker по умолчанию). Рискованные и разрушительные шаги
      (изменения типов, новые ограничения уникальности, удалённые колонки) требуют
      `verdin migrate apply --allow risky|destructive`, который вы запускаете один раз сами.
      См. [Миграции схемы](/ru/concepts/schema-migrations/).
- [ ] **Поставляйте схему вместе с сервером.** Смонтируйте каталог `schema/` только для
      чтения или вшейте его в образ, чтобы работало именно то, что вы закоммитили.

## Секреты

- [ ] **Сгенерируйте два обязательных секрета один раз** с помощью `verdin secrets` и
      храните их в хранилище секретов своей платформы: `VERDIN_ADMIN_JWT_SECRET`
      подписывает токены сессий, а `VERDIN_TOKEN_PEPPER` служит ключом для хешей API-токенов
      и других хранимых секретов. `verdin start` завершается с ошибкой, если любой из них
      отсутствует или короче 32 байт. Секреты читаются только из окружения, никогда из
      `verdin.toml`.
- [ ] **Не меняйте их.** Смена `VERDIN_TOKEN_PEPPER` ломает все API-токены, а также коды из
      приложений-аутентификаторов и резервные коды администраторов. Смена
      `VERDIN_ADMIN_JWT_SECRET` аннулирует короткоживущие токены доступа администраторов и
      конечных пользователей, открытые ссылки предпросмотра и незавершённые входы через
      OAuth (админ-панель и клиенты с refresh-токенами обновляют токены сами). Всем
      экземплярам проекта нужны одинаковые значения.
- [ ] Остальные используемые секреты тоже держите в окружении: `VERDIN_EMAIL_SMTP_PASSWORD`
      или `VERDIN_EMAIL_API_KEY`, `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`,
      `VERDIN_METRICS_TOKEN`, `VERDIN_SSO_<ID>_SECRET`, `VERDIN_IMAGE_SECRET`. Полный
      список — в [справочнике по конфигурации](/ru/reference/configuration/).

## База данных

- [ ] **Выберите СУБД.** PostgreSQL (14 или новее) — обычный выбор, и именно его стоит брать,
      если вы будете запускать [несколько экземпляров](/ru/deploy/scaling/). MySQL 8.4+ и
      MariaDB 10.11+ работают так же. SQLite подходит для одного экземпляра с постоянным
      диском.
- [ ] **Задайте `VERDIN_DATABASE_URL`**: `postgres://…`, `mysql://…` (MySQL и MariaDB) или
      `sqlite:///data/verdin.db`. Для серверов PostgreSQL, которым нужен TLS, добавьте
      `?sslmode=require`.
- [ ] **Подберите размер пула.** Каждый экземпляр открывает до `[database].pool_max`
      соединений (10). Держите `instances × pool_max` ниже лимита соединений сервера.

## URL, прокси и cookie

- [ ] **Работайте через HTTPS.** Verdin говорит на обычном HTTP; терминируйте TLS на
      обратном прокси, балансировщике нагрузки или на edge вашей платформы.
- [ ] **Задайте `[server].public_url`** (`VERDIN_SERVER__PUBLIC_URL`) — адрес, который
      используют браузеры, например `https://cms.example.com`. От него зависят ссылки в
      письмах, callback SSO, ежедневная сводка и ключи доступа; ключи доступа привязаны к
      его хосту.
- [ ] **Задайте `[server].trusted_proxies`** — адреса ваших обратных прокси (IP или
      диапазоны CIDR). Только тогда Verdin читает адрес клиента из `X-Forwarded-For`; без
      этого все клиенты за прокси делят один адрес для ограничений частоты и журналов
      аудита.
- [ ] **Не выключайте secure-cookie.** В `verdin start` refresh-cookie админки по умолчанию
      `Secure`. Не задавайте `[admin].secure_cookies`; значение `false` в продакшене даёт
      предупреждение при запуске.

## API

- [ ] **Разрешайте публике только необходимое.** Content API закрыт, пока вы не выдадите
      публичные разрешения (**Настройки → Публичный доступ**) или не создадите API-токены.
      См. [Разрешения](/ru/concepts/permissions/).
- [ ] **Задайте `[api].cors_origins`**, если content API или GraphQL вызывает браузер с
      другого origin, например `["https://www.example.com"]`. Без этого из браузера их могут
      вызывать только страницы того же origin. Admin API никогда не отвечает на
      кросс-доменные запросы.
- [ ] **Подумайте об ограничениях частоты** для анонимного трафика: `[api].public_rate_limit`
      и `[api].token_rate_limit` (запросов в минуту; `0`, значение по умолчанию, — без
      ограничений).

## Медиа

- [ ] **Храните загрузки там, где они переживут повторный деплой.** Локальный провайдер по
      умолчанию пишет на диск: дайте ему постоянный том или используйте провайдер S3 (AWS
      S3, Cloudflare R2, Backblaze B2, MinIO, Tigris…). На платформах с эфемерными дисками и
      при нескольких экземплярах используйте S3. См. [Медиа](/ru/concepts/media/).

## Почта

- [ ] **Настройте настоящего провайдера.** Значение по умолчанию `[email].provider = "log"`
      пишет письма в лог, и `verdin start` об этом предупреждает. Приглашениям, сбросу
      пароля, подтверждениям конечных пользователей, упоминаниям в комментариях и сводке
      нужны `smtp`, `resend` или `postmark` и `[email].from` с адресом, который принимает ваш
      провайдер.

## Резервные копии и мониторинг

- [ ] **Делайте резервные копии базы данных и хранилища медиа** по расписанию и пробуйте
      восстановление. См. [Резервные копии](/ru/deploy/backups/).
- [ ] **Направьте проверки работоспособности на `/_ready`**, а проверки живости — на
      `/_health`.
- [ ] **Пишите логи в JSON** (`[log].format = "json"`, значение по умолчанию в образе Docker)
      и собирайте стандартный поток ошибок.
- [ ] **Собирайте `/_metrics`**, если используете Prometheus, с `VERDIN_METRICS_TOKEN`. См.
      [Мониторинг](/ru/deploy/monitoring/).

## Перед запуском

- [ ] Зарегистрируйте первого администратора сами сразу после первого запуска: пока нет ни
      одного администратора, любой, кто откроет `/admin/`, может зарегистрироваться как
      Super Admin. Его также можно создать из командной строки:
      `verdin admin create --email …`.
- [ ] Изучите [модель безопасности](/ru/deploy/security/) и включите
      [двухфакторную аутентификацию](/ru/guides/auth/two-factor/) для Super Admin.

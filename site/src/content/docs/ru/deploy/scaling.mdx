Verdin хранит своё состояние в базе данных, поэтому ради доступности или нагрузки можно
запускать несколько экземпляров одного проекта за балансировщиком нагрузки. На этой странице
перечислено, что экземпляры делят между собой, что каждый хранит сам и какие настройки важны.

## Чек-лист

- **Общая база данных.** PostgreSQL, MySQL или MariaDB. SQLite — это файл на одной машине, и
  с несколькими экземплярами он не работает.
- **Одинаковая конфигурация везде.** Все экземпляры используют одни и те же `verdin.toml`,
  файлы схемы и секреты (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). При разных секретах сессии и API-токены, созданные на одном
  экземпляре, отклоняются остальными.
- **Продакшен-режим.** Запускайте `verdin start`, а не `verdin dev`. Меняйте схему при
  разработке, коммитьте её и выполняйте миграцию один раз на деплой.
- **Общее хранилище медиа.** Используйте провайдер S3 (`[upload] provider = { name = "s3", … }`)
  или для локального провайдера смонтируйте один и тот же том на всех экземплярах.
- **Проверки работоспособности.** Направьте балансировщик на `GET /_ready`, который отвечает
  `503`, когда база данных недоступна. `GET /_health` сообщает только, что процесс запущен;
  используйте его для проверки живости.
- **Общая шина событий.** Задайте `[cluster].bus = "database"` на каждом экземпляре, чтобы
  события реального времени, присутствие, сброс кеша и обновления поиска доходили до всех
  (см. [Общая шина событий](#общая-шина-событий)).
- **Задания плагинов на одном экземпляре.** Задайте `[plugins].run_jobs = false` на всех
  экземплярах, кроме одного; иначе каждый экземпляр выполняет запланированные задания.
- **Метрики для каждого экземпляра.** С `[metrics].enabled = true` каждый экземпляр отдаёт
  собственный `/_metrics`; собирайте метрики с каждого.

## Миграции при нескольких экземплярах

`verdin start --migrate` можно безопасно запускать на всех экземплярах одновременно. Каждый
запуск миграции держит блокировку в базе данных (advisory lock в PostgreSQL, `GET_LOCK` в
MySQL и MariaDB, с ожиданием до 60 секунд), поэтому первый экземпляр применяет шаги, а
остальные находят базу данных уже обновлённой.

Во время постепенного (rolling) деплоя экземпляры старой версии какое-то время продолжают
работать с уже мигрированной базой данных. Безопасные шаги создают таблицы, добавляют колонки
с NULL или значением по умолчанию и индексы, расширяют текстовые колонки или добавляют
значения enum — старая версия этого не замечает. Рискованные и разрушительные шаги
(`verdin migrate apply --allow risky|destructive`) применяйте отдельным деплоем, когда ни
одному экземпляру со старой схемой эти данные уже не нужны. См.
[Миграции схемы](/ru/concepts/schema-migrations/).

## Что общее

| Что | Как |
| --- | --- |
| Сессии администраторов, API-токены, разрешения | В базе данных; липкие сессии не нужны. |
| Переключатели функций и плагинов, локали, процессы проверки | В базе данных. Каждый экземпляр перечитывает их каждые `[server].sync_interval_secs` (10 с), поэтому изменение на одном экземпляре доходит до остальных в пределах этой задержки. |
| Доставки вебхуков | Очередь в базе данных. Экземпляр забирает доставку перед отправкой, поэтому каждая уходит один раз. |
| Запланированные релизы | Забираются через базу данных перед выполнением, поэтому каждый выполняется один раз. |
| Ежедневная сводка | Запуск каждого дня забирается через базу данных, поэтому администраторы получают одно письмо. |
| Челленджи ключей доступа | Использованные челленджи записываются в базу данных, поэтому на каждый отвечают один раз на всех экземплярах. |
| Очистка журнала аудита | Выполняется на каждом экземпляре; повторное удаление старых строк безвредно. |
| Хранилище «ключ — значение» плагинов | В базе данных. |
| События реального времени, присутствие и мягкие блокировки | С [шиной событий](#общая-шина-событий): клиент, подключённый к любому экземпляру, получает события всех экземпляров и видит каждого администратора в записи. |
| Кеш анонимных ответов | С шиной событий запись на любом экземпляре очищает кеш каждого экземпляра. |
| Поисковый индекс | С шиной событий каждый экземпляр перечитывает и индексирует записи, которые меняют остальные. |
| Преобразованные изображения | С шиной событий изменённый или удалённый файл исчезает из кеша преобразований каждого экземпляра. |

## Что остаётся у каждого экземпляра

- **Ограничения частоты** считаются каждым экземпляром отдельно. При `n` экземплярах клиент
  может сделать до `n` × `[api].public_rate_limit` запросов в минуту. Если нужен глобальный
  лимит, задайте его на балансировщике.
- **Без шины событий** (`[cluster].bus = "none"`, по умолчанию) события реального времени и
  присутствие относятся к экземпляру, к которому подключён клиент (для потоков событий
  используйте липкие сессии), запись очищает кеш ответов только своего экземпляра (держите
  `[api].cache_ttl_secs` в несколько секунд или `0`), а поисковый индекс отслеживает только
  записи своего экземпляра.
- **Поисковый индекс** (`[search]`) хранится на диске каждого экземпляра. С шиной событий
  экземпляры индексируют изменения друг друга по мере их появления; экземпляр, который
  запускается с пустым каталогом индекса, строит его из базы данных. Изменения, сделанные,
  пока экземпляр был выключен, попадают в его индекс при перестроении индекса: удалите
  каталог перед запуском или перестройте индекс после деплоя.
- **Преобразования изображений** (`[upload.transforms]`) кешируются на каждом экземпляре в
  `cache_dir`. Чтобы делить их, поставьте CDN перед `/uploads`.
- **Запланированные задания плагинов**: см. `run_jobs` выше.

## Общая шина событий

Часть происходящего живёт в памяти: потоки реального времени, кто какую запись редактирует,
кеш анонимных ответов, поисковый индекс. Шина событий передаёт это с экземпляра, где оно
произошло, остальным.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Или `VERDIN_CLUSTER__BUS=database` на каждом экземпляре. Шина использует базу данных
проекта, поэтому другие сервисы не нужны:

- **PostgreSQL**: экземпляр записывает каждое событие в таблицу `vd_cluster_events` и будит
  остальных через `NOTIFY`. Каждый экземпляр держит одно из соединений своего пула для
  `LISTEN`. Уведомление содержит только имя отправителя, поэтому события любого размера
  укладываются в лимит PostgreSQL в 8000 байт. Если соединение обрывается, экземпляр
  переподключается и читает таблицу, чтобы наверстать пропущенное. Он также читает таблицу
  каждые 30 секунд на случай потерянного уведомления.
- **MySQL, MariaDB и SQLite**: каждый экземпляр читает новые строки `vd_cluster_events`
  каждые `poll_interval_ms` (по умолчанию 1000). Запрос использует первичный ключ, поэтому
  чтение пустой таблицы стоит мало. Уменьшите интервал для более быстрых обновлений;
  изменение одного экземпляра доходит до остальных в пределах интервала.

Что передаётся: записи контента (в потоки реального времени, кеш ответов и поисковый индекс,
который заново читает изменённую запись), изменения медиа (потоки, кеш, кеш преобразований),
сигналы присутствия, а также уведомления о комментариях и задачах для админ-панели. Каждый
экземпляр игнорирует собственные события. Вебхуки, очистка CDN, история, журналы аудита и
хуки плагинов не передаются: экземпляр, сделавший изменение, выполняет их один раз.

Строки удаляются через 10 минут. Новый экземпляр начинает со следующего события, а не с
прежних. Экземпляр, который не успевает или теряет соединение с базой данных, отбрасывает
события, а не задерживает запись. Метрика `verdin_cluster_events_total` считает отправленные,
полученные и отброшенные события (см.
[Мониторинг](/ru/deploy/monitoring/#метрики-prometheus)).

Каждый экземпляр называет себя в шине случайным id при каждом запуске или значением
`[cluster].instance_id`, если вы его задали (например, имя пода). Id только отличает
экземпляры друг от друга; больше ничего от него не зависит.

С одним экземпляром оставьте `bus` равным `none`: события остаются в памяти и ничего не
записывается.

Бэкенды Redis и NATS пока недоступны. Шина на базе данных подходит для всех поддерживаемых
баз данных и не требует ничего дополнительного.

## Настройки

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Задавайте `run_jobs` для каждого экземпляра через `VERDIN_PLUGINS__RUN_JOBS=false`.

## Соединения с базой данных

Каждый экземпляр открывает до `[database].pool_max` соединений (по умолчанию 10). Держите
`instances × pool_max` ниже лимита сервера, с запасом для миграций, резервного копирования и
обслуживания. Лимит PostgreSQL по умолчанию — 100 соединений. В PostgreSQL шина событий держит одно из
соединений каждого экземпляра для `LISTEN`.

Плагины добавляют Verdin новое поведение без изменения и пересборки сервера. Плагин — это
модуль WebAssembly с манифестом, который кладут в каталог `plugins/` проекта. На этой странице
описано, что умеют плагины и как их устанавливать; чтобы написать свой, пройдите
[руководство по созданию плагина](/ru/extending/plugin-tutorial/), а подробности смотрите в
[справочнике по плагинам](/ru/extending/plugin-reference/).

## Что умеет плагин

| Точка расширения | Для чего |
| --- | --- |
| **Хуки на запись** | Перед созданием, обновлением, публикацией, снятием с публикации, удалением записи или отменой её черновика — изменить данные или отклонить запись с сообщением. После записи — отреагировать на неё (записать в журнал, уведомить, синхронизировать). |
| **Маршруты** | Обслуживать HTTP-эндпоинты под `/api/plugins/<name>/…`: приёмник вебхуков, вычисляемая лента, прокси к другому сервису. |
| **Запланированные задания** | Запускать функцию по расписанию cron (UTC). |
| **Функция запуска** | Запускать функцию, когда плагин стартует, включается или меняются его настройки: наполнение данными, настройка публичной роли (`bootstrap` в Strapi). |
| **Поля GraphQL** | Добавлять поля `name(args: JSON): JSON` в `Query` или `Mutation`. |
| **Виджеты главной панели** | Добавлять типы виджетов на главную панель админки в виде Web Components. |
| **Пользовательские поля** | Давать атрибутам собственный редактор в админке (выбор цвета, карта) в виде Web Components; значение хранится как обычный тип атрибута. |
| **Настройки** | Описывать форму настроек, которую администраторы заполняют в **Настройки → Плагины**. |

Плагин читает и записывает контент через тот же Document Service, что админка и API, поэтому
к его записям применяются вебхуки, история, этапы проверки и валидация.

<Aside type="note">
Плагины Verdin — это не плагины Strapi. Плагины Strapi — это пакеты Node.js с полным доступом
к серверу; Verdin не выполняет JavaScript на сервере. Пользовательские поля, объявленные в
схемах Strapi (атрибуты `customField`), загружаются как есть, а плагин Verdin может
предоставить для них редактор.
</Aside>

## Песочница

Плагины работают в песочнице WebAssembly ([Extism](https://extism.org) на Wasmtime). У модуля
нет собственных файлов, сокетов и подключения к базе данных. Всё, что он делает за пределами
своей памяти, идёт через несколько функций хоста, и сервер проверяет каждый вызов по
**возможностям**, объявленным в манифесте:

| Возможность | Разрешает |
| --- | --- |
| `read` | Чтение записей перечисленных типов содержимого (или `*`). |
| `write` | Создание, обновление, публикацию, снятие с публикации и удаление записей перечисленных типов (и их чтение). |
| `http` | HTTP-запросы к перечисленным хостам (`api.example.com`, `*.example.com`). |
| `kv` | Собственное хранилище «ключ — значение» в базе данных Verdin. |
| `public_permissions` | Чтение и замена разрешений публичной роли в content API. |

У каждого вызова также есть ограничения: по времени (по умолчанию 5 секунд) и по памяти (по
умолчанию 64 МБ), которые задаются в манифесте. Модуль, который упал (trap) или не уложился во
время, проваливает только этот вызов; при следующем вызове Verdin пересоздаёт его.

Чего песочница за вас не решает:

- **Маршруты публичные.** Запросы к `/api/plugins/<name>/…` не проверяются по **Публичному
  доступу** или разрешениям API-токенов. Плагин получает сведения о том, кто вызывает (кто
  угодно, API-токен или конечный пользователь), и должен проверять это сам.
- **Хуки видят все записи в свои типы** независимо от возможности `read` плагина.
- **Упавший хук «до» не блокирует запись.** Если модуль падает или превышает время, ошибка
  записывается в лог, а запись продолжается. Остановить её может только явный отказ.

## Установка плагина

<Steps>

1. Положите плагин в отдельный каталог внутри `plugins/` рядом с `verdin.toml`. В нём
   находятся манифест, модуль и, при необходимости, файлы для админ-панели:

   <FileTree>
   - verdin.toml
   - plugins/
     - reading-time/
       - plugin.toml
       - plugin.wasm
       - admin/ необязательно: Web Components для админ-панели
         - index.js
   - schema/
   </FileTree>

2. Перезапустите Verdin. При запуске он загружает каждый `plugins/*/plugin.toml` и пишет
   `plugin found` для каждого. Плагин, который не удалось загрузить (некорректный манифест,
   нет модуля, повторяющееся имя), показывается в **Настройки → Плагины** с причиной.

3. В админ-панели откройте **Настройки → Плагины**. Проверьте, что запрашивает плагин, в
   разделах **Доступ**, **Хуки**, **Маршруты** и **Задания**, затем включите его.

4. Если у плагина есть настройки, откройте **Настройки** на его карточке, заполните их и
   сохраните.

</Steps>

Установленные плагины изначально выключены. Включение плагина и изменение его настроек
вступают в силу сразу на всех экземплярах (другие экземпляры подхватывают изменение в
пределах `[server].sync_interval_secs`). Изменения `plugin.toml` или модуля требуют
перезапуска.

Для управления плагинами нужно разрешение `plugins.manage` (**Управление плагинами**). См.
[справочник по разрешениям](/ru/reference/permissions/).

## Настройка `[plugins]`

```toml title="verdin.toml"
[plugins]
path = "plugins"   # directory of plugins, relative to verdin.toml
run_jobs = true    # run scheduled jobs on this instance
```

При нескольких экземплярах задайте `run_jobs = false` на всех, кроме одного, чтобы каждое
задание выполнялось один раз. См. [справочник по конфигурации](/ru/reference/configuration/).

## Эксплуатация

- **Один вызов за раз.** У каждого плагина один экземпляр, и он обрабатывает один вызов за
  раз, поэтому медленный маршрут задерживает хуки этого плагина. Делайте функции короткими.
- **Журнал.** То, что пишет плагин, попадает в лог сервера и в **Настройки → Плагины →
  Журнал** (последние 200 строк, хранятся в памяти).
- **Деплой.** Поставляйте плагины вместе с проектом (в образе или на томе), как схему.
  Переключатели и настройки хранятся в базе данных.

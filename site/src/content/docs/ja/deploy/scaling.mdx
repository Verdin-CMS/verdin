Verdin は状態をデータベースに保持するので、可用性や負荷分散のために、同じプロジェクトのインスタンスをロードバランサーの背後で複数実行できます。このページでは、インスタンスが共有するもの、各インスタンスが独自に持つもの、そして重要な設定を説明します。

## チェックリスト

- **共有のデータベース。** PostgreSQL、MySQL、MariaDB のいずれか。SQLite は 1 台のマシン上のファイルなので、複数のインスタンスでは使えません。
- **どこでも同じ設定。** すべてのインスタンスが、同じ `verdin.toml`、スキーマファイル、シークレット（`VERDIN_ADMIN_JWT_SECRET`、`VERDIN_TOKEN_PEPPER`、`VERDIN_SSO_<ID>_SECRET` など）を使います。シークレットが異なると、あるインスタンスで作られたセッションや API トークンが、他のインスタンスで拒否されます。
- **本番モード。** `verdin dev` ではなく `verdin start` を実行します。スキーマは開発環境で変更してコミットし、デプロイごとに一度マイグレーションします。
- **共有のメディアストレージ。** S3 プロバイダー（`[upload] provider = { name = "s3", … }`）を使うか、ローカルプロバイダーならすべてのインスタンスに同じボリュームをマウントします。
- **ヘルスチェック。** ロードバランサーは `GET /_ready` に向けてください。データベースに到達できないと `503` を返します。`GET /_health` はプロセスが動いていることしか示さないので、生存確認に使います。
- **共有イベントバス。** すべてのインスタンスで `[cluster].bus = "database"` を設定すると、リアルタイムのイベント、プレゼンス、キャッシュの無効化、検索の更新がすべてのインスタンスに届きます（[共有イベントバス](#共有イベントバス)を参照）。
- **プラグインのジョブは 1 つのインスタンスで。** 1 つを除くすべてのインスタンスで `[plugins].run_jobs = false` を設定します。そうしないと、各インスタンスがスケジュールされたジョブを実行します。
- **メトリクスはインスタンスごと。** `[metrics].enabled = true` の場合、各インスタンスが自分の `/_metrics` を提供するので、それぞれをスクレイプしてください。

## 複数のインスタンスでのマイグレーション

`verdin start --migrate` は、すべてのインスタンスで同時に実行しても安全です。各マイグレーションの実行はデータベースでロック（PostgreSQL ではアドバイザリーロック、MySQL と MariaDB では `GET_LOCK`、最大 60 秒待機）を保持するので、最初のインスタンスがステップを適用し、他のインスタンスはデータベースが最新になっていることを確認します。

ローリングデプロイの間、古いバージョンのインスタンスは、マイグレーション済みのデータベースに対してしばらく動き続けます。安全なステップは、テーブルの作成、NULL 許容またはデフォルト値付きのカラムやインデックスの追加、テキストカラムの拡張、enum の値の追加を行うもので、古いバージョンはそれに気づきません。risky や destructive なステップ（`verdin migrate apply --allow risky|destructive`）は、古いスキーマのインスタンスがそのデータを必要としなくなってから、別のデプロイで適用してください。[スキーマのマイグレーション](/ja/concepts/schema-migrations/)を参照してください。

## 共有されるもの

| 対象 | 方法 |
| --- | --- |
| 管理者のセッション、API トークン、権限 | データベース内。スティッキーセッションは不要です。 |
| 機能の切り替え、プラグインの切り替え、ロケール、レビューワークフロー | データベース内。各インスタンスは `[server].sync_interval_secs`（10 秒）ごとに読み直すので、あるインスタンスでの変更はその時間内に他のインスタンスに届きます。 |
| Webhook の配信 | データベース内のキュー。インスタンスは送信前に配信を担当として確保するので、各配信は 1 回だけ送られます。 |
| 予約されたリリース | 実行前にデータベースで担当が確保されるので、各リリースは 1 回だけ実行されます。 |
| 日次ダイジェスト | 毎日の実行がデータベースで確保されるので、管理者に届くメールは 1 通です。 |
| パスキーのチャレンジ | 使用済みのチャレンジはデータベースに記録されるので、インスタンスをまたいでも各チャレンジへの応答は 1 回だけです。 |
| 監査ログの削除 | すべてのインスタンスで実行されます。古い行を 2 回削除しても害はありません。 |
| プラグインのキーバリューストア | データベース内。 |
| リアルタイムのイベント、プレゼンス、ソフトロック | [イベントバス](#共有イベントバス)を使うと、どのインスタンスに接続したクライアントにも全インスタンスのイベントが届き、エントリーを開いているすべての管理者が見えます。 |
| 匿名レスポンスのキャッシュ | イベントバスを使うと、どのインスタンスでの書き込みも、全インスタンスのキャッシュを空にします。 |
| 検索インデックス | イベントバスを使うと、各インスタンスが、他のインスタンスが変更したエントリーを読み直してインデックスに反映します。 |
| 変換された画像 | イベントバスを使うと、変更または削除されたファイルは、全インスタンスの変換キャッシュから消えます。 |

## 各インスタンスに残るもの

- **レート制限**は各インスタンスで数えられます。インスタンスが `n` 個あると、クライアントは 1 分あたり最大で `[api].public_rate_limit` の `n` 倍のリクエストを送れます。全体の制限が必要なら、ロードバランサーで強制してください。
- **イベントバスがない場合**（`[cluster].bus = "none"`、デフォルト）、リアルタイムのイベントとプレゼンスは、クライアントが接続しているインスタンスのものです（イベントストリームにはスティッキーセッションを使ってください）。書き込みは自分のインスタンスのレスポンスキャッシュだけを空にします（`[api].cache_ttl_secs` は数秒か `0` にしてください）。検索インデックスは、そのインスタンスが行った書き込みだけを追いかけます。
- **検索インデックス**（`[search]`）は各インスタンスのディスクにあります。イベントバスを使うと、インスタンスは互いの変更をその場でインデックスに反映します。空のインデックスディレクトリで起動したインスタンスは、データベースからインデックスを作ります。インスタンスが停止している間の変更は、インデックスを再構築したときにそのインデックスに届きます。起動前にディレクトリを削除するか、デプロイ後に再構築してください。
- **画像変換**（`[upload.transforms]`）は、インスタンスごとに `cache_dir` 配下にキャッシュされます。共有するには、`/uploads` の前に CDN を置いてください。
- **スケジュールされたプラグインのジョブ**: 上の `run_jobs` を参照してください。

## 共有イベントバス

一部の処理はメモリ上で行われます。リアルタイムのストリーム、どの管理者がどのエントリーを編集しているか、匿名レスポンスのキャッシュ、検索インデックスです。イベントバスは、それらが起きたインスタンスから他のインスタンスへ運びます。

```toml title="verdin.toml"
[cluster]
bus = "database"
```

または、すべてのインスタンスで `VERDIN_CLUSTER__BUS=database` を設定します。バスはプロジェクトのデータベースを使うので、他のサービスは不要です。

- **PostgreSQL**: インスタンスは各イベントを `vd_cluster_events` テーブルに書き込み、`NOTIFY` で他のインスタンスを起こします。各インスタンスは、プールの接続を 1 つ `LISTEN` のために保持します。通知は送信元の名前だけを伝えるので、どんなサイズのイベントでも PostgreSQL の 8000 バイトの上限に収まります。接続が切れた場合、インスタンスは再接続し、テーブルを読んで追いつきます。通知が失われた場合に備えて、30 秒ごとにテーブルも読みます。
- **MySQL、MariaDB、SQLite**: 各インスタンスは `poll_interval_ms`（デフォルトは 1000）ごとに `vd_cluster_events` の新しい行を読みます。クエリは主キーを使うので、空のテーブルを読むコストはわずかです。更新を速くしたい場合は間隔を短くしてください。あるインスタンスでの変更は、この間隔以内に他のインスタンスに届きます。

運ばれるもの: コンテンツの書き込み（リアルタイムのストリーム、レスポンスキャッシュ、検索インデックスへ。検索インデックスは変更されたエントリーを読み直します）、メディアの変更（ストリーム、キャッシュ、変換キャッシュ）、プレゼンスのハートビート、管理者向けのコメントとタスクの通知です。各インスタンスは自分のイベントを無視します。Webhook、CDN のパージ、履歴、監査ログ、プラグインのフックは運ばれません。変更を行ったインスタンスが 1 回だけ実行します。

行は 10 分後に削除されます。新しいインスタンスは、次のイベントから始まり、それ以前のイベントは受け取りません。追いつけないインスタンスや、データベースとの接続を失ったインスタンスは、書き込みを保留せずにイベントを破棄します。`verdin_cluster_events_total` メトリクスは、送信、受信、破棄されたイベントを数えます（[監視](/ja/deploy/monitoring/#prometheus-メトリクス)を参照）。

各インスタンスは、起動のたびにランダムな ID で、または設定した場合は `[cluster].instance_id`（たとえば Pod 名）で、バス上の名前を決めます。ID はインスタンスを区別するためだけのもので、他には何も依存しません。

インスタンスが 1 つの場合は、`bus` を `none` のままにしてください。イベントはメモリ上にとどまり、何も書き込まれません。

Redis と NATS のバックエンドはまだありません。データベースのバスは、他に何も動かさずに、サポートされているすべてのデータベースに対応します。

## 設定

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

`run_jobs` は、インスタンスごとに `VERDIN_PLUGINS__RUN_JOBS=false` で設定します。

## データベースの接続

各インスタンスは最大 `[database].pool_max` 個（デフォルトは 10）の接続を開きます。マイグレーション、バックアップ、保守の余裕を残して、`インスタンス数 × pool_max` をサーバーの上限より小さく保ってください。PostgreSQL のデフォルトの上限は 100 接続です。PostgreSQL では、イベントバスが各インスタンスの接続を 1 つ `LISTEN` のために保持します。

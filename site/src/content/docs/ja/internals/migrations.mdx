このページでは、`verdin-migrate` がデータベースをスキーマに合わせる方法を説明します。差分の計算、各ステップの評価、そして失敗しても状態が分からなくならないようなプランの適用です。日々の作業の流れ（`verdin migrate plan`、`--allow`、名前の変更）については、先に[スキーマのマイグレーション](/ja/concepts/schema-migrations/)を読んでください。コマンドのフラグは [CLI のリファレンス](/ja/reference/cli/)にあります。

## 流れ

<Diagram
  caption="スキーマファイルから適用済みの DDL まで"

  Snapshot[("vd_schema_snapshots")] --> Current["DbModel<br/>現在"]
  Current --> Diff{"diff"}
  Desired --> Diff

  Plan -->|適用| Db[("データベース")]`}
/>

1. `verdin-schema` がファイルを解析・検証して `Schema` にします。
2. `derive_model`（`derive.rs`）がそれを `DbModel` に変えます。リンクテーブルと[プラットフォームのテーブル](/ja/internals/storage/#プラットフォームのテーブル)を含め、スキーマが必要とするすべてのテーブル、カラム、インデックス、外部キーです。
3. 最後に適用したモデルを `vd_schema_snapshots` から読みます。
4. `diff`（`diff.rs`）が 2 つのモデルを比較し、`Change` のリストと名前変更のヒントを返します。
5. `build_plan`（`plan.rs`）が各変更を接続先の flavor 向けの SQL にし、評価し、必要な場合は事前チェックを付けます。
6. `apply`（`apply.rs`）がプランを実行し、目標のモデルを新しいスナップショットとして保存します。

**スナップショットはスキーマではなく物理モデルを保存します。** 後の Verdin のバージョンが同じスキーマからより多くのテーブル（新機能のためのリンクテーブル、新しいプラットフォームのテーブル）を導き出すと、スキーマを変えなくても差分がそれらを作成します。

**差分は稼働中のデータベースではなくスナップショットに対して計算されます。** これにより決定的になり、各エンジンが自身の構造を報告する方法の違いを避けられます。Verdin はデータベースを調べないので、テーブルへの手動の変更（ドリフト）は検出されません。

ある方言で同じ DDL になる変更からは、ステップが作られません。たとえば `string` → `text` は PostgreSQL と MySQL では型の変更ですが、SQLite ではどちらも `text` なので、SQLite にはステップがありません。

## 変更の分類

すべてのステップにはリスクレベル（`diff.rs` の `Risk`）があります。`apply` は許可したレベルまでのステップだけを実行し、それを超えるステップがあれば、何も実行する前にプラン全体を拒否します。

| リスク | 変更 |
|---|---|
| **Safe**（安全） | テーブルの作成。NULL 許容またはデフォルト値付きのカラムの追加。カラムの緩和（NULL 許容にする。型とデフォルトは同じ）。一意でないインデックスの作成、または新しいテーブルへの一意インデックスの作成。インデックスの削除。テーブルやカラムの名前変更 |
| **Risky**（要注意） | デフォルト値のない `NOT NULL` のカラムの追加。それ以外のカラムの型、NULL 許容、デフォルトの変更。既存のテーブルへの一意インデックスの追加。カラムを削除しない SQLite のテーブルの再構築 |
| **Destructive**（破壊的） | カラムの削除。テーブルの削除。カラムを削除する SQLite のテーブルの再構築 |

すべての属性カラムは NULL を許容する（[ストレージ](/ja/internals/storage/#システムのカラム)を参照）ので、必須のものを含め、属性の追加は常に安全です。`enumeration` の値はカラムではなくアプリケーションが確認するので、値を追加・削除しても DDL はまったく変わりません。

**事前チェック**は、プランの最初のステートメントの前に実行されるので、成功しえない risky なステップは、データベースに触れていない時点で実行を止めます。

| ステップ | 事前チェック |
|---|---|
| 既存のテーブルへの一意インデックス | インデックス対象のカラムに、NULL でない値の重複がない |
| デフォルト値のない `NOT NULL` のカラム | テーブルに行がない |
| カラムが `NOT NULL` になる | カラムに NULL がない |

**名前の変更。** 同じテーブルで、削除されたカラムと同じカラム型の追加されたカラムは、名前の変更として*提案*されます。`verdin migrate plan` は `--rename-column articles.title=headline` のようなヒントを出し、コンテンツタイプビルダーはそれを受け入れるか尋ねます。黙って推測されることはなく、フラグがなければプランは古いカラムを削除し、新しいカラムを追加します。削除されたテーブルと同じカラムを持つ作成されたテーブルにも、同じように `--rename-table old=new` のヒントが出ます。名前の変更は安全なステップで、名前を変えたテーブルはそのリンクテーブルも一緒に連れていきます。

**SQLite の再構築。** SQLite はカラムを変更できないので、テーブルにカラムの変更が 1 つでもあると、プランナーはそのテーブルのカラムとインデックスの変更をすべて 1 回の再構築に置き換えます。新しい形を一時的な名前で作成し、残るカラムをコピーし、古いテーブルを削除し、新しいテーブルの名前を変え、インデックスを作り直します。

## モード

| コマンド | 動作 |
|---|---|
| `verdin start` | 保留中のステップがあると、`verdin migrate plan` を案内するメッセージを出して起動を止めます。スキーマファイルは読み取り専用です。 |
| `verdin start --migrate` | 保留中の**安全な**ステップをサーバーの起動前に適用します。それより危険なものがあれば起動を止めます。 |
| `verdin dev` | 安全なステップを起動時に適用します。`schema/` のファイルウォッチャーが変更のたびに再読み込みします。安全なマイグレーションは適用されてアプリがその場で置き換わり、より危険な変更はログに記録され、実行中のアプリはそのままです。 |
| コンテンツタイプビルダー（`verdin dev` のみ） | `POST /schema/plan` がステップ、そのリスク、SQL、名前変更のヒントを表示します。`POST /schema/apply` が、ユーザーが確認したリスクレベルでそれらを実行します。 |
| `verdin migrate plan` | 各ステップを、そのリスクと接続先の方言向けの正確な SQL、プランに必要な `--allow` のレベル、名前変更のヒントとともに出力します。 |
| `verdin migrate apply` | プランを実行します。プランにそのようなステップが含まれる場合は、`--allow risky` または `--allow destructive` が必要です。 |

ビルダーが変更を適用するときは、まずマイグレーションを行い、次に `schema/*.json` を書き込み、それからアプリを置き換えます。マイグレーションに失敗すると、ファイルと実行中のアプリはそのまま残ります。ビルダーの出力はファイルなので、流れは git のコミットで終わります。

## トランザクションのない DDL でも持ちこたえる実行

PostgreSQL と SQLite は DDL をトランザクション内で実行します。MySQL と MariaDB は DDL ステートメントのたびに暗黙のコミットを行うので、プランの途中で失敗すると、データベースが 2 つの状態の間に残ってしまいます。`apply` はどちらにも対処します。

**どのエンジンでも:**

1. 専用の 1 つの接続でマイグレーションのロックを取得します。PostgreSQL では `pg_advisory_lock`、MySQL と MariaDB では最大 60 秒待つ `GET_LOCK('verdin_migrate:<database>')`、SQLite では `BEGIN IMMEDIATE` が書き込みを直列化します。SQLite では、テーブルの再構築がリンクテーブルにカスケードしないよう、実行中は `foreign_keys` もオフにします。
2. スナップショットからプランを計算し直し、許可されたリスクを確認します。
3. 最初の DDL ステートメントの前に、すべての事前チェックを実行します。

**PostgreSQL と SQLite では**、プラン全体、新しいスナップショット、`completed` のジャーナルの行を 1 つのトランザクションで実行します。失敗するとすべてロールバックされます。

**MySQL と MariaDB では**、各ステップが 1 つのステートメントで、進捗をステップごとに記録します。

1. プランを、状態 `running` で `vd_migrations_journal`（プランのハッシュとそのステップ）に記録します。
2. 各ステップを実行し、そのたびに完了したステップの数を記録します。
3. ステップが失敗すると、ジャーナルはエラーを保持し、`running` のままになります。すると `verdin migrate plan` は、中断された実行、適用済みのステップの数、最後のエラーを報告します。
4. 次の `apply` はプランを計算し直します。そのハッシュがジャーナルと一致すれば、失敗したステップから**再開**します。これらのエンジンでは単一の DDL ステートメントはアトミックなので、失敗したステップをもう一度実行します。再開時は、先のステップがすでにデータベースを変えているので、事前チェックはスキップされます。
5. その間にスキーマが変わっていればハッシュが異なるので、`apply` は拒否し、プランを作ったときのスキーマに戻すよう求めます。
6. 最後のステップが成功すると、新しいスナップショットとジャーナルの `completed` の状態が、1 つのトランザクションで一緒に書き込まれます。

プランのハッシュは flavor とすべてのステートメントを対象にしているので、再開した実行は、計画されたとおりの SQL を実行します。

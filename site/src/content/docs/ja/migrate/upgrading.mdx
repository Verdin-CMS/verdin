このページでは、プロジェクトを新しい Verdin のバージョンに移す方法を説明し、マイナーバージョン間で変わったことを一覧にします。Verdin は 0.x 向けの補足付きで[セマンティックバージョニング](https://semver.org/)に従います。1.0 までは、**マイナー**リリース（0.8 → 0.9）で動作が変わることがあり、**パッチ**リリース（0.9.0 → 0.9.1）は修正と堅牢化だけです。

## アップグレードの前に

1. 今のバージョンから新しいバージョンまでの**チェンジログを読みます**。[チェンジログ](/ja/project/changelog/)にはすべての変更が並び、[下の注意事項](#アップグレードの注意事項)には対応が必要なものがまとめてあります。
2. データベースとメディアストレージを**バックアップします**（[バックアップ](/ja/deploy/backups/)を参照）。古いバージョンに戻すには、そのバックアップをリストアする必要があります。古いバージョンは、新しいバージョンが追加したテーブルやカラムを元に戻しません。
3. 注意事項に、フロントエンドや編集者が頼りにしている動作が書かれている場合は、本番環境の**コピーで試してください**。

バージョンは飛ばしてもかまいません。マイグレーションはリリースごとに再生されるのではなく、データベースと新しいバージョンが期待するものとの差分から計算されるので、0.6 → 0.9 は 1 回の実行でマイグレーションできます。間にあるすべてのバージョンの注意事項を読んでください。

## アップグレードする

<Tabs syncKey="install">
<TabItem label="Docker">

<Steps>

1. Compose ファイル、マニフェスト、`Dockerfile` のイメージのタグを変更します。たとえば `ghcr.io/verdin-cms/verdin:0.10` → `ghcr.io/verdin-cms/verdin:0.11` です。マイナーのタグ（`0.9`）はそのパッチリリースに追従します。それらの到着時期も自分で決めたい場合は、フルバージョン（`0.9.1`）に固定してください。

2. プルして再起動します。

   ```sh frame="terminal"
   docker compose pull verdin
   docker compose up -d verdin
   docker compose logs -f verdin
   ```

   イメージのデフォルトのコマンド `start --migrate` が、提供を始める前に新しいバージョンのマイグレーションを適用します。ログで `applied migrations` と `verdin listening` を確認してください。

</Steps>

</TabItem>
<TabItem label="Binary">

<Steps>

1. [リリースのページ](https://github.com/Verdin-CMS/verdin/releases)から、プラットフォーム用のアーカイブ（たとえば `verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz`）をダウンロードし、リリースの `SHA256SUMS` と照合します。

   ```sh frame="terminal"
   sha256sum --ignore-missing -c SHA256SUMS
   tar xzf verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz
   ```

2. サーバーを停止し、`verdin` のバイナリを置き換えて、バージョンを確認します。

   ```sh frame="terminal"
   verdin version
   ```

3. プロジェクトのディレクトリで、マイグレーションを確認して適用します。

   ```sh frame="terminal"
   verdin migrate plan
   verdin migrate apply
   ```

   または、先に安全なステップを適用する `verdin start --migrate` で起動します。

4. いつもどおりサーバーを起動します（`verdin start`）。

</Steps>

## 起動時のマイグレーション

新しいバージョンは、しばしば独自のテーブルやカラム（セッション、設定、新しい機能）を追加します。`verdin start` は、データベースを、スキーマと新しいバージョンが必要とするものと比較します。

- 一致していれば起動します。
- ステップが保留中なら起動を拒否し、`verdin migrate plan` と `verdin migrate apply` を実行するか、`--migrate` 付きで起動するよう案内します。
- `--migrate` が適用するのは**安全な**ステップだけです。risky や destructive なステップがあると起動は失敗し、プランを読んだうえで `verdin migrate apply --allow risky`（または `destructive`）で自分で適用します。
- スキーマの変更をトランザクションで実行できない MySQL と MariaDB では、中断されたマイグレーションは次の `verdin migrate apply` で失敗したステップから再開します。

インスタンスが複数ある場合、ローリングアップグレードが使えます。最初の新しいインスタンスがマイグレーションのロックを取ってマイグレーションし、他のインスタンスはそれを待ち、やることが残っていないことを確認します。[複数のインスタンスの実行](/ja/deploy/scaling/)を参照してください。

<Aside type="caution">
プロジェクト全体を 1 つのバージョンにアップグレードしてください。2 つのマイナーバージョンのインスタンスを、ローリングデプロイにかかる時間より長く並べて動かさないでください。
</Aside>

## アップグレードの注意事項

バージョンごとの注目すべき変更と互換性のない変更です。古いものが最後に並びます。完全な一覧は[チェンジログ](/ja/project/changelog/)にあります。

### 0.9.1 → 0.10

データベースのマイグレーションはありません。ドキュメントは `docs/` からこのサイトに移りました。

- **`review-workflows.updateEntryStage` の Webhook の受信側**: `model` は、エントリーのイベントと同じく単数形の名前（`article`）になり、uid は `uid` に移りました。`model` を使っていた箇所では `uid` を読んでください。
- **TypeScript の型を再生成してください**（`verdin types`）。`Collections` と `Singles` が型エイリアスになりました。`createClient<VerdinSchema>` にはこれが必要です。
- **Docker**: イメージは変換のキャッシュと検索インデックスを `/data` に置き、`/app/public/uploads` を `/data/uploads` にリンクします。読み取り専用の `/app` を回避するためだけに `VERDIN_UPLOAD__TRANSFORMS__CACHE_DIR` や `VERDIN_SEARCH__DIR` を設定していた場合は、削除してかまいません。イメージには `HEALTHCHECK` があります。
- **CDN**: レスポンスには populate できる型のタグが付くため、パージでこれまでより多くのキャッシュが更新されます。変更は不要です。
- 管理パネルのリレーションフィールドは、インラインの検索ボックスではなくダイアログ（**エントリーをリンク**）でエントリーをリンクします。

### 0.9.0 → 0.9.1

堅牢化のリリースで、すべてのインストールでアップグレードを推奨します。そのマイグレーション（新しいテーブル 1 つ、新しいカラム 2 つ）は起動時に実行されます。

- **リバースプロキシの背後では、`[server].trusted_proxies` を設定してください。** クライアントのアドレスには、登録したプロキシの `X-Forwarded-For` だけが使われます。設定しないと、プロキシの背後にいるすべてのクライアントが、レート制限と監査ログで 1 つのアドレスを共有します。
- **別のオリジンのブラウザーのフロントエンドには `[api].cors_origins` が必要です。** 0.9.1 でコンテンツ API と GraphQL に CORS が加わりました。以前は CORS に対応していませんでした。
- **リレーションを介した読み取りは権限に従います。** `populate`、リレーションのフィルター、リレーションのソートは、どの API でも、呼び出し元が読み取れる型とフィールドにしか届きません。`find` の許可のない型を populate していた公開やトークンのリクエストは、得られるデータが減ります。足りない権限を許可してください。
- **SSO がより厳格になりました。** 設定には Super Admin が必要です。`defaultRoles` と `roleMap` で Super Admin は与えられません。プロバイダーの `email_verified` クレームは true である必要があります（`trustUnverifiedEmail` の場合を除く）。プロバイダーがそれを任されていない限り（`providerMfa`）、管理者の第二要素が適用されます。発行者とトークンのエンドポイントは公開の `https` の URL である必要があります。アップグレード後に SSO のログインを確認してください。
- **Super Admin** の作成、編集、削除、再招待、リセットは、別の Super Admin だけができます。
- **エンドユーザーのアカウントは**、管理者のアカウントと同様に、パスワードを繰り返し間違えると**ロックされます**。
- populate したリレーションが返すのは、エントリーとリレーションごとに最大 1,000 件です。
- 検索インデックスは最初の起動時に再構築されます（private なコンポーネントのフィールドはインデックスされなくなりました）。

### 0.8 → 0.9

- 管理画面の一覧の検索ボックスは、タイトルではなくすべてのテキストフィールド（`_q`）を検索します。
- 管理者の新しい権限 `deploy.manage`、`deploy.trigger`、`site.manage`。Editor は `deploy.trigger` と `site.manage` を得ます。
- 新しいオプション機能（リアルタイム、コメントとタスク、AI アクション、SEO とサイトマップ、リダイレクト、メニュー、フォーム）は、オンにするまでオフです。メトリクスには `[metrics].enabled = true` が必要です。

### 0.7 → 0.8

- **条件付きフィールドが適用されます。** `conditions` で非表示になったフィールドは必須でなくなりました。そのようなフィールドが必須であることに頼っていたコンテンツは、そのフィールドなしで保存されることがあります。
- 新しい `password` 属性の型。`verdin import strapi` が Strapi のパスワードのフィールドをインポートするようになりました。

### 0.7.0 → 0.7.1

- プラグインのランタイムが Wasmtime 48 に移行しました。既存のプラグインはビルドし直さなくても動きます。
- ソースからのビルドには Rust 1.95 以降が必要です。

### 0.6 → 0.7

- **複数のインスタンス**: 各インスタンスは、他のインスタンスが変更した設定を `[server].sync_interval_secs`（10 秒）ごとに読みます。複数実行する場合は、1 つを除くすべてで `[plugins].run_jobs = false` を設定してください。
- プラグインがホストを通じて書き込むコンテンツは、レビューワークフローの段階など、プラットフォームの書き込み前のチェックを通るようになりました。プラグイン自身の書き込み前のフックは、これらの書き込みでは引き続きスキップされるので、プラグインが自分自身を呼び出すことはありません。

### 0.5 → 0.6

- **監査ログ**はデフォルトでオンで、`[audit].retention_days`（90）の間エントリーを保持します。不要な場合は**設定 → 機能**で機能をオフにしてください。

### 0.4 → 0.5

- 変更は不要です。プラグインは `[plugins].path`（`plugins/`）から読み込まれ、オンにするまでオフのままです。

### 0.3 → 0.4

- `upload` と `uploads` に加えて、**`auth`、`users`、`connect` が予約されたルート名になりました。** API の名前がこれらのいずれかであるコンテンツタイプは、アップグレードの前に名前を変えてください。

### 0.2 → 0.3

- 属性名は、camelCase だけでなく Strapi のルール（英字で始まり、英字、数字、アンダースコアが続く）に従います。同じカラムに対応する 2 つの名前は拒否されます。
- `regex` のオプションは JavaScript 風のパターンを受け付けます。

### 0.1 → 0.2

- ボディサイズの上限とタイムアウトは API のルーターごとに適用されます。アップロードには独自の上限（`[upload].max_file_size`）があります。
- 既存のインストールの組み込みのロールは、新しい権限を一度だけ受け取ります。

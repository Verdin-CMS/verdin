リレーションは、記事とそのカテゴリーのように、2 つのコンテンツタイプのドキュメントをリンクします。このページでは、リレーションの種類、リンクの保存と解決の方法、そして書き込み、順序、読み取りのルールを説明します。リクエストの構文は [REST API](/ja/api/rest/#書き込み) を参照してください。

## 種類

リレーションは `type: "relation"` の属性で、`relation` の種類と `target` のコンテンツタイプを持ちます。

| 種類 | 1 件のドキュメントのリンク先 | 対象へのリンク元 | 逆側 |
| --- | --- | --- | --- |
| `oneWay` | 1 件の対象 | 任意の数のドキュメント | なし |
| `manyWay` | 複数の対象 | 任意の数のドキュメント | なし |
| `manyToOne` | 1 件の対象 | 任意の数のドキュメント | `oneToMany` |
| `oneToMany` | 複数の対象 | 1 件のドキュメント | `manyToOne` |
| `oneToOne` | 1 件の対象 | 1 件のドキュメント | `oneToOne` |
| `manyToMany` | 複数の対象 | 任意の数のドキュメント | `manyToMany` |

ブログのサンプルでは、記事をカテゴリー（逆側あり）とタグ（逆側なし）にリンクしています。

```json title="schema/content-types/article.json (excerpt)"
"category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
"tags": { "type": "relation", "relation": "manyToMany", "target": "tag" }
```

```json title="schema/content-types/category.json (excerpt)"
"articles": { "type": "relation", "relation": "oneToMany", "target": "article", "mappedBy": "category" }
```

- `inversedBy` を持つ側（またはどちらのキーも持たない側）が**所有**側です。リンクを保存し、書き込むのはこちら側です。
- `mappedBy` を持つ側が**逆**側です。所有側のリンクを逆向きに読み、読み取り専用です。書き込もうとすると、所有側の属性を示すバリデーションエラーになります。
- 両側は整合している必要があります。`mappedBy` は、`inversedBy` で指し返す対象の属性を示し、その種類は表の対応する逆側の種類でなければなりません。
- `oneWay` と `manyWay` に逆側はありません。

コンテンツタイプビルダーは、対象側の逆側の属性を自動で作成します。

## 行ではなくドキュメントでリンクする

ドキュメントは複数の行を持ちます。下書きと公開バージョン、そしてロケールごとにそれぞれ 1 つずつです。Verdin はリレーションを、元の**行**から対象の**ドキュメント**（その `documentId`）へのリンクとして、`{table}_{field}_lnk` という名前のリンクテーブルに保存します。対象の行は、リレーションを読み取るときに選ばれます。

- 公開された記事はカテゴリーの公開バージョンを、記事の下書きはカテゴリーの下書きを見ます。下書きと公開を使わない型にはバージョンが 1 つしかなく、どの読み手もそれを見ます。
- 対象も多言語化されている場合、読み取りでは同じロケールで解決されます。多言語化されていない対象の型は、すべてのロケールで共有されます。
- カテゴリーを非公開にすると、リンクに一切触れずに、公開された記事から隠れます。再び公開すると元に戻ります。
- 記事を公開すると、その記事自身のリンクだけが公開バージョンにコピーされます。

Strapi は代わりに行の ID をリンクするので、下書きを公開するたびにリンクを書き換える必要があります。Verdin はそうしないので、公開は下書きの行を 1 回コピーするだけで済みます。

整合性は外部キーではなく Verdin が保ちます。存在しないドキュメントをリンクするとバリデーションエラーになり、ドキュメントを削除すると、それを指すリンクが同じトランザクションで削除されます。

### 対象ごとに 1 件のドキュメント

`oneToOne` と `oneToMany` では、対象が属せる元のドキュメントは最大 1 件です。別のドキュメントが持っている対象をリンクすると、その対象は**移動**します。もう一方のドキュメントのリンクは、同じ書き込みで削除されます。これは Strapi と同じ動作です。この制約はバージョンごとに適用されるので、下書きとその公開バージョンが同じ対象を持つことはできます。

## 書き込み

所有側では、`data` は `documentId`、そのリスト、または変更を記述するオブジェクトを受け取ります。

| 入力 | 効果 |
| --- | --- |
| `"k2m…"` または `{ "documentId": "k2m…" }` | 1 件の対象をリンクします（対一リレーション）。 |
| `["k2m…", "p9x…"]` | すべてのリンクを、この順序で置き換えます。 |
| `null` または `[]` | すべてのリンクを削除します。 |
| `{ "set": ["k2m…"] }` | すべてのリンクを置き換えます。 |
| `{ "connect": [...], "disconnect": [...] }` | 他のリンクを保ったまま、リンクを追加・削除します。 |

対一リレーションに新しい対象を connect すると、前の対象が置き換えられます。`set` は `connect` や `disconnect` と組み合わせられません。

管理パネルでは、リレーションのフィールドにリンクされたエントリーが一覧表示されます。**エントリーをリンク**を押すとダイアログが開き、対象の型のエントリーをテキストフィールド全体から検索します。対象が多言語化されている場合はエントリーのロケールで検索します。エントリーを 1 件選ぶか、複数にチェックを入れて追加します。すでにリンクされているエントリーには印が付きます。

## 順序

対多リレーションはリンクの順序を保ちます。リストや `set` では、送った順序が保存されます。`connect` の項目では、入れる位置を指定できます。

```json
{
  "data": {
    "tags": {
      "connect": [
        { "documentId": "k2m…", "position": { "before": "p9x…" } },
        { "documentId": "a7c…", "position": { "end": true } }
      ]
    }
  }
}
```

`position` は `{ "before": documentId }`、`{ "after": documentId }`、`{ "start": true }`、`{ "end": true }` のいずれかです。位置は書き込みのたびに振り直されます。読み取りでは、populate で `sort` を指定しない限り、関連ドキュメントはリンクの順序で返されます。

## 読み取り

リレーションは、populate した場合にだけ返されます。

```http
GET /api/articles?populate[category][fields][0]=name&populate[tags][sort]=label:asc
```

対一リレーションはオブジェクトまたは `null`、対多リレーションは配列です。populate した各リレーションは、それぞれ `fields`、`filters`、`sort`、`populate`、`count` を最大 5 階層まで受け付けます。各階層は結合ではなく、リレーションごとに 1 回のバッチクエリ（`WHERE … IN (…)`）なので、深い populate でも行が増えません。ドキュメントとリレーションごとに返される関連ドキュメントは最大 1,000 件で、`count` で正確な数がわかります。

リレーションを介したフィルター（`filters[category][name][$eq]=News`）はどちら側からでもでき、対一リレーションのフィールドでソートすることもできます（`sort=category.name:asc`）。呼び出し元が読み取れない型へのリレーションを介した populate、フィルター、ソートは拒否されます（`populate=*` はスキップします）。そのため、呼び出し元の[権限](/ja/concepts/permissions/)が隠しているコンテンツが、リレーションを通じて明らかになることはありません。

## コンポーネント内のリレーション

[コンポーネント](/ja/concepts/components-and-dynamic-zones/)はリレーションを持てますが、`oneWay` と `manyWay` だけです。

```json title="schema/components/shared/related.json"
{
  "displayName": "Related",
  "attributes": {
    "label": { "type": "string" },
    "articles": { "type": "relation", "relation": "manyWay", "target": "article" }
  }
}
```

コンポーネントの JSON は `documentId` そのものを保存します。`oneWay` なら文字列、`manyWay` なら配列です。そのため、ほかの種類はここでは使えません。

- 逆側があると、誰がリンクしているかを見つけるために、すべてのドキュメントの JSON を検索しなければなりません。
- 「対象ごとに 1 件のドキュメント」（`oneToOne`、`oneToMany`）も、そのような検索なしには強制できません。

コンポーネント内では、`manyWay` のリストの順序は配列の順序です。参照は書き込み時に確認され、コンポーネントを populate したときに、ドキュメントのステータスとロケールで解決されます。存在しなくなった対象は省かれます。これらでフィルターすることはできません。

## ポリモーフィックリレーション

`morphToOne` と `morphToMany` は、任意のコンテンツタイプのドキュメントをリンクします。リンクは対象の `documentId` の隣にその型を保存し、書き込みでは両方を指定します。

```json
{ "data": { "related": [{ "__type": "api::article", "documentId": "k2m…" }, { "__type": "api::page", "documentId": "p9x…" }] } }
```

populate された項目は、`__type` を持つ対象のドキュメントで、リクエストのステータスとロケールで読み取られます。逆側の `morphOne` と `morphMany` は所有側の型（`target`）とその属性（`morphBy`）を指定し、読み取り専用です。ポリモーフィックリレーションでフィルターやソートはできず、コンポーネントの中にも置けません。

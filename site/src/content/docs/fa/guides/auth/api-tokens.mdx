توکن‌های API به سایت‌ها، برنامه‌ها و اسکریپت‌های شما اجازه می‌دهند API محتوا را با دسترسی بیشتری
نسبت به دسترسی عموم فراخوانی کنند. این راهنما یک توکن می‌سازد، دسترسی آن را انتخاب می‌کند، از آن
استفاده می‌کند و وقتی لو رفت آن را جایگزین می‌کند. توکن‌ها مانند توکن‌های API در Strapi کار می‌کنند.

API محتوا به‌طور پیش‌فرض بسته است: بدون توکن، درخواست‌ها فقط آنچه را **تنظیمات ← دسترسی
عمومی** اجازه می‌دهد دریافت می‌کنند، و تا وقتی شما مجوزی ندهید، این هیچ است.

## پیش از شروع

- مدیریت توکن‌ها به **مدیریت توکن‌های API** (`tokens.manage`) نیاز دارد.
  [مجوزها](/fa/reference/permissions/) را ببینید.
- `VERDIN_TOKEN_PEPPER` باید تنظیم شده باشد؛ بخش [جایی که pepper اهمیت دارد](#جایی-که-pepper-اهمیت-دارد) را ببینید.

## ساخت یک توکن

<Steps>

1. **تنظیمات ← توکن‌های API** را باز کنید و **ایجاد توکن** را انتخاب کنید.
2. یک **نام** و در صورت تمایل یک **توضیحات** وارد کنید.
3. **نوع** را انتخاب کنید:

   | نوع | اجازه می‌دهد |
   | --- | --- |
   | **فقط‌خواندنی** | یافتن و یافتن یکی روی همهٔ نوع‌های محتوا، فقط نسخه‌های منتشرشده. |
   | **دسترسی کامل** | همهٔ عمل‌ها روی همهٔ نوع‌های محتوا و کتابخانهٔ رسانه. |
   | **سفارشی** | فقط عمل‌هایی که در **مجوزها** علامت می‌زنید. |

4. زمان **انقضا** را انتخاب کنید: **هرگز**، یا پس از 7، 30 یا 90 روز.
5. برای توکن سفارشی، عمل‌ها را زیر **مجوزها** برای هر نوع محتوا علامت بزنید: **یافتن**،
   **یافتن یکی**، **ایجاد**، **به‌روزرسانی**، **حذف**، **انتشار** و **خواندن پیش‌نویس‌ها**.
   ردیف **کتابخانهٔ رسانه** بارگذاری‌ها را پوشش می‌دهد و ردیف **کاربران** مسیرهای `/api/users`
   [کاربران نهایی](/fa/guides/auth/end-users/) را.
6. **ایجاد** را انتخاب کنید، سپس توکن را کپی کنید. این تنها باری است که نمایش داده می‌شود.

</Steps>

توکن‌ها با `vd_` شروع می‌شوند. فهرست، نویسه‌های نخست هر توکن، زمان آخرین استفاده و زمان انقضای
آن را نشان می‌دهد.

## استفاده از توکن

آن را به‌صورت bearer token بفرستید:

<Tabs syncKey="api">
<TabItem label="REST">

```sh title="Terminal"
curl -H "Authorization: Bearer $VERDIN_TOKEN" 'http://localhost:1337/api/articles?status=draft'
```

</TabItem>
<TabItem label="GraphQL">

```sh title="Terminal"
curl -X POST http://localhost:1337/graphql \
  -H "Authorization: Bearer $VERDIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"query":"{ articles { documentId title } }"}'
```

</TabItem>
<TabItem label="TypeScript">

```ts
import { createClient } from '@verdin/client';
import type { VerdinSchema } from './verdin-types';

const verdin = createClient<VerdinSchema>({
  url: 'http://localhost:1337',
  token: process.env.VERDIN_TOKEN,
});
```

</TabItem>
</Tabs>

- دسترسی توکن جایگزین دسترسی عمومی می‌شود؛ به آن اضافه نمی‌شود. توکن سفارشی‌ای که روی یک نوع
  **یافتن** ندارد نمی‌تواند آن را فهرست کند، حتی اگر عموم بتوانند.
- خواندن پیش‌نویس‌ها (`?status=draft`) به **خواندن پیش‌نویس‌ها** نیاز دارد؛ توکن‌های فقط‌خواندنی
  هرگز پیش‌نویس‌ها را نمی‌بینند.
- توکن‌های ناشناخته و منقضی‌شده `401` می‌گیرند. عمل‌های خارج از دسترسی توکن `403` می‌گیرند.
- `[api].token_rate_limit` درخواست‌ها را برای هر توکن در هر دقیقه محدود می‌کند (به‌طور پیش‌فرض خاموش).
- همین توکن‌ها برای GraphQL و [سرور MCP](/fa/guides/integrations/mcp/) هم مجوز می‌دهند.

<Aside type="caution">
توکنی که در مرورگر باشد برای همهٔ بازدیدکنندگان قابل مشاهده است. از توکن‌ها فقط در سرورها،
گام‌های ساخت (build) و برنامه‌های خصوصی استفاده کنید؛ برای صفحه‌های عمومی، آنچه لازم دارند را در
**تنظیمات ← دسترسی عمومی** مجاز کنید.
</Aside>

## بازتولید یا حذف توکن

- **بازتولید** در ردیف یک توکن کلید جدیدی با همان نام، نوع و مجوزها می‌سازد. کلید فعلی بلافاصله
  از کار می‌افتد، بنابراین برنامه‌هایی که از آن استفاده می‌کنند تا وقتی آن‌ها را به‌روزرسانی نکنید
  خطا می‌گیرند.
- **حذف** توکن را پاک می‌کند؛ کلاینت‌هایی که از آن استفاده می‌کنند دسترسی را از دست می‌دهند.

به محض اینکه احتمال لو رفتن توکنی وجود داشت، یکی از این دو کار را انجام دهید.

## جایی که pepper اهمیت دارد

Verdin هرگز توکن‌ها را ذخیره نمی‌کند. یک هش کلیددار (HMAC-SHA256) از هر توکن را با کلید
`VERDIN_TOKEN_PEPPER` ذخیره می‌کند، بنابراین داشتن نسخه‌ای از پایگاه داده به‌تنهایی به کسی اجازهٔ
استفاده از آن‌ها را نمی‌دهد. همین pepper از این‌ها محافظت می‌کند:

- توکن‌های API.
- کلیدهای محرمانهٔ برنامهٔ احراز هویت و کدهای بازیابی مدیران
  ([تأیید دومرحله‌ای](/fa/guides/auth/two-factor/)).
- نشانی‌های IP هش‌شده‌ای که همراه با ارسالی‌های فرم ذخیره می‌شوند.

pepper را یک بار با `verdin secrets` تولید کنید، آن را بیرون از `verdin.toml` و نسخه‌های پشتیبان
پایگاه داده نگه دارید و به همهٔ نمونه‌ها همان مقدار را بدهید.

<Aside type="caution" title="تغییر pepper">
با pepper دیگر، همهٔ توکن‌های API از کار می‌افتند و برنامهٔ احراز هویت و کدهای بازیابی همهٔ مدیران
هم کار نمی‌کنند. فقط اگر لو رفته است آن را تغییر دهید، سپس توکن‌های جدید بسازید و تأیید دومرحله‌ای
همهٔ مدیران را بازنشانی کنید. کلیدهای دسترسی (passkey) و رمزهای عبور تحت تأثیر قرار نمی‌گیرند.
</Aside>

## Admin API

همهٔ مسیرها زیر `/admin/api` هستند و به `tokens.manage` نیاز دارند.

```http
GET    /admin/api/api-tokens?page=1&pageSize=25
POST   /admin/api/api-tokens                  { "name": "Website", "kind": "custom", "expiresInDays": 90,
                                                "permissions": [{ "subject": "api::article", "action": "find" }] }
GET    /admin/api/api-tokens/{id}
PUT    /admin/api/api-tokens/{id}             { "name": "…", "description": null, "kind": "read-only", "permissions": [...] }
POST   /admin/api/api-tokens/{id}/regenerate
DELETE /admin/api/api-tokens/{id}
```

- `kind` یکی از `read-only`، `full-access` یا `custom` است؛ `expiresInDays` اختیاری است (بدون آن
  هرگز منقضی نمی‌شود) و بعداً قابل تغییر نیست.
- `permissions` جفت‌های `{ subject, action }` را فهرست می‌کند. `subject` یک uid نوع محتوا،
  `plugin::upload` (کتابخانهٔ رسانه) یا `plugin::users-permissions.user` است؛ `action` یکی از
  `find`، `findOne`، `create`، `update`، `delete`، `publish` یا `readDrafts` است. `publish` و
  `readDrafts` برای دو subject آخر کاربرد ندارند.
- `POST /api-tokens` و `/regenerate` کلید را یک بار، به‌صورت `accessKey`، برمی‌گردانند.

دسترسی عمومی از همین جفت‌ها استفاده می‌کند: `PUT /admin/api/public-permissions`
`{ "permissions": [...] }`، که به **مدیریت نقش‌ها** (`roles.manage`) نیاز دارد.

مدیران می‌توانند از طریق هر ارائه‌دهندهٔ OpenID Connect وارد شوند: Microsoft Entra ID، Google Workspace،
Okta، Auth0، Keycloak، Authentik، GitLab و دیگران. هر ارائه‌دهنده یک دکمه در صفحهٔ ورود می‌گیرد و
ورود با رمز عبور هم در کنار آن کار می‌کند. این راهنما یک برنامه (application) ثبت می‌کند،
ارائه‌دهنده را در Verdin پیکربندی می‌کند و گروه‌ها را به نقش‌ها نگاشت می‌کند.

SSO در Strapi یک قابلیت نسخهٔ سازمانی (Enterprise) است. در Verdin بخشی از هستهٔ متن‌باز است.
برای کاربران نهایی سایت‌هایتان، به‌جای آن [ورود OAuth برای کاربران نهایی](/fa/guides/auth/end-users/)
را ببینید.

## پیش از شروع

- پیکربندی SSO به **مدیریت قابلیت‌ها** (`features.manage`) نیاز دارد.
- `[server].public_url` را روی نشانی‌ای تنظیم کنید که مدیران Verdin را با آن باز می‌کنند، مانند
  `https://cms.example.com`. نشانی بازگشت (redirect URI) از روی آن ساخته می‌شود.

## راه‌اندازی

<Steps>

1. **یک برنامه ثبت کنید** (یک کلاینت از نوع "web") نزد ارائه‌دهنده، با این نشانی بازگشت:

   ```text
   https://cms.example.com/admin/api/auth/sso/<id>/callback
   ```

   `<id>` شناسهٔ ارائه‌دهنده است که در گام 3 انتخاب می‌کنید، مانند `corp`. مسیر مدیریت از
   `[admin].path` پیروی می‌کند.

2. **کلید محرمانهٔ کلاینت را در محیط قرار دهید** و Verdin را دوباره راه‌اندازی کنید:

   ```sh title=".env"
   VERDIN_SSO_CORP_SECRET=…
   ```

   متغیر `VERDIN_SSO_<ID>_SECRET` است، با شناسه به حروف بزرگ و خط تیره‌ها به‌صورت زیرخط.
   کلاینت‌های عمومی (فقط PKCE، بدون secret) به متغیری نیاز ندارند.

3. **ارائه‌دهنده را اضافه کنید.** **تنظیمات ← قابلیت‌ها ← ورود یکپارچه** را روشن کنید،
   **پیکربندی ارائه‌دهندگان** و سپس **افزودن ارائه‌دهنده** را انتخاب کنید و این‌ها را پر کنید:

   - **شناسه**: حروف کوچک، ارقام و خط تیره، حداکثر 32 نویسه.
   - **متن دکمه**: در صفحهٔ ورود به‌صورت «ادامه با …» نمایش داده می‌شود.
   - **نشانی صادرکننده**: Verdin زیر آن `/.well-known/openid-configuration` را می‌خواند. باید از
     `https` استفاده کند، مگر روی `localhost`.
   - **شناسهٔ کلاینت** و **دامنه‌های دسترسی (Scopes)** (به‌طور پیش‌فرض `openid email profile`؛
     `openid` الزامی است).

   پنجره، **نشانی بازگشت برای ثبت نزد ارائه‌دهنده** و نام متغیر secret را نشان می‌دهد. ذخیره
   کنید.

4. **امتحان کنید** در یک پنجرهٔ خصوصی: صفحهٔ ورود **ادامه با Corp account** را نشان می‌دهد.

</Steps>

## چه کسی می‌تواند وارد شود، و با چه نقش‌هایی

| تنظیم | کلید JSON | اثر |
| --- | --- | --- |
| **دامنه‌های ایمیل مجاز** | `allowedDomains` | فقط این دامنه‌های ایمیل می‌توانند وارد شوند. خالی یعنی هر دامنه‌ای. |
| **ایجاد حساب در اولین ورود** | `autoCreate` | نخستین باری که کسی وارد می‌شود، یک حساب مدیر می‌سازد. بدون آن، فقط ایمیل‌هایی که از قبل حساب دارند می‌توانند وارد شوند. |
| **نقش‌های پیش‌فرض** | `defaultRoles` | کد نقش‌های حساب‌های ساخته‌شده، وقتی نگاشت نقش هیچ نقشی نمی‌دهد. |
| **ادعای نقش (claim)** | `roleClaim` | claim در ID token که گروه‌های کاربر را فهرست می‌کند، مانند `groups` یا `roles`. |
| **نگاشت نقش** | `roleMap` | هر مقدار claim کدام کد نقش را می‌دهد. |
| **اعتماد به ایمیل‌های تأییدنشده** | `trustUnverifiedEmail` | ایمیل‌هایی را که ارائه‌دهنده به‌عنوان تأییدشده علامت نمی‌زند می‌پذیرد. |
| **ارائه‌دهنده MFA را الزامی می‌کند** | `providerMfa` | پس از این ارائه‌دهنده، عامل دوم Verdin را از مدیران نمی‌خواهد. |

- ارائه‌دهنده‌ای که حساب می‌سازد به نقش‌های پیش‌فرض یا نگاشت نقش نیاز دارد.
- هیچ‌کدام نمی‌توانند نقش مدیر ارشد را بدهند؛ مدیران را دستی در **تنظیمات ← کاربران** ارتقا دهید.
- نقش‌ها فقط هنگام ساخت حساب تعیین می‌شوند. پس از آن، آن‌ها را در **تنظیمات ← کاربران** مدیریت
  کنید.
- نام و نام خانوادگی حساب ساخته‌شده از claimهای `given_name` و `family_name` می‌آید.

همین ارائه‌دهنده به‌صورت JSON، همان‌طور که قابلیت ذخیره می‌کند (`PUT /admin/api/features/sso`):

```json
{
  "enabled": true,
  "settings": {
    "providers": [
      {
        "id": "corp",
        "name": "Corp account",
        "issuer": "https://login.microsoftonline.com/<tenant>/v2.0",
        "clientId": "…",
        "scopes": ["openid", "email", "profile"],
        "autoCreate": true,
        "defaultRoles": ["author"],
        "roleClaim": "groups",
        "roleMap": { "<editors group id>": "editor" },
        "allowedDomains": ["corp.example"],
        "trustUnverifiedEmail": true,
        "providerMfa": true
      }
    ]
  }
}
```

## نکته‌های مربوط به ارائه‌دهندگان

- **Microsoft Entra ID** در ID tokenهای خود `email_verified` را نمی‌گذارد: برای آن **اعتماد به
  ایمیل‌های تأییدنشده** را روشن کنید. برای نگاشت گروه‌ها، claim `groups` را در پیکربندی توکن برنامه
  اضافه کنید؛ مقادیر آن شناسه‌های گروه‌اند.
- **Google Workspace**: صادرکننده `https://accounts.google.com` است. ورودها را با **دامنه‌های
  ایمیل مجاز** به دامنهٔ خود محدود کنید.
- **Keycloak**: صادرکننده URL مربوط به realm است، `https://<host>/realms/<realm>`.

## تأیید دومرحله‌ای

به‌طور پیش‌فرض، از مدیری که [عامل دوم](/fa/guides/auth/two-factor/) در Verdin دارد، پس از اینکه
ارائه‌دهنده او را برمی‌گرداند، آن عامل خواسته می‌شود. وقتی ارائه‌دهنده از قبل MFA را الزامی می‌کند،
**ارائه‌دهنده MFA را الزامی می‌کند** را روشن کنید تا دو بار از آن‌ها خواسته نشود.

## چگونه کار می‌کند

<Diagram
  caption="یک ورود SSO"
  code={`sequenceDiagram
  participant B as مرورگر
  participant V as Verdin
  participant P as ارائه‌دهنده
  B->>V: GET /admin/api/auth/sso/corp
  V-->>B: تغییرمسیر با state و چالش PKCE
  B->>P: ورود
  P-->>B: تغییرمسیر به callback با code
  B->>V: GET /admin/api/auth/sso/corp/callback
  V->>P: مبادلهٔ code (TLS)
  V-->>B: کوکی نشست، تغییرمسیر به /admin/`}
/>

- Verdin از جریان authorization code همراه با PKCE (S256) استفاده می‌کند. `state` امضا شده و به یک
  کوکی `HttpOnly` کوتاه‌عمر گره خورده است، و `nonce` از آن مشتق می‌شود.
- صادرکننده، مخاطب (audience) (و وقتی چند مخاطب وجود دارد `azp`)، انقضا و nonce در ID token را
  بررسی می‌کند. به یک claim `email` با `email_verified: true` نیاز دارد، مگر اینکه **اعتماد به
  ایمیل‌های تأییدنشده** روشن باشد.
- نقاط پایانی ارائه‌دهنده باید از `https` استفاده کنند.
- هر ورود SSO در [گزارش‌های حسابرسی](/fa/guides/content/audit-logs/) به‌صورت
  `admin.login`، همراه با ارائه‌دهنده، ثبت می‌شود.

وقتی ورودی شکست بخورد، مرورگر همراه با دلیل («ورود یکپارچه ناموفق بود») به صفحهٔ ورود برمی‌گردد،
و دلیل در لاگ سرور نوشته می‌شود. دلیل‌های رایج:

| دلیل | راه‌حل |
| --- | --- |
| the provider did not verify the email | **اعتماد به ایمیل‌های تأییدنشده** را روشن کنید، یا claim ارائه‌دهنده را درست کنید. |
| this email domain may not sign in | دامنه را به **دامنه‌های ایمیل مجاز** اضافه کنید. |
| no admin account for this identity | **ایجاد حساب در اولین ورود** را روشن کنید، یا ابتدا مدیر را بسازید. |
| the sign-in request expired or was not started here | دوباره از صفحهٔ ورود، در همان مرورگر، شروع کنید. |

<Aside type="note">
مدیر غیرفعال‌شده از طریق SSO هم نمی‌تواند وارد شود.
</Aside>

یک رابطه سندهای دو نوع محتوا را به هم پیوند می‌دهد، مانند یک مقاله و دسته‌اش. این صفحه گونه‌های
رابطه، نحوهٔ ذخیره و resolve شدن پیوندها، و قواعد نوشتن، مرتب کردن و خواندن آن‌ها را توضیح
می‌دهد. برای نحو درخواست، نگاه کنید به [REST API](/fa/api/rest/#نوشتن).

## گونه‌ها

یک رابطه ویژگی‌ای از نوع `type: "relation"` با یک گونهٔ `relation` و یک نوع محتوای `target`
است:

| گونه | یک سند پیوند می‌دهد به | یک هدف پیوند می‌گیرد از | سمت معکوس |
| --- | --- | --- | --- |
| `oneWay` | یک هدف | هر تعداد سند | ندارد |
| `manyWay` | چند هدف | هر تعداد سند | ندارد |
| `manyToOne` | یک هدف | هر تعداد سند | `oneToMany` |
| `oneToMany` | چند هدف | یک سند | `manyToOne` |
| `oneToOne` | یک هدف | یک سند | `oneToOne` |
| `manyToMany` | چند هدف | هر تعداد سند | `manyToMany` |

مثال وبلاگ مقاله‌ها را به یک دسته (با سمت معکوس) و به برچسب‌ها (بدون سمت معکوس) پیوند
می‌دهد:

```json title="schema/content-types/article.json (excerpt)"
"category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
"tags": { "type": "relation", "relation": "manyToMany", "target": "tag" }
```

```json title="schema/content-types/category.json (excerpt)"
"articles": { "type": "relation", "relation": "oneToMany", "target": "article", "mappedBy": "category" }
```

- سمتی که `inversedBy` دارد (یا هیچ‌یک از دو کلید را ندارد) سمت **مالک** است: پیوندها را ذخیره
  می‌کند و همان سمتی است که می‌نویسید.
- سمتی که `mappedBy` دارد سمت **معکوس** است: پیوندهای مالک را به‌صورت وارونه می‌خواند و
  فقط‌خواندنی است. نوشتن در آن یک خطای اعتبارسنجی است که ویژگی مالک را نام می‌برد.
- دو سمت باید با هم سازگار باشند: `mappedBy` ویژگی‌ای از هدف را نام می‌برد که با `inversedBy`
  به عقب اشاره می‌کند، با گونهٔ معکوس متناظر از جدول.
- `oneWay` و `manyWay` هرگز سمت معکوس ندارند.

سازندهٔ نوع محتوا ویژگی معکوس را برای شما روی هدف می‌سازد.

## پیوند با سند، نه با ردیف

یک سند چند ردیف دارد: یک پیش‌نویس و یک نسخهٔ منتشرشده، و از هر کدام یکی برای هر زبان. Verdin
یک رابطه را به‌صورت پیوندی از **ردیف** مبدأ به **سند** هدف (`documentId` آن) در یک جدول پیوند
با نام `{table}_{field}_lnk` ذخیره می‌کند. ردیف هدف هنگام خواندن رابطه انتخاب می‌شود:

- یک مقالهٔ منتشرشده نسخهٔ منتشرشدهٔ دسته‌اش را می‌بیند؛ پیش‌نویس آن، پیش‌نویس دسته را.
  نوع‌های بدون پیش‌نویس و انتشار یک نسخه دارند که هر خواننده‌ای آن را می‌بیند.
- وقتی هدف هم بومی‌سازی‌شده باشد، خواندن‌ها آن را در همان زبان resolve می‌کنند. نوع هدفی که
  بومی‌سازی‌شده نیست میان همهٔ زبان‌ها مشترک است.
- لغو انتشار یک دسته آن را از مقاله‌های منتشرشده پنهان می‌کند بدون اینکه به هیچ پیوندی دست
  بزند؛ انتشار دوباره آن را برمی‌گرداند.
- انتشار یک مقاله فقط پیوندهای خودش را به نسخهٔ منتشرشده کپی می‌کند.

Strapi به جای این، شناسهٔ ردیف‌ها را پیوند می‌دهد، بنابراین هر بار که یک پیش‌نویس منتشر می‌شود
باید پیوندها را بازنویسی کند. Verdin هرگز این کار را نمی‌کند و همین انتشار را به یک کپی سادهٔ
ردیف پیش‌نویس محدود نگه می‌دارد.

یکپارچگی به جای کلیدهای خارجی توسط Verdin حفظ می‌شود: پیوند دادن به سندی که وجود ندارد یک
خطای اعتبارسنجی است، و حذف یک سند پیوندهایی را که به آن اشاره می‌کنند در همان تراکنش حذف
می‌کند.

### یک سند برای هر هدف

برای `oneToOne` و `oneToMany`، یک هدف حداکثر به یک سند مبدأ تعلق دارد. پیوند دادن هدفی که سند
دیگری آن را در اختیار دارد، آن را **جابه‌جا می‌کند**: پیوند سند دیگر در همان نوشتن حذف می‌شود.
این رفتار Strapi است. این قاعده به ازای هر نسخه اعمال می‌شود: یک پیش‌نویس و نسخهٔ منتشرشدهٔ
آن می‌توانند یک هدف مشترک داشته باشند.

## نوشتن

در سمت مالک، `data` یک `documentId`، فهرستی از آن‌ها، یا شیئی که یک تغییر را توصیف می‌کند
می‌گیرد:

| ورودی | اثر |
| --- | --- |
| `"k2m…"` یا `{ "documentId": "k2m…" }` | پیوند به یک هدف (روابط به‌یک). |
| `["k2m…", "p9x…"]` | جایگزینی همهٔ پیوندها، به همین ترتیب. |
| `null` یا `[]` | حذف همهٔ پیوندها. |
| `{ "set": ["k2m…"] }` | جایگزینی همهٔ پیوندها. |
| `{ "connect": [...], "disconnect": [...] }` | افزودن و حذف پیوندها، با حفظ بقیه. |

متصل کردن یک هدف جدید به یک رابطهٔ به‌یک، هدف قبلی را جایگزین می‌کند. `set` را نمی‌توان با
`connect` یا `disconnect` ترکیب کرد.

در پنل مدیریت، یک فیلد رابطه مدخل‌های پیوندشده را فهرست می‌کند. **پیوند دادن یک مدخل** (یا
**پیوند دادن مدخل‌ها** برای روابط به‌چند) پنجره‌ای باز می‌کند که مدخل‌های نوع هدف را در
فیلدهای متنی‌شان جستجو می‌کند، و وقتی هدف بومی‌سازی‌شده باشد در زبان همان مدخل. یک مدخل را
انتخاب کنید، یا چند مدخل را علامت بزنید و اضافه کنید؛ مدخل‌هایی که از قبل پیوند شده‌اند
علامت‌گذاری شده‌اند.

## ترتیب

روابط به‌چند ترتیب پیوندهایشان را نگه می‌دارند. یک فهرست یا `set` ترتیبی را که می‌فرستید ذخیره
می‌کند. آیتم‌های `connect` می‌توانند بگویند کجا قرار بگیرند:

```json
{
  "data": {
    "tags": {
      "connect": [
        { "documentId": "k2m…", "position": { "before": "p9x…" } },
        { "documentId": "a7c…", "position": { "end": true } }
      ]
    }
  }
}
```

`position` یکی از `{ "before": documentId }`، `{ "after": documentId }`، `{ "start": true }` یا
`{ "end": true }` است. موقعیت‌ها در هر نوشتن دوباره شماره‌گذاری می‌شوند. خواندن‌ها سندهای
مرتبط را به ترتیب پیوند برمی‌گردانند، مگر اینکه populate یک `sort` بخواهد.

## خواندن

روابط فقط وقتی برگردانده می‌شوند که آن‌ها را populate کنید:

```http
GET /api/articles?populate[category][fields][0]=name&populate[tags][sort]=label:asc
```

یک رابطهٔ به‌یک یک شیء یا `null` است؛ یک رابطهٔ به‌چند یک آرایه است. هر رابطهٔ populateشده
می‌تواند `fields`، `filters`، `sort`، `populate` و `count` خودش را بگیرد، تا پنج سطح عمق. هر
سطح یک کوئری دسته‌ای برای هر رابطه است (`WHERE … IN (…)`)، نه یک join، بنابراین populateهای
عمیق ردیف‌ها را چند برابر نمی‌کنند. برای هر سند و رابطه حداکثر 1,000 سند مرتبط برگردانده
می‌شود؛ `count` عدد دقیق را می‌دهد.

می‌توانید از طریق روابط فیلتر کنید (`filters[category][name][$eq]=News`)، در هر دو سمت، و بر
اساس فیلدی از یک رابطهٔ به‌یک مرتب کنید (`sort=category.name:asc`). populate، فیلتر یا
مرتب‌سازی از طریق رابطه‌ای به نوعی که فراخواننده نمی‌تواند بخواند رد می‌شود (`populate=*` آن
را رد می‌کند)، بنابراین روابط هرگز محتوایی را که [مجوزهای](/fa/concepts/permissions/)
فراخواننده پنهان می‌کنند آشکار نمی‌کنند.

## روابط درون کامپوننت‌ها

یک [کامپوننت](/fa/concepts/components-and-dynamic-zones/) می‌تواند روابط داشته باشد، اما فقط
`oneWay` و `manyWay`:

```json title="schema/components/shared/related.json"
{
  "displayName": "Related",
  "attributes": {
    "label": { "type": "string" },
    "articles": { "type": "relation", "relation": "manyWay", "target": "article" }
  }
}
```

JSON کامپوننت خودِ `documentId`ها را ذخیره می‌کند: یک رشته برای `oneWay` و یک آرایه برای
`manyWay`. به همین دلیل گونه‌های دیگر آنجا مجاز نیستند:

- یک سمت معکوس باید JSON همهٔ سندها را جستجو کند تا بفهمد چه کسی به آن پیوند داده است.
- «یک سند برای هر هدف» (`oneToOne`، `oneToMany`) هم بدون چنین جستجویی قابل اعمال نیست.

درون کامپوننت‌ها، ترتیب یک فهرست `manyWay` همان ترتیب آرایه است. ارجاع‌ها هنگام نوشتن بررسی
می‌شوند و وقتی کامپوننت populate شود، در وضعیت و زبان سند resolve می‌شوند؛ هدف‌هایی که دیگر
وجود ندارند کنار گذاشته می‌شوند. نمی‌توان بر اساس آن‌ها فیلتر کرد.

## روابط چندریختی

`morphToOne` و `morphToMany` سندهایی از هر نوع محتوایی را پیوند می‌دهند. پیوندهایشان نوع هدف را
کنار `documentId` آن ذخیره می‌کنند و نوشتن‌ها هر دو را نام می‌برند:

```json
{ "data": { "related": [{ "__type": "api::article", "documentId": "k2m…" }, { "__type": "api::page", "documentId": "p9x…" }] } }
```

آیتم‌های populateشده سندهای هدف همراه با `__type` خود هستند که در وضعیت و زبان درخواست خوانده
می‌شوند. سمت‌های معکوس `morphOne` و `morphMany` نوع مالک (`target`) و ویژگی آن (`morphBy`) را نام
می‌برند و فقط‌خواندنی هستند. روابط چندریختی را نمی‌توان فیلتر یا مرتب کرد و نمی‌توانند درون
کامپوننت‌ها باشند.

Verdin دو مخاطب را جداگانه کنترل می‌کند: **مدیران**، که وارد پنل مدیریت می‌شوند، و
**فراخوانندگان content API**، که محتوا را از سایت‌ها و اپلیکیشن‌های شما می‌خوانند و می‌نویسند.
این صفحه توضیح می‌دهد هر کدام چگونه مجوز می‌گیرند و اجزا چگونه کنار هم قرار می‌گیرند. فهرست
کامل کنش‌ها در [مرجع مجوزها](/fa/reference/permissions/) آمده است.

| چه کسی | احراز هویت با | مجوزها از کجا می‌آیند | اعمال می‌شود بر |
| --- | --- | --- | --- |
| مدیر | ایمیل و گذرواژه (به‌علاوهٔ عامل دوم یا SSO) | [نقش‌های](#نقشهای-مدیر) او | پنل مدیریت و [Admin API](/fa/api/admin/) |
| فراخوانندهٔ ناشناس | بدون هدر `Authorization` | [دسترسی عمومی](#دسترسی-عمومی) | REST، GraphQL، بلادرنگ |
| سرور یا build | `Authorization: Bearer vd_…` | نوع [توکن API](#توکنهای-api) | REST، GraphQL، بلادرنگ |
| کاربر نهایی واردشده | `Authorization: Bearer <JWT>` | [نقش کاربر نهایی](#کاربران-نهایی) او | REST، GraphQL، بلادرنگ |

همه‌چیز به‌طور پیش‌فرض بسته است: content API تا وقتی دسترسی ندهید با `403` پاسخ می‌دهد، و یک
مدیر فقط کاری را می‌تواند انجام دهد که نقش‌هایش اجازه می‌دهند.

## نقش‌های مدیر

یک مدیر یک یا چند نقش دارد؛ مجوزهای آن‌ها روی هم جمع می‌شوند. سه نقش داخلی وجود دارد:

| نقش | می‌تواند |
| --- | --- |
| **مدیر ارشد** | همه‌چیز، از جمله کاربران، نقش‌ها و توکن‌های API. قابل ویرایش نیست. |
| **Editor** | خواندن، ایجاد، به‌روزرسانی، حذف و انتشار همهٔ محتوا؛ استفاده از کتابخانهٔ رسانه؛ راه‌اندازی استقرارها؛ مدیریت SEO، تغییرمسیرها، منوها و فرم‌ها. |
| **Author** | ایجاد محتوا، و خواندن، به‌روزرسانی و حذف فقط مدخل‌هایی که خودش ساخته است. نمی‌تواند منتشر کند. فایل بارگذاری می‌کند و فقط فایل‌های خودش را ویرایش یا حذف می‌کند. |

نقش‌های دیگر را در **تنظیمات ← نقش‌ها** می‌سازید (مجوز `roles.manage`). آخرین مدیر ارشد فعال
را نمی‌توان غیرفعال، حذف یا تنزل داد، بنابراین نمونه هرگز راه ورود به خودش را نمی‌بندد. یک نقش
همچنین می‌تواند اعضایش را ملزم به راه‌اندازی [تأیید دومرحله‌ای](/fa/guides/auth/two-factor/)
کند: تا وقتی این کار را نکنند، فقط به نمایهٔ خود دسترسی دارند.

### مجوز چیست

یک مجوز یک **کنش**، یک **موضوع** برای کنش‌های محتوا، و **شرط‌های** اختیاری است:

- **کنش‌های محتوا**: `content.read`، `content.create`، `content.update`،
  `content.delete` و `content.publish`، روی یک نوع محتوا (`api::article`) یا روی همهٔ آن‌ها
  (`*`).
- **کنش‌های رسانه**: `media.read`، `media.create`، `media.update` و `media.delete`، برای
  کتابخانهٔ رسانه.
- **کنش‌های تنظیمات**، مانند `users.manage`، `tokens.manage`، `webhooks.manage` یا
  `features.manage`، که صفحه‌های متناظر در **تنظیمات** را باز می‌کنند.
- **شرط‌ها**: `is-creator` یک مجوز محتوا یا رسانه را به چیزی محدود می‌کند که مدیر ساخته است.
  نقش Author این‌گونه کار می‌کند.

شرط‌ها بخشی از کوئری پایگاه داده می‌شوند: فهرستی که با `is-creator` فیلتر شده به‌درستی شمارش و
صفحه‌بندی می‌شود، به جای اینکه ردیف‌ها بعداً پنهان شوند.

### مجوزهای فیلد و زبان

مجوزهای محتوا را می‌توان بیشتر محدود کرد:

- **فیلدها.** `content.read`، `content.create` و `content.update` می‌توانند ویژگی‌هایی را که
  پوشش می‌دهند فهرست کنند. فیلدهای بیرون از فهرست در خواندن پنهان می‌شوند (از جمله در جستجو،
  فیلترها، مرتب‌سازی و مدخل‌های مرتبط) و در نوشتن رد می‌شوند.
- **زبان‌ها.** در [نوع‌های بومی‌سازی‌شده](/fa/concepts/internationalization/)، مجوزهای محتوا
  می‌توانند زبان‌هایی را که پوشش می‌دهند فهرست کنند. نسخه‌های زبان‌های دیگر قابل خواندن یا
  تغییر نیستند.

هر دو برای هر نوع محتوا در ویرایشگر نقش، زیر **فیلدها** و **زبان‌ها** تنظیم می‌شوند.

## Content API

فراخوانندگان content API با مجوزها (grant) بررسی می‌شوند: یک **کنش** روی یک **موضوع**.

| کنش | اجازه می‌دهد |
| --- | --- |
| `find` | فهرست کردن سندها (`GET /api/articles`)، یا خواندن یک نوع تکی. |
| `findOne` | خواندن یک سند (`GET /api/articles/{documentId}`). |
| `create` | `POST` |
| `update` | `PUT` |
| `delete` | `DELETE` |
| `publish` | مسیرهای `actions/publish`، `actions/unpublish` و `actions/discard-draft`. |
| `readDrafts` | خواندن با `status=draft`. |

موضوع‌ها نوع‌های محتوا، کتابخانهٔ رسانه (`plugin::upload`) و حساب‌های کاربران نهایی
(`plugin::users-permissions.user`) هستند، وقتی [کاربران نهایی](/fa/guides/auth/end-users/) روشن
باشد.

چند قاعده برای هر فراخواننده‌ای برقرار است:

- خواندن پیش‌نویس‌ها علاوه بر `find` یا `findOne` به `readDrafts` نیاز دارد. مجوزی که محتوای
  سایت شما را می‌خواند نمی‌تواند به‌طور تصادفی کار منتشرنشده را بخواند.
- populate، فیلتر یا مرتب‌سازی از طریق یک رابطه به دسترسی خواندن روی نوع هدف آن نیاز دارد.
- فیلدهای `private` هرگز برگردانده نمی‌شوند، مجوزها هر چه باشند.
- یک نوشتن سند نوشته‌شده را حتی بدون `find` برمی‌گرداند، مانند Strapi.
- همین مجوزها بر [GraphQL](/fa/api/graphql/) و [جریان بلادرنگ](/fa/api/realtime/) اعمال
  می‌شوند.

### دسترسی عمومی

درخواست‌های بدون هدر `Authorization` مجوزهای **تنظیمات ← دسترسی عمومی** را می‌گیرند. به‌طور
پیش‌فرض هیچ مجوزی داده نشده است. انتخاب‌های معمول `find` و `findOne` روی نوع‌هایی است که سایت
شما نشان می‌دهد.

### توکن‌های API

توکن‌های API برای سرورها، گام‌های build و اسکریپت‌ها هستند. آن‌ها را در
**تنظیمات ← توکن‌های API** بسازید (مجوز `tokens.manage`):

| نوع | مجوزها |
| --- | --- |
| **فقط‌خواندنی** | `find` و `findOne` روی همهٔ نوع‌ها. هرگز پیش‌نویس‌ها. |
| **دسترسی کامل** | همهٔ کنش‌ها روی همهٔ نوع‌ها، از جمله پیش‌نویس‌ها. |
| **سفارشی** | مجوزهایی که انتخاب می‌کنید، مانند دسترسی عمومی. |

- یک توکن با `vd_` شروع می‌شود. کلید محرمانهٔ آن یک بار، هنگام ساخت یا بازتولید، نشان داده
  می‌شود؛ Verdin فقط یک هش کلیددار از آن را ذخیره می‌کند.
- توکن‌ها ممکن است منقضی شوند. یک توکن ناشناخته، منقضی یا بدشکل `401` است: هرگز به دسترسی
  عمومی برنمی‌گردد.
- هر توکن معتبری می‌تواند سند OpenAPI را در `/api/_openapi.json` بخواند، مگر اینکه مستندات را
  عمومی کنید.

برای ساخت و چرخش توکن‌ها نگاه کنید به [توکن‌های API](/fa/guides/auth/api-tokens/).

### کاربران نهایی

کاربران نهایی افرادی هستند که وارد سایت یا اپلیکیشن شما می‌شوند، مانند افزونهٔ
users-permissions در Strapi. این قابلیت به‌طور پیش‌فرض خاموش است. هر حساب یک نقش دارد:

- **Public** نقش درخواست‌های بدون توکن است: مجوزهای آن همان مجوزهای
  **تنظیمات ← دسترسی عمومی** است.
- **Authenticated** به‌طور پیش‌فرض به حساب‌های جدید داده می‌شود.
- نقش‌های سفارشی هر مجموعه‌ای از مجوزها را، با همان کنش‌های بالا، نگه می‌دارند.

یک کاربر نهایی JWTی را که هنگام ورود گرفته به شکل `Authorization: Bearer <jwt>` می‌فرستد.
Verdin آن را با پیشوند `vd_` از توکن‌های API تشخیص می‌دهد. نگاه کنید به
[کاربران نهایی](/fa/guides/auth/end-users/).

## مقایسه با Strapi

مدل از Strapi v5 پیروی می‌کند: RBAC مدیران با شرط‌های `is-creator`، و یک content API با دسترسی
عمومی، توکن‌های API و نقش‌های users-permissions. تفاوت‌ها:

- همهٔ قابلیت‌ها برای همهٔ پروژه‌ها در دسترس‌اند: نقش‌های سفارشی، مجوزهای فیلد و زبان،
  [SSO](/fa/guides/auth/sso/) و [گزارش‌های حسابرسی](/fa/guides/content/audit-logs/).
- خواندن پیش‌نویس‌ها از طریق content API مجوز جداگانهٔ خودش را دارد، `readDrafts`.
- انتشار از طریق REST مجوز جداگانهٔ خودش، `publish`، و مسیرهای خودش را دارد.

Verdin تغییرات محتوا و رسانه را همان لحظه که commit می‌شوند، از طریق
[Server-Sent Events](https://developer.mozilla.org/docs/Web/API/Server-sent_events) (SSE) پخش می‌کند.
هر مشترک فقط رویدادهای مربوط به چیزهایی را دریافت می‌کند که اجازهٔ خواندنشان را دارد. این صفحه
پروتکل را شرح می‌دهد؛ برای استفاده از آن در فرانت‌اند، [به‌روزرسانی‌های بلادرنگ](/fa/guides/frontend/realtime/) را ببینید.

## فعال‌سازی

قابلیت بلادرنگ به‌طور پیش‌فرض خاموش است. آن را در **تنظیمات ← قابلیت‌ها ← بلادرنگ** روشن کنید (مجوز
`features.manage`). تا وقتی خاموش است، نقطه‌های پایانی پاسخ `404` می‌دهند.

## جریان محتوا

```
GET /api/_events
GET /api/_events?types=api::article,api::category
```

| پارامتر | توضیح |
| --- | --- |
| `types` | اختیاری، UIDهای نوع محتوا جداشده با ویرگول؛ `plugin::upload` کتابخانهٔ رسانه است. شکل Strapi یعنی `api::article.article` هم کار می‌کند. بدون آن، همهٔ نوع‌هایی را که اجازهٔ خواندنشان را دارید دریافت می‌کنید. |

احراز هویت مانند REST API است: یک توکن API یا JWT یک کاربر نهایی در
`Authorization: Bearer …`، یا بدون هدر برای دسترسی عمومی. یک توکن نامعتبر پیش از باز شدن
جریان پاسخ `401` می‌گیرد.

```sh title="Terminal"
curl -N -H "Authorization: Bearer $VERDIN_TOKEN" \
  'https://cms.example.com/api/_events?types=api::article'
```

```text
event: ready
data: {}

event: entry.publish
data: {"event":"entry.publish","uid":"api::article","documentId":"k2m7q4dx8n5t1v3b9c0e6a2wfr","locale":"en"}

event: media.create
data: {"event":"media.create","uid":"plugin::upload","documentId":"v3k9…","fileId":5}
```

## پیام‌ها

نخستین رویداد همیشه `ready` است. پس از آن هر تغییر یک رویداد SSE به نام همان تغییر است که
`data` آن یک شیء JSON است:

| فیلد | وجود دارد | توضیح |
| --- | --- | --- |
| `event` | همیشه | نام رویداد، همان‌طور که در خط `event:` در SSE آمده است. |
| `uid` | همیشه | UID نوع محتوا، یا `plugin::upload` برای رسانه. |
| `documentId` | همیشه | سند یا فایلی که تغییر کرده است. |
| `locale` | نوع‌های بومی‌سازی‌شده | زبانِ نسخه‌ای که تغییر کرده است. |
| `fileId` | رویدادهای رسانه | شناسهٔ عددی فایل، همان‌طور که در فیلدهای رسانه به کار می‌رود. |
| `actorId` | جریان مدیریت | مدیری که تغییر را انجام داده، وقتی تغییر را یک مدیر انجام داده باشد. |

| رویدادها | زمان ارسال | دریافت‌کنندگان |
| --- | --- | --- |
| `entry.create`، `entry.update`، `entry.discard-draft` | سندی ساخته یا ذخیره شود، یا پیش‌نویس آن دور ریخته شود | در نوع‌های دارای پیش‌نویس و انتشار، فراخوانندگانی که `readDrafts` دارند (این رویدادها فقط پیش‌نویس‌ها را تغییر می‌دهند). در نوع‌های دیگر، فراخوانندگانی که `find` یا `findOne` دارند. |
| `entry.publish`، `entry.unpublish`، `entry.delete` | سندی منتشر شود، از انتشار خارج شود یا حذف شود | فراخوانندگانی که روی آن نوع `find` یا `findOne` دارند |
| `media.create`، `media.update`، `media.delete` | فایلی بارگذاری، ویرایش یا حذف شود | فراخوانندگانی که روی کتابخانهٔ رسانه `find` یا `findOne` دارند |

رویدادها شناسه‌ها را حمل می‌کنند، نه محتوا را. برای خواندن سند یا فایل، آن را با REST یا GraphQL API
و با مجوزهای معمول فراخواننده دریافت کنید. رویدادها از همهٔ APIها می‌آیند: REST، GraphQL، پنل
مدیریت، بسته‌های انتشار و افزونه‌ها.

## طول عمر اتصال

- سرور هر 15 ثانیه یک کامنت keep-alive می‌فرستد.
- یک جریان محتوا پس از یک ساعت پایان می‌یابد. دوباره وصل شوید (`EventSource` مرورگرها این کار
  را خودش انجام می‌دهد)؛ این کار توکن را هم دوباره بررسی می‌کند.
- رویدادی به نام `lagged` با `data: {"missed": 12}` یعنی کلاینت بیش از حد کند خوانده و
  همین تعداد رویداد از دست رفته است. آنچه کلاینت نشان می‌دهد را دوباره دریافت کنید.
- بازپخش وجود ندارد: رویدادهایی که هنگام قطع بودن کلاینت رخ می‌دهند، بعداً فرستاده نمی‌شوند.

`EventSource` مرورگرها نمی‌تواند هدر `Authorization` بفرستد. برای دسترسی عمومی همان‌طور که هست
کار می‌کند؛ با توکن، از `fetch` با خوانندهٔ بدنهٔ جریانی استفاده کنید، یا از یک کلاینت SSE که
از هدرها پشتیبانی می‌کند.

## جریان مدیریت

پنل مدیریت با توکن دسترسی مدیر، جریان مخصوص خودش را باز می‌کند:

```
GET /admin/api/events?types=api::article
```

این جریان همان رویدادهای محتوا و رسانه را برای نوع‌هایی که مدیر اجازهٔ خواندنشان را دارد (با
`content.read` و `media.read`)، به‌همراه پیش‌نویس‌ها، حمل می‌کند و افزون بر آن:

- `actorId` در تغییراتی که مدیران انجام می‌دهند؛
- رویدادهای `presence` (پایین‌تر)؛
- `comment.create`، `comment.update`، `comment.delete`، `comment.resolve`،
  `comment.reopen`، `task.create`، `task.update` و `task.delete`، با `uid`،
  `documentId` و `locale` مدخل.

یک جریان مدیریت پس از 15 دقیقه پایان می‌یابد، یعنی طول عمر یک توکن دسترسی: با یک توکن تازه
دوباره وصل شوید.

### حضور

ویرایشگر مدخل به سرور می‌گوید چه کسی روی یک مدخل است:

```
POST /admin/api/presence
{ "uid": "api::article", "documentId": "k2m7q4…", "locale": "en", "editing": true }
```

- تا وقتی ویرایشگر باز است، آن را تقریباً هر 20 ثانیه بفرستید. `editing: true` یعنی مدیر
  تغییرات ذخیره‌نشده دارد. وقتی ویرایشگر بسته می‌شود، `"leave": true` را بفرستید.
- یک حضور 45 ثانیه پس از آخرین heartbeat منقضی می‌شود.
- پاسخ فهرست کسانی را که روی مدخل هستند برمی‌گرداند: `{ "data": [{ "userId": 3, "name": "Ada Lovelace", "editing": true, "holdsLock": true }] }`.
- `GET /admin/api/presence?uid=&documentId=&locale=` همان فهرست را می‌خواند.
- وقتی فهرست تغییر می‌کند، جریان‌های مدیریت یک رویداد `presence` با `uid`،
  `documentId` و `locale` مدخل و فهرست در `presence` دریافت می‌کنند.

نخستین مدیری که هنوز در حال ویرایش است، یک قفل نرم (`holdsLock`) در دست دارد. ویرایشگر آن را
به دیگران نشان می‌دهد، اما جلوی ذخیره کردن آن‌ها را نمی‌گیرد. خواندن حضور به `content.read` روی
آن نوع نیاز دارد.

## چند نمونه

رویدادها و حضور، مربوط به همان نمونه‌ای هستند که کلاینت به آن وصل است. پشت یک load
balancer، مسیرهای `/api/_events` و `/admin/api/events` را با sticky session مسیریابی کنید، یا
کلاینت‌های بلادرنگ را روی یک نمونه اجرا کنید. [مقیاس‌پذیری](/fa/deploy/scaling/) را ببینید.

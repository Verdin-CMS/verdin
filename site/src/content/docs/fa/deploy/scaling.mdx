Verdin وضعیت خود را در پایگاه داده نگه می‌دارد، بنابراین می‌توانید چند نمونه از یک
پروژه را برای دسترس‌پذیری یا تحمل بار پشت یک load balancer اجرا کنید. این صفحه فهرست می‌کند
نمونه‌ها چه چیزهایی را به اشتراک می‌گذارند، هر کدام چه چیزی را برای خود نگه می‌دارد، و چه تنظیماتی اهمیت دارند.

## چک‌لیست

- **یک پایگاه دادهٔ مشترک.** PostgreSQL، MySQL یا MariaDB. SQLite فایلی روی یک ماشین است
  و با چند نمونه کار نمی‌کند.
- **پیکربندی یکسان در همه‌جا.** همهٔ نمونه‌ها از همان `verdin.toml`،
  فایل‌های طرح‌واره و کلیدهای محرمانه (`VERDIN_ADMIN_JWT_SECRET`، `VERDIN_TOKEN_PEPPER`،
  `VERDIN_SSO_<ID>_SECRET`…) استفاده می‌کنند. با کلیدهای محرمانهٔ متفاوت، نشست‌ها و توکن‌های API ساخته‌شده در
  یک نمونه توسط نمونه‌های دیگر رد می‌شوند.
- **حالت تولید.** `verdin start` را اجرا کنید، نه `verdin dev`. طرح‌واره را در
  محیط توسعه تغییر دهید، آن را commit کنید، و در هر استقرار یک بار مهاجرت دهید.
- **ذخیره‌سازی رسانهٔ مشترک.** از ارائه‌دهندهٔ S3 استفاده کنید (`[upload] provider = { name = "s3", … }`)،
  یا برای ارائه‌دهندهٔ محلی همان volume را روی همهٔ نمونه‌ها mount کنید.
- **بررسی‌های سلامت.** load balancer را به `GET /_ready` هدایت کنید که وقتی
  پایگاه داده در دسترس نیست `503` پاسخ می‌دهد. `GET /_health` فقط می‌گوید فرایند بالا است؛ از آن برای
  liveness استفاده کنید.
- **کارهای افزونه‌ها روی یک نمونه.** `[plugins].run_jobs = false` را روی همهٔ نمونه‌ها به‌جز
  یکی تنظیم کنید؛ وگرنه هر نمونه کارهای زمان‌بندی‌شده را اجرا می‌کند.
- **متریک‌ها برای هر نمونه.** با `[metrics].enabled = true`، هر نمونه `/_metrics` خودش را
  ارائه می‌کند؛ از هر کدام scrape کنید.

## مهاجرت‌ها با چند نمونه

اجرای هم‌زمان `verdin start --migrate` روی همهٔ نمونه‌ها امن است. هر اجرای مهاجرت
یک قفل در پایگاه داده نگه می‌دارد (یک advisory lock در PostgreSQL، `GET_LOCK` در MySQL و
MariaDB، با حداکثر 60 ثانیه انتظار)، بنابراین نخستین نمونه گام‌ها را اعمال می‌کند و
بقیه پایگاه داده را به‌روز می‌یابند.

در یک rolling deploy، نمونه‌های نسخهٔ قدیمی تا مدتی روی پایگاه دادهٔ
مهاجرت‌داده‌شده به کار ادامه می‌دهند. گام‌های امن جدول می‌سازند، ستون‌های nullable یا دارای مقدار پیش‌فرض
و ایندکس اضافه می‌کنند، ستون‌های متنی را پهن‌تر می‌کنند یا مقادیر enum اضافه می‌کنند، که نسخهٔ قدیمی
متوجه آن‌ها نمی‌شود. گام‌های پرخطر یا مخرب (`verdin migrate apply --allow
risky|destructive`) را در یک استقرار جداگانه اعمال کنید، وقتی هیچ نمونه‌ای از طرح‌وارهٔ قدیمی دیگر به
آن داده‌ها نیاز ندارد. بخش [مهاجرت طرح‌واره](/fa/concepts/schema-migrations/) را ببینید.

## آنچه به اشتراک گذاشته می‌شود

| چه چیزی | چگونه |
| --- | --- |
| نشست‌های مدیر، توکن‌های API، مجوزها | در پایگاه داده؛ به sticky session نیازی نیست. |
| کلیدهای قابلیت‌ها، کلیدهای افزونه‌ها، زبان‌ها، گردش‌کارهای بازبینی | در پایگاه داده. هر نمونه آن‌ها را هر `[server].sync_interval_secs` (10 s) دوباره می‌خواند، بنابراین تغییری که در یک نمونه داده می‌شود در همین مدت به بقیه می‌رسد. |
| ارسال‌های وب‌هوک | یک صف در پایگاه داده. هر نمونه پیش از فرستادن یک ارسال آن را رزرو می‌کند، بنابراین هر کدام یک بار فرستاده می‌شود. |
| بسته‌های انتشار زمان‌بندی‌شده | پیش از اجرا در پایگاه داده رزرو می‌شوند، بنابراین هر کدام یک بار اجرا می‌شود. |
| خلاصهٔ روزانه | اجرای هر روز در پایگاه داده رزرو می‌شود، بنابراین مدیران یک ایمیل دریافت می‌کنند. |
| چالش‌های کلید دسترسی (passkey) | چالش‌های مصرف‌شده در پایگاه داده ثبت می‌شوند، بنابراین به هر کدام در کل نمونه‌ها یک بار پاسخ داده می‌شود. |
| پاک‌سازی گزارش‌های حسابرسی | روی همهٔ نمونه‌ها اجرا می‌شود؛ حذف دوبارهٔ ردیف‌های قدیمی بی‌ضرر است. |
| ذخیره‌گاه key-value افزونه‌ها | در پایگاه داده. |

## آنچه در هر نمونه می‌ماند

- **محدودیت‌های نرخ** توسط هر نمونه جداگانه شمرده می‌شوند. با `n` نمونه، یک کلاینت می‌تواند
  تا `n` برابر `[api].public_rate_limit` درخواست در دقیقه بفرستد. اگر به یک محدودیت سراسری نیاز دارید،
  آن را در load balancer اعمال کنید.
- **کش پاسخ‌های ناشناس** (`[api].cache_ttl_secs`). یک نوشتن، کش
  نمونه‌ای را که آن را انجام داده خالی می‌کند؛ بقیه تا منقضی شدن مدخل خود می‌توانند پاسخ قبلی را ارائه کنند.
  TTL را در حد چند ثانیه یا `0` نگه دارید.
- **رویدادهای بلادرنگ و حضور (presence)** مربوط به نمونه‌ای هستند که کلاینت به آن متصل است.
  برای جریان‌های رویداد از sticky session استفاده کنید ([بلادرنگ](/fa/guides/frontend/realtime/) را ببینید).
- **نمایهٔ جستجو** (`[search]`) روی دیسک نمونه قرار دارد و فقط
  نوشتن‌هایی را دنبال می‌کند که همان نمونه انجام می‌دهد. آن را روی یک نمونه فعال کنید و درخواست‌های `_q` را به آنجا بفرستید،
  یا بپذیرید که بقیه عقب می‌مانند تا وقتی با یک پوشهٔ نمایهٔ خالی دوباره راه‌اندازی شوند.
- **تبدیل‌های تصویر** (`[upload.transforms]`) برای هر نمونه جداگانه زیر
  `cache_dir` کش می‌شوند. برای اشتراک آن‌ها یک CDN جلوی `/uploads` قرار دهید.
- **کارهای زمان‌بندی‌شدهٔ افزونه‌ها**: `run_jobs` در بالا را ببینید.

## تنظیمات

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Short-lived when each instance keeps its own cache.
cache_ttl_secs = 5
```

`run_jobs` را برای هر نمونه با `VERDIN_PLUGINS__RUN_JOBS=false` تنظیم کنید.

## اتصال‌های پایگاه داده

هر نمونه تا `[database].pool_max` اتصال (به‌طور پیش‌فرض 10) باز می‌کند.
`instances × pool_max` را زیر حد سرور نگه دارید، با جای کافی برای مهاجرت‌ها، پشتیبان‌گیری و
نگهداری. حد پیش‌فرض PostgreSQL برابر 100 اتصال است.

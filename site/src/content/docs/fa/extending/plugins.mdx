افزونه‌ها بدون تغییر دادن یا ساخت دوبارهٔ سرور، رفتار تازه‌ای به Verdin اضافه می‌کنند. یک افزونه
یک ماژول WebAssembly همراه با یک manifest است که در پوشهٔ `plugins/` پروژه قرار می‌گیرد. این
صفحه توضیح می‌دهد افزونه‌ها چه کارهایی می‌توانند بکنند و چگونه یکی را نصب کنید؛ برای نوشتن یک افزونه،
[آموزش افزونه](/fa/extending/plugin-tutorial/) را دنبال کنید، و جزئیات را در
[مرجع افزونه](/fa/extending/plugin-reference/) بیابید.

## یک افزونه چه کارهایی می‌تواند بکند

| نقطهٔ گسترش | کاربرد |
| --- | --- |
| **هوک‌ها روی نوشتن** | پیش از اینکه یک مدخل ساخته، به‌روزرسانی، منتشر، از انتشار خارج یا حذف شود یا پیش‌نویس آن کنار گذاشته شود، داده را تغییر دهید یا نوشتن را با یک پیام رد کنید. پس از نوشتن، به آن واکنش نشان دهید (لاگ، اطلاع‌رسانی، همگام‌سازی). |
| **مسیرها** | نقطه‌های پایانی HTTP را زیر `/api/plugins/<name>/…` ارائه کنید: یک گیرندهٔ وب‌هوک، یک feed محاسبه‌شده، یک proxy به سرویسی دیگر. |
| **کارهای زمان‌بندی‌شده** | یک تابع را با زمان‌بندی cron (UTC) اجرا کنید. |
| **تابع راه‌اندازی** | یک تابع را هنگام شروع افزونه، روشن شدن آن یا تغییر تنظیماتش اجرا کنید: seed کردن، تنظیم نقش عمومی (`bootstrap` در Strapi). |
| **فیلدهای GraphQL** | فیلدهای `name(args: JSON): JSON` را به `Query` یا `Mutation` اضافه کنید. |
| **ویجت‌های داشبورد** | نوع‌های ویجت را به‌صورت Web Components به داشبورد مدیریت اضافه کنید. |
| **فیلدهای سفارشی** | به ویژگی‌ها یک ویرایشگر سفارشی در پنل مدیریت بدهید (یک انتخابگر رنگ، یک نقشه)، به‌صورت Web Components؛ مقدار به‌صورت یک نوع ویژگی معمولی ذخیره می‌شود. |
| **تنظیمات** | یک فرم تنظیمات تعریف کنید که مدیران آن را در **تنظیمات ← افزونه‌ها** پر می‌کنند. |

یک افزونه محتوا را از طریق همان Document Service (سرویس سند) می‌خواند و می‌نویسد که پنل مدیریت و
API از آن استفاده می‌کنند، بنابراین وب‌هوک‌ها، تاریخچه، مرحله‌های بازبینی و اعتبارسنجی روی نوشتن‌های آن هم اعمال می‌شوند.

<Aside type="note">
افزونه‌های Verdin افزونه‌های Strapi نیستند. افزونه‌های Strapi بسته‌های Node.js با دسترسی کامل
به سرور هستند؛ Verdin هیچ JavaScriptای را روی سرور اجرا نمی‌کند. فیلدهای سفارشی‌ای که در طرح‌واره‌های
Strapi تعریف شده‌اند (ویژگی‌های `customField`) همان‌طور که هستند بارگذاری می‌شوند، و یک افزونهٔ Verdin می‌تواند
ویرایشگر آن‌ها را فراهم کند.
</Aside>

## سندباکس

افزونه‌ها در یک سندباکس WebAssembly اجرا می‌شوند ([Extism](https://extism.org)، روی Wasmtime). یک ماژول
هیچ فایل، سوکت یا اتصال پایگاه دادهٔ مخصوص به خود ندارد. هر کاری که بیرون از
حافظهٔ خودش انجام می‌دهد از طریق چند تابع میزبان انجام می‌شود، و سرور هر فراخوانی را در برابر
**قابلیت‌هایی** (capabilities) که manifest تعریف می‌کند بررسی می‌کند:

| قابلیت | اجازه می‌دهد |
| --- | --- |
| `read` | خواندن مدخل‌های نوع‌های محتوای فهرست‌شده (یا `*`). |
| `write` | ساختن، به‌روزرسانی، انتشار، خارج کردن از انتشار و حذف مدخل‌های نوع‌های فهرست‌شده (و خواندن آن‌ها). |
| `http` | درخواست‌های HTTP به hostهای فهرست‌شده (`api.example.com`، `*.example.com`). |
| `kv` | یک ذخیره‌گاه key-value مخصوص به خود، در پایگاه دادهٔ Verdin. |
| `public_permissions` | خواندن و جایگزین کردن مجوزهای content API نقش عمومی. |

هر فراخوانی محدودیت‌هایی هم دارد: یک محدودیت زمان (به‌طور پیش‌فرض 5 ثانیه) و یک محدودیت حافظه (به‌طور پیش‌فرض 64 MB)،
که در manifest تنظیم می‌شوند. ماژولی که trap کند یا وقتش تمام شود فقط در همان فراخوانی
شکست می‌خورد؛ Verdin در فراخوانی بعدی آن را دوباره می‌سازد.

آنچه سندباکس به‌جای شما تصمیم نمی‌گیرد:

- **مسیرها عمومی هستند.** درخواست‌ها به `/api/plugins/<name>/…` در برابر
  **دسترسی عمومی** یا مجوزهای توکن API بررسی نمی‌شوند. افزونه دریافت می‌کند که چه کسی فراخوانی می‌کند (هر کسی،
  یک توکن API یا یک کاربر نهایی) و باید خودش آن را بررسی کند.
- **هوک‌ها همهٔ نوشتن‌ها روی نوع‌هایشان را می‌بینند**، فارغ از قابلیت `read` افزونه.
- **یک before hook که شکست بخورد جلوی نوشتن را نمی‌گیرد.** اگر ماژول crash کند یا وقتش تمام شود،
  خطا لاگ می‌شود و نوشتن ادامه پیدا می‌کند. فقط یک رد صریح آن را متوقف می‌کند.

## نصب یک افزونه

<Steps>

1. افزونه را در پوشهٔ مخصوص خودش زیر `plugins/`، کنار `verdin.toml` قرار دهید. این پوشه
   manifest، ماژول و، به‌صورت اختیاری، فایل‌های پنل مدیریت را نگه می‌دارد:

   <FileTree>
   - verdin.toml
   - plugins/
     - reading-time/
       - plugin.toml
       - plugin.wasm
       - admin/ اختیاری: Web Components برای پنل مدیریت
         - index.js
   - schema/
   </FileTree>

2. Verdin را دوباره راه‌اندازی کنید. هنگام شروع، همهٔ `plugins/*/plugin.toml` را بارگذاری می‌کند و برای هر کدام
   `plugin found` را در لاگ می‌نویسد. افزونه‌ای که بارگذاری نشود (manifest نامعتبر، ماژول غایب،
   نام تکراری) با ذکر دلیل در **تنظیمات ← افزونه‌ها** فهرست می‌شود.

3. در پنل مدیریت، **تنظیمات ← افزونه‌ها** را باز کنید. آنچه افزونه درخواست می‌کند را زیر
   **دسترسی**، **هوک‌ها**، **مسیرها** و **کارها** بررسی کنید، سپس آن را روشن کنید.

4. اگر افزونه تنظیمات دارد، **تنظیمات** را روی کارت آن باز کنید، آن‌ها را پر کنید و ذخیره کنید.

</Steps>

افزونه‌های نصب‌شده خاموش شروع می‌شوند. روشن و خاموش کردن یک افزونه و ویرایش تنظیمات آن
بلافاصله روی همهٔ نمونه‌ها اثر می‌کند (نمونه‌های دیگر تغییر را در مدت
`[server].sync_interval_secs` دریافت می‌کنند). تغییر در `plugin.toml` یا ماژول به راه‌اندازی دوباره نیاز دارد.

مدیریت افزونه‌ها به مجوز `plugins.manage` (**مدیریت افزونه‌ها**) نیاز دارد. بخش
[مرجع مجوزها](/fa/reference/permissions/) را ببینید.

## پیکربندی `[plugins]`

```toml title="verdin.toml"
[plugins]
path = "plugins"   # directory of plugins, relative to verdin.toml
run_jobs = true    # run scheduled jobs on this instance
```

با چند نمونه، `run_jobs = false` را روی همه به‌جز یکی تنظیم کنید تا هر کار یک بار اجرا شود. بخش
[مرجع پیکربندی](/fa/reference/configuration/) را ببینید.

## راهبری

- **هر بار یک فراخوانی.** هر افزونه یک نمونه دارد و هر بار یک فراخوانی را پردازش می‌کند، بنابراین
  یک مسیر کند، هوک‌های همان افزونه را به تأخیر می‌اندازد. توابع را کوتاه نگه دارید.
- **لاگ‌ها.** آنچه یک افزونه لاگ می‌کند به لاگ سرور و به **تنظیمات ← افزونه‌ها ←
  گزارش‌ها** می‌رود (200 خط آخر، که در حافظه نگه داشته می‌شوند).
- **استقرارها.** افزونه‌ها را همراه پروژه (در ایمیج یا volume) منتشر کنید، مانند
  طرح‌واره. کلیدهای روشن/خاموش و تنظیمات در پایگاه داده نگهداری می‌شوند.

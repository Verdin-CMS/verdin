Пройдіть цей список, перш ніж відкрити проєкт Verdin для реальних користувачів. Кожен пункт
посилається на сторінку з поясненням. Сторінки платформ ([Docker](/uk/deploy/docker/),
[Fly.io](/uk/deploy/fly/), [Render](/uk/deploy/render/), [Railway](/uk/deploy/railway/),
[Kubernetes](/uk/deploy/kubernetes/)) застосовують ці налаштування за вас, де це можливо.

## Запускайте production-сервер

- [ ] **Використовуйте `verdin start`, а не `verdin dev`.** `dev` дозволяє конструктору типів
      вмісту переписувати файли схеми, застосовує міграції після кожної зміни й послаблює
      правила для cookies і вебхуків для локальної роботи. Змінюйте схему в розробці,
      комітьте файли й розгортайте їх.
- [ ] **Застосовуйте міграції під час розгортання.** `verdin start` відмовляється працювати,
      поки база даних відстає від схеми. `verdin start --migrate` спершу застосовує
      *безпечні* кроки, що очікують (це типова команда образу Docker). Ризиковані чи
      деструктивні кроки (зміни типів, нові унікальні обмеження, видалені колонки) потребують
      `verdin migrate apply --allow risky|destructive`, який ви запускаєте один раз. Див.
      [Міграції схеми](/uk/concepts/schema-migrations/).
- [ ] **Постачайте схему разом із сервером.** Монтуйте каталог `schema/` лише для читання
      або вбудовуйте його в образ, щоб працювало саме те, що ви закомітили.

## Секрети

- [ ] **Згенеруйте два обов'язкові секрети один раз** через `verdin secrets` і зберігайте їх у
      сховищі секретів своєї платформи: `VERDIN_ADMIN_JWT_SECRET` підписує токени сесій, а
      `VERDIN_TOKEN_PEPPER` є ключем для хешів API-токенів та інших збережених секретів.
      `verdin start` не запуститься, якщо будь-якого з них немає або він коротший за 32 байти.
      Секрети читаються лише із середовища, ніколи з `verdin.toml`.
- [ ] **Не змінюйте їх.** Зміна `VERDIN_TOKEN_PEPPER` робить недійсними всі API-токени, а
      також коди застосунків-автентифікаторів і коди відновлення адміністраторів. Зміна
      `VERDIN_ADMIN_JWT_SECRET` анулює короткочасні access tokens адміністраторів і кінцевих
      користувачів, відкриті посилання попереднього перегляду та входи через OAuth, що
      тривають (адмін-панель і клієнти з refresh tokens оновлюють їх самі). Усім екземплярам
      проєкту потрібні однакові значення.
- [ ] Інші секрети, які ви використовуєте, теж тримайте в середовищі:
      `VERDIN_EMAIL_SMTP_PASSWORD` або `VERDIN_EMAIL_API_KEY`, `AWS_ACCESS_KEY_ID` /
      `AWS_SECRET_ACCESS_KEY`, `VERDIN_METRICS_TOKEN`, `VERDIN_SSO_<ID>_SECRET`,
      `VERDIN_IMAGE_SECRET`. Повний список — у [довіднику конфігурації](/uk/reference/configuration/).

## База даних

- [ ] **Виберіть рушій.** PostgreSQL (14 або новіший) — звичайний вибір і саме його варто
      брати, якщо ви запускатимете [кілька екземплярів](/uk/deploy/scaling/). MySQL 8.4+ і
      MariaDB 10.11+ працюють так само. SQLite підходить для одного екземпляра з постійним
      диском.
- [ ] **Задайте `VERDIN_DATABASE_URL`**: `postgres://…`, `mysql://…` (MySQL і MariaDB) або
      `sqlite:///data/verdin.db`. Додайте `?sslmode=require` для серверів PostgreSQL, які
      вимагають TLS.
- [ ] **Підберіть розмір пулу.** Кожен екземпляр відкриває до `[database].pool_max` з'єднань
      (10). Тримайте `instances × pool_max` нижче за ліміт з'єднань сервера.

## URL, проксі та cookies

- [ ] **Працюйте через HTTPS.** Verdin говорить звичайним HTTP; термінуйте TLS на зворотному
      проксі, балансувальнику навантаження або на краю вашої платформи.
- [ ] **Задайте `[server].public_url`** (`VERDIN_SERVER__PUBLIC_URL`) — адресу, яку
      використовують браузери, наприклад `https://cms.example.com`. Від неї залежать
      посилання в листах, callbacks SSO, щоденний дайджест і passkeys; passkeys прив'язані до
      її хоста.
- [ ] **Задайте `[server].trusted_proxies`** — адреси ваших зворотних проксі (IP або
      діапазони CIDR). Лише тоді Verdin читає адресу клієнта з `X-Forwarded-For`; без цього
      всі клієнти за проксі мають одну адресу для обмежень частоти й журналів аудиту.
- [ ] **Не вимикайте secure cookies.** У `verdin start` refresh cookie адмінки типово має
      `Secure`. Не задавайте `[admin].secure_cookies`; значення `false` у production
      записує попередження під час запуску.

## API

- [ ] **Дозволяйте лише те, що потрібно публіці.** API вмісту закритий, доки ви не надасте
      публічні дозволи (**Налаштування → Публічний доступ**) або не створите API-токени.
      Див. [Дозволи](/uk/concepts/permissions/).
- [ ] **Задайте `[api].cors_origins`**, якщо браузер з іншого origin викликає API вмісту або
      GraphQL, наприклад `["https://www.example.com"]`. Без цього з браузера їх можуть
      викликати лише сторінки з того самого origin. Admin API ніколи не відповідає на
      cross-origin запити.
- [ ] **Подумайте про обмеження частоти** для анонімного трафіку: `[api].public_rate_limit` і
      `[api].token_rate_limit` (запитів на хвилину; `0`, типове значення, — без обмежень).

## Медіа

- [ ] **Зберігайте завантаження там, де вони переживуть повторне розгортання.** Типовий
      локальний провайдер пише на диск: дайте йому постійний том або використовуйте
      провайдер S3 (AWS S3, Cloudflare R2, Backblaze B2, MinIO, Tigris…). На платформах з
      ефемерними дисками та з кількома екземплярами використовуйте S3. Див. [Медіа](/uk/concepts/media/).

## Пошта

- [ ] **Налаштуйте справжнього провайдера.** Типовий `[email].provider = "log"` пише листи в
      журнал, і `verdin start` попереджає про це. Запрошення, скидання паролів, підтвердження
      кінцевих користувачів, згадки в коментарях і дайджест потребують `smtp`, `resend` або
      `postmark`, а також `[email].from` з адресою, яку приймає ваш провайдер.

## Резервні копії та моніторинг

- [ ] **Регулярно робіть резервні копії бази даних і медіасховища** та спробуйте
      відновлення. Див. [Резервні копії](/uk/deploy/backups/).
- [ ] **Спрямуйте перевірки readiness на `/_ready`**, а перевірки liveness — на `/_health`.
- [ ] **Пишіть журнали в JSON** (`[log].format = "json"`, типово в образі Docker) і збирайте
      standard error.
- [ ] **Збирайте `/_metrics`**, якщо використовуєте Prometheus, з `VERDIN_METRICS_TOKEN`. Див.
      [Моніторинг](/uk/deploy/monitoring/).

## Перед запуском

- [ ] Зареєструйте першого адміністратора самі одразу після першого запуску: доки
      адміністратора немає, будь-хто, хто дістанеться до `/admin/`, може зареєструватися як
      Super Admin. Його також можна створити з командного рядка через
      `verdin admin create --email …`.
- [ ] Перегляньте [модель безпеки](/uk/deploy/security/) й увімкніть
      [двофакторну автентифікацію](/uk/guides/auth/two-factor/) для Super Admin.

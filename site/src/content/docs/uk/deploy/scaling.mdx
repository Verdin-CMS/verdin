Verdin зберігає свій стан у базі даних, тож можна запускати кілька екземплярів того самого
проєкту за балансувальником навантаження для доступності чи розподілу навантаження. На цій
сторінці перелічено, що екземпляри поділяють, що кожен тримає при собі та які налаштування
важливі.

## Чекліст

- **Спільна база даних.** PostgreSQL, MySQL або MariaDB. SQLite — це файл на одній машині, і з
  кількома екземплярами він не працює.
- **Однакова конфігурація всюди.** Кожен екземпляр використовує той самий `verdin.toml`, файли
  схеми й секрети (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). З різними секретами сесії й API-токени, створені на одному
  екземплярі, відхиляються іншими.
- **Production-режим.** Запускайте `verdin start`, а не `verdin dev`. Змінюйте схему в розробці,
  комітьте її й мігруйте один раз на розгортання.
- **Спільне медіасховище.** Використовуйте провайдер S3 (`[upload] provider = { name = "s3", … }`)
  або монтуйте той самий том на кожен екземпляр для локального провайдера.
- **Перевірки стану.** Спрямуйте балансувальник на `GET /_ready`, що відповідає `503`, коли база
  даних недоступна. `GET /_health` лише каже, що процес працює; використовуйте його для
  liveness.
- **Завдання плагінів на одному екземплярі.** Задайте `[plugins].run_jobs = false` на всіх
  екземплярах, крім одного; інакше кожен екземпляр виконуватиме заплановані завдання.
- **Метрики для кожного екземпляра.** З `[metrics].enabled = true` кожен екземпляр віддає
  власний `/_metrics`; збирайте з кожного.

## Міграції з кількома екземплярами

`verdin start --migrate` безпечно запускати на всіх екземплярах одночасно. Кожен запуск
міграції тримає блокування в базі даних (advisory lock у PostgreSQL, `GET_LOCK` у MySQL і
MariaDB, з очікуванням до 60 секунд), тож перший екземпляр застосовує кроки, а інші бачать, що
база даних уже актуальна.

Під час поетапного розгортання екземпляри старої версії ще деякий час працюють із мігрованою
базою даних. Безпечні кроки створюють таблиці, додають колонки, що допускають null або мають
типове значення, та індекси, розширюють текстові колонки чи додають значення enum — стара
версія цього не помічає. Ризиковані чи деструктивні кроки (`verdin migrate apply --allow
risky|destructive`) застосовуйте окремим розгортанням, коли жодному екземпляру старої схеми
вже не потрібні ці дані. Див. [Міграції схеми](/uk/concepts/schema-migrations/).

## Що спільне

| Що | Як |
| --- | --- |
| Сесії адміністраторів, API-токени, дозволи | У базі даних; sticky sessions не потрібні. |
| Перемикачі функцій і плагінів, локалі, процеси перевірки | У базі даних. Кожен екземпляр перечитує їх кожні `[server].sync_interval_secs` (10 с), тож зміна на одному екземплярі доходить до інших у межах цієї затримки. |
| Доставки вебхуків | Черга в базі даних. Екземпляр забирає доставку перед надсиланням, тож кожна надсилається один раз. |
| Заплановані релізи | Забираються в базі даних перед виконанням, тож кожен виконується один раз. |
| Щоденний дайджест | Запуск кожного дня забирається в базі даних, тож адміністратори отримують один лист. |
| Виклики passkey | Використані виклики записуються в базу даних, тож на кожен відповідають один раз на всіх екземплярах. |
| Очищення журналу аудиту | Виконується на кожному екземплярі; повторне видалення старих рядків нешкідливе. |
| Сховище ключ-значення плагінів | У базі даних. |

## Що залишається в кожному екземплярі

- **Обмеження частоти** рахує кожен екземпляр. З `n` екземплярами клієнт може зробити до
  `n` × `[api].public_rate_limit` запитів на хвилину. Якщо потрібен глобальний ліміт,
  забезпечте його на балансувальнику.
- **Кеш анонімних відповідей** (`[api].cache_ttl_secs`). Запис очищає кеш того екземпляра, що
  його зробив; інші можуть віддавати попередню відповідь, доки їхній запис не спливе. Тримайте
  TTL у кілька секунд або `0`.
- **Події реального часу й присутність** належать тому екземпляру, до якого підключено
  клієнта. Використовуйте sticky sessions для потоків подій (див.
  [Реальний час](/uk/guides/frontend/realtime/)).
- **Пошуковий індекс** (`[search]`) живе на диску екземпляра й відстежує лише записи цього
  екземпляра. Увімкніть його на одному екземплярі й спрямовуйте туди запити `_q` або змиріться з
  тим, що інші відстають, доки не перезапустяться з порожнім каталогом індексу.
- **Трансформації зображень** (`[upload.transforms]`) кешуються окремо на кожному екземплярі в
  `cache_dir`. Поставте CDN перед `/uploads`, щоб їх поділяти.
- **Заплановані завдання плагінів**: див. `run_jobs` вище.

## Налаштування

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Short-lived when each instance keeps its own cache.
cache_ttl_secs = 5
```

Задавайте `run_jobs` для кожного екземпляра через `VERDIN_PLUGINS__RUN_JOBS=false`.

## З'єднання з базою даних

Кожен екземпляр відкриває до `[database].pool_max` з'єднань (типово 10). Тримайте
`instances × pool_max` нижче за ліміт сервера, із запасом для міграцій, резервних копій і
обслуговування. Типовий ліміт PostgreSQL — 100 з'єднань.

Verdin зберігає свій стан у базі даних, тож можна запускати кілька екземплярів того самого
проєкту за балансувальником навантаження для доступності чи розподілу навантаження. На цій
сторінці перелічено, що екземпляри поділяють, що кожен тримає при собі та які налаштування
важливі.

## Чекліст

- **Спільна база даних.** PostgreSQL, MySQL або MariaDB. SQLite — це файл на одній машині, і з
  кількома екземплярами він не працює.
- **Однакова конфігурація всюди.** Кожен екземпляр використовує той самий `verdin.toml`, файли
  схеми й секрети (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). З різними секретами сесії й API-токени, створені на одному
  екземплярі, відхиляються іншими.
- **Production-режим.** Запускайте `verdin start`, а не `verdin dev`. Змінюйте схему в розробці,
  комітьте її й мігруйте один раз на розгортання.
- **Спільне медіасховище.** Використовуйте провайдер S3 (`[upload] provider = { name = "s3", … }`)
  або монтуйте той самий том на кожен екземпляр для локального провайдера.
- **Перевірки стану.** Спрямуйте балансувальник на `GET /_ready`, що відповідає `503`, коли база
  даних недоступна. `GET /_health` лише каже, що процес працює; використовуйте його для
  liveness.
- **Спільна шина подій.** Задайте `[cluster].bus = "database"` на кожному екземплярі, щоб події
  реального часу, присутність, інвалідація кешу й оновлення пошуку доходили до всіх (див.
  [Спільна шина подій](#спільна-шина-подій)).
- **Завдання плагінів на одному екземплярі.** Задайте `[plugins].run_jobs = false` на всіх
  екземплярах, крім одного; інакше кожен екземпляр виконуватиме заплановані завдання.
- **Метрики для кожного екземпляра.** З `[metrics].enabled = true` кожен екземпляр віддає
  власний `/_metrics`; збирайте з кожного.

## Міграції з кількома екземплярами

`verdin start --migrate` безпечно запускати на всіх екземплярах одночасно. Кожен запуск
міграції тримає блокування в базі даних (advisory lock у PostgreSQL, `GET_LOCK` у MySQL і
MariaDB, з очікуванням до 60 секунд), тож перший екземпляр застосовує кроки, а інші бачать, що
база даних уже актуальна.

Під час поетапного розгортання екземпляри старої версії ще деякий час працюють із мігрованою
базою даних. Безпечні кроки створюють таблиці, додають колонки, що допускають null або мають
типове значення, та індекси, розширюють текстові колонки чи додають значення enum — стара
версія цього не помічає. Ризиковані чи деструктивні кроки (`verdin migrate apply --allow
risky|destructive`) застосовуйте окремим розгортанням, коли жодному екземпляру старої схеми
вже не потрібні ці дані. Див. [Міграції схеми](/uk/concepts/schema-migrations/).

## Що спільне

| Що | Як |
| --- | --- |
| Сесії адміністраторів, API-токени, дозволи | У базі даних; sticky sessions не потрібні. |
| Перемикачі функцій і плагінів, локалі, процеси перевірки | У базі даних. Кожен екземпляр перечитує їх кожні `[server].sync_interval_secs` (10 с), тож зміна на одному екземплярі доходить до інших у межах цієї затримки. |
| Доставки вебхуків | Черга в базі даних. Екземпляр забирає доставку перед надсиланням, тож кожна надсилається один раз. |
| Заплановані релізи | Забираються в базі даних перед виконанням, тож кожен виконується один раз. |
| Щоденний дайджест | Запуск кожного дня забирається в базі даних, тож адміністратори отримують один лист. |
| Виклики passkey | Використані виклики записуються в базу даних, тож на кожен відповідають один раз на всіх екземплярах. |
| Очищення журналу аудиту | Виконується на кожному екземплярі; повторне видалення старих рядків нешкідливе. |
| Сховище ключ-значення плагінів | У базі даних. |
| Події реального часу, присутність і м'які блокування | Зі [шиною подій](#спільна-шина-подій): клієнт, підключений до будь-якого екземпляра, отримує події всіх і бачить кожного адміністратора на записі. |
| Кеш анонімних відповідей | З шиною подій запис на будь-якому екземплярі очищає кеш кожного екземпляра. |
| Пошуковий індекс | З шиною подій кожен екземпляр перечитує й індексує записи, які змінюють інші. |
| Трансформовані зображення | З шиною подій змінений або видалений файл зникає з кешу трансформацій кожного екземпляра. |

## Що залишається в кожному екземплярі

- **Обмеження частоти** рахує кожен екземпляр. З `n` екземплярами клієнт може зробити до
  `n` × `[api].public_rate_limit` запитів на хвилину. Якщо потрібен глобальний ліміт,
  забезпечте його на балансувальнику.
- **Без шини подій** (`[cluster].bus = "none"`, типово) події реального часу й присутність
  належать тому екземпляру, до якого підключено клієнта (використовуйте sticky sessions для
  потоків подій), запис очищає лише кеш відповідей власного екземпляра (тримайте
  `[api].cache_ttl_secs` у кілька секунд або `0`), а пошуковий індекс відстежує лише записи
  свого екземпляра.
- **Пошуковий індекс** (`[search]`) живе на диску кожного екземпляра. З шиною подій екземпляри
  індексують зміни один одного одразу; екземпляр, що стартує з порожнім каталогом індексу,
  будує його з бази даних. Зміни, зроблені, поки екземпляр не працював, потрапляють до його
  індексу під час перебудови індексу: видаліть каталог перед запуском або перебудуйте після
  розгортання.
- **Трансформації зображень** (`[upload.transforms]`) кешуються окремо на кожному екземплярі в
  `cache_dir`. Поставте CDN перед `/uploads`, щоб їх поділяти.
- **Заплановані завдання плагінів**: див. `run_jobs` вище.

## Спільна шина подій

Дещо відбувається в пам'яті: потоки реального часу, хто редагує який запис, кеш анонімних
відповідей, пошуковий індекс. Шина подій переносить їх з екземпляра, де вони сталися, до
інших.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Або `VERDIN_CLUSTER__BUS=database`, на кожному екземплярі. Шина використовує базу даних
проєкту, тож не потребує жодного іншого сервісу:

- **PostgreSQL**: екземпляр записує кожну подію в таблицю `vd_cluster_events` і будить інших
  через `NOTIFY`. Кожен екземпляр тримає одне з'єднання свого пулу для `LISTEN`. Сповіщення
  лише називає відправника, тож події будь-якого розміру вкладаються в ліміт PostgreSQL у 8000
  байтів. Якщо з'єднання обривається, екземпляр перепідключається й читає таблицю, щоб
  надолужити. Він також читає таблицю кожні 30 секунд на випадок втраченого сповіщення.
- **MySQL, MariaDB і SQLite**: кожен екземпляр читає нові рядки `vd_cluster_events` кожні
  `poll_interval_ms` (типово 1000). Запит використовує первинний ключ, тож читання порожньої
  таблиці коштує мало. Зменшіть інтервал для швидших оновлень; зміна одного екземпляра
  доходить до інших упродовж інтервалу.

Що подорожує: записи вмісту (до потоків реального часу, кешу відповідей і пошукового індексу,
який знову читає змінений запис), зміни медіа (потоки, кеш, кеш трансформацій), сигнали
присутності та сповіщення про коментарі й завдання для адмінки. Кожен екземпляр ігнорує власні
події. Вебхуки, очищення CDN, історія, журнали аудиту й хуки плагінів не подорожують: екземпляр,
що зробив зміну, виконує їх один раз.

Рядки видаляються через 10 хвилин. Новий екземпляр стартує з наступної події, а не з попередніх.
Екземпляр, що не встигає або втрачає з'єднання з базою даних, відкидає події, а не затримує
запис. Метрика `verdin_cluster_events_total` рахує надіслані, отримані й відкинуті події (див.
[Моніторинг](/uk/deploy/monitoring/#метрики-prometheus)).

Кожен екземпляр називає себе на шині випадковим id під час кожного запуску або значенням
`[cluster].instance_id`, якщо ви його задали (наприклад, назва пода). Id лише розрізняє
екземпляри; більше нічого від нього не залежить.

З одним екземпляром залишайте `bus` як `none`: події лишаються в пам'яті, і нічого не
записується.

Бекендів Redis і NATS поки що немає. Шина на базі даних покриває кожну підтримувану базу даних
без жодного додаткового сервісу.

## Налаштування

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Задавайте `run_jobs` для кожного екземпляра через `VERDIN_PLUGINS__RUN_JOBS=false`.

## З'єднання з базою даних

Кожен екземпляр відкриває до `[database].pool_max` з'єднань (типово 10). Тримайте
`instances × pool_max` нижче за ліміт сервера, із запасом для міграцій, резервних копій і
обслуговування. Типовий ліміт PostgreSQL — 100 з'єднань. У PostgreSQL шина подій тримає одне з
з'єднань кожного екземпляра для `LISTEN`.

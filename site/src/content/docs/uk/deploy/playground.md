[`deploy/playground/`](https://github.com/verdin-cms/verdin/tree/main/deploy/playground)
збирає контейнер для публічної демонстрації: [приклад блогу](https://github.com/verdin-cms/verdin/tree/main/examples/blog)
на SQLite з кількома опублікованими статтями й демо-обліковим записом, з яким можуть увійти
відвідувачі. Щогодини він викидає базу даних і починає заново. Контейнеру не потрібні ні том,
ні сервер бази даних, ні секрети від вас. Де його розмістити — вирішуєте ви; підійде будь-яка
платформа, що запускає один контейнер із публічною адресою HTTPS.

Скрипти запускали проти локальної збірки 2026-09-30 (три цикли скидання); образ зібрано, але
не запускали з опублікованого релізу.

## Що отримують відвідувачі

- Адмін-панель на `/admin/` з входом як **demo@example.com** / **verdin-demo-1234**. Обліковий
  запис має роль **Editor**: може створювати, редагувати, публікувати й видаляти вміст та
  завантажувати медіа, але не може керувати користувачами, ролями, API-токенами, вебхуками чи
  налаштуваннями.
- Публічний доступ на читання статей, категорій, тегів і домашньої сторінки через REST
  (`/api/articles?populate=*`) і GraphQL.
- Дві опубліковані статті, чернетка, дві категорії, два теги й домашня сторінка.

Super Admin теж існує, з випадковим паролем, якого ніхто не знає.

## Як це працює

`run.sh` виконує цикл:

1. Видаляє `/var/lib/verdin-playground` (база даних, завантаження, пошуковий індекс, кеш
   зображень) і генерує нові секрети, тож сесії минулого циклу завершуються.
2. Запускає `verdin start --migrate` і чекає на `/_ready`.
3. Запускає `seed.sh`: створює облікові записи через CLI та admin API, відкриває публічний
   доступ на читання й створює вміст.
4. Чекає `PLAYGROUND_RESET_SECONDS` (3600), зупиняє сервер і починає заново. Якщо сервер
   зупиняється сам, він одразу починає заново.

Конфігурація (`deploy/playground/verdin.toml`) обмежує завантаження до 2 MB, обмежує частоту
анонімних запитів до 300 на хвилину з однієї адреси, не допускає доставок вебхуків на приватні
адреси й вмикає пошук.

## Збірка та запуск

З кореня репозиторію:

```sh frame="terminal"
docker build -f deploy/playground/Dockerfile -t verdin-playground .
docker run -p 1337:1337 --tmpfs /var/lib/verdin-playground:uid=65532,gid=65532 verdin-playground
```

Образ — це Alpine з `curl` і `jq` (скриптам потрібна оболонка, якої в офіційному образі немає) і
статичним бінарником, скопійованим з `ghcr.io/verdin-cms/verdin`. Передайте
`--build-arg VERDIN_IMAGE=ghcr.io/verdin-cms/verdin:<version>`, щоб вибрати реліз. `tmpfs`
тримає дані в пам'яті; без нього дані живуть у файловій системі контейнера, що теж працює.

| Змінна | Типово | Що |
| --- | --- | --- |
| `PLAYGROUND_RESET_SECONDS` | `3600` | Час між скиданнями. |
| `PLAYGROUND_EMAIL`, `PLAYGROUND_PASSWORD` | `demo@example.com`, `verdin-demo-1234` | Демо-обліковий запис. |
| `VERDIN_SERVER__PUBLIC_URL` | | Публічна адреса пісочниці. |
| `VERDIN_SERVER__TRUSTED_PROXIES` | | Діапазон проксі платформи, щоб обмеження частоти діяли для кожного відвідувача окремо. |

## Розміщення

Запускайте рівно один екземпляр (база даних локальна), тримайте його запущеним (без
масштабування до нуля: таймер скидання живе в процесі) і поставте перед ним HTTPS: cookie сесії
адмін-панелі в режимі `start` має `Secure`, тож для входу потрібен HTTPS. Будь-хто може писати
вміст і завантажувати зображення до години, тож на сторінці, що посилається на пісочницю,
вкажіть розклад скидання й тримайте екземпляр на домені, окремому від усього, що ділить cookies.

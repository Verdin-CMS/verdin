Процес перевірки — це впорядкований список етапів, як-от *To do*, *In review* і *Ready*, через
які проходять записи певних типів вмісту перед публікацією. У цьому посібнику ви налаштуєте
процес, переміщатимете й призначатимете записи та побачите відповідний admin API.

У Strapi процеси перевірки — функція Enterprise. У Verdin вони є частиною ядра з відкритим
кодом.

## Перш ніж почати

- Увімкніть **Налаштування → Функції → Процеси перевірки**. Типово їх вимкнено.
- Налаштування процесів потребує **Керування процесами перевірки** (`workflows.manage`).
- Переміщення й призначення запису потребує доступу на оновлення до нього. Див.
  [Дозволи](/uk/reference/permissions/).

## Створіть процес

<Steps>

1. Відкрийте **Налаштування → Процеси перевірки** і виберіть **Новий процес**.
2. Дайте йому **Назва**.
3. У розділі **Типи вмісту** виберіть типи, записи яких ідуть цим процесом. Тип іде
   щонайбільше одним процесом.
4. У розділі **Етапи** перелічіть етапи по порядку. Кожен має **Назва етапу** і **Колір**.
   Використовуйте **Додати етап**, щоб додати ще, і кнопки зі стрілками, щоб змінити порядок.
   Нові записи починають із першого етапу.
5. За бажання виберіть для етапу **Ролі, які можуть переміщати записи на цей етап**. Якщо
   роль не вибрано, це може будь-хто, хто може оновлювати запис.
6. За бажання задайте **Етап, необхідний для публікації**. Тоді записи можна публікувати лише
   тоді, коли вони на цьому етапі. **Будь-який етап** не впливає на публікацію.
7. Збережіть.

</Steps>

Записи, що існували до того, як їхній тип приєднався до процесу, перебувають на першому
етапі.

Коли ви пізніше змінюєте процес:

- Видалення етапу повертає його записи на перший етап.
- Видалення типу вмісту з процесу скидає етапи його записів.
- Видалення процесу скидає етапи й виконавців його записів.

## Переміщення й призначення записів

Редактор запису показує панель **Перевірка** з **Етап** і **Виконавець**.

- Виберіть інший **Етап**, щоб перемістити запис. Етапи, зарезервовані для інших ролей, вибрати
  не можна, і панель про це повідомляє. Адміністратори з **Керування процесами перевірки**
  завжди можуть переміщати записи.
- Виберіть **Виконавець** серед активних адміністраторів, які можуть читати тип вмісту, або
  виберіть **Прибрати виконавця**. Призначати запис може будь-хто, хто може його оновлювати.
- Коли процес має обов'язковий етап, панель показує, якого етапу має досягти запис, перш ніж
  **Опублікувати** спрацює.

Вигляд списку показує стовпець **Етап**, а домашня сторінка перелічує призначені вам записи в
розділі **Призначено мені**. Локалізовані типи зберігають етап для кожної локалі.

## Що блокує етап публікації

Обов'язковий етап діє для всіх способів публікації: адмін-панелі, REST, GraphQL, релізів і
плагінів. Публікація запису поза цим етапом не вдається з `400`:

```text
the entry must be in the review stage `Ready` to be published
```

У Strapi вимога етапу діє лише в адмін-панелі. Ролі етапів теж відрізняються: у Verdin вони
обмежують, хто переміщує записи *на* етап.

## Журнали аудиту й вебхуки

- Зміни етапів і призначення записуються в [журнали аудиту](/uk/guides/content/audit-logs/) як
  `entry.stage` і `entry.assign`.
- Вебхуки можуть підписатися на **Етап запису змінено** (`review-workflows.updateEntryStage`).
  Див. [Вебхуки](/uk/guides/integrations/webhooks/).

## Admin API

Усі маршрути розташовані під `/admin/api` і приймають access token адміністратора.

| Маршрут | Дозвіл | Що робить |
| --- | --- | --- |
| `GET /review-workflows`, `GET /review-workflows/{id}` | `workflows.manage` | Процеси з їхніми етапами. |
| `POST /review-workflows`, `PUT /review-workflows/{id}` | `workflows.manage` | Створити або замінити процес (тіло нижче). |
| `DELETE /review-workflows/{id}` | `workflows.manage` | Записи його типів втрачають етапи. |
| `GET /content/{uid}/{documentId}/review?locale=` | читання запису | Етап, виконавець і етапи, на які ви можете перемістити запис (`canMoveTo`). |
| `PUT /content/{uid}/{documentId}/review?locale=` | оновлення запису | `{ "stageId": 3, "assigneeId": 7 }`. Обидва поля необов'язкові; `"assigneeId": null` прибирає виконавця. |
| `GET /content/{uid}/review?documentIds=a,b` | читання типу | Етапи до 200 записів, із процесом у `meta.workflow`. |
| `GET /review/assigned` | виконано вхід | Записи, призначені вам. |
| `GET /review/assignees?uid=` | оновлення типу | Активні адміністратори, які можуть читати тип. |
| `GET /review/roles` | `workflows.manage` | Коди й назви ролей для ролей етапів. |

Процес у форматі для `POST` і `PUT`:

```json
{
  "name": "Editorial",
  "contentTypes": ["api::article"],
  "stages": [
    { "id": 1, "name": "To do", "color": "#4945ff" },
    { "id": 2, "name": "In review", "color": "#ff8800" },
    { "name": "Ready", "color": "#2f9e44", "roles": ["editor"] }
  ],
  "publishStage": "Ready"
}
```

- Процес має від 1 до 50 етапів з унікальними назвами й кольорами `#rrggbb`.
- `publishStage` називає один з етапів; пропустіть його, якщо обов'язкового етапу немає.
- Надсилайте наявні етапи з їхнім `id`, щоб їхні записи лишалися на місці. Етапи без `id` —
  нові.

<Aside type="note">
Вимкнення функції приховує етапи й припиняє застосування етапу публікації. Процеси та етапи
записів зберігаються до повторного ввімкнення.
</Aside>

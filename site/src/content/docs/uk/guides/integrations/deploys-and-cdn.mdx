Два інструменти для сайтів, що кешують те, що віддає Verdin:

- **Розгортання** додає кнопку **Розгорнути** в шапку адмінки. Вона викликає build hook вашого
  сайту (Netlify, Vercel, Cloudflare Pages або будь-який CI), а провайдер повідомляє, як іде
  збірка.
- **Очищення CDN** позначає відповіді API вмісту тегами за типом вмісту й очищає ці теги в
  Cloudflare, Fastly чи на вашому власному ендпоінті, коли вміст публічно змінюється.

Обидва є частиною ядра: перемикача функції немає. Розгортання налаштовується в
**Налаштування → Розгортання**, CDN — у `verdin.toml`.

## Розгортання

  P-->>V: callback: ready (url)

### Додайте ціль

<Steps>

1. У свого провайдера створіть build hook для сайту й скопіюйте його URL (Netlify: **Build
   hooks**; Vercel: **Deploy Hooks**; Cloudflare Pages: **Deploy hooks**; CI: будь-яка URL,
   що запускає pipeline за `POST`).
2. У Verdin перейдіть до **Налаштування → Розгортання** і виберіть **Додати ціль**.
3. Дайте їй **Назва** (наприклад, **Продакшн-сайт**) і вставте **URL вебхука збірки**.
4. Збережіть. URL хука — секрет: відтепер показується лише його хост. Щоб спрямувати ціль на
   інший хук, використовуйте **Замінити URL**.

</Steps>

Адміністратори, які можуть розгортати, тепер бачать **Розгорнути** в шапці. З кількома цілями
вона відкриває меню **Розгорнути на**. Після підтвердження Verdin надсилає:

```http
POST <build hook URL>
content-type: application/json

{ "trigger": "verdin", "triggeredBy": "editor@example.com" }
```

Ціль розгортається щонайбільше раз на 10 секунд, тож подвійне клацання не запускає дві збірки.
Запит спливає за тайм-аутом через 15 секунд і не переходить за перенаправленнями. Хук, що
відповідає чимось, крім `2xx`, записується як **Відхилено**.

### Повідомлення про стан збірки

Без зворотного виклику розгортання лишається в стані **Запущено**. Щоб бачити в адмінці
**Збірка**, **Готово** і **Помилка**, а також посилання на розгорнутий сайт, дайте провайдерові
URL зворотного виклику цілі: натисніть кнопку **URL зворотного виклику** цілі й скопіюйте його.

<Tabs syncKey="deploy-provider">
<TabItem label="Netlify">

У **Site configuration → Build & deploy → Deploy notifications** додайте вихідний вебхук для
**Deploy started**, **Deploy succeeded** і **Deploy failed** з URL зворотного виклику.

</TabItem>
<TabItem label="Vercel">

У **Team settings → Webhooks** створіть вебхук для подій `deployment.created`,
`deployment.succeeded` і `deployment.error` з URL зворотного виклику.

</TabItem>
<TabItem label="Інший CI">

Надішліть `POST` із JSON, що містить `status` (`building`, `ready` або `error`) і, за
бажання, розгорнуту `url` та `message`:

```sh title="Terminal"
curl -X POST "$VERDIN_CALLBACK_URL" -H 'content-type: application/json' \
  -d '{ "status": "ready", "url": "https://www.example.com" }'
```

</TabItem>
</Tabs>

Verdin розуміє `state` Netlify, `type` Vercel і простий `status` та оновлює останнє
розгортання цілі. Він відповідає `204` або `404`, коли URL неправильна. URL зворотного виклику
має вигляд `{public_url}{admin path}/api/deploy/callback/{id}/{secret}`, тож задайте
[`[server].public_url`](/uk/reference/configuration/) — адресу, до якої можуть дістатися
провайдери.

<Aside type="caution">
URL зворотного виклику містить секрет: будь-хто, хто його має, може повідомляти стани
розгортання для цієї цілі. Запускати розгортання чи щось читати він не може.
</Aside>

**Історія розгортань** показує останні 50 розгортань, найновіші зверху, з ціллю, часом
початку, статусом, HTTP-статусом хука й повідомленням провайдера. Видалення цілі видаляє її
історію, але не build hook.

### Дозволи

| Дозвіл | Дозволяє |
| --- | --- |
| **Запуск розгортань** (`deploy.trigger`) | Кнопку **Розгорнути** в шапці. Його має вбудована роль Editor. |
| **Керування цілями розгортання та CDN** (`deploy.manage`) | **Налаштування → Розгортання**: цілі, URL зворотного виклику й очищення CDN. |

Див. [Дозволи](/uk/reference/permissions/). URL build hook підпорядковуються тим самим правилам
адрес, що й [вебхуки](/uk/guides/integrations/webhooks/): з `verdin start` вони не можуть
вказувати на приватні мережі, якщо цього не дозволяє
[`[webhooks].allow_private_networks`](/uk/reference/configuration/).

### Розгортання після кожної зміни

Кнопка підходить сайтам, що перезбираються на вимогу. Щоб перезбирати після кожної публікації,
створіть [вебхук](/uk/guides/integrations/webhooks/) для `entry.publish` і `entry.unpublish` з
build hook як URL. Для запланованої групи змін опублікуйте їх через
[реліз](/uk/guides/content/releases/) і прив'яжіть вебхук до `releases.publish`.

## Очищення CDN

Коли CDN кешує API вмісту, він віддає застарілий вміст, доки кеш не спливе. Із заданим `[cdn]`
Verdin позначає свої відповіді тегами й очищає потрібні теги, коли вміст змінюється, тож
кешувати можна надовго.

### Як працюють теги

Кожен успішний `GET` API вмісту містить `vd` (усе), `vd-<singularName>` (тип вмісту) і тег
кожного типу, який можуть заповнити його документи через populate: цілі зв'язків, зокрема
всередині компонентів і динамічних зон, з урахуванням їхніх власних зв'язків. Для статей
прикладу блогу, в обох форматах заголовків:

```http
Cache-Tag: vd,vd-article,vd-category,vd-tag
Surrogate-Key: vd vd-article vd-category vd-tag
```

Тип із поліморфним зв'язком може дістатися будь-якого типу, тож його відповіді містять теги
всіх типів.

Cloudflare читає `Cache-Tag`, Fastly — `Surrogate-Key`. Коли вміст публічно змінюється, Verdin
очищає тег типу:

- під час публікації, зняття з публікації чи видалення запису;
- під час будь-якого запису в тип без чернеток і публікації (його записи одразу публічні).

Збереження чернетки нічого не очищає, бо чернетки публічно не віддаються. Зміни протягом
секунди (`debounce_ms`) збираються в одне очищення, а невдале очищення повторюється двічі.

### Налаштування

<Tabs syncKey="cdn">
<TabItem label="Cloudflare">

```toml title="verdin.toml"
[cdn]
provider = "cloudflare"
zone_id = "023e105f4ecef8ad9ca31a8372d0c353"
```

`VERDIN_CDN_TOKEN` — це API-токен із дозволом **Cache Purge** для зони.

</TabItem>
<TabItem label="Fastly">

```toml title="verdin.toml"
[cdn]
provider = "fastly"
service_id = "SU1Z0isxPaozGVKXdv0eY"
```

`VERDIN_CDN_TOKEN` — це API-токен Fastly з правом очищати сервіс.

</TabItem>
<TabItem label="Webhook">

```toml title="verdin.toml"
[cdn]
provider = "webhook"
url = "https://purge.example.com/verdin"
```

Verdin надсилає `POST { "tags": ["vd-article"] }` з `Authorization: Bearer <VERDIN_CDN_TOKEN>`,
якщо токен задано. Використовуйте це для іншого CDN, зворотного проксі чи API ревалідації
вашого фреймворку.

</TabItem>
</Tabs>

```sh title="Terminal"
export VERDIN_CDN_TOKEN=...
```

Verdin перевіряє розділ під час запуску й відмовляється працювати без `zone_id`, `service_id`,
`url` чи токена, потрібних провайдерові. Див. [`[cdn]`](/uk/reference/configuration/).

Що кешувати, однаково вирішує ваш CDN: налаштуйте правило кешу для шляхів API (наприклад,
`/api/*` для анонімних `GET`) з довгим edge TTL. Не кешуйте автентифіковані запити, читання
попереднього перегляду й `/api/_events`.

### Перевірка й ручне очищення

Розділ **CDN** у **Налаштування → Розгортання** показує провайдера й **Останні очищення**
(**Очищено** або **Помилка**, з тегами). **Очистити все** скидає кожну відповідь із тегом `vd`.

Оскільки відповіді містять теги типів, які вони можуть заповнити, перейменування категорії
також очищає кешовані списки статей, що могли б її містити, незалежно від того, чи запит просив
`populate`.

Власний кеш Verdin у пам'яті ([`[api].cache_ttl_secs`](/uk/reference/configuration/)) — окрема
річ: він очищається під час кожної зміни.

API-токени дають вашим сайтам, застосункам і скриптам змогу викликати API вмісту з ширшим
доступом, ніж має публіка. У цьому посібнику ви створите токен, виберете його доступ,
використаєте його й заміните, якщо він витече. Токени працюють як API-токени Strapi.

Типово API вмісту закритий: без токена запити отримують лише те, що дозволяє
**Налаштування → Публічний доступ**, а це нічого, доки ви не надасте доступ.

## Перш ніж почати

- Керування токенами потребує **Керування API-токенами** (`tokens.manage`). Див.
  [Дозволи](/uk/reference/permissions/).
- `VERDIN_TOKEN_PEPPER` має бути задано; див. [Де важливий pepper](#де-важливий-pepper).

## Створіть токен

<Steps>

1. Відкрийте **Налаштування → API-токени** і виберіть **Створити токен**.
2. Введіть **Назва** і, за бажання, **Опис**.
3. Виберіть **Тип**:

   | Тип | Дозволяє |
   | --- | --- |
   | **Лише читання** | «Знайти» та «Знайти один» для всіх типів вмісту, лише опубліковані версії. |
   | **Повний доступ** | Усі дії для всіх типів вмісту й медіатеки. |
   | **Налаштовуваний** | Лише дії, які ви позначите в **Дозволи**. |

4. Виберіть, коли він **Спливає**: **Ніколи** або через 7, 30 чи 90 днів.
5. Для налаштовуваного токена позначте дії в розділі **Дозволи** для кожного типу вмісту:
   **Знайти**, **Знайти один**, **Створити**, **Оновити**, **Видалити**, **Опублікувати** і
   **Читати чернетки**. Рядок **Медіатека** стосується завантажень, а рядок **Користувачі** —
   маршрутів `/api/users` [кінцевих користувачів](/uk/guides/auth/end-users/).
6. Виберіть **Створити**, а потім скопіюйте токен. Він показується лише цього разу.

</Steps>

Токени починаються з `vd_`. Список показує перші символи кожного, коли його востаннє
використовували і коли він спливає.

## Використання токена

Надсилайте його як bearer-токен:

<Tabs syncKey="api">
<TabItem label="REST">

```sh title="Terminal"
curl -H "Authorization: Bearer $VERDIN_TOKEN" 'http://localhost:1337/api/articles?status=draft'
```

</TabItem>
<TabItem label="GraphQL">

```sh title="Terminal"
curl -X POST http://localhost:1337/graphql \
  -H "Authorization: Bearer $VERDIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"query":"{ articles { documentId title } }"}'
```

</TabItem>
<TabItem label="TypeScript">

```ts
import { createClient } from '@verdin/client';
import type { VerdinSchema } from './verdin-types';

const verdin = createClient<VerdinSchema>({
  url: 'http://localhost:1337',
  token: process.env.VERDIN_TOKEN,
});
```

</TabItem>
</Tabs>

- Доступ токена замінює публічний доступ, а не додається до нього. Налаштовуваний токен без
  **Знайти** для типу не може переглядати його список, навіть якщо публіка може.
- Читання чернеток (`?status=draft`) потребує **Читати чернетки**; токени лише для читання
  ніколи не бачать чернеток.
- Невідомі й прострочені токени отримують `401`. Дії поза доступом токена отримують `403`.
- `[api].token_rate_limit` обмежує запити на токен за хвилину (типово вимкнено).
- Ті самі токени авторизують GraphQL і [MCP-сервер](/uk/guides/integrations/mcp/).

<Aside type="caution">
Токен у браузері бачить кожен відвідувач. Використовуйте токени лише із серверів, кроків збірки
й приватних застосунків; для публічних сторінок надайте потрібне в
**Налаштування → Публічний доступ**.
</Aside>

## Перегенерація або видалення токена

- **Перегенерувати** в рядку токена створює новий ключ із тією самою назвою, типом і
  дозволами. Поточний ключ одразу перестає працювати, тож застосунки, що його використовують,
  отримуватимуть помилки, доки ви їх не оновите.
- **Видалити** видаляє токен; клієнти, що ним користуються, втрачають доступ.

Робіть одне з двох, щойно токен міг витекти.

## Де важливий pepper

Verdin ніколи не зберігає токени. Він зберігає хеш із ключем (HMAC-SHA256) кожного з них, з
ключем `VERDIN_TOKEN_PEPPER`, тож сама лише копія бази даних не дає змоги ними скористатися.
Той самий pepper захищає:

- API-токени.
- Секрети автентифікаторів і коди відновлення адміністраторів ([двофакторна
  автентифікація](/uk/guides/auth/two-factor/)).
- Хешовані IP-адреси, збережені разом із надісланими формами.

Згенеруйте pepper один раз через `verdin secrets`, не тримайте його у `verdin.toml` і
резервних копіях бази даних і давайте кожному екземпляру однакове значення.

<Aside type="caution" title="Зміна pepper">
З іншим pepper перестають працювати всі API-токени, а також застосунки-автентифікатори й коди
відновлення всіх адміністраторів. Змінюйте його, лише якщо він витік, а потім створіть нові
токени й скиньте двофакторну автентифікацію кожного адміністратора. Passkeys і паролі це не
зачіпає.
</Aside>

## Admin API

Усі маршрути розташовані під `/admin/api` і потребують `tokens.manage`.

```http
GET    /admin/api/api-tokens?page=1&pageSize=25
POST   /admin/api/api-tokens                  { "name": "Website", "kind": "custom", "expiresInDays": 90,
                                                "permissions": [{ "subject": "api::article", "action": "find" }] }
GET    /admin/api/api-tokens/{id}
PUT    /admin/api/api-tokens/{id}             { "name": "…", "description": null, "kind": "read-only", "permissions": [...] }
POST   /admin/api/api-tokens/{id}/regenerate
DELETE /admin/api/api-tokens/{id}
```

- `kind` — це `read-only`, `full-access` або `custom`; `expiresInDays` необов'язковий (без
  нього токен не спливає), і змінити його пізніше не можна.
- `permissions` перелічує пари `{ subject, action }`. `subject` — це uid типу вмісту,
  `plugin::upload` (медіатека) або `plugin::users-permissions.user`; `action` — це `find`,
  `findOne`, `create`, `update`, `delete`, `publish` або `readDrafts`. `publish` і `readDrafts`
  не застосовуються до двох останніх суб'єктів.
- `POST /api-tokens` і `/regenerate` повертають ключ один раз як `accessKey`.

Публічний доступ використовує ті самі пари: `PUT /admin/api/public-permissions`
`{ "permissions": [...] }`, що потребує **Керування ролями** (`roles.manage`).

Кінцеві користувачі — це люди, які входять на ваш сайт або в застосунок, а не в адмін-панель.
Verdin дає їм реєстрацію, вхід, підтвердження ел. пошти, скидання пароля, провайдерів OAuth і
ролі, які визначають, що вони можуть робити в API вмісту. Маршрути й payload — ті самі, що в
плагіні users-permissions Strapi v5, тож наявні фронтенди працюють і далі.

## Перш ніж почати

<Steps>

1. Увімкніть **Налаштування → Функції → Користувачі та права** (типово вимкнено) або ввімкніть
   **Кінцеві користувачі** в **Налаштування → Кінцеві користувачі → Налаштування**.
2. Налаштуйте `[email]`, якщо використовуєте підтвердження ел. пошти чи скидання пароля:

   ```toml title="verdin.toml"
   [email]
   provider = "smtp"          # log (default), smtp, resend or postmark
   from = "My site <no-reply@example.com>"

   [email.smtp]
   host = "smtp.example.com"
   port = 587
   username = "apikey"        # password in VERDIN_EMAIL_SMTP_PASSWORD
   ```

   Resend і Postmark читають свій ключ з `VERDIN_EMAIL_API_KEY`. **Налаштування → Функції →
   Ел. пошта** має **Надіслати тестовий лист**. Для локальної роботи `docker/compose.dev.yml`
   містить Mailpit (SMTP на порту 1025, поштова скринька на `http://localhost:8025`).

3. Задайте `[server].public_url`: його використовують посилання в листах і callbacks OAuth.

</Steps>

Керування обліковими записами й ролями потребує **Керування кінцевими користувачами**
(`endusers.manage`). Зміна вкладки налаштувань (реєстрація, провайдери, шаблони) потребує
**Керування функціями** (`features.manage`).

## Налаштуйте реєстрацію та сесії

У **Налаштування → Кінцеві користувачі → Налаштування**, у розділі **Реєстрація та сесії**:

| Налаштування | Типово | Дія |
| --- | --- | --- |
| **Дозволити реєстрацію** | увімкнено | Будь-хто може створити обліковий запис через API вмісту. Вимкнено: `register` відповідає `400`. |
| **Підтверджувати адреси ел. пошти** | вимкнено | Нові користувачі мають відкрити надіслане посилання, перш ніж зможуть увійти. |
| **Типова роль** | Authenticated | Роль нових облікових записів. |
| **Сесії** | Один довготривалий токен | **Один довготривалий токен** (застарілий режим Strapi) або **Короткі токени з оновленням**. |
| **Тривалість сесії (днів)** | 30 | Термін дії довготривалого токена. |
| **Термін дії токена доступу (хвилин)**, **Термін дії токена оновлення (днів)** | 30, 30 | З токенами оновлення. |

У розділі **Сторінки вашого застосунку** задайте **Після підтвердження ел. пошти** (куди
потрапляють користувачі після підтвердження адреси) і **Сторінка скидання пароля** (ваша
сторінка, що отримує `?code=` і просить новий пароль). Скидання пароля потребує сторінки
скидання.

## Налаштуйте ролі

Кожен запит виконується від імені однієї з ролей:

- **Public**: запити без токена. Її дозволи — це дозволи з **Налаштування → Публічний доступ**.
- **Authenticated**: вбудована роль, яка надається новим обліковим записам. Її не можна
  видалити.
- **Власні ролі**: створюйте їх у **Налаштування → Кінцеві користувачі → Ролі** через
  **Створити роль**.

**Дозволи** ролі використовують ту саму матрицю, що й публічний доступ та API-токени:
**Знайти**, **Знайти один**, **Створити**, **Оновити**, **Видалити**, **Опублікувати** і
**Читати чернетки** для кожного типу вмісту, **Медіатека** та **Користувачі** (маршрути
`/api/users`). Користувач, що увійшов, отримує лише дозволи своєї ролі, а не ще й публічний
доступ: надайте публічні дозволи на читання й ролі, якщо вони потрібні користувачам, що
увійшли. Видалення ролі переносить її користувачів в Authenticated.

Щоб діяти від імені користувача, фронтенд надсилає його JWT як `Authorization: Bearer <jwt>`.
API-токени починаються з `vd_`, і саме так Verdin їх розрізняє.

## Реєстрація та вхід

<Tabs>
<TabItem label="Реєстрація">

```sh title="Terminal"
curl -X POST http://localhost:1337/api/auth/local/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"ana","email":"ana@example.com","password":"a long password"}'
# → { "jwt": "…", "user": { "id": 1, "username": "ana", … } }
#   або { "user": … }, коли ввімкнено підтвердження ел. пошти
```

</TabItem>
<TabItem label="Вхід">

```sh title="Terminal"
curl -X POST http://localhost:1337/api/auth/local \
  -H 'Content-Type: application/json' \
  -d '{"identifier":"ana@example.com","password":"a long password"}'
# → { "jwt": "…", "user": {…} }
```

`identifier` — це ел. пошта або ім'я користувача.

</TabItem>
<TabItem label="Читання від імені користувача">

```sh title="Terminal"
curl -H "Authorization: Bearer $JWT" http://localhost:1337/api/users/me
curl -H "Authorization: Bearer $JWT" http://localhost:1337/api/articles
```

</TabItem>
</Tabs>

Вхід відхиляється для заблокованих користувачів («Your account has been blocked by an
administrator») і, коли ввімкнено підтвердження, для непідтверджених («Your account email is
not confirmed»).

## Токени й сесії

- **Один довготривалий токен** (`jwtManagement: "legacy-support"`): JWT діє
  **Тривалість сесії (днів)**.
- **Короткі токени з оновленням** (`jwtManagement: "refresh"`, як у Strapi 5): JWT діє
  **Термін дії токена доступу (хвилин)**, а відповіді на вхід також містять `refreshToken`.
  Викличте `POST /api/auth/refresh` з `{ refreshToken }`, щоб отримати нову пару. Кожен refresh
  token спрацьовує один раз; пред'явлення вже використаного завершує всю сесію.
  `POST /api/auth/logout` з `{ refreshToken }` завершує її навмисно.
- Зміна чи скидання пароля відкликає попередні токени користувача, як і блокування
  користувача.
- Запити входу, реєстрації й скидання обмежено 20 на хвилину для кожної IP-адреси клієнта.
- Паролі зберігаються з Argon2id. Облікові записи, імпортовані зі Strapi, зберігають свій хеш
  bcrypt до наступного входу, коли його буде перехешовано.

## Підтвердження ел. пошти й скидання паролів

Коли **Підтверджувати адреси ел. пошти** ввімкнено, реєстрація надсилає посилання на
`/api/auth/email-confirmation?confirmation=…`. Його відкриття підтверджує обліковий запис і
перенаправляє на **Після підтвердження ел. пошти**. `POST /api/auth/send-email-confirmation` з
`{ email }` надсилає нове посилання.

Для забутого пароля:

<Steps>

1. Ваш застосунок викликає `POST /api/auth/forgot-password` з `{ email }`. Відповідь однакова
   незалежно від того, чи існує обліковий запис.
2. Користувач отримує лист із посиланням на вашу **Сторінка скидання пароля** з `?code=…`. Код
   діє годину.
3. Ваша сторінка викликає `POST /api/auth/reset-password` з
   `{ code, password, passwordConfirmation }` і отримує `{ jwt, user }`.

</Steps>

Користувачі, що увійшли, змінюють пароль через `POST /api/auth/change-password`
(`{ currentPassword, password, passwordConfirmation }`).

Листи редагуються в **Налаштування → Кінцеві користувачі → Налаштування → Шаблони листів**:
**Тема**, **Повідомлення** і необов'язкове **Тіло HTML (необов’язково)** для
**Підтвердження ел. пошти** і **Скидання пароля**. Вони приймають заповнювачі `{{username}}`,
`{{email}}` і `{{url}}`; у тілі HTML значення екрануються.

## Вхід через провайдерів OAuth

Є вбудовані шаблони для GitHub, Google, Microsoft, Discord, Facebook, GitLab і LinkedIn.
Будь-яка інша назва — це загальний провайдер OAuth 2, якому потрібні **URL авторизації**,
**URL токена** і **URL відомостей про користувача**: Keycloak, Auth0 і Okta працюють саме
так, з URL вашого realm чи tenant. Sign in with Apple не підтримується.

<Steps>

1. У **Налаштування → Кінцеві користувачі → Налаштування → Провайдери входу** виберіть
   **Додати GitHub** (або інший шаблон, або **Додати провайдера OAuth 2**).
2. У провайдера зареєструйте **URL зворотного виклику для реєстрації у провайдера**, показаний
   у діалозі: `https://cms.example.com/api/connect/github/callback`.
3. Введіть **ID клієнта**, необов'язкові **Області доступу** і **Переспрямування до вашого
   застосунку** — сторінку вашого фронтенду, що отримує `?access_token=` після входу.
   Увімкніть **Увімкнено**.
4. Покладіть секрет клієнта в середовище сервера й перезапустіть його:

   ```sh title=".env"
   VERDIN_OAUTH_GITHUB_SECRET=…
   ```

   Змінна називається `VERDIN_OAUTH_<PROVIDER>_SECRET`. Секрети ніколи не зберігаються в базі
   даних.

</Steps>

Вхід відбувається за схемою Strapi:

<Diagram
  caption="Вхід кінцевих користувачів через OAuth"
  code={`sequenceDiagram
  participant B as Браузер
  participant V as Verdin
  participant P as Провайдер
  B->>V: GET /api/connect/github
  V-->>B: перенаправлення до провайдера
  B->>P: згода
  P-->>B: перенаправлення на /api/connect/github/callback
  B->>V: callback
  V-->>B: перенаправлення на вашу сторінку ?access_token=…
  B->>V: GET /api/auth/github/callback?access_token=…
  V-->>B: { jwt, user }`}
/>

OAuth `state` підписаний і прив'язаний до браузера через cookie. Облікові записи
зіставляються за ел. поштою; адреса, яку вже використовує інший провайдер або обліковий запис
з ел. поштою й паролем, відхиляється («Email is already taken.»).

## Керування обліковими записами в адмін-панелі

**Налаштування → Кінцеві користувачі → Користувачі** показує облікові записи з пошуком за
ім'ям користувача чи ел. поштою. Можна **Додати користувача**, відредагувати обліковий запис
(ім'я користувача, ел. пошта, пароль, роль, **Підтверджено**, **Заблоковано**),
**Заблокувати** чи **Розблокувати** його та видалити.

## Маршрути

Маршрути розташовані під префіксом API вмісту, типово `/api`. Формат запитів і відповідей
відповідає Strapi v5.

| Маршрут | Що робить |
| --- | --- |
| `POST /auth/local/register` | `{ username, email, password }` → `{ jwt, user }` або `{ user }`, коли ввімкнено підтвердження ел. пошти. |
| `POST /auth/local` | `{ identifier, password }` → `{ jwt, user }`. |
| `GET /auth/email-confirmation?confirmation=` | Підтверджує ел. пошту, потім перенаправляє або повертає користувача. |
| `POST /auth/send-email-confirmation` | `{ email }`: нове посилання для підтвердження. |
| `POST /auth/forgot-password` | `{ email }`: надсилає поштою посилання для скидання. |
| `POST /auth/reset-password` | `{ code, password, passwordConfirmation }` → `{ jwt, user }`. |
| `POST /auth/change-password` | Потрібен вхід. `{ currentPassword, password, passwordConfirmation }` → `{ jwt, user }`. |
| `POST /auth/refresh`, `POST /auth/logout` | Лише в режимі оновлення: `{ refreshToken }`. |
| `GET /users/me` | Користувач, що увійшов. |
| `GET /users`, `GET /users/count`, `GET /users/{id}` | Потребує «Знайти» / «Знайти один» для «Користувачі». Звичайний JSON без обгортки `data`, як у Strapi. `populate=role` додає роль, `_q=` шукає за іменами користувачів і адресами, `pagination[page]` і `pagination[pageSize]` (щонайбільше 100) гортають сторінки. |
| `POST /users`, `PUT /users/{id}`, `DELETE /users/{id}` | Потребує «Створити» / «Оновити» / «Видалити» для «Користувачі». `{ username, email, password, confirmed, blocked, role }`, де `role` — id ролі. |
| `GET /connect/{provider}` | Починає вхід через OAuth. |
| `GET /auth/{provider}/callback?access_token=` | Обмінює токен провайдера на `{ jwt, user }`. |

`verdin import strapi` переносить кінцевих користувачів разом із паролями, власними ролями та
дозволами ролей public, authenticated і власних. Див. [Міграція зі Strapi](/uk/migrate/from-strapi/).

<Aside type="caution">
Роль із «Створити», «Оновити» чи «Видалити» для **Користувачі** дає своїм учасникам змогу
керувати обліковими записами всіх кінцевих користувачів. Надавайте її лише довіреним ролям або
API-токенам.
</Aside>

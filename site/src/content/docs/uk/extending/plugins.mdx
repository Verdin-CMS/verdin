Плагіни додають поведінку до Verdin без зміни чи перезбирання сервера. Плагін — це модуль
WebAssembly з маніфестом, покладений у каталог `plugins/` проєкту. На цій сторінці пояснено,
що можуть плагіни і як встановити плагін; щоб написати власний, пройдіть
[посібник із плагінів](/uk/extending/plugin-tutorial/), а подробиці шукайте в
[довіднику плагінів](/uk/extending/plugin-reference/).

## Що може плагін

| Точка розширення | Для чого |
| --- | --- |
| **Хуки на запис** | Перед створенням, оновленням, публікацією, зняттям з публікації, видаленням запису або відкиданням його чернетки — змінити дані чи відхилити запис із повідомленням. Після запису — відреагувати на нього (журнал, сповіщення, синхронізація). |
| **Маршрути** | Обслуговувати HTTP-ендпоінти в `/api/plugins/<name>/…`: приймач вебхуків, обчислюваний фід, проксі до іншого сервісу. |
| **Заплановані завдання** | Запускати функцію за розкладом cron (UTC). |
| **Функція запуску** | Запускати функцію, коли плагін стартує, вмикається або змінюються його налаштування: початкове наповнення, налаштування публічної ролі (`bootstrap` у Strapi). |
| **Поля GraphQL** | Додавати поля `name(args: JSON): JSON` до `Query` або `Mutation`. |
| **Віджети панелі** | Додавати типи віджетів на панель адмінки як Web Components. |
| **Власні поля** | Давати атрибутам власний редактор в адмінці (вибір кольору, мапа) як Web Components; значення зберігається як звичайний тип атрибута. |
| **Налаштування** | Оголошувати форму налаштувань, яку адміністратори заповнюють у **Налаштування → Плагіни**. |

Плагін читає й записує вміст через той самий Document Service, що й адмінка та API, тож
вебхуки, історія, етапи перевірки й валідація застосовуються до його записів.

<Aside type="note">
Плагіни Verdin — не плагіни Strapi. Плагіни Strapi — це пакети Node.js з повним доступом до
сервера; Verdin не запускає JavaScript на сервері. Власні поля, оголошені в схемах Strapi
(атрибути `customField`), завантажуються як є, а плагін Verdin може надати для них редактор.
</Aside>

## Пісочниця

Плагіни працюють у пісочниці WebAssembly ([Extism](https://extism.org) на Wasmtime). Модуль не
має власних файлів, сокетів чи з'єднання з базою даних. Усе, що він робить поза власною
пам'яттю, проходить через кілька функцій хоста, а сервер перевіряє кожен виклик за
**можливостями**, оголошеними в маніфесті:

| Можливість | Надає |
| --- | --- |
| `read` | Читання записів перелічених типів вмісту (або `*`). |
| `write` | Створення, оновлення, публікацію, зняття з публікації та видалення записів перелічених типів (і їх читання). |
| `http` | HTTP-запити до перелічених хостів (`api.example.com`, `*.example.com`). |
| `kv` | Власне сховище ключ-значення в базі даних Verdin. |
| `public_permissions` | Читання й заміна дозволів публічної ролі для API вмісту. |

Кожен виклик також має обмеження: за часом (типово 5 секунд) і за пам'яттю (типово 64 МБ),
задані в маніфесті. Модуль, що падає (trap) або вичерпує час, ламає лише цей виклик; Verdin
перестворює його під час наступного виклику.

Чого пісочниця за вас не вирішує:

- **Маршрути публічні.** Запити до `/api/plugins/<name>/…` не перевіряються за
  **Публічний доступ** чи дозволами API-токенів. Плагін отримує інформацію про те, хто
  викликає (будь-хто, API-токен або кінцевий користувач), і має це перевіряти.
- **Хуки бачать усі записи в свої типи**, незалежно від можливості `read` плагіна.
- **Хук before, що падає, не блокує запис.** Якщо модуль аварійно завершується або
  перевищує час, помилка записується в журнал, а запис продовжується. Зупиняє його лише явна
  відмова.

## Встановлення плагіна

<Steps>

1. Покладіть плагін в окремий каталог у `plugins/`, поруч із `verdin.toml`. Він містить
   маніфест, модуль і, за бажання, файли для адмін-панелі:

   <FileTree>
   - verdin.toml
   - plugins/
     - reading-time/
       - plugin.toml
       - plugin.wasm
       - admin/ необов'язково: Web Components для адмін-панелі
         - index.js
   - schema/
   </FileTree>

2. Перезапустіть Verdin. Він завантажує кожен `plugins/*/plugin.toml` під час запуску й пише
   `plugin found` для кожного. Плагін, який не вдалося завантажити (некоректний маніфест,
   відсутній модуль, дубльована назва), показується в **Налаштування → Плагіни** з причиною.

3. В адмін-панелі відкрийте **Налаштування → Плагіни**. Перегляньте, що плагін просить, у
   розділах **Доступ**, **Хуки**, **Маршрути** і **Завдання**, а потім увімкніть його.

4. Якщо плагін має налаштування, відкрийте **Налаштування** на його картці, заповніть їх і
   збережіть.

</Steps>

Встановлені плагіни спочатку вимкнені. Перемикання плагіна й редагування його налаштувань
набувають чинності одразу, на кожному екземплярі (інші екземпляри підхоплюють зміну протягом
`[server].sync_interval_secs`). Зміни в `plugin.toml` чи модулі потребують перезапуску.

Керування плагінами потребує дозволу `plugins.manage` (**Керування плагінами**). Див.
[довідник дозволів](/uk/reference/permissions/).

## Налаштування `[plugins]`

```toml title="verdin.toml"
[plugins]
path = "plugins"   # directory of plugins, relative to verdin.toml
run_jobs = true    # run scheduled jobs on this instance
```

З кількома екземплярами задайте `run_jobs = false` на всіх, крім одного, щоб кожне завдання
виконувалося один раз. Див. [довідник конфігурації](/uk/reference/configuration/).

## Експлуатація

- **Один виклик за раз.** Кожен плагін має один екземпляр і обробляє один виклик за раз, тож
  повільний маршрут затримує хуки цього плагіна. Робіть функції короткими.
- **Журнали.** Те, що пише плагін, потрапляє в журнал сервера й у **Налаштування → Плагіни →
  Журнал** (останні 200 рядків у пам'яті).
- **Розгортання.** Постачайте плагіни разом із проєктом (в образі чи на томі), як схему.
  Перемикачі й налаштування зберігаються в базі даних.

На цій сторінці пояснено, як перевести проєкт на новішу версію Verdin, і перелічено, що
змінилося між мінорними версіями. Verdin дотримується [Semantic Versioning](https://semver.org/)
з особливістю для 0.x: до 1.0 **мінорний** реліз (0.8 → 0.9) може змінювати поведінку, а
**патч**-реліз (0.9.0 → 0.9.1) лише виправляє й посилює захист.

## Перед оновленням

1. **Прочитайте changelog** від своєї версії до нової: [changelog](/uk/project/changelog/)
   перелічує кожну зміну, а [примітки нижче](#примітки-до-оновлення) підсумовують ті, що
   потребують дій.
2. **Зробіть резервну копію** бази даних і медіасховища (див. [Резервні копії](/uk/deploy/backups/)).
   Повернення до старішої версії означає відновлення цієї копії: старіші версії не скасовують
   таблиці й колонки, які додала новіша.
3. **Спробуйте на копії** production, якщо примітки згадують поведінку, на яку покладаються ваш
   фронтенд чи редактори.

Версії можна пропускати. Міграції обчислюються з різниці між базою даних і тим, що очікує нова
версія, а не відтворюються реліз за релізом, тож 0.6 → 0.9 мігрує за один запуск. Прочитайте
примітки всіх проміжних версій.

## Оновлення

<Tabs syncKey="install">
<TabItem label="Docker">

<Steps>

1. Змініть тег образу у файлі Compose, маніфесті чи `Dockerfile`, наприклад
   `ghcr.io/verdin-cms/verdin:0.10` → `ghcr.io/verdin-cms/verdin:0.11`. Мінорний тег (`0.10`)
   слідує за своїми патч-релізами; зафіксуйте повну версію (`0.10.0`), щоб самим вирішувати,
   коли вони надходять.

2. Завантажте образ і перезапустіть:

   ```sh frame="terminal"
   docker compose pull verdin
   docker compose up -d verdin
   docker compose logs -f verdin
   ```

   Типова команда образу, `start --migrate`, застосовує міграції нової версії перед
   обслуговуванням. Шукайте в журналах `applied migrations` і `verdin listening`.

</Steps>

</TabItem>
<TabItem label="Binary">

<Steps>

1. Завантажте архів для своєї платформи зі [сторінки релізів](https://github.com/Verdin-CMS/verdin/releases),
   наприклад `verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz`, і перевірте його за `SHA256SUMS`
   релізу:

   ```sh frame="terminal"
   sha256sum --ignore-missing -c SHA256SUMS
   tar xzf verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz
   ```

2. Зупиніть сервер, замініть бінарник `verdin` і перевірте версію:

   ```sh frame="terminal"
   verdin version
   ```

3. Перегляньте й застосуйте міграції з каталогу проєкту:

   ```sh frame="terminal"
   verdin migrate plan
   verdin migrate apply
   ```

   Або запустіть із `verdin start --migrate`, що спершу застосовує безпечні кроки.

4. Запустіть сервер як зазвичай (`verdin start`).

</Steps>

## Міграції під час запуску

Нова версія часто додає власні таблиці чи колонки (сесії, налаштування, нові функції).
`verdin start` порівнює базу даних із тим, чого потребують схема й нова версія:

- Якщо вони збігаються, він запускається.
- Якщо є кроки, що очікують, він відмовляється запускатися й радить виконати
  `verdin migrate plan` і `verdin migrate apply` або запустити з `--migrate`.
- `--migrate` застосовує лише **безпечні** кроки. Якщо крок ризикований чи деструктивний,
  запуск не вдається, і ви застосовуєте його самі через `verdin migrate apply --allow risky`
  (або `destructive`), прочитавши план.
- У MySQL і MariaDB, де зміни схеми не можуть виконуватися в транзакції, перервана міграція
  продовжується з невдалого кроку під час наступного `verdin migrate apply`.

З кількома екземплярами поетапне оновлення працює: перший новий екземпляр бере блокування
міграції й мігрує, інші чекають на нього й не знаходять, що робити. Див.
[Кілька екземплярів](/uk/deploy/scaling/).

<Aside type="caution">
Оновлюйте весь проєкт до однієї версії. Не тримайте екземпляри двох мінорних версій запущеними
поруч довше, ніж триває поетапне розгортання.
</Aside>

## Примітки до оновлення

Помітні й несумісні зміни за версіями, найстаріші внизу. Повний список — у
[changelog](/uk/project/changelog/).

### 0.9.1 → 0.10

Міграції бази даних немає. Документація переїхала з `docs/` на цей сайт.

- **Отримувачі вебхуків `review-workflows.updateEntryStage`**: `model` тепер містить назву в
  однині (`article`), як у подіях записів, а uid переїхав до `uid`. Читайте `uid` там, де
  використовували `model`.
- **Згенеруйте заново типи TypeScript** командою `verdin types`: `Collections` і `Singles`
  тепер псевдоніми типів, яких потребує `createClient<VerdinSchema>`.
- **Docker**: образ зберігає кеш трансформацій і пошуковий індекс у `/data` та пов'язує
  `/app/public/uploads` із `/data/uploads`. Якщо ви задавали
  `VERDIN_UPLOAD__TRANSFORMS__CACHE_DIR` чи `VERDIN_SEARCH__DIR` лише щоб обійти `/app`,
  доступний тільки для читання, їх можна прибрати. Образ має `HEALTHCHECK`.
- **CDN**: відповіді містять теги типів, які вони можуть заповнити через populate, тож очищення
  оновлює більшу частину кешу, ніж раніше; нічого змінювати не треба.
- Поля зв'язків в адмін-панелі пов'язують записи через діалог (**Пов’язати запис**) замість
  вбудованого поля пошуку.

### 0.9.0 → 0.9.1

Реліз посилення захисту; оновлення рекомендовано для кожної інсталяції. Його міграція (одна
нова таблиця, дві нові колонки) виконується під час запуску.

- **За зворотним проксі задайте `[server].trusted_proxies`.** Для адреси клієнта
  використовується `X-Forwarded-For` лише від перелічених проксі; інакше всі клієнти за
  проксі мають одну адресу для обмежень частоти й журналів аудиту.
- **Браузерні фронтенди з іншого origin потребують `[api].cors_origins`.** 0.9.1 додає CORS до
  API вмісту й GraphQL; раніше підтримки CORS не було.
- **Читання через зв'язки враховує дозволи.** `populate`, фільтри й сортування за зв'язками
  доходять лише до типів і полів, які клієнт може читати, у кожному API. Публічні запити й
  запити з токеном, що заповнювали типи без дозволу `find`, тепер отримують менше даних:
  надайте відсутні дозволи.
- **SSO суворіший.** Його налаштування потребують Super Admin; `defaultRoles` і `roleMap` не
  можуть надати Super Admin; claim провайдера `email_verified` має бути true (якщо не
  `trustUnverifiedEmail`); другий фактор адміністраторів застосовується, якщо провайдеру не
  довірено цього (`providerMfa`); видавець і token endpoint мають бути публічними URL `https`.
  Перевірте входи через SSO після оновлення.
- **Super Admin** може створювати, редагувати, видаляти, повторно запрошувати чи скидати лише
  інший Super Admin.
- **Облікові записи кінцевих користувачів блокуються** після повторних неправильних паролів, як
  і облікові записи адміністраторів.
- Заповнені зв'язки повертають щонайбільше 1 000 записів на запис і зв'язок.
- Пошукові індекси перебудовуються під час першого запуску (приватні поля компонентів більше не
  індексуються).

### 0.8 → 0.9

- Поле пошуку в списку адмінки шукає в усіх текстових полях (`_q`), а не лише в заголовку.
- Нові дозволи адміністраторів `deploy.manage`, `deploy.trigger` і `site.manage`; Editors
  отримують `deploy.trigger` і `site.manage`.
- Нові необов'язкові функції (реальний час, коментарі й завдання, дії ШІ, SEO та мапа сайту,
  перенаправлення, меню, форми) вимкнені, доки ви їх не ввімкнете. Метрики потребують
  `[metrics].enabled = true`.

### 0.7 → 0.8

- **Умовні поля застосовуються**: поле, приховане своїми `conditions`, більше не
  обов'язкове. Вміст, що покладався на обов'язковість такого поля, тепер може зберігатися без
  нього.
- Новий тип атрибута `password`; `verdin import strapi` тепер імпортує поля паролів Strapi.

### 0.7.0 → 0.7.1

- Середовище виконання плагінів переходить на Wasmtime 48. Наявні плагіни працюють без
  перезбирання.
- Збірка з вихідного коду потребує Rust 1.95 або новішого.

### 0.6 → 0.7

- **Кілька екземплярів**: кожен екземпляр перечитує налаштування, змінені іншими, кожні
  `[server].sync_interval_secs` (10 с). Якщо запускаєте більше одного, задайте
  `[plugins].run_jobs = false` на всіх, крім одного.
- Вміст, який плагіни записують через хост, тепер проходить перевірки платформи перед записом,
  як-от етапи процесів перевірки. Власні хуки before-write плагінів для таких записів однаково
  пропускаються, тож плагін не може запустити сам себе.

### 0.5 → 0.6

- **Журнали аудиту** типово ввімкнені й зберігають записи `[audit].retention_days` (90).
  Вимкніть функцію в **Налаштування → Функції**, якщо вони вам не потрібні.

### 0.4 → 0.5

- Нічого змінювати не треба. Плагіни завантажуються з `[plugins].path` (`plugins/`) і лишаються
  вимкненими, доки їх не ввімкнути.

### 0.3 → 0.4

- **`auth`, `users` і `connect` — зарезервовані назви маршрутів**, разом з `upload` і `uploads`:
  перейменуйте типи вмісту, чия назва в API збігається з однією з них, перед оновленням.

### 0.2 → 0.3

- Назви атрибутів відповідають правилу Strapi (літера, далі літери, цифри й підкреслення), а не
  лише camelCase. Дві назви, що відповідають одній колонці, відхиляються.
- Параметри `regex` приймають шаблони, подібні до JavaScript.

### 0.1 → 0.2

- Обмеження розміру тіла й тайм-аути застосовуються для кожного маршрутизатора API;
  завантаження мають власні обмеження (`[upload].max_file_size`).
- Вбудовані ролі наявних інсталяцій один раз отримують нові дозволи.

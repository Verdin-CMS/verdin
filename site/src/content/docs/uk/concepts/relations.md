Зв'язок пов'язує документи двох типів вмісту, наприклад статтю та її категорію. На цій
сторінці пояснено види зв'язків, як посилання зберігаються й розв'язуються, а також правила
їх запису, упорядкування й читання. Синтаксис запитів описано в
[REST API](/uk/api/rest/#запис-даних).

## Види

Зв'язок — це атрибут із `type: "relation"`, видом `relation` і цільовим типом вмісту `target`:

| Вид | Документ посилається на | На ціль посилається | Зворотна сторона |
| --- | --- | --- | --- |
| `oneWay` | одну ціль | будь-яка кількість документів | немає |
| `manyWay` | багато цілей | будь-яка кількість документів | немає |
| `manyToOne` | одну ціль | будь-яка кількість документів | `oneToMany` |
| `oneToMany` | багато цілей | один документ | `manyToOne` |
| `oneToOne` | одну ціль | один документ | `oneToOne` |
| `manyToMany` | багато цілей | будь-яка кількість документів | `manyToMany` |

Приклад блогу пов'язує статті з категорією (зі зворотною стороною) і з тегами (без неї):

```json title="schema/content-types/article.json (excerpt)"
"category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
"tags": { "type": "relation", "relation": "manyToMany", "target": "tag" }
```

```json title="schema/content-types/category.json (excerpt)"
"articles": { "type": "relation", "relation": "oneToMany", "target": "article", "mappedBy": "category" }
```

- Сторона з `inversedBy` (або без жодного з цих ключів) — це сторона-**власник**: вона зберігає
  посилання, і саме її ви записуєте.
- Сторона з `mappedBy` — **зворотна** сторона: вона читає посилання власника у зворотному
  напрямку й доступна лише для читання. Запис у неї — помилка валідації, що називає атрибут
  власника.
- Обидві сторони мають узгоджуватися: `mappedBy` називає атрибут цілі, який вказує назад через
  `inversedBy`, з відповідним зворотним видом із таблиці.
- `oneWay` і `manyWay` ніколи не мають зворотної сторони.

Конструктор типів вмісту сам створює зворотний атрибут у цілі.

## Зв'язок за документом, а не за рядком

Документ має кілька рядків: чернетку й опубліковану версію, і по одній кожної на локаль.
Verdin зберігає зв'язок як посилання з вихідного **рядка** на цільовий **документ** (його
`documentId`) у таблиці зв'язків з назвою `{table}_{field}_lnk`. Цільовий рядок вибирається
під час читання зв'язку:

- Опублікована стаття бачить опубліковану версію своєї категорії; її чернетка бачить чернетку
  категорії. Типи без чернеток і публікації мають одну версію, яку бачать усі читачі.
- Коли ціль теж локалізована, читання розв'язує її в тій самій локалі. Нелокалізований цільовий
  тип спільний для всіх локалей.
- Зняття категорії з публікації ховає її з опублікованих статей, не чіпаючи жодного посилання;
  повторна публікація повертає її.
- Публікація статті копіює в опубліковану версію лише її власні посилання.

Strapi натомість пов'язує id рядків, тож мусить переписувати посилання щоразу, коли
публікується чернетка. Verdin цього ніколи не робить, тож публікація залишається однією копією
рядка чернетки.

Цілісність підтримує Verdin, а не зовнішні ключі: посилання на документ, якого не існує, — це
помилка валідації, а видалення документа прибирає посилання на нього в тій самій транзакції.

### Один документ на ціль

Для `oneToOne` і `oneToMany` ціль належить щонайбільше одному вихідному документу. Посилання
на ціль, яку тримає інший документ, **переносить** її: посилання іншого документа видаляється в
тому самому записі. Так поводиться Strapi. Правило діє в межах версії: чернетка та її
опублікована версія можуть тримати ту саму ціль.

## Запис

На стороні-власнику `data` приймає `documentId`, їх список або об'єкт, що описує зміну:

| Вхідні дані | Результат |
| --- | --- |
| `"k2m…"` або `{ "documentId": "k2m…" }` | Пов'язати одну ціль (зв'язки to-one). |
| `["k2m…", "p9x…"]` | Замінити всі посилання, у цьому порядку. |
| `null` або `[]` | Видалити всі посилання. |
| `{ "set": ["k2m…"] }` | Замінити всі посилання. |
| `{ "connect": [...], "disconnect": [...] }` | Додати й видалити посилання, зберігши інші. |

Під'єднання нової цілі до зв'язку to-one замінює попередню. `set` не можна поєднувати з
`connect` чи `disconnect`.

В адмін-панелі поле зв'язку показує пов'язані записи. **Пов’язати запис** (або
**Пов’язати записи** для зв'язків to-many) відкриває діалог, що шукає записи цільового типу за
їхніми текстовими полями, у локалі запису, коли ціль локалізована. Виберіть один запис або
позначте кілька й додайте їх; уже пов'язані записи позначено.

## Упорядкування

Зв'язки to-many зберігають порядок своїх посилань. Список або `set` зберігає порядок, у якому
ви надсилаєте. Елементи `connect` можуть вказувати, куди їх поставити:

```json
{
  "data": {
    "tags": {
      "connect": [
        { "documentId": "k2m…", "position": { "before": "p9x…" } },
        { "documentId": "a7c…", "position": { "end": true } }
      ]
    }
  }
}
```

`position` — це `{ "before": documentId }`, `{ "after": documentId }`, `{ "start": true }` або
`{ "end": true }`. Позиції перенумеровуються під час кожного запису. Читання повертає пов'язані
документи в порядку посилань, якщо populate не просить `sort`.

## Читання

Зв'язки повертаються, лише коли ви заповнюєте їх через populate:

```http
GET /api/articles?populate[category][fields][0]=name&populate[tags][sort]=label:asc
```

Зв'язок to-one — це об'єкт або `null`; зв'язок to-many — масив. Кожен заповнений зв'язок може
мати власні `fields`, `filters`, `sort`, `populate` і `count`, до п'яти рівнів углиб. Кожен
рівень — це один пакетний запит на зв'язок (`WHERE … IN (…)`), а не join, тож глибокі populate
не множать рядки. Для кожного документа й зв'язку повертається щонайбільше 1 000 пов'язаних
документів; `count` дає точну кількість.

Можна фільтрувати через зв'язки (`filters[category][name][$eq]=News`) з будь-якого боку та
сортувати за полем зв'язку to-one (`sort=category.name:asc`). Populate, фільтрування чи
сортування через зв'язок на тип, який клієнт не може читати, відхиляється (`populate=*` його
пропускає), тож зв'язки ніколи не розкривають вміст, який приховують
[дозволи](/uk/concepts/permissions/) клієнта.

## Зв'язки всередині компонентів

[Компонент](/uk/concepts/components-and-dynamic-zones/) може містити зв'язки, але лише `oneWay`
і `manyWay`:

```json title="schema/components/shared/related.json"
{
  "displayName": "Related",
  "attributes": {
    "label": { "type": "string" },
    "articles": { "type": "relation", "relation": "manyWay", "target": "article" }
  }
}
```

JSON компонента зберігає самі `documentId`: рядок для `oneWay`, масив для `manyWay`. Ось чому
інші види там заборонені:

- Зворотній стороні довелося б шукати в JSON кожного документа, щоб знайти, хто на неї
  посилається.
- Правило «один документ на ціль» (`oneToOne`, `oneToMany`) теж неможливо забезпечити без
  такого пошуку.

Усередині компонентів порядок списку `manyWay` — це порядок масиву. Посилання перевіряються
під час запису й розв'язуються, коли компонент заповнюється, у статусі та локалі документа;
цілі, яких більше не існує, пропускаються. Фільтрувати за ними не можна.

## Поліморфні зв'язки

`morphToOne` і `morphToMany` пов'язують документи будь-якого типу вмісту. Їхні посилання
зберігають тип цілі поруч із її `documentId`, і запис називає обидва:

```json
{ "data": { "related": [{ "__type": "api::article", "documentId": "k2m…" }, { "__type": "api::page", "documentId": "p9x…" }] } }
```

Заповнені елементи — це цільові документи з їхнім `__type`, прочитані в статусі й локалі
запиту. Зворотні сторони `morphOne` і `morphMany` називають тип власника (`target`) і його
атрибут (`morphBy`) і доступні лише для читання. Поліморфні зв'язки не можна фільтрувати чи
сортувати, і вони не можуть бути всередині компонентів.

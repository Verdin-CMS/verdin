Verdin окремо контролює дві аудиторії: **адміністраторів**, які входять в адмін-панель, і
**клієнтів API вмісту**, які читають і записують вміст із ваших сайтів і застосунків. На цій
сторінці пояснено, як авторизується кожна з них і як усе поєднується. Повний список дій
наведено в [довіднику дозволів](/uk/reference/permissions/).

| Хто | Автентифікується через | Дозволи визначає | Діє для |
| --- | --- | --- | --- |
| Адміністратор | Ел. пошту й пароль (плюс другий фактор або SSO) | Його [ролі](#ролі-адміністраторів) | Адмін-панелі та [admin API](/uk/api/admin/) |
| Анонімний клієнт | Без заголовка `Authorization` | [Публічний доступ](#публічний-доступ) | REST, GraphQL, реального часу |
| Сервер або збірка | `Authorization: Bearer vd_…` | Тип [API-токена](#api-токени) | REST, GraphQL, реального часу |
| Кінцевий користувач, що увійшов | `Authorization: Bearer <JWT>` | Його [роль кінцевого користувача](#кінцеві-користувачі) | REST, GraphQL, реального часу |

Типово все закрито: API вмісту відповідає `403`, доки ви не надасте доступ, а адміністратор
може робити лише те, що дозволяють його ролі.

## Ролі адміністраторів

Адміністратор має одну чи кілька ролей; їхні дозволи додаються. Є три вбудовані ролі:

| Роль | Може |
| --- | --- |
| **Super Admin** | Усе, включно з користувачами, ролями та API-токенами. Не редагується. |
| **Editor** | Читати, створювати, оновлювати, видаляти й публікувати весь вміст; користуватися медіатекою; запускати розгортання; керувати SEO, перенаправленнями, меню та формами. |
| **Author** | Створювати вміст, а також читати, оновлювати й видаляти лише створені ним записи. Не може публікувати. Завантажує файли й редагує чи видаляє лише власні. |

Інші ролі створюються в **Налаштування → Ролі** (дозвіл `roles.manage`). Останнього активного
Super Admin не можна деактивувати, видалити чи понизити, тож екземпляр ніколи не заблокує сам
себе. Роль також може вимагати від своїх учасників налаштувати
[двофакторну автентифікацію](/uk/guides/auth/two-factor/): доки вони цього не зроблять, їм
доступний лише їхній профіль.

### Що таке дозвіл

Дозвіл — це **дія**, **суб'єкт** для дій з вмістом і необов'язкові **умови**:

- **Дії з вмістом**: `content.read`, `content.create`, `content.update`,
  `content.delete` і `content.publish` для одного типу вмісту (`api::article`) або для всіх
  (`*`).
- **Дії з медіа**: `media.read`, `media.create`, `media.update` і `media.delete` для медіатеки.
- **Дії з налаштуваннями**, як-от `users.manage`, `tokens.manage`, `webhooks.manage` або
  `features.manage`, що відкривають відповідні сторінки **Налаштування**.
- **Умови**: `is-creator` обмежує дозвіл на вміст або медіа тим, що створив адміністратор. Саме
  так працює роль Author.

Умови стають частиною запиту до бази даних: список, відфільтрований за `is-creator`, правильно
рахує й розбиває на сторінки, а не ховає рядки постфактум.

### Дозволи для полів і локалей

Дозволи на вміст можна звузити ще більше:

- **Поля.** `content.read`, `content.create` і `content.update` можуть перелічувати атрибути,
  які вони охоплюють. Поля поза списком приховуються під час читання (включно з пошуком,
  фільтрами, сортуванням і пов'язаними записами) і відхиляються під час запису.
- **Локалі.** У [локалізованих типах](/uk/concepts/internationalization/) дозволи на вміст
  можуть перелічувати локалі, які вони охоплюють. Версії в інших локалях не можна читати чи
  змінювати.

Обидва обмеження задаються для кожного типу вмісту в редакторі ролі, у розділах **Поля** і
**Мови**.

## API вмісту

Клієнти API вмісту перевіряються за дозволами: **дія** над **суб'єктом**.

| Дія | Дозволяє |
| --- | --- |
| `find` | Перелік документів (`GET /api/articles`) або читання поодинокого типу. |
| `findOne` | Читання одного документа (`GET /api/articles/{documentId}`). |
| `create` | `POST` |
| `update` | `PUT` |
| `delete` | `DELETE` |
| `publish` | Маршрути `actions/publish`, `actions/unpublish` і `actions/discard-draft`. |
| `readDrafts` | Читання з `status=draft`. |

Суб'єкти — це типи вмісту, медіатека (`plugin::upload`) і облікові записи кінцевих
користувачів (`plugin::users-permissions.user`), коли [кінцевих користувачів](/uk/guides/auth/end-users/)
увімкнено.

Кілька правил діють для всіх клієнтів:

- Для читання чернеток потрібен `readDrafts` на додачу до `find` або `findOne`. Дозвіл, що читає
  вміст вашого сайту, не може випадково прочитати неопубліковану роботу.
- Для populate, фільтрування чи сортування через зв'язок потрібен доступ на читання до
  цільового типу.
- Поля `private` ніколи не повертаються, хоч би які були дозволи.
- Запис повертає записаний документ навіть без `find`, як у Strapi.
- Ті самі дозволи діють для [GraphQL](/uk/api/graphql/) і
  [потоку реального часу](/uk/api/realtime/).

### Публічний доступ

Запити без заголовка `Authorization` отримують дозволи з **Налаштування → Публічний доступ**.
Типово нічого не дозволено. Зазвичай вибирають `find` і `findOne` для типів, які показує ваш
сайт.

### API-токени

API-токени призначені для серверів, кроків збірки й скриптів. Створюйте їх у
**Налаштування → API-токени** (дозвіл `tokens.manage`):

| Тип | Дозволи |
| --- | --- |
| **Лише читання** | `find` і `findOne` для всіх типів. Ніколи — чернетки. |
| **Повний доступ** | Усі дії для всіх типів, включно з чернетками. |
| **Налаштовуваний** | Дозволи, які ви вибираєте, як для публічного доступу. |

- Токен починається з `vd_`. Його секрет показується один раз — під час створення або
  регенерації; Verdin зберігає лише його хеш із ключем.
- Токени можуть мати термін дії. Невідомий, прострочений або некоректний токен — це `401`:
  запит ніколи не переходить у публічний доступ.
- Будь-який дійсний токен може читати документ OpenAPI за адресою `/api/_openapi.json`, якщо
  ви не зробили документацію публічною.

Про створення й ротацію див. [API-токени](/uk/guides/auth/api-tokens/).

### Кінцеві користувачі

Кінцеві користувачі — це люди, які входять на ваш сайт або в застосунок, як із плагіном
users-permissions у Strapi. Типово функцію вимкнено. Кожен обліковий запис має одну роль:

- **Public** — роль запитів без токена: її дозволи — це дозволи з
  **Налаштування → Публічний доступ**.
- **Authenticated** типово надається новим обліковим записам.
- Власні ролі містять будь-який набір дозволів із тими самими діями, що й вище.

Кінцевий користувач надсилає JWT, отриманий під час входу, як `Authorization: Bearer <jwt>`.
Verdin відрізняє його від API-токенів за префіксом `vd_`. Див.
[Кінцеві користувачі](/uk/guides/auth/end-users/).

## Порівняно зі Strapi

Модель відповідає Strapi v5: RBAC адміністраторів з умовами `is-creator` і API вмісту з
публічним доступом, API-токенами та ролями users-permissions. Відмінності:

- Усі функції доступні кожному проєкту: власні ролі, дозволи для полів і локалей,
  [SSO](/uk/guides/auth/sso/) і [журнали аудиту](/uk/guides/content/audit-logs/).
- Читання чернеток через API вмісту — окремий дозвіл `readDrafts`.
- Публікація через REST має окремий дозвіл `publish` і власні маршрути.

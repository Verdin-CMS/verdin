Коли ви змінюєте файл схеми, база даних має встигати за ним: новому атрибуту потрібна колонка,
новому зв'язку — таблиця зв'язків. Verdin обчислює цю міграцію за вас, показує її перед
виконанням і ніколи не видаляє дані без явної вказівки. На цій сторінці пояснено, як це
працює.

## Від схеми до плану

Verdin ніколи не просить вас писати міграцію. Він порівнює дві моделі бази даних:

1. **Бажану**: виведену з ваших файлів `schema/*.json`, з усіма потрібними таблицями,
   колонками й індексами (включно з таблицями зв'язків і власними таблицями Verdin).
2. **Поточну**: модель, яку залишила остання міграція, збережену в базі даних як знімок.

Різниця — це **план**: список кроків, кожен зі своїм SQL для вашої бази даних і рівнем ризику.
Оскільки план будується зі збереженого знімка, а не з інспекції бази даних, він
детермінований і однаковий для всіх діалектів. Зміни, що дають той самий SQL у вашій базі
даних, як-от `integer` → `biginteger` у SQLite, не створюють кроків.

`verdin migrate plan` виводить його. Тут атрибут блогу `excerpt` перейменовано на `summary` в
`article.json`:

```text title="Terminal"
$ verdin migrate plan
  1. [safe] add column articles.summary
       ALTER TABLE "articles" ADD COLUMN "summary" text
  2. [destructive] drop column articles.excerpt
       ALTER TABLE "articles" DROP COLUMN "excerpt"

requires: verdin migrate apply --allow destructive

possible renames (pass them to keep the data):
  --rename-column articles.excerpt=summary
```

## Рівні ризику

| Ризик | Кроки | Чому |
| --- | --- | --- |
| **safe** | Створити таблицю, додати колонку, додати чи видалити неунікальний індекс, перейменувати таблицю чи колонку. | Не може втратити дані чи зламатися на наявних рядках. |
| **risky** | Змінити тип колонки, додати унікальний індекс до наявної таблиці, перебудувати таблицю SQLite (SQLite не вміє змінювати колонки на місці). | Може зламатися на наявних даних (дублікати, значення, що не конвертуються) або переписати їх. |
| **destructive** | Видалити колонку чи таблицю. | Видаляє дані. |

Кожна колонка атрибута допускає null (`required` перевіряється під час публікації), тож
додавання атрибутів, обов'язкових чи ні, завжди безпечне. Додавання `"unique": true` до
заголовка статті блогу — ризиковане, бо наявні заголовки можуть повторюватися:

```text title="Terminal"
$ verdin migrate plan
  1. [risky] create unique index articles_title_uq
       CREATE UNIQUE INDEX "articles_title_uq" ON "articles" ("title", "locale", "publication_state")

requires: verdin migrate apply --allow risky
```

Перш ніж виконати перший оператор, Verdin запускає перевірку для кожного ризикованого кроку,
який може не вдатися, — наприклад, шукає дублікати перед унікальним індексом — і зупиняється з
повідомленням, якщо знаходить проблему. На цей момент нічого ще не змінено.

## Застосування плану

`verdin migrate apply` виконує кроки, що очікують. Він приймає найвищий ризик, на який ви
погоджуєтеся:

```sh title="Terminal"
verdin migrate apply                        # лише безпечні кроки (типово)
verdin migrate apply --allow risky          # також зміни типів і унікальні індекси
verdin migrate apply --allow destructive    # також видалення
```

Якщо хоч один крок перевищує дозволений ризик, нічого не виконується:

```text title="Terminal"
$ verdin migrate apply
Error: these steps need explicit approval:
  create unique index articles_title_uq (risky)
```

Міграція бере блокування, тож два екземпляри ніколи не мігрують одночасно. У PostgreSQL і
SQLite весь план виконується в одній транзакції: помилка відкочує все. MySQL і MariaDB
фіксують кожен DDL-оператор окремо, тож Verdin записує свій прогрес крок за кроком у журнал.
Після помилки усуньте причину й знову запустіть `verdin migrate apply`: він продовжить із
невдалого кроку, якщо план не змінився, і відмовиться, якщо схема тим часом змінилася.

## Перейменування

Видалений атрибут і новий виглядають як видалення й додавання, що призвело б до втрати даних
колонки. Verdin ніколи не вгадує перейменування. Він пропонує його, коли колонка зникає, а в
тій самій таблиці з'являється колонка того самого типу (або таблиця зникає, а з'являється
таблиця з тими самими колонками), і ви явно його підтверджуєте:

```text title="Terminal"
$ verdin migrate apply --rename-column articles.excerpt=summary
applied 1 step
```

- `--rename-column TABLE.OLD=NEW` перейменовує колонку; `TABLE` — це таблиця типу вмісту (його
  `collectionName`).
- `--rename-table OLD=NEW` перейменовує таблицю. Таблиці зв'язків типу перейменовуються разом
  із нею.
- Передайте ті самі прапорці до `migrate plan`, щоб переглянути результат.

Перейменування — безпечні кроки. Конструктор типів вмісту пропонує ті самі варіанти у своєму
діалозі.

## `verdin dev` і `verdin start`

| | `verdin dev` | `verdin start` |
| --- | --- | --- |
| Під час запуску | Застосовує безпечні кроки, що очікують. Зупиняється, якщо очікують інші кроки. | Відмовляється запускатися, поки є кроки, що очікують, якщо не передати `--migrate`, який спершу застосовує безпечні кроки. |
| Зміни схеми під час роботи | **Конструктор типів вмісту** показує план з ризиками й пропозиціями перейменувань і застосовує його після підтвердження, включно з ризикованішими кроками. Ручні правки (або `git pull`) підхоплює спостерігач за файлами: безпечні плани застосовуються, і застосунок перезавантажується; інші записуються в журнал, а запущений застосунок лишається як був. | Схема доступна лише для читання. Розгорніть нові файли й виконайте міграцію. |

Конструктор спершу мігрує базу даних, потім записує файли схеми, а потім перезавантажує API
вмісту, admin API, GraphQL і документ OpenAPI без перезапуску. Якщо міграція не вдається, файли
й запущений застосунок лишаються як були.

У production запустіть `verdin migrate plan` на копії бази даних, а потім `verdin migrate apply`
з прийнятним для вас ризиком, перш ніж запускати нову версію. Див.
[Оновлення](/uk/migrate/upgrading/) і [Резервні копії](/uk/deploy/backups/).

## Порівняно зі Strapi

Strapi синхронізує базу даних зі схемою під час запуску, не показуючи, що саме зробить. Verdin
спершу планує, показує SQL, без запиту застосовує лише безпечні кроки й вимагає `--allow` для
всього, що може не вдатися або видалити дані.

На цій сторінці описано таблиці, які Verdin виводить із вашої схеми, і як зберігається кожен вид атрибутів. Прочитайте її, перш ніж щось змінювати в `crates/verdin-migrate/src/derive.rs` чи Document Service, або коли потрібно запитувати базу даних напряму. Що приймає кожен тип атрибута, див. у [типах атрибутів](/uk/reference/attribute-types/).

Ці таблиці ніколи не пишуть вручну: [рушій міграцій](/uk/internals/migrations/) створює й розвиває їх зі схеми.

## Правила іменування

| Об'єкт | Назва |
|---|---|
| Таблиця типу вмісту | `collectionName`, типово `pluralName` з дефісами, заміненими на підкреслення (`blog-posts` → `blog_posts`) |
| Колонка | Назва атрибута в snake case (`metaTitle` → `meta_title`) |
| Посилання зв'язків | `{table}_{column}_lnk` |
| Посилання поліморфних зв'язків | `{table}_{column}_mph` |
| Медіапосилання | `{table}_{column}_mda` |
| Індекс | `{table}_{part}_uq` для унікальних індексів, `{table}_{part}_idx` для інших |
| Таблиця платформи | Префікс `vd_` (`vd_admin_users`, `vd_schema_snapshots`…) |

Правила, які забезпечує валідатор схеми (`crates/verdin-schema/src/naming.rs` і `validate.rs`):

- `collectionName` відповідає `^[a-z][a-z0-9_]*$`, має щонайбільше 50 символів і не може починатися з `vd_`.
- `singularName` і `pluralName` — у kebab case (`^[a-z][a-z0-9-]*$`, без дефісів на початку, в кінці чи подвоєних). `upload`, `uploads`, `auth`, `users` і `connect` зарезервовані, бо API вмісту використовує ці маршрути.
- Назви атрибутів починаються з літери й продовжуються літерами, цифрами чи підкресленнями (правило Strapi) і мають щонайбільше 50 символів.
- У типах вмісту зарезервовані `id`, `documentId`, `locale`, `publicationState`, `publishedAt`, `createdAt`, `updatedAt`, `createdBy` і `updatedBy`, а також будь-яка назва, чий snake case з ними збігається. У компонентах зарезервовано `id`.
- Згенеровані ідентифікатори обмежено 60 символами (PostgreSQL дозволяє 63, MySQL — 64). Довша назва обрізається й отримує 8-символьний хеш повної назви, тож різні довгі назви лишаються різними, а результат детермінований.

Кожен ідентифікатор у згенерованому SQL береться в лапки, тож зарезервовані слова SQL — коректні назви атрибутів.

## Системні колонки

Кожна таблиця типу вмісту починається з таких колонок:

```sql
id                 BIGINT       primary key, auto-increment
document_id        CHAR(26)     NOT NULL           -- ULID, shared by every version of a document
locale             VARCHAR(16)  NOT NULL DEFAULT '' -- '' for types that are not localized
publication_state  SMALLINT     NOT NULL           -- 0 = draft, 1 = published
published_at       <datetime>   NULL
created_at         <datetime>   NOT NULL
updated_at         <datetime>   NOT NULL
created_by_id      BIGINT       NULL               -- vd_admin_users.id
updated_by_id      BIGINT       NULL
UNIQUE (document_id, locale, publication_state)
INDEX  (publication_state, locale)
```

- `document_id` — це ULID у нижньому регістрі, що генерується під час створення. Він однаковий для чернетки, опублікованої версії й кожної локалі.
- Нелокалізовані типи використовують `locale = ''`, а не `NULL`, бо NULL ніколи не конфліктують в унікальних індексах у жодному рушії, що зламало б обмеження `(document_id, locale, publication_state)`.
- Колонка стану — `publication_state`, а не `state`, бо `state` — поширена назва атрибута.

Далі йдуть колонки атрибутів, по одній на скалярний атрибут. **Кожна колонка атрибута допускає null.** Як і в Strapi v5, чернетки можуть бути неповними, тож `required` перевіряється під час публікації версії (або під час кожного запису в типи без чернеток і публікації), а не базою даних. Завдяки цьому додавання обов'язкового атрибута — безпечна міграція.

Атрибути `unique` і кожен `uid` отримують унікальний індекс за `(column, locale, publication_state)`. Чернетка та її опублікована версія можуть мати однакове значення, два опубліковані документи — ні, і база даних забезпечує це без гонок. Порушення повідомляється як `ValidationError` для цього поля.

## Чернетки й публікація

Verdin наслідує модель Strapi v5. Погляд користувача див. у [чернетки й публікація](/uk/concepts/draft-and-publish/); ось що відбувається в таблиці.

- Документ має щонайбільше один рядок чернетки (`publication_state = 0`) і один опублікований рядок (`publication_state = 1`) на локаль.
- Записи з адмін-панелі спрямовані на рядок чернетки.
- **Публікація** перевіряє атрибути `required` і правила валідації на чернетці, а потім копіює значення атрибутів чернетки в опублікований рядок (оновлюючи його або вставляючи вперше) в одній транзакції. Посилання зв'язків і медіа чернетки копіюються разом із ним.
- **Зняття з публікації** видаляє опублікований рядок. Його посилання видаляються разом із ним через `ON DELETE CASCADE`.
- **Відкидання чернетки** перезаписує чернетку значеннями й посиланнями опублікованого рядка.
- Типи вмісту без чернеток і публікації мають лише опублікований рядок.
- У локалізованих типах нелокалізовані атрибути спільні: публікація однієї локалі копіює їх в опубліковані рядки інших локалей.

## Зв'язки: посилання за id документа

**Це головна відмінність від сховища Strapi.** Strapi пов'язує рядки за id рядка й мусить переписувати посилання під час публікації. Verdin зберігає зв'язок як *вихідний рядок → цільовий документ*:

```sql
-- articles_category_lnk
id                  BIGINT   primary key, auto-increment
source_id           BIGINT   NOT NULL REFERENCES articles(id) ON DELETE CASCADE
target_document_id  CHAR(26) NOT NULL
position            DOUBLE   NOT NULL   -- 1..n, rewritten on every write
UNIQUE (source_id, target_document_id)
UNIQUE (source_id)                      -- to-one kinds only
INDEX  (target_document_id)
```

- Цільовий рядок вибирається під час читання, у версії, що читається: опублікована стаття бачить опубліковані категорії, чернетка — чернетки. Якщо категорію знято з публікації, вона зникає з опублікованих статей без зміни жодного посилання.
- Публікація копіює лише власні посилання вихідного рядка.
- Таблицю зв'язків має лише сторона-**власник** (атрибут з `inversedBy` або односпрямований зв'язок). Зворотна сторона (`mappedBy`) читає ту саму таблицю у зворотному напрямку й доступна лише для читання: запис у неї — помилка валідації, що називає атрибут власника.
- «Щонайбільше одна ціль» (`oneToOne`, `manyToOne`, `oneWay`) — це унікальний індекс за `source_id`. «Ціль належить одному вихідному документу» (`oneToOne`, `oneToMany`) не може бути індексом, бо чернетка та її опублікована версія законно мають спільні цілі. Document Service забезпечує це *перенесенням* цілі: посилання на неї видаляє посилання, які мають на неї інші документи в тому самому стані, — так поводиться Strapi.
- Зовнішнього ключа на `target_document_id` немає, бо `document_id` не унікальний у цільовій таблиці. Document Service відхиляє посилання на документи, яких не існує, а коли видаляється остання версія документа, прибирає посилання на нього в тій самій транзакції.
- Рядки посилань зберігають первинний ключ `id`, тож таблиці зв'язків виглядають для рушія міграцій і перебудов таблиць SQLite так само, як будь-які інші.
- Перейменування таблиці перейменовує разом із нею її таблиці зв'язків. Міграції виконуються з вимкненими `foreign_keys` у SQLite, тож перебудова таблиці не каскадує в її таблиці зв'язків.

**Поліморфні зв'язки** (`morphToOne`, `morphToMany`) пов'язують документи будь-якого типу вмісту. Їхні посилання живуть у `{table}_{column}_mph` із `source_id`, `target_type` (uid цілі), `target_document_id` і `position`, унікальним `(source_id, target_type, target_document_id)`, а для `morphToOne` — з унікальним `source_id`. Зворотні сторони (`morphOne`, `morphMany`) не мають таблиці: вони читають посилання власника, що вказують на них, і доступні лише для читання. Видалення документа прибирає поліморфні посилання на нього. Що з ними можна й не можна робити, див. у [зв'язках](/uk/concepts/relations/).

## Компоненти й динамічні зони: JSON-колонка

Атрибут-компонент або динамічна зона — це **одна JSON-колонка** в рядку документа (`jsonb` у PostgreSQL, `json` у MySQL і MariaDB, `text` у SQLite). Strapi зберігає кожен компонент в окремій таблиці з поліморфними таблицями з'єднань; колонка дає змогу уникнути цих join-ів і робить публікацію та історію простим копіюванням.

```json
// "seo" column (a single component)
{ "id": 1, "metaTitle": "…", "metaDescription": "…" }

// "blocks" column (a dynamic zone)
[
  { "id": 1, "__component": "blocks.hero", "title": "…" },
  { "id": 2, "__component": "blocks.quote", "text": "…", "author": "…" }
]
```

- Кожен елемент компонента має цілочисельний `id`, унікальний у межах свого атрибута. Нові елементи отримують наступний вільний номер.
- Дані перевіряються за схемою компонента під час кожного запису.
- Публікація й відкидання копіюють JSON як є.
- **Зв'язки й медіа всередині компонентів** зберігаються в самому JSON: `documentId` для зв'язків (там дозволено лише `oneWay` і `manyWay`) і id файлів для медіа. Вони перевіряються під час запису й розв'язуються пакетними запитами, коли компонент заповнюється. Поліморфні зв'язки й атрибути `password` не можуть бути всередині компонентів.
- **Фільтрування** потребує JSON-функцій, специфічних для діалекту. Скалярні поля одиночних компонентів читаються через JSON-шлях (`#>>` у PostgreSQL, `JSON_VALUE` у MySQL і MariaDB, `json_extract` у SQLite). Повторювані компоненти використовують `EXISTS` за елементами масиву (`jsonb_array_elements`, `JSON_TABLE`, `json_each`). Динамічні зони можна фільтрувати лише за `__component`, бо їхні елементи мають різні поля.

Бік моделювання див. у [компоненти й динамічні зони](/uk/concepts/components-and-dynamic-zones/).

## Таблиці платформи

Таблиці платформи є частиною кожної виведеної моделі, тож рушій міграцій створює й розвиває їх точно так само, як таблиці вмісту; вони з'являються як безпечні кроки у `verdin migrate plan`. Їх визначено в `crates/verdin-migrate/src/system.rs`.

| Область | Таблиці |

| Міграції | `vd_schema_snapshots`, `vd_migrations_journal` (належать рушію міграцій, створюються під час першого використання) |
| Адміністратори | `vd_admin_users`, `vd_admin_roles`, `vd_admin_user_roles`, `vd_admin_permissions`, `vd_sessions` (refresh tokens), `vd_admin_tokens` (посилання запрошення й скидання), `vd_admin_two_factor`, `vd_admin_passkeys`, `vd_spent_challenges` |

| Кінцеві користувачі | `vd_users`, `vd_user_roles`, `vd_user_role_permissions`, `vd_end_user_sessions` |
| Екземпляр | `vd_settings` (перемикачі функцій, макети видів редагування, разові маркери оновлень), `vd_locales` |
| Медіа | `vd_files`, `vd_folders` |
| Робочий процес вмісту | `vd_history_versions`, `vd_releases`, `vd_release_actions`, `vd_workflows`, `vd_workflow_stages`, `vd_document_stages` |

## Медіатаблиці

Файли — це рядки `vd_files` у форматі Strapi (`name`, `alternative_text`, `caption`, `width`, `height`, `formats`, `hash`, `ext`, `mime`, `size`, `url`, `provider`…), а також `focal_point`, `folder_id` і `folder_path`. Папки (`vd_folders`) зберігають `path` зі Strapi, що складається з `path_id`, наприклад `/1/4`.

Медіаатрибут — це таблиця зв'язків `{table}_{column}_mda` із `source_id` (рядок вмісту), `file_id` (рядок `vd_files`) і `position`. Вона має унікальний `(source_id, file_id)` і, коли атрибут не `multiple`, унікальний `source_id`. Обидві колонки — зовнішні ключі з `ON DELETE CASCADE`, тож видалення файлу чи рядка прибирає його посилання. Медіапосилання підпорядковуються тим самим правилам чернеток і публікації, що й посилання зв'язків: кожна версія володіє своїми посиланнями, а публікація їх копіює.

Як працюють завантаження, формати й провайдери сховища, описано в [медіа](/uk/concepts/media/).

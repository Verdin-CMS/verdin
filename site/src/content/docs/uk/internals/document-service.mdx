Document Service (`DocumentService` у `crates/verdin-content/src/service.rs`) — єдиний код, що читає й записує рядки вмісту. API вмісту, admin API, GraphQL, MCP, плагіни, імпорт і мапа сайту проходять через нього, тож валідація, чернетки й публікація, правила зв'язків і події поводяться однаково, хоч би який API зробив виклик. Як і Document Service у Strapi v5, він працює з документами (що ідентифікуються за `documentId`), а не з рядками.

## API

Основні методи (спрощено; точні типи див. у вихідному коді):

| Метод | Що робить |
|---|---|
| `find_many(uid, &Query) -> Page` | Сторінка документів із `meta` у формі сторінок або зсуву |
| `find_one(uid, document_id, &Query) -> Option<Json>` | Один документ у статусі й локалі запиту |
| `single_document_id(uid)` | Документ поодинокого типу, якщо він існує |
| `create(uid, &data, WriteOptions) -> String` | Створює документ і повертає його `documentId` |
| `update(uid, document_id, &data, WriteOptions)` | Часткове оновлення чернетки (або єдиної версії); за потреби створює версію нової локалі |
| `delete(uid, document_id)` | Видаляє всі версії документа в поточній локалі |
| `publish(uid, document_id, actor)` | Копіює чернетку в опубліковану версію |
| `unpublish(uid, document_id)` | Видаляє опубліковану версію |
| `discard_draft(uid, document_id)` | Замінює чернетку опублікованою версією |
| `uid_availability(…)` | Чи вільне значення `uid`, з вільною пропозицією |
| `document_locales`, `timeline`, `usage`… | Допоміжні методи для адмін-панелі |

`WriteOptions` має два поля: `publish` (опублікувати після запису в типах із чернетками й публікацією) і `actor` (адміністратор, що записується в `created_by_id` / `updated_by_id`).

Сервіс — це значення, яке дешево клонувати, що налаштовується методами-білдерами: `in_locale(locale)` для локалізованих типів, `with_listener`, `with_hook`, `dry_run()` (повністю перевірити запис і відкотити його; використовується пробними запусками імпорту) і `without_plugin_hooks()` (для записів, які роблять самі плагіни).

Він не знає, хто викликає. Дозволи застосовує шар API до виклику: він відхиляє дії, яких клієнт не має, обмежує, які типи запит може заповнювати чи фільтрувати, і додає до запиту фільтри умов (наприклад, умова «власні записи» ролі адміністратора **Author** стає `created_by_id = <admin id>`). Фільтри є частиною SQL, тож пагінація й підрахунки лишаються точними.

## Що робить кожен запис

1. **Хуки.** Спершу по черзі виконуються `DocumentHook`: етапи процесу перевірки, потім плагіни. Хук може замінити дані або відхилити запис, що стає `400`. Вони використовують назви lifecycle Strapi (`beforeCreate`, `beforeUpdate`, `beforeDelete`, `beforePublish`, `beforeUnpublish`, `beforeDiscardDraft`).
2. **Валідація вхідних даних** (`input.rs`): невідомі ключі, системні поля (`id`, `documentId`, мітки часу) і зворотні (`mappedBy`) сторони зв'язків — помилки; кожне значення перевіряється за типом атрибута й обмеженнями (`min`, `max`, `minLength`, `maxLength`, `regex`, значення enumeration, кардинальність зв'язку, `allowedTypes` медіа); компоненти й динамічні зони валідуються рекурсивно; значення `password` хешуються argon2.
3. **Посилання.** Пов'язані документи й медіафайли мають існувати; це перевіряється всередині транзакції.
4. **Рядки й посилання** в одній транзакції: рядок вставляється або оновлюється, потім переписуються його таблиці зв'язків, поліморфних зв'язків і медіа (позиції перенумеровуються 1..n). Посилання на ціль `oneToOne` чи `oneToMany` забирає її в інших документів у тому самому стані.
5. **Обов'язкові поля й правила.** Коли версія стає опублікованою, або під час кожного запису в типи без чернеток і публікації, перевіряються атрибути `required` (включно з тими, що всередині компонентів і динамічних зон) і правила валідації між полями. Невдача відкочує весь запис.
6. **Унікальність** забезпечують унікальні індекси з областю дії. Порушення зіставляється з атрибутом і повідомляється як `ValidationError`, без гонок.
7. **Commit, потім події.** Після фіксації транзакції сервіс викликає кожен `DocumentListener` з `DocumentEvent` (`entry.create`, `entry.update`, `entry.publish`, `entry.unpublish`, `entry.discard-draft`, `entry.delete`), що містить uid, `documentId`, локаль і виконавця.

Помилки валідації мають формат Strapi: список `{ path, message, name: "ValidationError" }`, де `path` вказує в дані (`["seo", "metaTitle"]`, `["blocks", 2, "text"]`). Адмін-панель зіставляє їх зі своїми полями.

Слухачі тримають похідний стан узгодженим із вмістом без коду в окремих обробниках: вебхуки, історія вмісту, кеш відповідей, хуки after плагінів, журнал аудиту, події реального часу, коментарі й завдання, позначки «переглянуто», очищення CDN і пошуковий індекс. Слухач, що падає, записує власну помилку; запис уже успішний. Оскільки слухачі виконуються після commit, пробний запуск ніколи до них не доходить.

## Читання

Читання вибирає рядки запитаного статусу й локалі, застосовує фільтри й сортування в SQL, а потім заповнює те, що запитано:

- **Зв'язки** завантажуються пакетними запитами, по одному на зв'язок і рівень (`WHERE … IN (…)`, частинами по 500 id), ніколи — каскадними join-ами. Це запобігає і декартовим вибухам, і запитам N+1. Для кожного запису й зв'язку заповнюється щонайбільше 1 000 пов'язаних записів; підрахунки лишаються точними.
- Цілі читаються в тій самій версії, що й джерело: опубліковані документи бачать опубліковані цілі, чернетки — чернетки.
- **Компоненти й динамічні зони** беруться з їхньої JSON-колонки; зв'язки й медіа всередині них розв'язуються тими самими пакетними запитами.
- **Пошук `_q`** використовує індекс Tantivy, коли ввімкнено `[search]`, а інакше — нечутливий до регістру `$containsi` за текстовими полями.

Як виглядає вивід (плоскі документи, формати значень, синтаксис `populate`, обмеження), описано в [REST API](/uk/api/rest/).

## Життєвий цикл запиту до API вмісту

  caption="Запит GET /api/articles від сокета до бази даних"
  code={`sequenceDiagram
  participant C as Клієнт
  participant L as Спільні шари
  participant H as handlers.rs
  participant Q as verdin-query
  participant D as Document Service
  participant DB as База даних
  C->>L: GET /api/articles?filters…
  L->>H: IP клієнта, id запиту, CORS, обмеження, кеш
  H->>H: маршрут за pluralName, авторизація токена чи публічної ролі
  H->>Q: розбір і валідація за схемою
  Q-->>H: типізований Query
  H->>D: find_many(uid, query)
  D->>DB: SELECT … WHERE … ORDER BY … LIMIT
  D->>DB: один пакетний запит на кожен заповнюваний зв'язок
  D-->>H: документи й meta сторінки
  H-->>C: { data, meta }`}
/>

1. **Спільні шари** (від зовнішнього): визначається адреса клієнта (з `X-Forwarded-For` лише від `[server].trusted_proxies`), метрики рахують запит, якщо ввімкнені, задається id запиту, що передається як `x-request-id`, tracing відкриває span, а CORS застосовується до API вмісту й GraphQL, коли задано `[api].cors_origins`.
2. **Шари API вмісту**: обмеження частоти для кожного клієнта, `ETag` і необов'язковий кеш анонімних читань, обмеження розміру тіла (`[server].body_limit`) і тайм-аут запиту, теги кешу CDN на відповідях.
3. **Маршрутизація.** Сегмент шляху шукається серед `pluralName` (типи колекцій) і `singularName` (поодинокі типи) типів вмісту. Невідомі назви — `404`.
4. **Авторизація** (`verdin-auth`). Відсутність заголовка `Authorization` означає публічну роль; `Bearer vd_…` — це API-токен. Недійсний або прострочений токен — це `401`, а не публічна роль. Дія маршруту (`find`, `findOne`, `create`, `update`, `delete`, `publish`) має бути дозволена для типу, інакше відповідь — `403`.
5. **Розбір запиту** (`verdin-query`). Сирий рядок запиту розбирається в дерево квадратних дужок (щонайбільше 16 КБ, 12 рівнів, 1 000 пар), а потім у типізований `Query`, перевірений за полями типу: невідомі й `private` поля — `400`, а populate, фільтри й сортування за зв'язками обмежено типами, які клієнт може читати. Читання `?status=draft` також потребує `readDrafts`.
6. **Document Service.** Обробник викликає `find_many`, `find_one`, `create`, `update`, `delete` або дію. Записи без `?status=draft` публікують у типах із чернетками й публікацією (поведінка Strapi v5) і читають записану версію для відповіді.
7. **Відповідь.** `{ "data": …, "meta": … }`. Помилки використовують ту саму обгортку з `data: null` і об'єктом `error`.

Маршрути admin API йдуть тим самим шляхом із сесією адміністратора замість API-токена, RBAC адмінки замість дозволів API вмісту й типовою роботою з чернетками: вони читають чернетки й записують лише чернетки, а публікація — явна дія. GraphQL перетворює свої аргументи на те саме дерево параметрів перед кроком 5, тож має спільні з REST парсер, обмеження й правила дозволів.

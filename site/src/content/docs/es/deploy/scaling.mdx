Verdin guarda su estado en la base de datos, así que puedes ejecutar varias instancias del mismo
proyecto detrás de un balanceador de carga, por disponibilidad o por carga. Esta página enumera
lo que comparten las instancias, lo que cada una se guarda para sí y los ajustes que importan.

## Lista de comprobación

- **Una base de datos compartida.** PostgreSQL, MySQL o MariaDB. SQLite es un archivo en una
  máquina y no funciona con varias instancias.
- **La misma configuración en todas partes.** Todas las instancias usan el mismo
  `verdin.toml`, los mismos archivos de esquema y los mismos secretos
  (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`, `VERDIN_SSO_<ID>_SECRET`…). Con secretos
  distintos, las sesiones y los tokens de API creados en una instancia los rechazan las demás.
- **Modo producción.** Ejecuta `verdin start`, no `verdin dev`. Cambia el esquema en
  desarrollo, confírmalo en git y migra una vez por despliegue.
- **Almacenamiento de medios compartido.** Usa el proveedor S3
  (`[upload] provider = { name = "s3", … }`), o monta el mismo volumen en todas las instancias
  para el proveedor local.
- **Comprobaciones de salud.** Apunta el balanceador de carga a `GET /_ready`, que responde
  `503` cuando no se puede llegar a la base de datos. `GET /_health` solo indica que el proceso
  está en marcha; úsalo para la comprobación de liveness.
- **El bus de eventos compartido.** Define `[cluster].bus = "database"` en todas las instancias,
  para que los eventos en tiempo real, la presencia, la invalidación de cachés y las
  actualizaciones de búsqueda lleguen a todas (consulta
  [Bus de eventos compartido](#bus-de-eventos-compartido)).
- **Tareas de plugins en una sola instancia.** Define `[plugins].run_jobs = false` en todas las
  instancias salvo una; si no, cada instancia ejecuta las tareas programadas.
- **Métricas por instancia.** Con `[metrics].enabled = true`, cada instancia sirve su propio
  `/_metrics`; haz scrape de cada una.

## Migraciones con varias instancias

`verdin start --migrate` se puede ejecutar sin riesgo en todas las instancias a la vez. Cada
ejecución de migración mantiene un bloqueo en la base de datos (un advisory lock en PostgreSQL,
`GET_LOCK` en MySQL y MariaDB, con una espera de hasta 60 segundos), así que la primera
instancia aplica los pasos y las demás encuentran la base de datos al día.

Durante un despliegue progresivo, las instancias de la versión antigua siguen funcionando un
tiempo contra la base de datos migrada. Los pasos seguros crean tablas, añaden columnas que
admiten nulos o tienen valor por defecto e índices, amplían columnas de texto o añaden valores
de enum, cosas que la versión antigua no nota. Aplica los pasos arriesgados o destructivos
(`verdin migrate apply --allow risky|destructive`) en un despliegue aparte, cuando ninguna
instancia del esquema antiguo necesite ya los datos. Consulta
[Migraciones de esquema](/es/concepts/schema-migrations/).

## Qué se comparte

| Qué | Cómo |
| --- | --- |
| Sesiones de administración, tokens de API, permisos | En la base de datos; no hacen falta sesiones persistentes. |
| Interruptores de funcionalidades y de plugins, idiomas, flujos de revisión | En la base de datos. Cada instancia los vuelve a leer cada `[server].sync_interval_secs` (10 s), así que un cambio hecho en una instancia llega a las demás dentro de ese plazo. |
| Envíos de webhooks | Una cola en la base de datos. Una instancia reclama un envío antes de mandarlo, así que cada uno sale una sola vez. |
| Lanzamientos programados | Se reclaman en la base de datos antes de ejecutarse, así que cada uno se ejecuta una vez. |
| Resumen diario | La ejecución de cada día se reclama en la base de datos, así que los administradores reciben un solo correo. |
| Desafíos de passkeys | Los desafíos usados se registran en la base de datos, así que cada uno se responde una sola vez entre todas las instancias. |
| Purga del registro de auditoría | Se ejecuta en todas las instancias; borrar dos veces las filas antiguas no hace daño. |
| Almacén clave-valor de los plugins | En la base de datos. |
| Eventos en tiempo real, presencia y bloqueos suaves | Con el [bus de eventos](#bus-de-eventos-compartido): un cliente conectado a cualquier instancia recibe los eventos de todas y ve a todos los administradores de una entrada. |
| La caché de respuestas anónimas | Con el bus de eventos, una escritura en cualquier instancia vacía la caché de todas. |
| El índice de búsqueda | Con el bus de eventos, cada instancia vuelve a leer e indexa las entradas que cambian las demás. |
| Imágenes transformadas | Con el bus de eventos, un archivo modificado o borrado sale de la caché de transformaciones de todas las instancias. |

## Qué se queda en cada instancia

- **Los límites de peticiones** los cuenta cada instancia. Con `n` instancias, un cliente puede
  hacer hasta `n` veces `[api].public_rate_limit` peticiones por minuto. Si necesitas un límite
  global, aplícalo en el balanceador de carga.
- **Sin el bus de eventos** (`[cluster].bus = "none"`, el valor por defecto), los eventos en
  tiempo real y la presencia son los de la instancia a la que está conectado cada cliente (usa
  sesiones persistentes para los flujos de eventos), una escritura vacía solo la caché de
  respuestas de su propia instancia (mantén `[api].cache_ttl_secs` en unos pocos segundos, o en
  `0`) y el índice de búsqueda solo sigue las escrituras que hace su instancia.
- **El índice de búsqueda** (`[search]`) vive en el disco de cada instancia. Con el bus de
  eventos, las instancias indexan los cambios de las demás según ocurren; una instancia que
  arranca con un directorio de índice vacío lo construye a partir de la base de datos. Los
  cambios hechos mientras una instancia estaba caída llegan a su índice cuando este se
  reconstruye: borra el directorio antes de arrancarla, o reconstruye tras un despliegue.
- **Las transformaciones de imágenes** (`[upload.transforms]`) se cachean por instancia en
  `cache_dir`. Pon una CDN delante de `/uploads` para compartirlas.
- **Las tareas programadas de los plugins**: consulta `run_jobs` más arriba.

## Bus de eventos compartido

Algunas cosas ocurren en memoria: los flujos en tiempo real, quién está editando qué entrada,
la caché de respuestas anónimas, el índice de búsqueda. El bus de eventos las lleva de la
instancia donde ocurren a las demás.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

O `VERDIN_CLUSTER__BUS=database`, en todas las instancias. El bus usa la base de datos del
proyecto, así que no necesita ningún otro servicio:

- **PostgreSQL**: una instancia escribe cada evento en la tabla `vd_cluster_events` y despierta a
  las demás con `NOTIFY`. Cada instancia reserva una de las conexiones de su pool para `LISTEN`.
  La notificación solo nombra al emisor, así que los eventos de cualquier tamaño quedan por
  debajo del límite de 8000 bytes de PostgreSQL. Si la conexión se cae, la instancia se
  reconecta y lee la tabla para ponerse al día. También lee la tabla cada 30 segundos por si se
  pierde una notificación.
- **MySQL, MariaDB y SQLite**: cada instancia lee las filas nuevas de `vd_cluster_events` cada
  `poll_interval_ms` (1000 por defecto). La consulta usa la clave primaria, así que leer una tabla
  vacía cuesta poco. Reduce el intervalo para actualizaciones más rápidas; el cambio de una
  instancia llega a las demás dentro del intervalo.

Lo que viaja: las escrituras de contenido (a los flujos en tiempo real, la caché de respuestas y
el índice de búsqueda, que vuelve a leer la entrada modificada), los cambios de medios (flujos,
caché, caché de transformaciones), los latidos de presencia y los avisos de comentarios y tareas
para el administrador. Cada instancia ignora sus propios eventos. Los webhooks, las purgas de
CDN, el historial, los registros de auditoría y los hooks de plugins no viajan: la instancia que
hizo el cambio los ejecuta una sola vez.

Las filas se borran a los 10 minutos. Una instancia nueva empieza con el siguiente evento, no
con los anteriores. Una instancia que no puede seguir el ritmo, o que pierde su conexión con la
base de datos, descarta eventos en lugar de retener una escritura. La métrica
`verdin_cluster_events_total` cuenta los eventos enviados, recibidos y descartados (consulta
[Monitorización](/es/deploy/monitoring/#métricas-de-prometheus)).

Cada instancia se nombra en el bus con un id aleatorio en cada arranque, o con
`[cluster].instance_id` si lo defines (el nombre de un pod, por ejemplo). El id solo sirve para
distinguir instancias; nada más depende de él.

Con una sola instancia, deja `bus` en `none`: los eventos se quedan en memoria y no se escribe
nada.

Los backends de Redis y NATS aún no están disponibles. El bus de la base de datos cubre todas
las bases de datos compatibles sin nada más que ejecutar.

## Ajustes

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Define `run_jobs` por instancia con `VERDIN_PLUGINS__RUN_JOBS=false`.

## Conexiones a la base de datos

Cada instancia abre hasta `[database].pool_max` conexiones (10 por defecto). Mantén
`instances × pool_max` por debajo del límite del servidor, con margen para migraciones, copias
de seguridad y mantenimiento. El límite por defecto de PostgreSQL es de 100 conexiones. En PostgreSQL, el bus de eventos reserva una de las conexiones de cada instancia para `LISTEN`.

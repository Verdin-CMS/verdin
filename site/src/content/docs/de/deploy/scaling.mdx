Verdin hält seinen Zustand in der Datenbank, du kannst also mehrere Instanzen desselben
Projekts hinter einem Load Balancer betreiben, für Verfügbarkeit oder Last. Diese Seite listet,
was die Instanzen teilen, was jede für sich behält und welche Einstellungen wichtig sind.

## Checkliste

- **Eine gemeinsame Datenbank.** PostgreSQL, MySQL oder MariaDB. SQLite ist eine Datei auf
  einer Maschine und funktioniert nicht mit mehreren Instanzen.
- **Überall dieselbe Konfiguration.** Jede Instanz nutzt dieselbe `verdin.toml`, dieselben
  Schemadateien und dieselben Secrets (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). Mit unterschiedlichen Secrets lehnen die anderen Instanzen
  Sitzungen und API-Tokens ab, die auf einer Instanz entstanden sind.
- **Produktionsmodus.** Nimm `verdin start`, nicht `verdin dev`. Ändere das Schema in der
  Entwicklung, committe es und migriere einmal pro Deploy.
- **Gemeinsamer Medienspeicher.** Nimm den S3-Provider
  (`[upload] provider = { name = "s3", … }`), oder binde für den lokalen Provider dasselbe
  Volume in jede Instanz ein.
- **Health Checks.** Richte den Load Balancer auf `GET /_ready`, das mit `503` antwortet, wenn
  die Datenbank nicht erreichbar ist. `GET /_health` sagt nur, dass der Prozess läuft; nimm es
  für die Liveness.
- **Der gemeinsame Event-Bus.** Setze `[cluster].bus = "database"` auf jeder Instanz, damit
  Echtzeit-Events, Präsenz, Cache-Invalidierung und Suchaktualisierungen alle erreichen (siehe
  [Gemeinsamer Event-Bus](#gemeinsamer-event-bus)).
- **Plugin-Jobs auf einer Instanz.** Setze `[plugins].run_jobs = false` auf jeder Instanz bis
  auf eine; sonst führt jede Instanz die geplanten Jobs aus.
- **Metriken pro Instanz.** Mit `[metrics].enabled = true` liefert jede Instanz ihr eigenes
  `/_metrics`; scrape jede einzeln.

## Migrationen mit mehreren Instanzen

`verdin start --migrate` kann gefahrlos auf allen Instanzen gleichzeitig laufen. Jeder
Migrationslauf hält eine Sperre in der Datenbank (ein Advisory Lock auf PostgreSQL,
`GET_LOCK` auf MySQL und MariaDB, mit bis zu 60 Sekunden Wartezeit), sodass die erste Instanz
die Schritte anwendet und die anderen die Datenbank aktuell vorfinden.

Während eines Rolling Deploys laufen Instanzen der alten Version noch eine Weile gegen die
migrierte Datenbank. Sichere Schritte legen Tabellen an, fügen nullable Spalten oder Spalten
mit Standardwert und Indizes hinzu, verbreitern Textspalten oder ergänzen Enum-Werte, was die
alte Version nicht bemerkt. Wende riskante oder destruktive Schritte
(`verdin migrate apply --allow risky|destructive`) in einem eigenen Deploy an, sobald keine
Instanz des alten Schemas die Daten mehr braucht. Siehe
[Schemamigrationen](/de/concepts/schema-migrations/).

## Was geteilt wird

| Was | Wie |
| --- | --- |
| Admin-Sitzungen, API-Tokens, Berechtigungen | In der Datenbank; keine Sticky Sessions nötig. |
| Funktionsschalter, Plugin-Schalter, Sprachen, Review-Workflows | In der Datenbank. Jede Instanz liest sie alle `[server].sync_interval_secs` (10 s) neu, eine Änderung auf einer Instanz erreicht die anderen also innerhalb dieser Frist. |
| Webhook-Zustellungen | Eine Warteschlange in der Datenbank. Eine Instanz beansprucht eine Zustellung, bevor sie sie sendet, jede geht also einmal raus. |
| Geplante Releases | Werden vor der Ausführung in der Datenbank beansprucht, jedes läuft also einmal. |
| Täglicher Digest | Der Lauf jedes Tages wird in der Datenbank beansprucht, Admins bekommen also eine E-Mail. |
| Passkey-Challenges | Verbrauchte Challenges werden in der Datenbank festgehalten, jede wird also instanzübergreifend nur einmal beantwortet. |
| Bereinigung des Audit-Logs | Läuft auf jeder Instanz; alte Zeilen doppelt zu löschen schadet nicht. |
| Key-Value-Speicher der Plugins | In der Datenbank. |
| Echtzeit-Events, Präsenz und weiche Sperren | Mit dem [Event-Bus](#gemeinsamer-event-bus): Ein Client, der mit irgendeiner Instanz verbunden ist, bekommt die Events aller Instanzen und sieht jeden Admin in einem Eintrag. |
| Der Antwort-Cache für anonyme Anfragen | Mit dem Event-Bus leert ein Schreibvorgang auf irgendeiner Instanz den Cache jeder Instanz. |
| Der Suchindex | Mit dem Event-Bus liest und indexiert jede Instanz die Einträge neu, die die anderen ändern. |
| Transformierte Bilder | Mit dem Event-Bus verschwindet eine geänderte oder gelöschte Datei aus dem Transform-Cache jeder Instanz. |

## Was auf jeder Instanz bleibt

- **Rate Limits** zählt jede Instanz für sich. Mit `n` Instanzen kann ein Client bis zum
  `n`-Fachen von `[api].public_rate_limit` Anfragen pro Minute stellen. Setze ein globales
  Limit am Load Balancer durch, wenn du eines brauchst.
- **Ohne den Event-Bus** (`[cluster].bus = "none"`, der Standard) sind Echtzeit-Events und
  Präsenz die der Instanz, mit der ein Client verbunden ist (nutze Sticky Sessions für die
  Event-Streams), ein Schreibvorgang leert nur den Antwort-Cache seiner eigenen Instanz (halte
  `[api].cache_ttl_secs` bei wenigen Sekunden oder bei `0`), und der Suchindex folgt nur den
  Schreibvorgängen seiner Instanz.
- **Der Suchindex** (`[search]`) liegt auf der Festplatte jeder Instanz. Mit dem Event-Bus
  indexieren die Instanzen die Änderungen der anderen, sobald sie passieren; eine Instanz, die
  mit leerem Indexverzeichnis startet, baut ihn aus der Datenbank auf. Änderungen, die passiert
  sind, während eine Instanz aus war, erreichen ihren Index, wenn er neu aufgebaut wird: Lösche
  das Verzeichnis vor dem Start oder baue nach einem Deploy neu auf.
- **Bildtransformationen** (`[upload.transforms]`) werden pro Instanz unter `cache_dir`
  gecacht. Stell ein CDN vor `/uploads`, um sie zu teilen.
- **Geplante Plugin-Jobs**: siehe `run_jobs` oben.

## Gemeinsamer Event-Bus

Manches passiert im Arbeitsspeicher: die Echtzeit-Streams, wer welchen Eintrag bearbeitet, der
Antwort-Cache für anonyme Anfragen, der Suchindex. Der Event-Bus trägt es von der Instanz, auf
der es passiert, zu den anderen.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Oder `VERDIN_CLUSTER__BUS=database`, auf jeder Instanz. Der Bus nutzt die Datenbank des
Projekts und braucht deshalb keinen weiteren Dienst:

- **PostgreSQL**: Eine Instanz schreibt jedes Event in die Tabelle `vd_cluster_events` und
  weckt die anderen mit `NOTIFY`. Jede Instanz behält eine ihrer Pool-Verbindungen für
  `LISTEN`. Die Benachrichtigung nennt nur den Absender, sodass Events jeder Größe unter dem
  Limit von 8000 Byte in PostgreSQL bleiben. Bricht die Verbindung ab, verbindet sich die
  Instanz neu und liest die Tabelle, um aufzuholen. Sie liest die Tabelle außerdem alle 30
  Sekunden, falls eine Benachrichtigung verloren geht.
- **MySQL, MariaDB und SQLite**: Jede Instanz liest neue Zeilen von `vd_cluster_events` alle
  `poll_interval_ms` (standardmäßig 1000). Die Abfrage nutzt den Primärschlüssel, eine leere
  Tabelle zu lesen kostet also wenig. Senke das Intervall für schnellere Aktualisierungen; die
  Änderung einer Instanz erreicht die anderen innerhalb des Intervalls.

Was übertragen wird: Content-Schreibvorgänge (an die Echtzeit-Streams, den Antwort-Cache und
den Suchindex, der den geänderten Eintrag erneut liest), Medienänderungen (Streams, Cache,
Transform-Cache), Präsenz-Heartbeats sowie Kommentar- und Aufgabenhinweise für den Admin. Jede
Instanz ignoriert ihre eigenen Events. Webhooks, CDN-Purges, Verlauf, Audit-Logs und
Plugin-Hooks werden nicht übertragen: Die Instanz, die die Änderung gemacht hat, führt sie
einmal aus.

Zeilen werden nach 10 Minuten gelöscht. Eine neue Instanz beginnt mit dem nächsten Event, nicht
mit den früheren. Eine Instanz, die nicht mithalten kann oder ihre Datenbankverbindung
verliert, verwirft Events, statt einen Schreibvorgang aufzuhalten. Die Metrik
`verdin_cluster_events_total` zählt gesendete, empfangene und verworfene Events (siehe
[Monitoring](/de/deploy/monitoring/#prometheus-metriken)).

Jede Instanz nennt sich auf dem Bus bei jedem Start mit einer zufälligen ID oder mit
`[cluster].instance_id`, falls du sie setzt (zum Beispiel einen Pod-Namen). Die ID
unterscheidet die Instanzen nur; nichts anderes hängt von ihr ab.

Lass `bus` bei einer einzigen Instanz auf `none`: Events bleiben im Arbeitsspeicher und nichts
wird geschrieben.

Redis- und NATS-Backends gibt es noch nicht. Der Datenbank-Bus deckt jede unterstützte
Datenbank ab, ohne dass etwas anderes laufen muss.

## Einstellungen

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Setze `run_jobs` pro Instanz mit `VERDIN_PLUGINS__RUN_JOBS=false`.

## Datenbankverbindungen

Jede Instanz öffnet bis zu `[database].pool_max` Verbindungen (standardmäßig 10). Halte
`instances × pool_max` unter dem Limit des Servers, mit Luft für Migrationen, Backups und
Wartung. Das Standardlimit von PostgreSQL liegt bei 100 Verbindungen. Auf PostgreSQL behält der
Event-Bus eine der Verbindungen jeder Instanz für `LISTEN`.

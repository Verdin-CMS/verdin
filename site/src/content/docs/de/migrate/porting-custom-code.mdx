`verdin import strapi` übernimmt Schema und Inhalte eines Strapi-Projekts, aber nicht das
JavaScript in `src/`: Verdin führt auf dem Server kein JavaScript aus. Dieser Code wird zu einem
[WebAssembly-Plugin](/de/extending/plugins/): Hooks für Lifecycles, Routen für eigene Controller,
eine Startfunktion für `bootstrap`, Jobs für Cron-Tasks. Diese Seite ordnet jede Art von
Strapi-Code ihrem Verdin-Gegenstück zu, führt durch den in ein Plugin portierten Code eines
echten Projekts und listet die Grenzen, die du einplanen musst.

Das durchgespielte Beispiel ist
[`examples/strapi-port`](https://github.com/Verdin-CMS/verdin/tree/main/examples/strapi-port):
das Plugin `tienda`, in Rust geschrieben, mit dem Schema, das es braucht, und einer README, die es
baut und installiert. Lies zuerst das [Plugin-Tutorial](/de/extending/plugin-tutorial/), wenn du
noch nie ein Plugin geschrieben hast; die [Plugin-Referenz](/de/extending/plugin-reference/) hat
jede Payload und jede Host-Funktion.

## Wohin jedes Stück gehört

| Strapi | Verdin | Hinweise |
| --- | --- | --- |
| Eigene Routen und Controller (`src/api/*/routes`, `controllers`) | Plugin-Routen: `[routes]`, eine Funktion für `/api/plugins/<name>/…` | Die URL ändert sich. Die Funktion verteilt selbst nach Methode und Pfad. |
| Lifecycles (`lifecycles.js`), Middlewares des Document Service | `[[hooks]]` auf `beforeCreate`, `afterUpdate`… | Dieselben Event-Namen. Before-Hooks können die Daten ersetzen oder den Schreibvorgang ablehnen. |
| Services (`src/api/*/services`) | Funktionen im Modul des Plugins und `verdin_content` für `strapi.documents(…)` | Keine geteilten Services zwischen Plugins. |
| `bootstrap()` in `src/index.js` | Funktion `[startup]` | Läuft beim Start, wenn das Plugin eingeschaltet wird und wenn sich seine Einstellungen ändern. |
| `register()` | Nichts zu portieren | Das Manifest deklariert, was `register` eingerichtet hat. |
| Cron-Tasks (`config/cron-tasks.js`) | `[[jobs]]` | Cron-Syntax in UTC, Sekunden optional. |
| Plugin-Konfiguration (`config/plugins.js`) | `[[settings]]` und `verdin_config` | Bearbeitet unter **Einstellungen → Plugins**. |
| `strapi.log` | `verdin_log` | Server-Log und **Einstellungen → Plugins → Protokolle**. |
| Admin-Widgets (`app.widgets.register`) | `[[admin.widgets]]`: Web Components | Oder die eingebauten Dashboard-Widgets. |
| Benutzerdefinierte Felder | `[[admin.fields]]` | Der Name `customField` im Schema bleibt erhalten. |
| Injection Zones, eigene Admin-Seiten, React-Erweiterungen | Nicht unterstützt | Das Branding steht in `[admin.branding]`. |
| Ein eigener Endpunkt, der Formulareinsendungen speichert | Eingebaute [Formulare](/de/guides/frontend/forms/) | Validierung, Spam-Falle, Rate Limit, E-Mails und CSV-Export inklusive. |
| Policies und Middlewares | Eingebaute Berechtigungen, Rate Limits und CORS; Prüfungen in deinen Plugin-Routen | Kein Einstiegspunkt in die Request-Pipeline. Siehe [Policies und Middlewares](#policies-und-middlewares). |
| E-Mails aus Code (`strapi.plugin('email')`) | Die HTTP-API eines E-Mail-Providers, über die Fähigkeit `http` | Keine E-Mail-Host-Funktion. |

## Das Beispielprojekt

Das Strapi-Projekt hinter dem Beispiel ist ein kleiner Shop mit Umfragen:

- **`producto`**: Produkte, mit den Flags `a_la_venta` (im Verkauf) und `reservable`.
- **`reserva`**: Reservierungen, die Besucher senden. Ein Lifecycle `beforeCreate` setzt
  `estado` auf `pendiente`, prüft, dass das zugehörige Produkt im Verkauf und reservierbar ist,
  und begrenzt `unidades` auf 1–10.
- **`encuesta`** und **`voto`**: Umfragen mit einer Liste von Optionen und ihre Stimmen. Zwei
  eigene Routen, `POST /api/polls/:slug/vote` und `GET /api/polls/:slug/results`, erlauben eine
  Stimme pro Besucher und Umfrage, nur in offenen Umfragen und nur für eine gültige Option. Ein
  Cron-Task schließt Umfragen, deren Datum `cierra_el` vorbei ist.
- **`bootstrap`** setzt die Berechtigungen der öffentlichen Rolle, damit eine frische
  Installation nicht offen bleibt.
- Ein **Admin-Widget** zeigt die offenen Umfragen.

In Verdin ist das alles ein Plugin, `tienda`:

<FileTree>
- examples/strapi-port/
  - verdin.toml
  - schema/
    - content-types/ producto, reserva, encuesta, voto
  - plugin/
    - Cargo.toml
    - plugin.toml das Manifest
    - src/lib.rs Hooks, Routen, der Job und die Startfunktion
    - admin/index.js das Dashboard-Widget
</FileTree>

```toml title="plugin/plugin.toml (abridged)"
name = "tienda"
version = "0.1.0"

[capabilities]
read = ["api::producto"]
write = ["api::voto", "api::encuesta"]
public_permissions = true

[[hooks]]
on = "beforeCreate"
uid = "api::reserva"
function = "before_create_reserva"

[routes]
function = "handle"

[[jobs]]
schedule = "*/15 * * * *"
function = "close_polls"

[startup]
function = "startup"
```

UIDs von Inhaltstypen sind kürzer als die von Strapi: `api::producto`, nicht
`api::producto.producto`.

## Lifecycles zu Hooks

Der Strapi-Lifecycle, vereinfacht:

```js title="src/api/reserva/content-types/reserva/lifecycles.js"
const { errors } = require('@strapi/utils');

module.exports = {
  async beforeCreate(event) {
    const { data } = event.params;
    data.estado = 'pendiente';
    const documentId = data.producto?.connect?.[0]?.documentId ?? data.producto;
    const producto = await strapi.documents('api::producto.producto').findOne({ documentId });
    if (!producto?.a_la_venta || !producto.reservable) {
      throw new errors.ApplicationError('This product cannot be reserved');
    }
    data.unidades = Math.min(Math.max(parseInt(data.unidades, 10) || 1, 1), 10);
  },
};
```

Der Verdin-Hook erhält `{ event, uid, documentId, locale, data }` und antwortet `{ "data": … }`,
um zu ersetzen, was geschrieben wird, `{ "error": "…" }`, um den Schreibvorgang abzulehnen (der
Client bekommt ein `400` mit der Meldung, wie bei Strapis `ApplicationError`), oder `{}`, um ihn
durchzulassen:

```rust title="plugin/src/lib.rs (abridged)"
#[plugin_fn]
pub fn before_create_reserva(Json(input): Json<Value>) -> FnResult<Json<Value>> {
    let mut data = input["data"].clone();
    data["estado"] = json!("pendiente");

    let Some(producto_id) = relation_id(&data["producto"]) else {
        return Ok(Json(json!({ "error": "Choose a product to reserve" })));
    };
    let found = content(json!({ "op": "findOne", "uid": "api::producto", "documentId": producto_id }))?;
    let producto = &found["document"];
    if producto.is_null() {
        return Ok(Json(json!({ "error": "The product does not exist or is not published" })));
    }
    if producto["a_la_venta"] != true {
        return Ok(Json(json!({ "error": "The product is not on sale" })));
    }
    if producto["reservable"] != true {
        return Ok(Json(json!({ "error": "The product cannot be reserved" })));
    }

    let max = settings()["maxUnidades"].as_i64().unwrap_or(10).max(1);
    let unidades = as_number(&data["unidades"]).map_or(1, |n| n.round() as i64);
    data["unidades"] = json!(unidades.clamp(1, max));
    Ok(Json(json!({ "data": data })))
}
```

Was du beim Portieren von Lifecycles wissen musst:

- **`data` sind die Daten der Anfrage, wie gesendet.** Eine Relation kann als documentId, als
  `{ "documentId": … }`, als Liste oder als `{ connect }` / `{ set }` ankommen (das Admin-Panel
  und Clients unterscheiden sich). Das `relation_id` des Beispiels akzeptiert alle. Bei
  `beforeUpdate` enthält `data` nur die gesendeten Felder.
- **Die Daten, die du zurückgibst, werden validiert** wie das Original, nach dem Hook: Ein Hook
  kann nichts schreiben, was das Schema ablehnt. Schemagrenzen (`min`, `max`) lehnen einen Wert
  ab; ein Hook kann ihn stattdessen begrenzen, wie hier.
- **Hooks wissen nicht, wer schreibt.** Die Eingabe enthält keinen Benutzer und kein Token.
  Prüfungen, die vom Aufrufer abhängen, gehören in die Berechtigungen oder in eine Plugin-Route.
- **After-Hooks bekommen keine Daten**: `{ event, uid, documentId, locale }`, gesendet, sobald der
  Schreibvorgang committet ist. Lies den Eintrag mit `verdin_content`, wenn du ihn brauchst.
- **Ein fehlschlagender Hook blockiert den Schreibvorgang nicht.** Stürzt das Modul ab oder läuft
  in ein Timeout, wird der Fehler protokolliert und der Schreibvorgang geht weiter; nur eine
  Antwort `{ error }` lehnt ihn ab.
- **Schreibvorgänge durch Plugins überspringen Before-Hooks.** Eine Regel, die für jeden
  Schreibvorgang gelten muss, muss auch von jedem Plugin-Code angewendet werden, der diesen Typ
  schreibt.

## Controller und eigene Routen zu Plugin-Routen

Strapi lieferte die Umfrage-Routen unter `/api/polls/:slug/vote` aus. Ein Verdin-Plugin liefert
alles unter `/api/plugins/<name>/` aus, das Frontend ruft also
`/api/plugins/tienda/polls/:slug/vote` auf (oder ein Reverse Proxy schreibt den alten Pfad um).
Eine exportierte Funktion erhält jede Anfrage und verteilt nach Methode und Pfad:

```rust title="plugin/src/lib.rs (abridged)"
#[plugin_fn]
pub fn handle(Json(request): Json<Value>) -> FnResult<Json<Value>> {
    let method = request["method"].as_str().unwrap_or_default();
    let path = request["path"].as_str().unwrap_or_default();
    let segments: Vec<&str> = path.split('/').filter(|part| !part.is_empty()).collect();
    let response = match (method, segments.as_slice()) {
        ("GET", ["polls"]) => open_polls()?,
        ("POST", ["polls", slug, "vote"]) => vote(slug, &request)?,
        ("GET", ["polls", slug, "results"]) => results(slug)?,
        (_, ["polls"] | ["polls", _, "vote" | "results"]) => fail(405, "Method not allowed"),
        _ => fail(404, "Not Found"),
    };
    Ok(Json(response))
}
```

Die Anfrage ist `{ method, path, query, headers, body, actor }`, mit `body` als String, den du
selbst parst, und `query` als rohem Query-String. Die Antwort ist `{ status, headers?, body }`.
Nichts formt sie für dich: Damit ein Strapi-Frontend weiter funktioniert, antworte `{ "data": … }`
und bei Fehlern `{ "data": null, "error": { "status", "name", "message", "details" } }`, wie es
die Helfer `ok` und `fail` des Beispiels tun.

Die Stimmen-Route prüft der Reihe nach: einen gültigen Body, eine Umfrage mit diesem Slug,
`estado` ist `abierta`, die Option ist eine der `opciones`, und keine frühere Stimme mit
demselben Fingerprint. Dann legt sie das `voto` an und antwortet mit 201 und den Ergebnissen.

<Aside type="caution" title="Keine Client-Adresse in Plugin-Routen">
Plugin-Routen erhalten nur die Header `content-type`, `accept`, `user-agent` und
`accept-language`: keine IP-Adresse, keine Cookies und keinen Wert von `Authorization`. Ein
Strapi-Controller, der `ctx.request.ip` für „eine Stimme pro Besucher“ nutzte, braucht einen
anderen Schlüssel. Das Beispiel nimmt einen `fingerprint` aus dem Request-Body, den die Website
erzeugt (eine zufällige ID im Local Storage oder ein Hash von Browsermerkmalen). Er stoppt
Doppelklicks und beiläufige Wiederholungen, nicht einen entschlossenen Abstimmer. Für stärkere
Limits verlange einen angemeldeten Endbenutzer (den `actor`) oder setze die Prüfung vor Verdin.
</Aside>

Weitere Unterschiede zu Strapi-Routen:

- **Routen sind öffentlich.** Öffentlicher Zugriff und die Berechtigungen von API-Tokens werden
  nicht angewendet. `actor` sagt, wer aufruft: `{ "kind": "public" }`,
  `{ "kind": "token", "id": … }` oder `{ "kind": "user", "id": … }` (ein Endbenutzer; nur die
  ID). Lehne ab, was der Aufrufer nicht tun darf, wie es eine Strapi-Policy täte. Ein ungültiges
  Token wird mit `401` abgelehnt, bevor das Plugin läuft.
- **Ein Aufruf pro Plugin gleichzeitig.** Aufrufe an ein Plugin warten aufeinander, sodass sich
  Prüfung und Anlegen in der Stimmen-Route auf einer Instanz nicht überschneiden können. Bei
  mehreren Instanzen können sie es; das Beispiel speichert außerdem eine `clave`
  (`<poll>:<fingerprint>`) mit `unique: true`, sodass die Datenbank ein Duplikat ablehnt, das
  durchrutscht.
- **Rate Limits gelten**: `[api].public_rate_limit` und `[api].token_rate_limit` zählen
  Plugin-Routen wie den Rest der Content-API.
- **Anonyme `GET`-Antworten können gecacht werden**, wenn `[api].cache_ttl_secs` gesetzt ist.
  Content-Schreibvorgänge leeren den Cache, Stimmen eingeschlossen.
- **Nur manche Response-Header bleiben erhalten**: `content-type`, `cache-control`, `location`,
  `etag`, `last-modified` und `content-disposition`.

## Services zu Funktionen und Content-Aufrufen

Ein Strapi-Service ist geteilter Code; in einem Plugin ist er eine gewöhnliche Funktion im Modul.
Aufrufe von `strapi.documents(uid)` werden zu `verdin_content`-Aufrufen, begrenzt durch die
Fähigkeiten `read` und `write`:

| Strapi | `verdin_content` |
| --- | --- |
| `findMany({ filters, sort, populate, … })` | `{ "op": "findMany", "uid", "query": { "filters", "sort", "populate", "pagination", … } }` |
| `findOne({ documentId })` | `{ "op": "findOne", "uid", "documentId" }` |
| `create({ data })` | `{ "op": "create", "uid", "data" }` |
| `update({ documentId, data })` | `{ "op": "update", "uid", "documentId", "data" }` |
| `delete({ documentId })` | `{ "op": "delete", "uid", "documentId" }` |
| `publish` / `unpublish` | `{ "op": "publish" }` / `{ "op": "unpublish" }` |
| `count({ filters })` | `findMany` mit `"pagination": { "pageSize": 1 }`, dann `meta.pagination.total` |

- **Lesezugriffe liefern veröffentlichte Versionen**, sofern die Abfrage nicht
  `"status": "draft"` verlangt. Ein Hook, der ein Produkt nachschlägt, das nur als Entwurf
  existiert, findet nichts, wie die Fehlermeldung des Beispiels sagt.
- **Schreibvorgänge sind veröffentlicht**, sofern die Anfrage nicht `"status": "draft"` hat, wie
  ein REST-Schreibvorgang.
- **Die Abfrage folgt den Regeln der REST-API.** `private`-Attribute können nicht in Filtern oder
  `fields` genutzt werden, daher ist die `clave` des Beispiels nicht private (die öffentliche
  Rolle hat keinen Zugriff auf Stimmen, sie liest also sonst niemand).
- **Kein rohes SQL, kein `strapi.db.query`.** Alles läuft über den Document Service, mit seiner
  Validierung, seinen Webhooks, dem Verlauf und dem Audit-Log.
- **Keine Uhr ohne WASI.** Setze `wasi = true` im Manifest für Zeit und Zufallszahlen; der Job
  des Beispiels nutzt stattdessen das `scheduledAt`, das er erhält.

## `bootstrap` zur Startfunktion

Strapi-Projekte setzen die Berechtigungen der öffentlichen Rolle oft in `bootstrap`, damit eine
frische Datenbank nutzbar ist und nicht mehr offen ist als nötig. Die Startfunktion von Verdin
tut dasselbe mit der Fähigkeit `public_permissions`:

```toml title="plugin/plugin.toml"
[capabilities]
public_permissions = true

[startup]
function = "startup"
```

```rust title="plugin/src/lib.rs (abridged)"
#[plugin_fn]
pub fn startup(Json(input): Json<Value>) -> FnResult<Json<Value>> {
    let permissions = json!([
        { "subject": "api::producto", "action": "find" },
        { "subject": "api::producto", "action": "findOne" },
        { "subject": "api::encuesta", "action": "find" },
        { "subject": "api::encuesta", "action": "findOne" },
        { "subject": "api::reserva", "action": "create" },
    ]);
    let result = unsafe {
        verdin_public_permissions(Json(json!({ "op": "set", "permissions": permissions })))?
    }
    .0;
    if let Some(error) = result["error"].as_str() {
        return Ok(Json(json!({ "error": format!("public permissions: {error}") })));
    }
    Ok(Json(json!({})))
}
```

- Sie läuft mit `{ "reason": "start" | "enabled" | "settings" }`: wenn der Server mit
  eingeschaltetem Plugin startet, wenn das Plugin eingeschaltet wird und wenn sich seine
  Einstellungen ändern. Mach sie gefahrlos wiederholbar: Suche nach dem, was du anlegst, bevor du
  es erstellst.
- `set` **ersetzt alle** öffentlichen Berechtigungen, Änderungen unter **Einstellungen →
  Öffentlicher Zugriff** werden also beim nächsten Start rückgängig gemacht. Das Beispiel hat
  eine Einstellung, um das auszuschalten.
- Sie läuft im Hintergrund auf einer eigenen Modulinstanz, mit eigenem Zeitlimit
  (`[startup].timeout_ms`, standardmäßig 30 Sekunden), sodass ein langsames Seeding Hooks und
  Routen nicht aufhält. Ein Fehlschlag oder eine Antwort `{ "error" }` wird protokolliert; das
  Plugin bleibt eingeschaltet.
- Bei mehreren Instanzen führen sie nur die mit `[plugins].run_jobs = true` aus.

## Cron-Tasks zu Jobs

```js title="config/cron-tasks.js"
module.exports = {
  closePolls: {
    task: async ({ strapi }) => { /* close polls past cierra_el */ },
    options: { rule: '*/15 * * * *' },
  },
};
```

```toml title="plugin/plugin.toml"
[[jobs]]
schedule = "*/15 * * * *"
function = "close_polls"
```

Der Job erhält `{ "scheduledAt": "…" }` und aktualisiert im Beispiel jede offene Umfrage, deren
`cierra_el` früher liegt. Jobs laufen in UTC, nur solange das Plugin eingeschaltet ist, und nur
auf Instanzen mit `[plugins].run_jobs = true`. Ein Lauf, der verpasst wurde, während der Server
aus war, wird nicht nachgeholt.

## Admin-Widgets

Ein Strapi-Admin-Widget ist eine React-Komponente; ein Verdin-Widget ist ein Custom Element im
`admin/`-Skript des Plugins, im Manifest deklariert:

```toml title="plugin/plugin.toml"
[admin]
script = "index.js"

[[admin.widgets]]
id = "polls"
title = "Open polls"
element = "tienda-polls"
```

Das Element bekommt einen `context` mit `fetch`. Das Widget des Beispiels ruft die eigene Route
`GET /api/plugins/tienda/polls` des Plugins auf. Anfragen an die Content-API (Plugin-Routen
eingeschlossen) gehen ohne die Sitzung des Admins raus, eine Route, die ein Widget nutzt, muss
also für die Öffentlichkeit in Ordnung sein oder ein API-Token akzeptieren. Injection Zones,
eigene Admin-Seiten und React-Erweiterungen haben kein Gegenstück. Siehe
[Erweiterungspunkte im Admin-Panel](/de/extending/plugin-reference/#erweiterungspunkte-im-admin-panel).

## Eigene Formulare zu Formularen

Ein Vorschlags- oder Kontaktformular ist in Strapi meist ein eigener Endpunkt (oder ein
Inhaltstyp mit öffentlicher Berechtigung `create`) plus Code, der jemandem eine E-Mail schickt.
Portiere es nicht: Die eingebaute Funktion [Formulare](/de/guides/frontend/forms/) erledigt das
alles ohne Code. Redakteure definieren die Felder im Admin, die Website sendet per
`POST /api/_forms/{slug}`, und Einsendungen werden validiert, an die Adressen unter
**Benachrichtigen** gemailt und als CSV exportiert. Formulare haben außerdem eine Spam-Falle und
ein Rate Limit pro Besucher (10 Einsendungen pro Minute), was eine Plugin-Route nicht kann, weil
sie die Adresse des Clients nicht sieht.

## Policies und Middlewares

Verdin hat keinen Einstiegspunkt in die HTTP-Request-Pipeline. Was es stattdessen bietet:

| Strapi | Verdin |
| --- | --- |
| Policies im Stil von `is-authenticated` auf REST-Routen | Öffentlicher Zugriff, Berechtigungen von API-Tokens und Rollen von Endbenutzern. Siehe [Berechtigungen](/de/reference/permissions/). Feinere Regeln (ein Endbenutzer, der nur seine eigenen Einträge bearbeitet) brauchen eine Plugin-Route. |
| Eine Policy auf einer eigenen Route | Prüfe `actor` in der Plugin-Route. |
| Eine Rate-Limit-Middleware | `[api].public_rate_limit`, `[api].token_rate_limit` und `[admin].auth_rate_limit`. |
| Eine CORS- oder Security-Header-Middleware | `[api].cors_origins`; andere Response-Header am Reverse Proxy. |
| Eine Middleware, die Anfragen oder Antworten von Core-Routen umschreibt | Nicht unterstützt. Nutze eine Plugin-Route für das neue Verhalten oder einen Reverse Proxy. |
| Eine Policy, die manche Schreibvorgänge ablehnt | Ein Before-Hook, der `{ error }` antwortet, ohne den Aufrufer zu kennen. |

## Grenzen, die du einplanen musst

- **Keine Client-Adresse und wenige Header** in Plugin-Routen (siehe oben).
- **Schreibvorgänge durch Plugins überspringen die Before-Hooks jedes Plugins**, Regeln in
  Before-Hooks gelten für sie also nicht.
- **After-Hooks, die durch die eigenen Schreibvorgänge eines Plugins ausgelöst werden, laufen,
  nachdem sein Aufruf zurückgekehrt ist**, nicht im Schreibvorgang, und Hooks, die schreiben,
  verschachteln sich höchstens 4 Ebenen tief (siehe
  [Schreibvorgänge durch Plugins](/de/extending/plugin-reference/#schreibvorgänge-durch-plugins)).
  Erledige Folgearbeit, die vor der Antwort passieren muss, in dem Code, der schreibt, nachdem
  `verdin_content` zurückgekehrt ist.
- **Ein Aufruf pro Plugin gleichzeitig**: Eine langsame Route verzögert die Hooks dieses
  Plugins. Halte Aufrufe kurz und beobachte `verdin_plugin_call_duration_seconds` in den
  [Metriken](/de/deploy/monitoring/).
- **Routen sind öffentlich** und müssen `actor` prüfen.
- **Verdin 0.11 oder neuer** für die Startfunktion und `verdin_public_permissions`: Ein Modul,
  das eine Host-Funktion importiert, die der Server nicht hat, wird gar nicht geladen.

## Checkliste

<Steps>

1. Importiere das Projekt mit `verdin import strapi` und liste dann den Code in `src/` auf:
   Routen, Controller, Services, Lifecycles, Policies, Middlewares, `bootstrap`, Cron-Tasks und
   Admin-Erweiterungen.
2. Lass weg, was Verdin eingebaut kann: Formulare, von Hand gesetzte öffentliche
   Berechtigungen, Rate Limits, CORS, Webhooks, geplantes Veröffentlichen
   ([Releases](/de/guides/content/releases/)).
3. Schreibe ein Plugin mit dem Rest, nach dem Beispiel: Hooks, Routen, ein Job, eine
   Startfunktion. Gib ihm nur die Fähigkeiten, die es braucht.
4. Prüfe, dass Hooks, die Inhalte schreiben, sich nicht auf Verschachtelung tiefer als 4 Ebenen
   verlassen.
5. Baue es, installiere es unter `plugins/`, schalte es unter **Einstellungen → Plugins** ein
   und lies dort sein Log.
6. Aktualisiere das Frontend: URLs der Plugin-Routen (`/api/plugins/<name>/…`), Fingerprints
   oder Endbenutzer-Anmeldung, wo der Code sich auf die Adresse des Clients stützte, und die
   [anderen Änderungen](/de/migrate/from-strapi/#änderungen-am-frontend) einer Migration.

</Steps>

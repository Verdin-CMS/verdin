이 페이지에서는 프로젝트를 새 Verdin 버전으로 옮기는 방법을 설명하고, 마이너 버전 사이에 바뀐 것을 나열합니다. Verdin은
0.x 방식을 더한 [Semantic Versioning](https://semver.org/)을 따릅니다. 1.0 전까지 **마이너** 릴리스(0.8 → 0.9)는 동작이
바뀔 수 있고, **패치** 릴리스(0.9.0 → 0.9.1)는 수정과 보안 강화만 합니다.

## 업그레이드하기 전에

1. 현재 버전부터 새 버전까지의 **changelog를 읽으세요**. [changelog](/ko/project/changelog/)에 모든 변경이 있고,
   [아래 참고 사항](#업그레이드-참고-사항)은 조치가 필요한 것을 요약합니다.
2. 데이터베이스와 미디어 스토리지를 **백업하세요**([백업](/ko/deploy/backups/) 참고). 이전 버전으로 돌아가려면 그 백업을
   복원해야 합니다. 이전 버전은 새 버전이 추가한 테이블과 컬럼을 되돌리지 않습니다.
3. 참고 사항에 프런트엔드나 편집자가 의존하는 동작이 언급되어 있으면 프로덕션 **사본에서 시험해 보세요**.

버전을 건너뛸 수 있습니다. 마이그레이션은 릴리스마다 하나씩 재생하는 것이 아니라 데이터베이스와 새 버전이 기대하는 것의
차이로 계산하므로, 0.6 → 0.9도 한 번에 마이그레이션됩니다. 그 사이 모든 버전의 참고 사항을 읽으세요.

## 업그레이드

<Tabs syncKey="install">
<TabItem label="Docker">

<Steps>

1. Compose 파일, 매니페스트, `Dockerfile`에서 이미지 태그를 바꿉니다. 예: `ghcr.io/verdin-cms/verdin:0.10` →
   `ghcr.io/verdin-cms/verdin:0.11`. 마이너 태그(`0.10`)는 패치 릴리스를 따라갑니다. 패치가 들어오는 시점도 직접 정하려면
   전체 버전(`0.10.0`)을 고정하세요.

2. 이미지를 받고 재시작합니다.

   ```sh frame="terminal"
   docker compose pull verdin
   docker compose up -d verdin
   docker compose logs -f verdin
   ```

   이미지의 기본 명령인 `start --migrate`가 서비스하기 전에 새 버전의 마이그레이션을 적용합니다. 로그에서
   `applied migrations`와 `verdin listening`을 확인하세요.

</Steps>

</TabItem>
<TabItem label="Binary">

<Steps>

1. [릴리스 페이지](https://github.com/Verdin-CMS/verdin/releases)에서 플랫폼용 아카이브(예:
   `verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz`)를 내려받고, 릴리스의 `SHA256SUMS`로 확인합니다.

   ```sh frame="terminal"
   sha256sum --ignore-missing -c SHA256SUMS
   tar xzf verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz
   ```

2. 서버를 멈추고, `verdin` 바이너리를 교체하고, 버전을 확인합니다.

   ```sh frame="terminal"
   verdin version
   ```

3. 프로젝트 디렉터리에서 마이그레이션을 검토하고 적용합니다.

   ```sh frame="terminal"
   verdin migrate plan
   verdin migrate apply
   ```

   또는 safe 단계를 먼저 적용하는 `verdin start --migrate`로 시작하세요.

4. 평소처럼 서버를 시작합니다(`verdin start`).

</Steps>

</TabItem>
</Tabs>

## 시작할 때의 마이그레이션

새 버전은 흔히 자체 테이블이나 컬럼(세션, 설정, 새 기능)을 추가합니다. `verdin start`는 데이터베이스를 스키마와 새
버전이 필요로 하는 것과 비교합니다.

- 일치하면 시작합니다.
- 대기 중인 단계가 있으면 시작을 거부하고, `verdin migrate plan`과 `verdin migrate apply`를 실행하거나 `--migrate`로
  시작하라고 알려 줍니다.
- `--migrate`는 **safe** 단계만 적용합니다. risky나 destructive 단계가 있으면 시작이 실패하며, 플랜을 읽은 뒤
  `verdin migrate apply --allow risky`(또는 `destructive`)로 직접 적용합니다.
- 스키마 변경을 트랜잭션에서 실행할 수 없는 MySQL과 MariaDB에서는 중단된 마이그레이션이 다음 `verdin migrate apply`에서
  실패한 단계부터 재개됩니다.

인스턴스가 여러 개면 롤링 업그레이드가 동작합니다. 첫 새 인스턴스가 마이그레이션 잠금을 잡고 마이그레이션하며, 나머지는
기다렸다가 할 일이 남지 않은 것을 확인합니다. [여러 인스턴스 실행](/ko/deploy/scaling/)을 참고하세요.

<Aside type="caution">
프로젝트 전체를 한 버전으로 업그레이드하세요. 두 마이너 버전의 인스턴스를 롤링 배포에 걸리는 시간보다 오래 나란히 실행하지
마세요.
</Aside>

## 업그레이드 참고 사항

버전별 주요 변경과 호환성을 깨는 변경이며, 오래된 것이 마지막입니다. 전체 목록은 [changelog](/ko/project/changelog/)에
있습니다.

### 0.9.1 → 0.10

데이터베이스 마이그레이션은 없습니다. 문서가 `docs/`에서 이 사이트로 옮겨졌습니다.

- **`review-workflows.updateEntryStage` 웹훅 수신자**: `model`은 이제 항목 이벤트처럼 단수 이름(`article`)이고, uid는
  `uid`로 옮겨졌습니다. `model`을 쓰던 곳에서는 `uid`를 읽으세요.
- **TypeScript 타입을 다시 생성하세요**(`verdin types`). `Collections`와 `Singles`가 이제 타입 별칭이며,
  `createClient<VerdinSchema>`에 이것이 필요합니다.
- **Docker**: 이미지는 변환 캐시와 검색 인덱스를 `/data`에 두고 `/app/public/uploads`를 `/data/uploads`로 링크합니다. 읽기
  전용 `/app`을 피하려고만 `VERDIN_UPLOAD__TRANSFORMS__CACHE_DIR`나 `VERDIN_SEARCH__DIR`를 설정했다면 지워도 됩니다.
  이미지에 `HEALTHCHECK`가 있습니다.
- **CDN**: 응답에 populate할 수 있는 타입의 태그가 붙으므로, 퍼지가 전보다 더 많은 캐시를 새로 고칩니다. 바꿀 것은 없습니다.
- 관리자 패널의 관계 필드는 인라인 검색 상자 대신 대화 상자(**항목 연결**)로 항목을 연결합니다.

### 0.9.0 → 0.9.1

보안 강화 릴리스이며, 모든 설치에서 업그레이드를 권장합니다. 마이그레이션(새 테이블 하나, 새 컬럼 두 개)은 시작할 때
실행됩니다.

- **리버스 프록시 뒤에서는 `[server].trusted_proxies`를 설정하세요.** 나열한 프록시의 `X-Forwarded-For`만 클라이언트
  주소로 씁니다. 그러지 않으면 프록시 뒤의 모든 클라이언트가 요청 한도와 감사 로그에서 주소 하나를 공유합니다.
- **다른 출처의 브라우저 프런트엔드에는 `[api].cors_origins`가 필요합니다.** 0.9.1이 콘텐츠 API와 GraphQL에 CORS를
  추가했습니다. 이전에는 CORS 지원이 없었습니다.
- **관계를 통한 읽기가 권한을 따릅니다.** `populate`, 관계 필터, 관계 정렬은 모든 API에서 호출자가 읽을 수 있는 타입과
  필드에만 닿습니다. `find` 권한이 없는 타입을 populate하던 공개 요청과 토큰 요청은 이제 더 적은 데이터를 받습니다. 빠진
  권한을 허용하세요.
- **SSO가 더 엄격해졌습니다.** 설정에는 Super Admin이 필요하고, `defaultRoles`와 `roleMap`은 Super Admin을 줄 수 없으며,
  제공업체의 `email_verified` 클레임이 true여야 하고(`trustUnverifiedEmail`이 아니면), 제공업체를 신뢰하지 않으면
  (`providerMfa`) 관리자의 두 번째 인증 수단이 적용되며, 발급자와 토큰 엔드포인트는 공개 `https` URL이어야 합니다.
  업그레이드 후 SSO 로그인을 확인하세요.
- **Super Admin**은 다른 Super Admin만 생성, 편집, 삭제, 재초대, 재설정할 수 있습니다.
- **최종 사용자 계정은** 관리자 계정처럼 비밀번호를 반복해서 틀리면 **잠깁니다**.
- populate한 관계는 항목과 관계당 최대 1,000개 항목을 반환합니다.
- 검색 인덱스는 첫 시작에서 다시 만들어집니다(private 컴포넌트 필드는 더 이상 인덱싱하지 않음).

### 0.8 → 0.9

- 관리자 목록의 검색 상자가 제목 대신 모든 텍스트 필드를 검색합니다(`_q`).
- 새 관리자 권한 `deploy.manage`, `deploy.trigger`, `site.manage`. Editor는 `deploy.trigger`와 `site.manage`를 받습니다.
- 새 선택 기능(실시간, 댓글과 작업, AI 기능, SEO와 사이트맵, 리디렉션, 메뉴, 폼)은 켜기 전까지 꺼져 있습니다. 메트릭에는
  `[metrics].enabled = true`가 필요합니다.

### 0.7 → 0.8

- **조건부 필드가 적용됩니다.** `conditions`로 숨겨진 필드는 더 이상 필수가 아닙니다. 그런 필드가 필수라는 데 의존하던
  콘텐츠는 이제 그 필드 없이 저장될 수 있습니다.
- 새 `password` 속성 타입. `verdin import strapi`가 이제 Strapi의 비밀번호 필드를 가져옵니다.

### 0.7.0 → 0.7.1

- 플러그인 런타임이 Wasmtime 48로 옮겨 갑니다. 기존 플러그인은 다시 빌드하지 않아도 계속 동작합니다.
- 소스에서 빌드하려면 Rust 1.95 이상이 필요합니다.

### 0.6 → 0.7

- **여러 인스턴스**: 각 인스턴스가 다른 인스턴스가 바꾼 설정을 `[server].sync_interval_secs`(10초)마다 읽습니다. 두 개
  이상 실행한다면 하나를 뺀 모든 인스턴스에 `[plugins].run_jobs = false`를 설정하세요.
- 플러그인이 호스트를 통해 쓰는 콘텐츠가 이제 검토 워크플로 단계 같은 플랫폼의 쓰기 전 검사를 거칩니다. 이 쓰기에서
  플러그인 자체의 쓰기 전 훅은 여전히 건너뛰므로 플러그인이 자기 자신을 실행시킬 수 없습니다.

### 0.5 → 0.6

- **감사 로그**가 기본적으로 켜져 있으며 `[audit].retention_days`(90) 동안 항목을 보관합니다. 원하지 않으면
  **설정 → 기능**에서 끄세요.

### 0.4 → 0.5

- 바꿀 것이 없습니다. 플러그인은 `[plugins].path`(`plugins/`)에서 로드되며 켜기 전까지 꺼져 있습니다.

### 0.3 → 0.4

- `upload`, `uploads`와 함께 **`auth`, `users`, `connect`가 예약된 라우트 이름입니다**. API 이름이 이 중 하나인 콘텐츠
  타입은 업그레이드 전에 이름을 바꾸세요.

### 0.2 → 0.3

- 속성 이름이 camelCase만이 아니라 Strapi의 규칙(문자로 시작하고 문자, 숫자, 밑줄)을 따릅니다. 같은 컬럼에 대응하는 두
  이름은 거부됩니다.
- `regex` 옵션이 JavaScript 같은 패턴을 받습니다.

### 0.1 → 0.2

- 본문 크기 한도와 타임아웃이 API 라우터별로 적용됩니다. 업로드에는 자체 한도(`[upload].max_file_size`)가 있습니다.
- 기존 설치의 기본 제공 역할이 새 권한을 한 번 받습니다.

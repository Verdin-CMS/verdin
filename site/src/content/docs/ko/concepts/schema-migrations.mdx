스키마 파일을 바꾸면 데이터베이스도 따라가야 합니다. 새 속성에는 컬럼이, 새 관계에는 링크 테이블이
필요합니다. Verdin은 이 마이그레이션을 대신 계산하고, 실행하기 전에 보여 주며, 명시적으로 허용하지 않는
한 데이터를 삭제하지 않습니다. 이 페이지에서는 그 방법을 설명합니다.

## 스키마에서 플랜으로

Verdin은 마이그레이션을 직접 작성하라고 요구하지 않습니다. 데이터베이스의 두 모델을 비교합니다.

1. **목표**: `schema/*.json` 파일에서 도출한 모델로, 파일이 필요로 하는 모든 테이블, 컬럼, 인덱스(링크
   테이블과 Verdin 자체 테이블 포함)를 담습니다.
2. **현재**: 마지막 마이그레이션이 남긴 모델로, 데이터베이스에 스냅샷으로 저장되어 있습니다.

그 차이가 **플랜**입니다. 단계의 리스트이며, 각 단계에는 해당 데이터베이스용 SQL과 위험 수준이 있습니다.
플랜은 데이터베이스를 조사하는 대신 저장된 스냅샷에서 나오므로 결정적이며 모든 방언에서 같습니다. SQLite에서
`integer`를 `biginteger`로 바꾸는 것처럼 데이터베이스에서 같은 SQL을 만드는 변경은 단계를 만들지 않습니다.

`verdin migrate plan`이 플랜을 출력합니다. 다음은 `article.json`에서 blog의 `excerpt` 속성을
`summary`로 이름을 바꾼 경우입니다.

```text title="Terminal"
$ verdin migrate plan
  1. [safe] add column articles.summary
       ALTER TABLE "articles" ADD COLUMN "summary" text
  2. [destructive] drop column articles.excerpt
       ALTER TABLE "articles" DROP COLUMN "excerpt"

requires: verdin migrate apply --allow destructive

possible renames (pass them to keep the data):
  --rename-column articles.excerpt=summary
```

## 위험 수준

| 위험 | 단계 | 이유 |
| --- | --- | --- |
| **safe** | 테이블 생성, 컬럼 추가, 고유하지 않은 인덱스 추가·삭제, 테이블이나 컬럼 이름 변경. | 데이터를 잃거나 기존 행 때문에 실패할 수 없습니다. |
| **risky** | 컬럼 타입 변경, 기존 테이블에 고유 인덱스 추가, SQLite 테이블 재구성(SQLite는 컬럼을 제자리에서 변경할 수 없음). | 기존 데이터 때문에 실패하거나(중복, 변환되지 않는 값) 데이터를 다시 쓸 수 있습니다. |
| **destructive** | 컬럼이나 테이블 삭제. | 데이터를 삭제합니다. |

모든 속성 컬럼은 nullable이므로(`required`는 게시할 때 검사), 필수 여부와 상관없이 속성을 추가하는 것은
항상 safe입니다. blog의 글 제목에 `"unique": true`를 추가하는 것은 기존 제목이 중복될 수 있으므로
risky입니다.

```text title="Terminal"
$ verdin migrate plan
  1. [risky] create unique index articles_title_uq
       CREATE UNIQUE INDEX "articles_title_uq" ON "articles" ("title", "locale", "publication_state")

requires: verdin migrate apply --allow risky
```

첫 구문을 실행하기 전에, Verdin은 실패할 수 있는 risky 단계마다 검사를 실행합니다(예: 고유 인덱스 전에
중복 찾기). 문제를 찾으면 메시지와 함께 멈춥니다. 이 시점에는 아무것도 바뀌지 않았습니다.

## 플랜 적용

`verdin migrate apply`는 대기 중인 단계를 실행합니다. 받아들일 최고 위험 수준을 지정합니다.

```sh title="Terminal"
verdin migrate apply                        # safe 단계만(기본값)
verdin migrate apply --allow risky          # 타입 변경과 고유 인덱스도
verdin migrate apply --allow destructive    # 삭제도
```

허용한 위험보다 높은 단계가 하나라도 있으면 아무것도 실행하지 않습니다.

```text title="Terminal"
$ verdin migrate apply
Error: these steps need explicit approval:
  create unique index articles_title_uq (risky)
```

마이그레이션은 잠금을 잡으므로 두 인스턴스가 동시에 마이그레이션하지 않습니다. PostgreSQL과 SQLite에서는
플랜 전체가 트랜잭션 하나로 실행되며, 실패하면 전부 롤백됩니다. MySQL과 MariaDB는 DDL 구문을 하나씩 자동
커밋하므로, Verdin은 진행 상황을 단계별로 저널에 기록합니다. 실패하면 원인을 고치고 `verdin migrate apply`를
다시 실행하세요. 플랜이 바뀌지 않았으면 실패한 단계부터 재개하고, 그 사이에 스키마가 바뀌었으면 거부합니다.

## 이름 변경

속성을 지우고 새 속성을 추가하면 삭제와 추가로 보이며, 컬럼의 데이터를 잃게 됩니다. Verdin은 이름 변경을
추측하지 않습니다. 같은 테이블에서 컬럼 하나가 사라지고 같은 타입의 컬럼이 나타나면(또는 테이블이 사라지고
같은 컬럼을 가진 테이블이 나타나면) 이름 변경을 제안하며, 여러분이 명시적으로 확인합니다.

```text title="Terminal"
$ verdin migrate apply --rename-column articles.excerpt=summary
applied 1 step
```

- `--rename-column TABLE.OLD=NEW`는 컬럼 이름을 바꿉니다. `TABLE`은 콘텐츠 타입의 테이블
  (`collectionName`)입니다.
- `--rename-table OLD=NEW`는 테이블 이름을 바꿉니다. 타입의 링크 테이블도 함께 이름이 바뀝니다.
- 결과를 미리 보려면 같은 플래그를 `migrate plan`에 넘기세요.

이름 변경은 safe 단계입니다. 콘텐츠 타입 빌더도 대화 상자에서 같은 제안을 보여 줍니다.

## `verdin dev`와 `verdin start`

| | `verdin dev` | `verdin start` |
| --- | --- | --- |
| 시작할 때 | 대기 중인 safe 단계를 적용합니다. 다른 단계가 대기 중이면 멈춥니다. | 대기 중인 단계가 있으면 시작을 거부합니다. `--migrate`를 넘기면 safe 단계를 먼저 적용합니다. |
| 실행 중 스키마 변경 | **콘텐츠 타입 빌더**가 위험과 이름 변경 제안이 담긴 플랜을 보여 주고, 확인하면 더 위험한 단계를 포함해 적용합니다. 직접 편집(또는 `git pull`)은 파일 감시기가 감지합니다. safe 플랜은 적용되고 앱이 다시 로드되며, 그 밖의 플랜은 로그에 남고 실행 중인 앱은 그대로 유지됩니다. | 스키마는 읽기 전용입니다. 새 파일을 배포하고 마이그레이션하세요. |

빌더는 먼저 데이터베이스를 마이그레이션하고, 그다음 스키마 파일을 쓰고, 재시작 없이 콘텐츠 API, admin API,
GraphQL, OpenAPI 문서를 다시 로드합니다. 마이그레이션이 실패하면 파일과 실행 중인 앱은 그대로 유지됩니다.

프로덕션에서는 새 버전을 시작하기 전에 데이터베이스 사본을 대상으로 `verdin migrate plan`을 실행한 뒤,
받아들일 위험 수준으로 `verdin migrate apply`를 실행하세요. [업그레이드](/ko/migrate/upgrading/)와
[백업](/ko/deploy/backups/)을 참고하세요.

## Strapi와 비교

Strapi는 시작할 때 무엇을 할지 보여 주지 않고 데이터베이스를 스키마와 동기화합니다. Verdin은 먼저 플랜을
세우고, SQL을 보여 주고, 요청하지 않아도 safe 단계만 적용하며, 실패하거나 데이터를 삭제할 수 있는 것에는
`--allow`를 요구합니다.

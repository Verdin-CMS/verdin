Verdin은 상태를 데이터베이스에 두므로, 가용성이나 부하 분산을 위해 같은 프로젝트의 인스턴스 여러 개를
로드 밸런서 뒤에서 실행할 수 있습니다. 이 페이지에서는 인스턴스가 공유하는 것, 각 인스턴스가 따로 가지는 것,
중요한 설정을 나열합니다.

## 체크리스트

- **공유 데이터베이스.** PostgreSQL, MySQL, MariaDB. SQLite는 한 머신의 파일이므로 여러 인스턴스에서 동작하지
  않습니다.
- **모든 곳에서 같은 설정.** 모든 인스턴스가 같은 `verdin.toml`, 스키마 파일, 시크릿(`VERDIN_ADMIN_JWT_SECRET`,
  `VERDIN_TOKEN_PEPPER`, `VERDIN_SSO_<ID>_SECRET`…)을 씁니다. 시크릿이 다르면 한 인스턴스에서 만든 세션과
  API 토큰을 다른 인스턴스가 거부합니다.
- **프로덕션 모드.** `verdin dev`가 아니라 `verdin start`를 실행하세요. 스키마는 개발 환경에서 바꾸고,
  커밋하고, 배포마다 한 번 마이그레이션하세요.
- **공유 미디어 스토리지.** S3 프로바이더(`[upload] provider = { name = "s3", … }`)를 쓰거나, 로컬
  프로바이더라면 모든 인스턴스에 같은 볼륨을 마운트하세요.
- **헬스 체크.** 로드 밸런서는 데이터베이스에 연결할 수 없으면 `503`으로 응답하는 `GET /_ready`를 보게
  하세요. `GET /_health`는 프로세스가 살아 있다는 것만 알려 주므로 liveness에 쓰세요.
- **플러그인 작업은 인스턴스 하나에서.** 하나를 뺀 모든 인스턴스에 `[plugins].run_jobs = false`를 설정하세요.
  그러지 않으면 인스턴스마다 예약된 작업을 실행합니다.
- **인스턴스별 메트릭.** `[metrics].enabled = true`이면 각 인스턴스가 자체 `/_metrics`를 제공합니다. 각각
  스크레이프하세요.

## 여러 인스턴스에서의 마이그레이션

`verdin start --migrate`는 모든 인스턴스에서 동시에 실행해도 안전합니다. 마이그레이션 실행마다 데이터베이스에서
잠금을 잡으므로(PostgreSQL은 advisory lock, MySQL과 MariaDB는 `GET_LOCK`, 최대 60초 대기), 첫 인스턴스가 단계를
적용하고 나머지는 데이터베이스가 최신 상태임을 확인합니다.

롤링 배포 중에는 이전 버전의 인스턴스가 한동안 마이그레이션된 데이터베이스로 계속 실행됩니다. safe 단계는
테이블 생성, nullable이거나 기본값이 있는 컬럼과 인덱스 추가, 텍스트 컬럼 확장, enum 값 추가이며, 이전 버전은
이를 알아차리지 못합니다. risky나 destructive 단계(`verdin migrate apply --allow risky|destructive`)는 이전
스키마의 인스턴스가 더 이상 그 데이터를 필요로 하지 않을 때 별도 배포에서 적용하세요.
[스키마 마이그레이션](/ko/concepts/schema-migrations/)을 참고하세요.

## 공유되는 것

| 대상 | 방식 |
| --- | --- |
| 관리자 세션, API 토큰, 권한 | 데이터베이스에 있습니다. sticky 세션이 필요 없습니다. |
| 기능 스위치, 플러그인 스위치, 로케일, 검토 워크플로 | 데이터베이스에 있습니다. 각 인스턴스가 `[server].sync_interval_secs`(10초)마다 다시 읽으므로, 한 인스턴스에서 바꾼 내용이 그 시간 안에 다른 인스턴스에 반영됩니다. |
| 웹훅 전송 | 데이터베이스의 큐. 인스턴스가 보내기 전에 전송을 가져가므로 각 전송은 한 번만 나갑니다. |
| 예약된 릴리스 | 실행 전에 데이터베이스에서 가져가므로 각 릴리스는 한 번만 실행됩니다. |
| 일일 다이제스트 | 하루치 실행을 데이터베이스에서 가져가므로 관리자는 이메일을 한 통만 받습니다. |
| 패스키 챌린지 | 사용한 챌린지를 데이터베이스에 기록하므로, 인스턴스 전체에서 각 챌린지는 한 번만 응답됩니다. |
| 감사 로그 정리 | 모든 인스턴스에서 실행됩니다. 오래된 행을 두 번 삭제해도 문제가 없습니다. |
| 플러그인 키-값 저장소 | 데이터베이스에 있습니다. |

## 인스턴스마다 남는 것

- **요청 한도**는 인스턴스마다 셉니다. 인스턴스가 `n`개면 클라이언트는 분당 최대 `[api].public_rate_limit`의
  `n`배만큼 요청할 수 있습니다. 전역 한도가 필요하면 로드 밸런서에서 강제하세요.
- **익명 응답 캐시**(`[api].cache_ttl_secs`). 쓰기는 그 쓰기를 처리한 인스턴스의 캐시만 비웁니다. 다른
  인스턴스는 항목이 만료될 때까지 이전 응답을 제공할 수 있습니다. TTL은 몇 초나 `0`으로 두세요.
- **실시간 이벤트와 프레즌스**는 클라이언트가 연결된 인스턴스의 것입니다. 이벤트 스트림에는 sticky 세션을
  쓰세요([실시간](/ko/guides/frontend/realtime/) 참고).
- **검색 인덱스**(`[search]`)는 인스턴스의 디스크에 있고 그 인스턴스가 처리한 쓰기만 따라갑니다. 인스턴스
  하나에서만 켜고 `_q` 요청을 그쪽으로 보내거나, 다른 인스턴스가 빈 인덱스 디렉터리로 재시작할 때까지 뒤처지는
  것을 받아들이세요.
- **이미지 변환**(`[upload.transforms]`)은 인스턴스마다 `cache_dir` 아래에 캐시됩니다. 공유하려면 `/uploads`
  앞에 CDN을 두세요.
- **예약된 플러그인 작업**: 위의 `run_jobs`를 참고하세요.

## 설정

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Short-lived when each instance keeps its own cache.
cache_ttl_secs = 5
```

인스턴스마다 `VERDIN_PLUGINS__RUN_JOBS=false`로 `run_jobs`를 설정하세요.

## 데이터베이스 연결

각 인스턴스는 최대 `[database].pool_max`개(기본 10)의 연결을 엽니다. 마이그레이션, 백업, 유지 보수를 위한
여유를 두고 `인스턴스 수 × pool_max`를 서버 한도보다 작게 유지하세요. PostgreSQL의 기본 한도는 연결 100개입니다.

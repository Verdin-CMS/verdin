이 페이지에서는 `verdin-migrate`가 데이터베이스를 스키마에 맞추는 방법을 설명합니다. 차이를 계산하는 방법, 각 단계를 평가하는 방법, 그리고 실패해도 상태를 추측할 필요가 없도록 플랜을 적용하는 방법입니다. 일상적인 작업 흐름(`verdin migrate plan`, `--allow`, 이름 변경)은 먼저 [스키마 마이그레이션](/ko/concepts/schema-migrations/)을 읽으세요. 명령 플래그는 [CLI 레퍼런스](/ko/reference/cli/)에 있습니다.

## 흐름

  Current --> Diff{"diff"}
  Desired --> Diff
  Diff -->|변경| Plan["Flavor별 플랜<br/>단계, 위험, SQL, 사전 검사"]
  Plan -->|적용| Db[("데이터베이스")]`}

1. `verdin-schema`가 파일을 파싱하고 검증해 `Schema`로 만듭니다.
2. `derive_model`(`derive.rs`)이 이를 `DbModel`로 바꿉니다. 스키마에 필요한 모든 테이블, 컬럼, 인덱스, 외래 키이며, 링크 테이블과 [플랫폼 테이블](/ko/internals/storage/#플랫폼-테이블)을 포함합니다.
3. 마지막으로 적용된 모델을 `vd_schema_snapshots`에서 읽습니다.
4. `diff`(`diff.rs`)가 두 모델을 비교해 `Change` 목록과 이름 변경 힌트를 반환합니다.
5. `build_plan`(`plan.rs`)이 각 변경을 연결된 flavor용 SQL로 만들고, 평가하고, 필요한 곳에 사전 검사를 붙입니다.
6. `apply`(`apply.rs`)가 플랜을 실행한 뒤 목표 모델을 새 스냅샷으로 저장합니다.

**스냅샷은 스키마가 아니라 물리 모델을 저장합니다.** 나중 Verdin 버전이 같은 스키마에서 더 많은 테이블(새 기능의 링크 테이블, 새 플랫폼 테이블)을 도출하면, diff가 스키마 변경 없이 그 테이블을 만듭니다.

**diff는 실제 데이터베이스가 아니라 스냅샷과 비교합니다.** 그래서 결정적이며, 엔진마다 자기 구조를 보고하는 방식의 차이를 피합니다. Verdin은 데이터베이스를 조사하지 않으므로 테이블에 대한 수동 변경(드리프트)은 감지하지 않습니다.

어떤 방언에서 같은 DDL이 되는 변경은 단계를 만들지 않습니다. 예를 들어 `string` → `text`는 PostgreSQL과 MySQL에서는 타입 변경이지만 SQLite에서는 둘 다 `text`이므로 SQLite에는 단계가 없습니다.

## 변경 분류

모든 단계에는 위험 수준(`diff.rs`의 `Risk`)이 있습니다. `apply`는 허용한 수준까지의 단계만 실행하며, 그보다 높은 단계가 있으면 아무것도 실행하기 전에 플랜 전체를 거부합니다.

| 위험 | 변경 |
|---|---|
| **Safe** | 테이블 생성, nullable이거나 기본값이 있는 컬럼 추가, 컬럼 완화(nullable로, 같은 타입과 기본값), 고유하지 않은 인덱스 또는 새 테이블의 고유 인덱스 생성, 인덱스 삭제, 테이블이나 컬럼 이름 변경 |
| **Risky** | 기본값 없는 `NOT NULL` 컬럼 추가, 그 밖의 방식으로 컬럼의 타입, nullability, 기본값 변경, 기존 테이블에 고유 인덱스 추가, 컬럼을 삭제하지 않는 SQLite 테이블 재구성 |
| **Destructive** | 컬럼 삭제, 테이블 삭제, 컬럼을 삭제하는 SQLite 테이블 재구성 |

모든 속성 컬럼은 nullable이므로([스토리지](/ko/internals/storage/#시스템-컬럼) 참고), 필수 속성을 포함해 속성을 추가하는 것은 항상 safe입니다. `enumeration` 값은 컬럼이 아니라 애플리케이션이 검사하므로, 값을 추가하거나 제거해도 DDL이 전혀 바뀌지 않습니다.

**사전 검사**는 플랜의 첫 구문 전에 실행되므로, 성공할 수 없는 risky 단계는 데이터베이스를 건드리지 않은 상태에서 실행을 멈춥니다.

| 단계 | 사전 검사 |
|---|---|
| 기존 테이블의 고유 인덱스 | 인덱싱할 컬럼에 NULL이 아닌 중복 값이 없음 |
| 기본값 없는 `NOT NULL` 컬럼 | 테이블에 행이 없음 |
| 컬럼이 `NOT NULL`이 됨 | 컬럼에 NULL이 없음 |

**이름 변경.** 같은 테이블에서 컬럼 하나가 삭제되고 같은 컬럼 타입의 컬럼이 추가되면 이름 변경으로 *제안*합니다. `verdin migrate plan`은 `--rename-column articles.title=headline` 같은 힌트를 출력하고, 콘텐츠 타입 빌더는 이를 받아들일지 묻습니다. 조용히 추론하는 일은 없으며, 플래그가 없으면 플랜은 이전 컬럼을 삭제하고 새 컬럼을 추가합니다. 삭제된 테이블과 같은 컬럼을 가진 새 테이블에도 같은 방식으로 `--rename-table old=new` 힌트가 붙습니다. 이름 변경은 safe 단계이며, 이름이 바뀐 테이블은 링크 테이블도 함께 가져갑니다.

**SQLite 재구성.** SQLite는 컬럼을 변경할 수 없으므로, 테이블에 컬럼 변경이 하나라도 있으면 플래너가 그 테이블의 컬럼과 인덱스 변경을 모두 재구성 하나로 대체합니다. 임시 이름으로 새 형태를 만들고, 남는 컬럼을 복사하고, 이전 테이블을 삭제하고, 새 테이블의 이름을 바꾸고, 인덱스를 다시 만듭니다.

## 모드

| 명령 | 일어나는 일 |
|---|---|
| `verdin start` | 대기 중인 단계가 있으면 `verdin migrate plan`을 안내하는 메시지와 함께 부팅을 멈춥니다. 스키마 파일은 읽기 전용입니다. |
| `verdin start --migrate` | 대기 중인 **safe** 단계를 서버 시작 전에 적용합니다. 더 위험한 것이 있으면 부팅을 멈춥니다. |
| `verdin dev` | 부팅 시 safe 단계를 적용합니다. `schema/`의 파일 감시기가 변경마다 다시 로드합니다. safe 마이그레이션은 적용되고 앱이 제자리에서 교체되며, 더 위험한 변경은 로그에 남고 실행 중인 앱은 그대로 유지됩니다. |
| 콘텐츠 타입 빌더(`verdin dev`에서만) | `POST /schema/plan`이 단계, 위험, SQL, 이름 변경 힌트를 보여 줍니다. `POST /schema/apply`가 사용자가 확인한 위험 수준으로 실행합니다. |
| `verdin migrate plan` | 각 단계를 위험과 연결된 방언용 정확한 SQL과 함께, 플랜에 필요한 `--allow` 수준, 이름 변경 힌트를 출력합니다. |
| `verdin migrate apply` | 플랜을 실행합니다. 플랜에 그런 단계가 있으면 `--allow risky` 또는 `--allow destructive`가 필요합니다. |

빌더가 변경을 적용할 때는 먼저 마이그레이션하고, 그다음 `schema/*.json`을 쓰고, 그다음 앱을 교체합니다. 마이그레이션이 실패하면 파일과 실행 중인 앱은 그대로 유지됩니다. 빌더의 결과물이 파일이므로 흐름은 git 커밋으로 끝납니다.

## 비트랜잭션 DDL에서도 살아남는 실행

PostgreSQL과 SQLite는 트랜잭션 안에서 DDL을 실행합니다. MySQL과 MariaDB는 DDL 구문마다 암묵적으로 커밋하므로, 플랜 중간에 실패하면 데이터베이스가 두 상태 사이에 남게 됩니다. `apply`는 두 경우를 모두 처리합니다.

**모든 엔진에서:**

1. 전용 연결 하나에서 마이그레이션 잠금을 잡습니다. PostgreSQL은 `pg_advisory_lock`, MySQL과 MariaDB는 최대 60초 기다리는 `GET_LOCK('verdin_migrate:<database>')`, SQLite는 `BEGIN IMMEDIATE`로 쓰기 작업을 직렬화합니다. SQLite에서는 테이블 재구성이 링크 테이블로 cascade되지 않도록 실행 동안 `foreign_keys`도 끕니다.
2. 스냅샷에서 플랜을 다시 계산하고 허용된 위험을 확인합니다.
3. 첫 DDL 구문 전에 모든 사전 검사를 실행합니다.

**PostgreSQL과 SQLite에서는** 플랜 전체, 새 스냅샷, `completed` 저널 행이 트랜잭션 하나로 실행됩니다. 실패하면 전부 롤백됩니다.

**MySQL과 MariaDB에서는** 각 단계가 구문 하나이며, 진행 상황을 단계별로 기록합니다.

1. `vd_migrations_journal`에 플랜(플랜의 해시와 단계)을 상태 `running`으로 기록합니다.
2. 각 단계를 실행하고, 단계마다 완료한 단계 수를 기록합니다.
3. 단계가 실패하면 저널은 오류를 보관하고 `running` 상태로 남습니다. 그러면 `verdin migrate plan`이 중단된 실행, 적용된 단계 수, 마지막 오류를 보고합니다.
4. 다음 `apply`가 플랜을 다시 계산합니다. 해시가 저널과 같으면 실패한 단계부터 **재개**합니다. 이 엔진들에서 DDL 구문 하나는 원자적이므로 실패한 단계를 다시 실행합니다. 재개할 때는 앞 단계들이 이미 데이터베이스를 바꿨으므로 사전 검사를 건너뜁니다.
5. 그 사이에 스키마가 바뀌었으면 해시가 달라지므로 `apply`가 거부하며, 플랜을 만들었던 스키마로 되돌리라고 요청합니다.
6. 마지막 단계가 성공하면 새 스냅샷과 저널의 `completed` 상태를 트랜잭션 하나로 함께 씁니다.

플랜 해시는 flavor와 모든 구문을 포함하므로, 재개한 실행은 계획한 SQL을 정확히 실행합니다.

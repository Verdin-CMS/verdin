Verdin שומר את המצב שלו במסד הנתונים, כך שאפשר להריץ כמה מופעים של אותו פרויקט מאחורי מאזן
עומסים לזמינות או לעומס. העמוד הזה מפרט מה המופעים חולקים, מה כל אחד שומר לעצמו, ואילו
הגדרות חשובות.

## רשימת בדיקה

- **מסד נתונים משותף.** PostgreSQL, MySQL או MariaDB. SQLite הוא קובץ על מכונה אחת ולא
  עובד עם כמה מופעים.
- **אותה תצורה בכל מקום.** כל מופע משתמש באותו `verdin.toml`, באותם קובצי סכמה ובאותם
  סודות (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). עם סודות שונים, סשנים ואסימוני API שנוצרו במופע אחד נדחים
  באחרים.
- **מצב ייצור.** הריצו `verdin start`, לא `verdin dev`. שנו את הסכמה בפיתוח, עשו לה commit,
  ובצעו הגירה פעם אחת בכל פריסה.
- **אחסון מדיה משותף.** השתמשו בספק S3 (`[upload] provider = { name = "s3", … }`), או חברו
  את אותו volume לכל מופע עבור הספק המקומי.
- **בדיקות תקינות.** כוונו את מאזן העומסים ל-`GET /_ready`, שעונה `503` כשאי אפשר להגיע
  למסד הנתונים. `GET /_health` אומר רק שהתהליך רץ; השתמשו בו לבדיקת חיוּת.
- **אפיק האירועים המשותף.** הגדירו `[cluster].bus = "database"` בכל מופע, כדי שאירועי זמן
  אמת, נוכחות, ביטול מטמון ועדכוני חיפוש יגיעו לכולם (ראו
  [אפיק אירועים משותף](#אפיק-אירועים-משותף)).
- **משימות תוספים במופע אחד.** הגדירו `[plugins].run_jobs = false` בכל המופעים חוץ מאחד;
  אחרת כל מופע מריץ את המשימות המתוזמנות.
- **מדדים לכל מופע.** עם `[metrics].enabled = true`, כל מופע מגיש `/_metrics` משלו; אספו
  מכל אחד.

## הגירות עם כמה מופעים

בטוח להריץ `verdin start --migrate` בכל המופעים בו-זמנית. כל הרצת הגירה מחזיקה נעילה במסד
הנתונים (advisory lock ב-PostgreSQL, `GET_LOCK` ב-MySQL וב-MariaDB, עם המתנה של עד 60
שניות), כך שהמופע הראשון מחיל את השלבים והאחרים מוצאים את מסד הנתונים מעודכן.

במהלך פריסה מדורגת (rolling deploy), מופעים של הגרסה הישנה ממשיכים לרוץ זמן מה מול מסד
הנתונים שעבר הגירה. שלבים בטוחים יוצרים טבלאות, מוסיפים עמודות ניתנות ל-null או עם ברירת
מחדל ואינדקסים, מרחיבים עמודות טקסט או מוסיפים ערכי enum, והגרסה הישנה לא מבחינה בהם. החילו
שלבים מסוכנים או הרסניים (`verdin migrate apply --allow
risky|destructive`) בפריסה נפרדת, כשאף מופע של הסכמה הישנה כבר לא צריך את הנתונים. ראו
[הגירות סכמה](/he/concepts/schema-migrations/).

## מה משותף

| מה | איך |
| --- | --- |
| סשנים של ניהול, אסימוני API, הרשאות | במסד הנתונים; אין צורך ב-sticky sessions. |
| מתגי תכונות, מתגי תוספים, שפות, תהליכי בקרה | במסד הנתונים. כל מופע קורא אותם מחדש כל `[server].sync_interval_secs` (10 שניות), כך ששינוי שבוצע במופע אחד מגיע לאחרים בתוך הזמן הזה. |
| שליחות webhook | תור במסד הנתונים. מופע לוקח שליחה לפני שהוא שולח אותה, כך שכל אחת יוצאת פעם אחת. |
| מהדורות מתוזמנות | נלקחות דרך מסד הנתונים לפני שהן רצות, כך שכל אחת רצה פעם אחת. |
| תקציר יומי | ההרצה של כל יום נלקחת דרך מסד הנתונים, כך שהמנהלים מקבלים הודעת דוא"ל אחת. |
| אתגרי מפתחות גישה | אתגרים שנוצלו נרשמים במסד הנתונים, כך שכל אחד נענה פעם אחת בכל המופעים. |
| ניקוי יומן הביקורת | רץ בכל מופע; מחיקת שורות ישנות פעמיים אינה מזיקה. |
| מאגר key-value של תוספים | במסד הנתונים. |
| אירועי זמן אמת, נוכחות ונעילות רכות | עם [אפיק האירועים](#אפיק-אירועים-משותף): לקוח שמחובר לכל מופע מקבל את האירועים של כולם ורואה כל מנהל שנמצא ברשומה. |
| מטמון התגובות האנונימיות | עם אפיק האירועים, כתיבה בכל מופע מרוקנת את המטמון של כל המופעים. |
| אינדקס החיפוש | עם אפיק האירועים, כל מופע קורא מחדש ומאנדקס את הרשומות שהאחרים משנים. |
| תמונות שעברו המרה | עם אפיק האירועים, קובץ ששונה או נמחק יוצא ממטמון ההמרות של כל מופע. |

## מה נשאר בכל מופע

- **הגבלות קצב** נספרות על ידי כל מופע. עם `n` מופעים, לקוח יכול לבצע עד `n` כפול
  `[api].public_rate_limit` בקשות לדקה. אכפו מגבלה גלובלית במאזן העומסים אם אתם צריכים כזו.
- **ללא אפיק האירועים** (`[cluster].bus = "none"`, ברירת המחדל), אירועי זמן אמת ונוכחות
  הם של המופע שאליו הלקוח מחובר (השתמשו ב-sticky sessions עבור זרמי האירועים), כתיבה
  מרוקנת רק את מטמון התגובות של המופע שלה (שמרו את `[api].cache_ttl_secs` על כמה שניות,
  או `0`), ואינדקס החיפוש עוקב רק אחרי הכתיבות שהמופע שלו מבצע.
- **אינדקס החיפוש** (`[search]`) נמצא בדיסק של כל מופע. עם אפיק האירועים, המופעים מאנדקסים
  את השינויים של האחרים תוך כדי התרחשותם; מופע שעולה עם תיקיית אינדקס ריקה בונה אותו
  ממסד הנתונים. שינויים שבוצעו בזמן שמופע היה למטה מגיעים לאינדקס שלו כשהאינדקס נבנה
  מחדש: מחקו את התיקייה לפני העלייה, או בנו מחדש אחרי פריסה.
- **המרות תמונות** (`[upload.transforms]`) נשמרות במטמון לכל מופע תחת `cache_dir`. שימו CDN
  לפני `/uploads` כדי לשתף אותן.
- **משימות תוספים מתוזמנות**: ראו `run_jobs` למעלה.

## אפיק אירועים משותף

דברים מסוימים קורים בזיכרון: זרמי זמן האמת, מי עורך איזו רשומה, מטמון התגובות
האנונימיות, אינדקס החיפוש. אפיק האירועים מעביר אותם מהמופע שבו הם קורים אל האחרים.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

או `VERDIN_CLUSTER__BUS=database`, בכל מופע. האפיק משתמש במסד הנתונים של הפרויקט, כך
שהוא לא צריך שום שירות נוסף:

- **PostgreSQL**: מופע כותב כל אירוע לטבלה `vd_cluster_events` ומעיר את האחרים עם
  `NOTIFY`. כל מופע שומר אחד מחיבורי ה-pool שלו עבור `LISTEN`. ההתראה רק נותנת את שם
  השולח, כך שאירועים בכל גודל נשארים מתחת למגבלת 8000 הבתים של PostgreSQL. אם החיבור
  נפול, המופע מתחבר מחדש וקורא את הטבלה כדי להשלים פערים. הוא גם קורא את הטבלה כל 30
  שניות למקרה שהתראה אבדה.
- **MySQL, MariaDB ו-SQLite**: כל מופע קורא שורות חדשות של `vd_cluster_events` כל
  `poll_interval_ms` (1000 כברירת מחדל). השאילתה משתמשת במפתח הראשי, כך שקריאת טבלה ריקה
  עולה מעט. הורידו את המרווח לעדכונים מהירים יותר; שינוי של מופע אחד מגיע לאחרים בתוך
  המרווח.

מה עובר: כתיבות תוכן (לזרמי זמן האמת, למטמון התגובות ולאינדקס החיפוש, שקורא שוב את
הרשומה ששונתה), שינויי מדיה (זרמים, מטמון, מטמון ההמרות), פעימות נוכחות והודעות על
תגובות ומשימות עבור הניהול. כל מופע מתעלם מהאירועים של עצמו. Webhooks, ניקוי CDN, היסטוריה,
יומני ביקורת ו-hooks של תוספים לא עוברים: המופע שביצע את השינוי מריץ אותם פעם אחת.

שורות נמחקות אחרי 10 דקות. מופע חדש מתחיל עם האירוע הבא, לא עם הקודמים. מופע שלא מצליח
לעמוד בקצב, או שמאבד את חיבור מסד הנתונים שלו, משמיט אירועים במקום להחזיק כתיבה. המדד
`verdin_cluster_events_total` סופר אירועים שנשלחו, התקבלו והושמטו (ראו
[ניטור](/he/deploy/monitoring/#מדדי-prometheus)).

כל מופע נותן לעצמו שם באפיק עם מזהה אקראי בכל הפעלה, או עם `[cluster].instance_id` אם
הגדרתם אותו (שם pod, למשל). המזהה רק מבדיל בין מופעים; שום דבר אחר לא תלוי בו.

עם מופע אחד, השאירו את `bus` על `none`: האירועים נשארים בזיכרון ושום דבר לא נכתב.

backends של Redis ו-NATS עדיין לא זמינים. אפיק מסד הנתונים מכסה כל מסד נתונים נתמך בלי
שום דבר נוסף להריץ.

## הגדרות

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

הגדירו את `run_jobs` לכל מופע עם `VERDIN_PLUGINS__RUN_JOBS=false`.

## חיבורי מסד נתונים

כל מופע פותח עד `[database].pool_max` חיבורים (10 כברירת מחדל). שמרו על
`instances × pool_max` מתחת למגבלה של השרת, עם מקום להגירות, גיבויים ותחזוקה. מגבלת ברירת
המחדל של PostgreSQL היא 100 חיבורים. ב-PostgreSQL, אפיק האירועים שומר אחד מהחיבורים של כל מופע עבור `LISTEN`.

עברו על הרשימה הזו לפני שאתם מציבים פרויקט Verdin מול משתמשים אמיתיים. כל פריט מקשר לעמוד
שמסביר אותו. עמודי הפלטפורמות ([Docker](/he/deploy/docker/), [Fly.io](/he/deploy/fly/),
[Render](/he/deploy/render/), [Railway](/he/deploy/railway/),
[Kubernetes](/he/deploy/kubernetes/)) מחילים את ההגדרות האלה בשבילכם היכן שאפשר.

## הריצו את שרת הייצור

- [ ] **השתמשו ב-`verdin start`, לא ב-`verdin dev`.** `dev` מאפשר לבונה סוגי התוכן לשכתב
      קובצי סכמה, מחיל הגירות בכל שינוי ומקל בכללי העוגיות וה-webhooks לעבודה מקומית. שנו
      את הסכמה בפיתוח, עשו commit לקבצים, ופרסו אותם.
- [ ] **החילו הגירות בזמן הפריסה.** `verdin start` מסרב לרוץ כשמסד הנתונים מפגר אחרי
      הסכמה. `verdin start --migrate` מחיל קודם את השלבים ה*בטוחים* הממתינים (זו פקודת
      ברירת המחדל של האימג' של Docker). שלבים מסוכנים או הרסניים (שינויי טיפוס, אילוצי
      ייחודיות חדשים, עמודות שהוסרו) דורשים `verdin migrate apply --allow risky|destructive`,
      שאתם מריצים פעם אחת. ראו [הגירות סכמה](/he/concepts/schema-migrations/).
- [ ] **שלחו את הסכמה עם השרת.** חברו את תיקיית `schema/` לקריאה בלבד, או אפו אותה לתוך
      האימג' שלכם, כך שמה שרץ הוא מה שעשיתם לו commit.

## סודות

- [ ] **צרו את שני הסודות הנדרשים פעם אחת** עם `verdin secrets` ושמרו אותם במאגר הסודות
      של הפלטפורמה שלכם: `VERDIN_ADMIN_JWT_SECRET` חותם על אסימוני סשן,
      ו-`VERDIN_TOKEN_PEPPER` משמש מפתח ל-hashes של אסימוני API ושל סודות שמורים אחרים.
      `verdin start` נכשל אם אחד מהם חסר או קצר מ-32 בייטים. הסודות נקראים רק מהסביבה,
      אף פעם לא מ-`verdin.toml`.
- [ ] **שמרו אותם יציבים.** שינוי `VERDIN_TOKEN_PEPPER` גורם לכל אסימוני ה-API להפסיק
      לעבוד, וגם לקודים מאפליקציית האימות ולקודי השחזור של המנהלים. שינוי
      `VERDIN_ADMIN_JWT_SECRET` מבטל את אסימוני הגישה קצרי המועד של מנהלים ושל משתמשי קצה,
      קישורי תצוגה מקדימה פתוחים והתחברויות OAuth שבתהליך (פאנל הניהול ולקוחות עם אסימוני
      רענון מחדשים אותם בעצמם). כל המופעים של פרויקט צריכים את אותם ערכים.
- [ ] שימו בסביבה גם את שאר הסודות שאתם משתמשים בהם: `VERDIN_EMAIL_SMTP_PASSWORD`
      או `VERDIN_EMAIL_API_KEY`, `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`,
      `VERDIN_METRICS_TOKEN`, `VERDIN_SSO_<ID>_SECRET`, `VERDIN_IMAGE_SECRET`. הרשימה
      המלאה נמצאת ב[תיעוד התצורה](/he/reference/configuration/).

## מסד נתונים

- [ ] **בחרו את המנוע.** PostgreSQL (14 ומעלה) הוא הבחירה הרגילה, וזה שכדאי לבחור אם
      תריצו [כמה מופעים](/he/deploy/scaling/). MySQL 8.4+ ו-MariaDB 10.11+ עובדים באותה
      דרך. SQLite מתאים למופע יחיד עם דיסק קבוע.
- [ ] **הגדירו את `VERDIN_DATABASE_URL`**: `postgres://…`, `mysql://…` (MySQL ו-MariaDB) או
      `sqlite:///data/verdin.db`. הוסיפו `?sslmode=require` לשרתי PostgreSQL שדורשים TLS.
- [ ] **קבעו את גודל ה-pool.** כל מופע פותח עד `[database].pool_max` חיבורים (10). שמרו
      על `instances × pool_max` מתחת למגבלת החיבורים של השרת.

## כתובות URL, proxies ועוגיות

- [ ] **הגישו ב-HTTPS.** Verdin מדבר HTTP רגיל; סיימו TLS ב-reverse proxy, במאזן עומסים
      או בקצה של הפלטפורמה שלכם.
- [ ] **הגדירו את `[server].public_url`** (`VERDIN_SERVER__PUBLIC_URL`) לכתובת שהדפדפנים
      משתמשים בה, כמו `https://cms.example.com`. קישורים בדוא"ל, callbacks של SSO, התקציר
      היומי ומפתחות גישה (passkeys) תלויים בה; מפתחות גישה קשורים ל-host שלה.
- [ ] **הגדירו את `[server].trusted_proxies`** לכתובות של ה-reverse proxies שלכם (כתובות
      IP או טווחי CIDR). רק אז Verdin קורא את כתובת הלקוח מ-`X-Forwarded-For`; בלי זה,
      כל הלקוחות מאחורי ה-proxy חולקים כתובת אחת להגבלת קצב וליומני ביקורת.
- [ ] **השאירו עוגיות מאובטחות פעילות.** ב-`verdin start` עוגיית הרענון של הניהול היא
      `Secure` כברירת מחדל. השאירו את `[admin].secure_cookies` לא מוגדר; הגדרה שלו ל-`false`
      בייצור רושמת אזהרה בהפעלה.

## APIs

- [ ] **העניקו רק את מה שהציבור צריך.** API התוכן סגור עד שתעניקו הרשאות ציבוריות
      (**הגדרות ← גישה ציבורית**) או תיצרו אסימוני API. ראו
      [הרשאות](/he/concepts/permissions/).
- [ ] **הגדירו את `[api].cors_origins`** אם דפדפן ממקור אחר קורא ל-API התוכן או
      ל-GraphQL, למשל `["https://www.example.com"]`. בלי זה, רק דפים מאותו מקור יכולים
      לקרוא להם מדפדפן. API הניהול אף פעם לא עונה לבקשות cross-origin.
- [ ] **שקלו הגבלת קצב** לתעבורה אנונימית: `[api].public_rate_limit` ו-
      `[api].token_rate_limit` (בקשות לדקה; `0`, ברירת המחדל, הוא ללא הגבלה).

## מדיה

- [ ] **אחסנו העלאות היכן שהן שורדות פריסה מחדש.** ספק ברירת המחדל המקומי כותב לדיסק: תנו
      לו volume קבוע, או השתמשו בספק S3 (AWS S3, Cloudflare R2, Backblaze B2, MinIO,
      Tigris…). בפלטפורמות עם דיסקים זמניים, ועם כמה מופעים, השתמשו ב-S3. ראו
      [מדיה](/he/concepts/media/).

## דוא"ל

- [ ] **הגדירו ספק אמיתי.** ברירת המחדל `[email].provider = "log"` כותבת הודעות דוא"ל
      ליומן, ו-`verdin start` מזהיר על כך. הזמנות, איפוסי סיסמה, אישורים של משתמשי קצה,
      אזכורים בתגובות והתקציר צריכים `smtp`, `resend` או `postmark`, ו-`[email].from`
      מוגדר לכתובת שהספק שלכם מקבל.

## גיבויים וניטור

- [ ] **גבו את מסד הנתונים ואת אחסון המדיה** לפי לוח זמנים, ונסו שחזור. ראו
      [גיבויים](/he/deploy/backups/).
- [ ] **כוונו בדיקות תקינות ל-`/_ready`** ובדיקות חיוּת ל-`/_health`.
- [ ] **רשמו יומנים כ-JSON** (`[log].format = "json"`, ברירת המחדל של האימג' של Docker)
      ואספו את ה-standard error.
- [ ] **אספו את `/_metrics`** אם אתם משתמשים ב-Prometheus, עם `VERDIN_METRICS_TOKEN`. ראו
      [ניטור](/he/deploy/monitoring/).

## לפני העלייה לאוויר

- [ ] רשמו את המנהל הראשון בעצמכם מיד אחרי ההפעלה הראשונה: עד שקיים מנהל, כל מי שמגיע
      ל-`/admin/` יכול להירשם כ-Super Admin. אפשר גם ליצור אותו משורת הפקודה עם
      `verdin admin create --email …`.
- [ ] עברו על [מודל האבטחה](/he/deploy/security/) והפעילו
      [אימות דו-שלבי](/he/guides/auth/two-factor/) ל-Super Admins.

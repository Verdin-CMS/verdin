כשמשנים קובץ סכמה, מסד הנתונים צריך להתעדכן בהתאם: מאפיין חדש צריך עמודה, קשר חדש צריך
טבלת קישור. Verdin מחשב את ההגירה הזו בשבילכם, מציג אותה לפני שהוא מריץ אותה, ולעולם לא
מוחק נתונים בלי שאמרו לו. העמוד הזה מסביר איך.

## מסכמה לתוכנית

Verdin אף פעם לא מבקש מכם לכתוב הגירה. הוא משווה בין שני מודלים של מסד הנתונים:

1. **הרצוי**: נגזר מקובצי ה-`schema/*.json` שלכם, עם כל טבלה, עמודה ואינדקס שהם צריכים
   (כולל טבלאות קישור והטבלאות של Verdin עצמו).
2. **הנוכחי**: המודל שההגירה האחרונה השאירה, שנשמר במסד הנתונים כתמונת מצב (snapshot).

ההבדל הוא **תוכנית**: רשימה של שלבים, כל אחד עם ה-SQL שלו עבור מסד הנתונים שלכם ורמת סיכון.
מכיוון שהתוכנית נגזרת מתמונת המצב השמורה ולא מבדיקה של מסד הנתונים, היא דטרמיניסטית וזהה
בכל דיאלקט. שינויים שמייצרים את אותו SQL במסד הנתונים שלכם, כמו `integer` ל-`biginteger`
ב-SQLite, לא מייצרים שלב.

`verdin migrate plan` מדפיס אותה. כאן שם המאפיין `excerpt` של הבלוג שונה ל-`summary`
ב-`article.json`:

```text title="Terminal"
$ verdin migrate plan
  1. [safe] add column articles.summary
       ALTER TABLE "articles" ADD COLUMN "summary" text
  2. [destructive] drop column articles.excerpt
       ALTER TABLE "articles" DROP COLUMN "excerpt"

requires: verdin migrate apply --allow destructive

possible renames (pass them to keep the data):
  --rename-column articles.excerpt=summary
```

## רמות סיכון

| סיכון | שלבים | למה |
| --- | --- | --- |
| **בטוח** (`safe`) | יצירת טבלה, הוספת עמודה, הוספה או הסרה של אינדקס שאינו ייחודי, שינוי שם של טבלה או עמודה. | לא יכולים לאבד נתונים או להיכשל על שורות קיימות. |
| **מסוכן** (`risky`) | שינוי הטיפוס של עמודה, הוספת אינדקס ייחודי לטבלה קיימת, בנייה מחדש של טבלת SQLite (ב-SQLite אי אפשר לשנות עמודות במקום). | עלולים להיכשל על נתונים קיימים (כפילויות, ערכים שלא ניתנים להמרה), או לכתוב אותם מחדש. |
| **הרסני** (`destructive`) | הסרת עמודה או טבלה. | מוחקים נתונים. |

כל עמודת מאפיין ניתנת ל-null (`required` נבדק בזמן הפרסום), כך שהוספת מאפיינים, חובה או
לא, תמיד בטוחה. הוספת `"unique": true` לכותרת המאמר בבלוג היא מסוכנת, כי כותרות קיימות
עלולות לחזור על עצמן:

```text title="Terminal"
$ verdin migrate plan
  1. [risky] create unique index articles_title_uq
       CREATE UNIQUE INDEX "articles_title_uq" ON "articles" ("title", "locale", "publication_state")

requires: verdin migrate apply --allow risky
```

לפני שהפקודה הראשונה רצה, Verdin מריץ בדיקה לכל שלב מסוכן שעלול להיכשל, כמו חיפוש כפילויות
לפני אינדקס ייחודי, ועוצר עם הודעה אם בדיקה מוצאת בעיה. בשלב הזה שום דבר עוד לא השתנה.

## החלת תוכנית

`verdin migrate apply` מריץ את השלבים הממתינים. הוא מקבל את רמת הסיכון הגבוהה ביותר שאתם
מסכימים לה:

```sh title="Terminal"
verdin migrate apply                        # שלבים בטוחים בלבד (ברירת המחדל)
verdin migrate apply --allow risky          # גם שינויי טיפוס ואינדקסים ייחודיים
verdin migrate apply --allow destructive    # גם מחיקות
```

אם שלב כלשהו מעל לסיכון המותר, שום דבר לא רץ:

```text title="Terminal"
$ verdin migrate apply
Error: these steps need explicit approval:
  create unique index articles_title_uq (risky)
```

הגירה לוקחת נעילה, כך ששני מופעים אף פעם לא מבצעים הגירה בו-זמנית. ב-PostgreSQL וב-SQLite
כל התוכנית רצה בטרנזקציה אחת: כישלון מבטל הכול. MySQL ו-MariaDB מבצעים commit לכל פקודת
DDL בנפרד, ולכן Verdin רושם את ההתקדמות שלו שלב אחר שלב ביומן. אחרי כישלון, תקנו את הסיבה
והריצו שוב `verdin migrate apply`: הוא ממשיך מהשלב שנכשל אם התוכנית לא השתנתה, ומסרב אם
הסכמה השתנתה בינתיים.

## שינויי שם

מאפיין שהוסר ומאפיין חדש נראים כמו הסרה והוספה, מה שהיה מאבד את הנתונים של העמודה. Verdin
אף פעם לא מנחש שינוי שם. הוא מציע אחד כשעמודה נעלמת ועמודה מאותו טיפוס מופיעה באותה טבלה
(או כשטבלה נעלמת ומופיעה טבלה עם אותן עמודות), ואתם מאשרים אותו במפורש:

```text title="Terminal"
$ verdin migrate apply --rename-column articles.excerpt=summary
applied 1 step
```

- `--rename-column TABLE.OLD=NEW` משנה שם של עמודה; `TABLE` היא הטבלה של סוג התוכן
  (ה-`collectionName` שלו).
- `--rename-table OLD=NEW` משנה שם של טבלה. טבלאות הקישור של הסוג משנות את שמן יחד איתה.
- העבירו את אותם דגלים ל-`migrate plan` כדי לראות מראש את התוצאה.

שינויי שם הם שלבים בטוחים. בונה סוגי התוכן מציע את אותן הצעות בחלון שלו.

## `verdin dev` ו-`verdin start`

| | `verdin dev` | `verdin start` |
| --- | --- | --- |
| בהפעלה | מחיל שלבים בטוחים ממתינים. עוצר אם שלבים אחרים ממתינים. | מסרב לעלות כל עוד שלב כלשהו ממתין, אלא אם מעבירים `--migrate`, שמחיל קודם שלבים בטוחים. |
| שינויי סכמה בזמן ריצה | **בונה סוגי התוכן** מציג את התוכנית עם הסיכונים שלה והצעות לשינויי שם, ומחיל אותה כשאתם מאשרים, כולל שלבים מסוכנים יותר. עריכות ידניות (או `git pull`) נקלטות על ידי מעקב קבצים: תוכניות בטוחות מוחלות והאפליקציה נטענת מחדש; האחרות נרשמות ביומן והאפליקציה הרצה נשארת כפי שהייתה. | הסכמה לקריאה בלבד. פרסו את הקבצים החדשים ובצעו הגירה. |

הבונה מבצע קודם את ההגירה של מסד הנתונים, אחר כך כותב את קובצי הסכמה, ואז טוען מחדש את API
התוכן, API הניהול, GraphQL ומסמך ה-OpenAPI בלי הפעלה מחדש. אם ההגירה נכשלת, הקבצים
והאפליקציה הרצה נשארים כפי שהיו.

בייצור, הריצו `verdin migrate plan` מול עותק של מסד הנתונים, ואז `verdin migrate apply`
עם רמת הסיכון שאתם מסכימים לה, לפני הפעלת הגרסה החדשה. ראו [שדרוג](/he/migrate/upgrading/)
ו[גיבויים](/he/deploy/backups/).

## בהשוואה ל-Strapi

Strapi מסנכרן את מסד הנתונים עם הסכמה כשהוא עולה, בלי להראות מה הוא עומד לעשות. Verdin
מתכנן קודם, מציג את ה-SQL, מחיל רק שלבים בטוחים בלי שיבקשו ממנו, ודורש `--allow` לכל דבר
שעלול להיכשל או למחוק נתונים.

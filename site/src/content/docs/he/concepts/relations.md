קשר מקשר בין מסמכים של שני סוגי תוכן, כמו מאמר והקטגוריה שלו. העמוד הזה מסביר את סוגי
הקשרים, איך קישורים נשמרים ונפתרים, ואת הכללים לכתיבה, לסידור ולקריאה שלהם. לתחביר
הבקשות, ראו את ה-[REST API](/he/api/rest/#כתיבה).

## סוגים

קשר הוא מאפיין מסוג `type: "relation"` עם סוג קשר `relation` וסוג תוכן יעד `target`:

| סוג | מסמך מקשר ל | יעד מקושר מ | צד הפוך |
| --- | --- | --- | --- |
| `oneWay` | יעד אחד | כל מספר של מסמכים | אין |
| `manyWay` | יעדים רבים | כל מספר של מסמכים | אין |
| `manyToOne` | יעד אחד | כל מספר של מסמכים | `oneToMany` |
| `oneToMany` | יעדים רבים | מסמך אחד | `manyToOne` |
| `oneToOne` | יעד אחד | מסמך אחד | `oneToOne` |
| `manyToMany` | יעדים רבים | כל מספר של מסמכים | `manyToMany` |

דוגמת הבלוג מקשרת מאמרים לקטגוריה (עם צד הפוך) ולתגיות (בלי צד הפוך):

```json title="schema/content-types/article.json (excerpt)"
"category": { "type": "relation", "relation": "manyToOne", "target": "category", "inversedBy": "articles" },
"tags": { "type": "relation", "relation": "manyToMany", "target": "tag" }
```

```json title="schema/content-types/category.json (excerpt)"
"articles": { "type": "relation", "relation": "oneToMany", "target": "article", "mappedBy": "category" }
```

- הצד עם `inversedBy` (או בלי אף אחד מהמפתחות) הוא הצד ה**בעלים**: הוא שומר את הקישורים
  ואליו כותבים.
- הצד עם `mappedBy` הוא הצד ה**הפוך**: הוא קורא את הקישורים של הבעלים בכיוון ההפוך והוא
  לקריאה בלבד. כתיבה אליו היא שגיאת אימות שמציינת את מאפיין הבעלים.
- שני הצדדים חייבים להתאים: `mappedBy` מציין מאפיין של היעד שמצביע בחזרה עם `inversedBy`,
  עם הסוג ההפוך המתאים מהטבלה.
- ל-`oneWay` ול-`manyWay` אף פעם אין צד הפוך.

בונה סוגי התוכן יוצר בשבילכם את המאפיין ההפוך ביעד.

## מקושר לפי מסמך, לא לפי שורה

למסמך יש כמה שורות: טיוטה וגרסה מפורסמת, ואחת מכל אחת לכל שפה. Verdin שומר קשר כקישור
מה**שורה** של המקור אל ה**מסמך** של היעד (ה-`documentId` שלו), בטבלת קישור בשם
`{table}_{field}_lnk`. שורת היעד נבחרת כשהקשר נקרא:

- מאמר מפורסם רואה את הגרסה המפורסמת של הקטגוריה שלו; הטיוטה שלו רואה את הטיוטה של
  הקטגוריה. לסוגים בלי טיוטה ופרסום יש גרסה אחת, שכל קורא רואה.
- כשגם היעד מתורגם, הקריאות פותרות אותו באותה שפה. סוג יעד שאינו מתורגם משותף לכל השפות.
- ביטול פרסום של קטגוריה מסתיר אותה ממאמרים מפורסמים בלי לגעת באף קישור; פרסום מחדש
  מחזיר אותה.
- פרסום מאמר מעתיק רק את הקישורים שלו עצמו לגרסה המפורסמת.

Strapi מקשר במקום זאת מזהי שורות, ולכן הוא צריך לכתוב מחדש קישורים בכל פעם שטיוטה
מתפרסמת. Verdin אף פעם לא עושה זאת, כך שהפרסום נשאר העתקה אחת של שורת הטיוטה.

השלמות נשמרת על ידי Verdin ולא על ידי מפתחות זרים: קישור למסמך שאינו קיים הוא שגיאת אימות,
ומחיקת מסמך מסירה את הקישורים שמצביעים עליו באותה טרנזקציה.

### מסמך אחד לכל יעד

ב-`oneToOne` וב-`oneToMany`, יעד שייך לכל היותר למסמך מקור אחד. קישור יעד שמסמך אחר מחזיק
**מעביר** אותו: הקישור של המסמך האחר מוסר באותה כתיבה. זו ההתנהגות של Strapi. היא נאכפת לכל
גרסה: טיוטה והגרסה המפורסמת שלה יכולות להחזיק את אותו יעד.

## כתיבה

בצד הבעלים, `data` מקבל `documentId`, רשימה שלהם, או אובייקט שמתאר שינוי:

| קלט | השפעה |
| --- | --- |
| `"k2m…"` או `{ "documentId": "k2m…" }` | קישור יעד אחד (קשרי to-one). |
| `["k2m…", "p9x…"]` | החלפת כל הקישורים, בסדר הזה. |
| `null` או `[]` | הסרת כל הקישורים. |
| `{ "set": ["k2m…"] }` | החלפת כל הקישורים. |
| `{ "connect": [...], "disconnect": [...] }` | הוספה והסרה של קישורים, תוך שמירה על האחרים. |

חיבור יעד חדש לקשר to-one מחליף את הקודם. אי אפשר לשלב את `set` עם `connect` או עם
`disconnect`.

בפאנל הניהול, שדה קשר מציג את הרשומות המקושרות. **קישור רשומה** (או **קישור רשומות** בקשרי
to-many) פותח חלון שמחפש ברשומות של סוג היעד, בכל שדות הטקסט שלהן, ובשפה של הרשומה כשהיעד
מתורגם. בחרו רשומה אחת, או סמנו כמה והוסיפו אותן; רשומות שכבר מקושרות מסומנות.

## סדר

קשרי to-many שומרים על סדר הקישורים שלהם. רשימה או `set` שומרים את הסדר שאתם שולחים.
פריטי `connect` יכולים לציין לאן הם נכנסים:

```json
{
  "data": {
    "tags": {
      "connect": [
        { "documentId": "k2m…", "position": { "before": "p9x…" } },
        { "documentId": "a7c…", "position": { "end": true } }
      ]
    }
  }
}
```

`position` הוא `{ "before": documentId }`, `{ "after": documentId }`, `{ "start": true }` או
`{ "end": true }`. המיקומים ממוספרים מחדש בכל כתיבה. קריאות מחזירות מסמכים קשורים בסדר
הקישור, אלא אם ה-populate מבקש `sort`.

## קריאה

קשרים מוחזרים רק כשמבצעים להם populate:

```http
GET /api/articles?populate[category][fields][0]=name&populate[tags][sort]=label:asc
```

קשר to-one הוא אובייקט או `null`; קשר to-many הוא מערך. כל קשר שעובר populate יכול לקבל
`fields`, `filters`, `sort`, `populate` ו-`count` משלו, עד חמש רמות עומק. כל רמה היא שאילתה
מקובצת אחת לכל קשר (`WHERE … IN (…)`), לא join, כך ש-populate עמוק לא מכפיל שורות. מוחזרים
לכל היותר 1,000 מסמכים קשורים לכל מסמך וקשר; `count` נותן את המספר המדויק.

אפשר לסנן דרך קשרים (`filters[category][name][$eq]=News`), בכל אחד מהצדדים, ולמיין לפי
שדה של קשר to-one (`sort=category.name:asc`). populate, סינון או מיון דרך קשר לסוג שהמבקש
לא יכול לקרוא נדחים (`populate=*` מדלג עליו), כך שקשרים אף פעם לא חושפים תוכן ש
[ההרשאות](/he/concepts/permissions/) של המבקש מסתירות.

## קשרים בתוך רכיבים

[רכיב](/he/concepts/components-and-dynamic-zones/) יכול להחזיק קשרים, אבל רק `oneWay`
ו-`manyWay`:

```json title="schema/components/shared/related.json"
{
  "displayName": "Related",
  "attributes": {
    "label": { "type": "string" },
    "articles": { "type": "relation", "relation": "manyWay", "target": "article" }
  }
}
```

ה-JSON של הרכיב שומר את ערכי ה-`documentId` עצמם: מחרוזת ל-`oneWay`, מערך ל-`manyWay`.
זו הסיבה שהסוגים האחרים אינם מותרים שם:

- צד הפוך היה צריך לחפש ב-JSON של כל מסמך כדי למצוא מי מקשר אליו.
- גם את "מסמך אחד לכל יעד" (`oneToOne`, `oneToMany`) אי אפשר לאכוף בלי חיפוש כזה.

בתוך רכיבים, הסדר של רשימת `manyWay` הוא הסדר של המערך. ההפניות נבדקות בכתיבה ונפתרות
כשהרכיב עובר populate, בסטטוס ובשפה של המסמך; יעדים שכבר לא קיימים מושמטים. אי אפשר לסנן
לפיהן.

## קשרים פולימורפיים

`morphToOne` ו-`morphToMany` מקשרים מסמכים מכל סוג תוכן. הקישורים שלהם שומרים את הסוג של
היעד לצד ה-`documentId` שלו, והכתיבות מציינות את שניהם:

```json
{ "data": { "related": [{ "__type": "api::article", "documentId": "k2m…" }, { "__type": "api::page", "documentId": "p9x…" }] } }
```

פריטים שעברו populate הם מסמכי היעד עם ה-`__type` שלהם, שנקראים בסטטוס ובשפה של הבקשה.
הצדדים ההפוכים `morphOne` ו-`morphMany` מציינים את סוג הבעלים (`target`) ואת המאפיין שלו
(`morphBy`), והם לקריאה בלבד. אי אפשר לסנן או למיין לפי קשרים פולימורפיים, והם לא יכולים
להיות בתוך רכיבים.

Verdin שולט בשני קהלים בנפרד: **מנהלים**, שמתחברים לפאנל הניהול, ו**מבקשים של API התוכן**,
שקוראים וכותבים תוכן מהאתרים והאפליקציות שלכם. העמוד הזה מסביר איך כל אחד מהם מקבל הרשאה
ואיך החלקים משתלבים. הרשימה המלאה של הפעולות נמצאת ב[תיעוד ההרשאות](/he/reference/permissions/).

| מי | מאמת עם | ההרשאות מגיעות מ | חל על |
| --- | --- | --- | --- |
| מנהל | דוא"ל וסיסמה (ועוד גורם שני או SSO) | ה[תפקידים](#תפקידי-ניהול) שלו | פאנל הניהול ו-[API הניהול](/he/api/admin/) |
| מבקש אנונימי | בלי כותרת `Authorization` | [גישה ציבורית](#גישה-ציבורית) | REST, GraphQL, זמן אמת |
| שרת או build | `Authorization: Bearer vd_…` | הסוג של [אסימון ה-API](#אסימוני-api) | REST, GraphQL, זמן אמת |
| משתמש קצה מחובר | `Authorization: Bearer <JWT>` | [תפקיד משתמש הקצה](#משתמשי-קצה) שלו | REST, GraphQL, זמן אמת |

הכול סגור כברירת מחדל: API התוכן עונה `403` עד שתעניקו גישה, ומנהל יכול לעשות רק את מה
שהתפקידים שלו מתירים.

## תפקידי ניהול

למנהל יש תפקיד אחד או יותר; ההרשאות שלהם מצטברות. שלושה תפקידים מובנים:

| תפקיד | יכול |
| --- | --- |
| **Super Admin** | הכול, כולל משתמשים, תפקידים ואסימוני API. אי אפשר לערוך אותו. |
| **Editor** | לקרוא, ליצור, לעדכן, למחוק ולפרסם את כל התוכן; להשתמש בספריית המדיה; להפעיל פריסות; לנהל SEO, הפניות, תפריטים וטפסים. |
| **Author** | ליצור תוכן, ולקרוא, לעדכן ולמחוק רק את הרשומות שיצר. לא יכול לפרסם. מעלה קבצים ועורך או מוחק רק את שלו. |

יוצרים תפקידים נוספים ב-**הגדרות ← תפקידים** (הרשאה `roles.manage`). את ה-Super Admin הפעיל
האחרון אי אפשר להשבית, למחוק או להוריד בדרגה, כך שהמופע אף פעם לא נועל את עצמו בחוץ. תפקיד
יכול גם לחייב את חבריו להגדיר [אימות דו-שלבי](/he/guides/auth/two-factor/): עד שיעשו זאת,
הם יכולים להגיע רק לפרופיל שלהם.

### מהי הרשאה

הרשאה היא **פעולה**, **נושא** עבור פעולות תוכן, ו**תנאים** אופציונליים:

- **פעולות תוכן**: `content.read`, `content.create`, `content.update`,
  `content.delete` ו-`content.publish`, על סוג תוכן אחד (`api::article`) או על כולם (`*`).
- **פעולות מדיה**: `media.read`, `media.create`, `media.update` ו-`media.delete`, עבור
  ספריית המדיה.
- **פעולות הגדרות**, כמו `users.manage`, `tokens.manage`, `webhooks.manage` או
  `features.manage`, שפותחות את העמודים המתאימים ב**הגדרות**.
- **תנאים**: `is-creator` מגביל הרשאת תוכן או מדיה למה שהמנהל יצר. כך עובד התפקיד Author.

התנאים הופכים לחלק משאילתת מסד הנתונים: רשימה שמסוננת לפי `is-creator` נספרת ומחולקת
לעמודים נכון, במקום להסתיר שורות בדיעבד.

### הרשאות שדה ושפה

אפשר לצמצם הרשאות תוכן עוד יותר:

- **שדות.** `content.read`, `content.create` ו-`content.update` יכולות לפרט את המאפיינים
  שהן חלות עליהם. שדות מחוץ לרשימה מוסתרים בקריאות (כולל חיפוש, מסננים, מיון ורשומות
  קשורות) ונדחים בכתיבות.
- **שפות.** ב[סוגים מתורגמים](/he/concepts/internationalization/), הרשאות תוכן יכולות לפרט
  את השפות שהן חלות עליהן. אי אפשר לקרוא או לשנות גרסאות בשפות אחרות.

את שתיהן מגדירים לכל סוג תוכן בעורך התפקיד, תחת **שדות** ו**שפות**.

## API התוכן

מבקשים של API התוכן נבדקים מול הרשאות: **פעולה** על **נושא**.

| פעולה | מתירה |
| --- | --- |
| `find` | הצגת רשימת מסמכים (`GET /api/articles`), או קריאה של סוג יחיד. |
| `findOne` | קריאת מסמך אחד (`GET /api/articles/{documentId}`). |
| `create` | `POST` |
| `update` | `PUT` |
| `delete` | `DELETE` |
| `publish` | הנתיבים `actions/publish`, `actions/unpublish` ו-`actions/discard-draft`. |
| `readDrafts` | קריאה עם `status=draft`. |

הנושאים הם סוגי תוכן, ספריית המדיה (`plugin::upload`), וחשבונות משתמשי קצה
(`plugin::users-permissions.user`) כש[משתמשי קצה](/he/guides/auth/end-users/) מופעלים.

כמה כללים חלים על כל מבקש:

- קריאת טיוטות דורשת `readDrafts` בנוסף ל-`find` או ל-`findOne`. הרשאה שקוראת את התוכן של
  האתר שלכם לא יכולה לקרוא בטעות עבודה שלא פורסמה.
- populate, סינון או מיון דרך קשר דורשים הרשאת קריאה לסוג היעד שלו.
- שדות `private` אף פעם לא מוחזרים, בלי קשר להרשאות.
- כתיבה מחזירה את המסמך שנכתב גם בלי `find`, כמו ב-Strapi.
- אותן הרשאות חלות על [GraphQL](/he/api/graphql/) ועל
  [זרם הזמן האמת](/he/api/realtime/).

### גישה ציבורית

בקשות בלי כותרת `Authorization` מקבלות את ההרשאות שב-**הגדרות ← גישה ציבורית**. שום דבר
לא מוענק כברירת מחדל. בחירות אופייניות הן `find` ו-`findOne` על הסוגים שהאתר שלכם מציג.

### אסימוני API

אסימוני API מיועדים לשרתים, לשלבי build ולסקריפטים. צרו אותם ב-
**הגדרות ← אסימוני API** (הרשאה `tokens.manage`):

| סוג | הרשאות |
| --- | --- |
| **קריאה בלבד** | `find` ו-`findOne` על כל סוג. אף פעם לא טיוטות. |
| **גישה מלאה** | כל פעולה על כל סוג, כולל טיוטות. |
| **מותאם אישית** | ההרשאות שתבחרו, כמו בגישה ציבורית. |

- אסימון מתחיל ב-`vd_`. הסוד שלו מוצג פעם אחת, כשהוא נוצר או מחודש; Verdin שומר רק hash
  עם מפתח שלו.
- לאסימונים יכול להיות תוקף. אסימון לא מוכר, שפג תוקפו או פגום הוא `401`: הוא אף פעם לא
  נופל חזרה לגישה ציבורית.
- כל אסימון תקין יכול לקרוא את מסמך ה-OpenAPI בכתובת `/api/_openapi.json`, אלא אם הופכים את
  התיעוד לציבורי.

ראו [אסימוני API](/he/guides/auth/api-tokens/) ליצירה ולהחלפה שלהם.

### משתמשי קצה

משתמשי קצה הם האנשים שמתחברים לאתר או לאפליקציה שלכם, כמו בתוסף users-permissions של
Strapi. התכונה כבויה כברירת מחדל. לכל חשבון יש תפקיד אחד:

- **Public** הוא התפקיד של בקשות בלי אסימון: ההרשאות שלו הן אלה של
  **הגדרות ← גישה ציבורית**.
- **Authenticated** ניתן לחשבונות חדשים כברירת מחדל.
- תפקידים מותאמים מחזיקים כל קבוצה של הרשאות, עם אותן פעולות כמו למעלה.

משתמש קצה שולח את ה-JWT שקיבל בהתחברות כ-`Authorization: Bearer <jwt>`. Verdin מבחין בינו
לבין אסימוני API לפי הקידומת `vd_`. ראו [משתמשי קצה](/he/guides/auth/end-users/).

## בהשוואה ל-Strapi

המודל עוקב אחרי Strapi v5: RBAC לניהול עם תנאי `is-creator`, ו-API תוכן עם גישה ציבורית,
אסימוני API ותפקידי users-permissions. ההבדלים:

- כל תכונה זמינה לכל פרויקט: תפקידים מותאמים, הרשאות שדה ושפה,
  [SSO](/he/guides/auth/sso/) ו[יומני ביקורת](/he/guides/content/audit-logs/).
- לקריאת טיוטות דרך API התוכן יש הרשאה משלה, `readDrafts`.
- לפרסום דרך REST יש הרשאה משלה, `publish`, ונתיבים משלו.

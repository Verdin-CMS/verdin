ה-Document Service (`DocumentService` ב-`crates/verdin-content/src/service.rs`) הוא הקוד היחיד שקורא וכותב שורות תוכן. API התוכן, API הניהול, GraphQL, MCP, תוספים, ייבואים ומפת האתר עוברים כולם דרכו, כך שאימות, טיוטה ופרסום, כללי קשרים ואירועים מתנהגים אותו דבר לא משנה איזה API ביצע את הקריאה. כמו ה-Document Service של Strapi v5, הוא עובד על מסמכים (שמזוהים לפי `documentId`), לא על שורות.

## API

המתודות העיקריות (בפישוט; ראו את קוד המקור לטיפוסים המדויקים):

| מתודה | עושה |
|---|---|
| `find_many(uid, &Query) -> Page` | עמוד של מסמכים, עם `meta` בצורת עמוד או היסט |
| `find_one(uid, document_id, &Query) -> Option<Json>` | מסמך אחד בסטטוס ובשפה של השאילתה |
| `single_document_id(uid)` | המסמך של סוג יחיד, אם הוא קיים |
| `create(uid, &data, WriteOptions) -> String` | יוצר מסמך ומחזיר את ה-`documentId` שלו |
| `update(uid, document_id, &data, WriteOptions)` | עדכון חלקי של הטיוטה (או של הגרסה היחידה); יוצר גרסת שפה חדשה כשצריך |
| `delete(uid, document_id)` | מוחק כל גרסה של המסמך בשפה הנוכחית |
| `publish(uid, document_id, actor)` | מעתיק את הטיוטה לגרסה המפורסמת |
| `unpublish(uid, document_id)` | מוחק את הגרסה המפורסמת |
| `discard_draft(uid, document_id)` | מחליף את הטיוטה בגרסה המפורסמת |
| `uid_availability(…)` | האם ערך `uid` פנוי, עם הצעה פנויה |
| `document_locales`, `timeline`, `usage`… | פונקציות עזר לפאנל הניהול |

ל-`WriteOptions` יש שני שדות: `publish` (פרסום אחרי הכתיבה, בסוגים עם טיוטה ופרסום) ו-`actor` (המנהל שנרשם ב-`created_by_id` / `updated_by_id`).

השירות הוא ערך שזול לשכפל ומוגדר עם מתודות בונה: `in_locale(locale)` לסוגים מתורגמים, `with_listener`, `with_hook`, `dry_run()` (אימות מלא של כתיבה וביטולה, שמשמש בהרצות בדיקה של ייבוא) ו-`without_plugin_hooks()` (לכתיבות שתוספים מבצעים בעצמם).

הוא לא יודע מי קורא לו. ההרשאות מוחלות על ידי שכבת ה-API לפני הקריאה: היא דוחה פעולות שאין למבקש, מגבילה לאילו סוגים שאילתה יכולה לבצע populate או לסנן דרכם, ומוסיפה לשאילתה מסנני תנאים (למשל, התנאי "הרשומות שלי" של התפקיד **Author** בניהול הופך ל-`created_by_id = <admin id>`). המסננים הם חלק מה-SQL, כך שהעימוד והספירות נשארים מדויקים.

## מה כל כתיבה עושה

1. **Hooks.** רכיבי `DocumentHook` רצים ראשונים, לפי הסדר: שלבי תהליכי בקרה, ואז תוספים. hook יכול להחליף את הנתונים או לדחות את הכתיבה, מה שהופך ל-`400`. הם משתמשים בשמות ה-lifecycle של Strapi (`beforeCreate`, `beforeUpdate`, `beforeDelete`, `beforePublish`, `beforeUnpublish`, `beforeDiscardDraft`).
2. **אימות הקלט** (`input.rs`): מפתחות לא מוכרים, שדות מערכת (`id`, `documentId`, חותמות זמן) וצדדים הפוכים (`mappedBy`) של קשרים הם שגיאות; כל ערך נבדק מול טיפוס המאפיין והאילוצים שלו (`min`, `max`, `minLength`, `maxLength`, `regex`, ערכי enumeration, קרדינליות של קשרים, `allowedTypes` של מדיה); רכיבים ואזורים דינמיים מאומתים באופן רקורסיבי; ערכי `password` מגובבים עם argon2.
3. **הפניות.** מסמכים קשורים וקובצי מדיה חייבים להתקיים, והדבר נבדק בתוך הטרנזקציה.
4. **שורות וקישורים**, בטרנזקציה אחת: השורה מוכנסת או מתעדכנת, ואז טבלאות הקישור של הקשרים, הקשרים הפולימורפיים והמדיה שלה נכתבות מחדש (המיקומים ממוספרים מחדש 1..n). קישור של יעד `oneToOne` או `oneToMany` מעביר אותו ממסמכים אחרים באותו מצב.
5. **שדות חובה וכללים.** כשגרסה מתפרסמת, או בכל כתיבה לסוגים בלי טיוטה ופרסום, נבדקים מאפייני `required` (כולל אלה שבתוך רכיבים ואזורים דינמיים) וכללי אימות בין שדות. כישלון מבטל את כל הכתיבה.
6. **ייחודיות** נאכפת על ידי האינדקסים הייחודיים לפי היקף. הפרה ממופה בחזרה למאפיין שלה ומדווחת כ-`ValidationError`, בלי race conditions.
7. **Commit, ואז אירועים.** אחרי שהטרנזקציה מבצעת commit, השירות קורא לכל `DocumentListener` עם `DocumentEvent` (`entry.create`, `entry.update`, `entry.publish`, `entry.unpublish`, `entry.discard-draft`, `entry.delete`), שנושא את ה-uid, ה-`documentId`, השפה והמבצע.

שגיאות אימות משתמשות בפורמט של Strapi: רשימה של `{ path, message, name: "ValidationError" }`, שבה `path` מצביע לתוך הנתונים (`["seo", "metaTitle"]`, `["blocks", 2, "text"]`). פאנל הניהול ממפה אותן בחזרה לשדות שלו.

המאזינים שומרים מצב נגזר מתואם עם התוכן בלי קוד לכל handler: webhooks, היסטוריית תוכן, מטמון התגובות, ה-after hooks של תוספים, יומן הביקורת, אירועי זמן אמת, תגובות ומשימות, סימוני "נצפה", ניקויי CDN ואינדקס החיפוש. מאזין שנכשל רושם ביומן את השגיאה שלו; הכתיבה כבר הצליחה. מכיוון שהמאזינים רצים אחרי ה-commit, הרצת בדיקה אף פעם לא מגיעה אליהם.

## קריאות

קריאה בוחרת את השורות של הסטטוס והשפה המבוקשים, מחילה מסננים ומיון ב-SQL, ואז מבצעת populate למה שהתבקש:

- **קשרים** נטענים עם שאילתות מקובצות, אחת לכל קשר ורמה (`WHERE … IN (…)`, במקטעים של 500 מזהים), אף פעם לא עם joins מדורגים. זה מונע גם פיצוצים קרטזיים וגם שאילתות N+1. לכל היותר 1,000 רשומות קשורות עוברות populate לכל רשומה וקשר; הספירות נשארות מדויקות.
- היעדים נקראים באותה גרסה כמו המקור: מסמכים מפורסמים רואים יעדים מפורסמים, טיוטות רואות טיוטות.
- **רכיבים ואזורים דינמיים** מגיעים מעמודת ה-JSON שלהם; קשרים ומדיה שבתוכם נפתרים עם אותן שאילתות מקובצות.
- **חיפוש `_q`** משתמש באינדקס Tantivy כש-`[search]` פעיל, ואחרת ב-`$containsi` שאינו תלוי ברישיות על שדות הטקסט.

איך הפלט נראה (מסמכים שטוחים, פורמטי ערכים, תחביר `populate`, מגבלות) מתועד ב-[REST API](/he/api/rest/).

## מחזור החיים של בקשה ל-API התוכן

  caption="בקשת GET /api/articles, מה-socket ועד מסד הנתונים"
  code={`sequenceDiagram

  participant L as שכבות משותפות

  participant D as Document Service

  C->>L: GET /api/articles?filters…
  L->>H: IP של הלקוח, מזהה בקשה, CORS, מגבלות, מטמון
  H->>H: ניתוב לפי pluralName, הרשאת אסימון או תפקיד ציבורי
  H->>Q: פענוח ואימות מול הסכמה
  Q-->>H: Query עם טיפוסים
  H->>D: find_many(uid, query)
  D->>DB: SELECT … WHERE … ORDER BY … LIMIT
  D->>DB: שאילתה מקובצת אחת לכל קשר שעובר populate
  D-->>H: מסמכים ו-meta של העמוד
  H-->>C: { data, meta }`}
/>

1. **שכבות משותפות** (מהחיצונית פנימה): כתובת הלקוח נקבעת (תוך שימוש ב-`X-Forwarded-For` רק מ-`[server].trusted_proxies`), המדדים סופרים את הבקשה כשהם פעילים, מזהה בקשה נקבע ומועבר כ-`x-request-id`, ה-tracing פותח span, ו-CORS חל על API התוכן ועל GraphQL כש-`[api].cors_origins` מוגדר.
2. **שכבות API התוכן**: הגבלות קצב לכל לקוח, `ETag`s והמטמון האופציונלי של קריאות אנונימיות, מגבלת גודל הגוף (`[server].body_limit`) וזמן ההמתנה לבקשה, תגיות מטמון של CDN בתגובות.
3. **ניתוב.** מקטע הנתיב מחופש בין ה-`pluralName`s (סוגי אוסף) וה-`singularName`s (סוגים יחידים) של סוגי התוכן. שמות לא מוכרים הם `404`.
4. **הרשאה** (`verdin-auth`). בלי כותרת `Authorization` פירושו התפקיד הציבורי; `Bearer vd_…` הוא אסימון API. אסימון לא תקין או שפג תוקפו הוא `401`, אף פעם לא התפקיד הציבורי. הפעולה של הנתיב (`find`, `findOne`, `create`, `update`, `delete`, `publish`) חייבת להיות מוענקת לסוג, אחרת התשובה היא `403`.
5. **פענוח השאילתה** (`verdin-query`). מחרוזת השאילתה הגולמית מפוענחת לעץ סוגריים (לכל היותר 16 KB, 12 רמות, 1,000 זוגות), ואז ל-`Query` עם טיפוסים שמאומת מול השדות של הסוג: שדות לא מוכרים ו-`private` הם `400`, ו-populate, מסנני קשרים ומיון לפי קשרים מוגבלים לסוגים שהמבקש רשאי לקרוא. קריאת `?status=draft` דורשת גם `readDrafts`.
6. **Document Service.** ה-handler קורא ל-`find_many`, `find_one`, `create`, `update`, `delete` או לפעולה. כתיבות בלי `?status=draft` מפרסמות בסוגים עם טיוטה ופרסום (ההתנהגות של Strapi v5), וקוראות בחזרה את הגרסה שנכתבה עבור התגובה.
7. **תגובה.** `{ "data": …, "meta": … }`. שגיאות משתמשות באותה מעטפת עם `data: null` ואובייקט `error`.

נתיבי API הניהול עוברים באותו מסלול עם סשן של מנהל במקום אסימון API, RBAC של ניהול במקום הרשאות API התוכן, וברירות מחדל שמתחילות בטיוטה: הם קוראים טיוטות וכותבים רק טיוטות, ופרסום הוא פעולה מפורשת. GraphQL מתרגם את הארגומנטים שלו לאותו עץ פרמטרים לפני שלב 5, כך שהוא חולק את המפרש, המגבלות וכללי ההרשאות.

Verdin garde son état dans la base de données : vous pouvez donc exécuter plusieurs instances du
même projet derrière un répartiteur de charge, pour la disponibilité ou pour la charge. Cette
page liste ce que les instances partagent, ce que chacune garde pour elle, et les paramètres qui
comptent.

## Check-list

- **Une base de données partagée.** PostgreSQL, MySQL ou MariaDB. SQLite est un fichier sur une
  seule machine et ne fonctionne pas avec plusieurs instances.
- **La même configuration partout.** Chaque instance utilise les mêmes `verdin.toml`, fichiers
  de schéma et secrets (`VERDIN_ADMIN_JWT_SECRET`, `VERDIN_TOKEN_PEPPER`,
  `VERDIN_SSO_<ID>_SECRET`…). Avec des secrets différents, les sessions et les jetons d’API
  créés sur une instance sont refusés par les autres.
- **Le mode production.** Exécutez `verdin start`, pas `verdin dev`. Modifiez le schéma en
  développement, commitez-le, et migrez une fois par déploiement.
- **Un stockage des médias partagé.** Utilisez le fournisseur S3
  (`[upload] provider = { name = "s3", … }`), ou montez le même volume sur chaque instance pour
  le fournisseur local.
- **Des health checks.** Pointez le répartiteur de charge vers `GET /_ready`, qui répond `503`
  quand la base de données est injoignable. `GET /_health` indique seulement que le processus
  tourne ; utilisez-le pour la liveness.
- **Le bus d’événements partagé.** Définissez `[cluster].bus = "database"` sur chaque
  instance, pour que les événements temps réel, la présence, l’invalidation des caches et les
  mises à jour de la recherche les atteignent toutes (voir
  [Bus d’événements partagé](#bus-dévénements-partagé)).
- **Les tâches de plugins sur une seule instance.** Définissez `[plugins].run_jobs = false` sur
  toutes les instances sauf une ; sinon, chaque instance exécute les tâches planifiées.
- **Des métriques par instance.** Avec `[metrics].enabled = true`, chaque instance sert son
  propre `/_metrics` ; collectez chacune d’elles.

## Migrations avec plusieurs instances

`verdin start --migrate` peut être exécuté sans risque sur toutes les instances à la fois.
Chaque exécution de migration détient un verrou dans la base de données (un advisory lock sur
PostgreSQL, `GET_LOCK` sur MySQL et MariaDB, avec une attente de 60 secondes au maximum) : la
première instance applique les étapes et les autres trouvent la base de données à jour.

Pendant un déploiement progressif, des instances de l’ancienne version continuent de tourner un
moment sur la base de données migrée. Les étapes sans risque créent des tables, ajoutent des
colonnes acceptant `NULL` ou dotées d’une valeur par défaut et des index, élargissent des
colonnes de texte ou ajoutent des valeurs d’énumération, ce que l’ancienne version ne remarque
pas. Appliquez les étapes risquées ou destructives (`verdin migrate apply --allow
risky|destructive`) dans un déploiement séparé, une fois qu’aucune instance de l’ancien schéma
n’a plus besoin des données. Voir [Migrations de schéma](/fr/concepts/schema-migrations/).

## Ce qui est partagé

| Quoi | Comment |
| --- | --- |
| Sessions d’administration, jetons d’API, autorisations | Dans la base de données ; aucune sticky session nécessaire. |
| Interrupteurs des fonctionnalités et des plugins, langues, workflows de relecture | Dans la base de données. Chaque instance les relit toutes les `[server].sync_interval_secs` (10 s) : une modification faite sur une instance atteint les autres dans ce délai. |
| Envois de webhooks | Une file d’attente dans la base de données. Une instance réserve un envoi avant de l’envoyer : chacun part une seule fois. |
| Releases planifiées | Réservées dans la base de données avant leur exécution : chacune s’exécute une seule fois. |
| Résumé quotidien | L’exécution de chaque jour est réservée dans la base de données : les administrateurs reçoivent un seul e-mail. |
| Challenges de passkeys | Les challenges utilisés sont enregistrés dans la base de données : chacun ne reçoit qu’une réponse, toutes instances confondues. |
| Purge du journal d’audit | S’exécute sur chaque instance ; supprimer deux fois d’anciennes lignes est sans conséquence. |
| Stockage clé-valeur des plugins | Dans la base de données. |
| Événements temps réel, présence et verrous souples | Avec le [bus d’événements](#bus-dévénements-partagé) : un client connecté à n’importe quelle instance reçoit les événements de toutes et voit chaque administrateur sur une entrée. |
| Le cache des réponses anonymes | Avec le bus d’événements, une écriture sur n’importe quelle instance vide le cache de chaque instance. |
| L’index de recherche | Avec le bus d’événements, chaque instance relit et indexe les entrées que les autres modifient. |
| Images transformées | Avec le bus d’événements, un fichier modifié ou supprimé quitte le cache de transformation de chaque instance. |

## Ce qui reste propre à chaque instance

- **Les limites de débit** sont comptées par chaque instance. Avec `n` instances, un client peut
  faire jusqu’à `n` fois `[api].public_rate_limit` requêtes par minute. Appliquez une limite
  globale au niveau du répartiteur de charge si vous en avez besoin.
- **Sans le bus d’événements** (`[cluster].bus = "none"`, la valeur par défaut), les
  événements temps réel et la présence sont ceux de l’instance à laquelle un client est
  connecté (utilisez des sticky sessions pour les flux d’événements), une écriture ne vide que
  le cache des réponses de sa propre instance (limitez `[api].cache_ttl_secs` à quelques
  secondes, ou à `0`), et l’index de recherche ne suit que les écritures de son instance.
- **L’index de recherche** (`[search]`) réside sur le disque de chaque instance. Avec le bus
  d’événements, les instances indexent les modifications des autres au fur et à mesure ; une
  instance qui démarre avec un répertoire d’index vide le construit à partir de la base de
  données. Les modifications faites pendant qu’une instance était arrêtée n’atteignent son index
  que lorsque celui-ci est reconstruit : supprimez le répertoire avant de la démarrer, ou
  reconstruisez-le après un déploiement.
- **Les transformations d’images** (`[upload.transforms]`) sont mises en cache par instance
  sous `cache_dir`. Placez un CDN devant `/uploads` pour les partager.
- **Les tâches planifiées des plugins** : voir `run_jobs` ci-dessus.

## Bus d’événements partagé

Certaines choses se passent en mémoire : les flux temps réel, qui modifie quelle entrée, le
cache des réponses anonymes, l’index de recherche. Le bus d’événements les transporte de
l’instance où elles se produisent vers les autres.

```toml title="verdin.toml"
[cluster]
bus = "database"
```

Ou `VERDIN_CLUSTER__BUS=database`, sur chaque instance. Le bus utilise la base de données du
projet ; il n’a donc besoin d’aucun autre service :

- **PostgreSQL** : une instance écrit chaque événement dans la table `vd_cluster_events` et
  réveille les autres avec `NOTIFY`. Chaque instance garde une des connexions de son pool pour
  `LISTEN`. La notification ne nomme que l’émetteur : des événements de toute taille restent
  donc sous la limite de 8000 octets de PostgreSQL. Si la connexion tombe, l’instance se
  reconnecte et lit la table pour rattraper son retard. Elle lit aussi la table toutes les
  30 secondes au cas où une notification se perdrait.
- **MySQL, MariaDB et SQLite** : chaque instance lit les nouvelles lignes de
  `vd_cluster_events` toutes les `poll_interval_ms` (1000 par défaut). La requête utilise la clé
  primaire : lire une table vide coûte peu. Baissez l’intervalle pour des mises à jour plus
  rapides ; la modification d’une instance atteint les autres dans cet intervalle.

Ce qui circule : les écritures de contenu (vers les flux temps réel, le cache des réponses et
l’index de recherche, qui relit l’entrée modifiée), les modifications de médias (flux, cache,
cache de transformation), les signaux de présence et les avis de commentaires et de tâches
pour l’administration. Chaque instance ignore ses propres événements. Les webhooks, les purges
de CDN, l’historique, les journaux d’audit et les hooks de plugins ne circulent pas : l’instance
qui a fait la modification les exécute une seule fois.

Les lignes sont supprimées au bout de 10 minutes. Une nouvelle instance commence par
l’événement suivant, pas par les précédents. Une instance qui n’arrive pas à suivre, ou qui
perd sa connexion à la base de données, abandonne des événements plutôt que de bloquer une
écriture. La métrique `verdin_cluster_events_total` compte les événements envoyés, reçus et
abandonnés (voir [Supervision](/fr/deploy/monitoring/#métriques-prometheus)).

Chaque instance se nomme sur le bus avec un identifiant aléatoire à chaque démarrage, ou avec
`[cluster].instance_id` si vous le définissez (un nom de pod, par exemple). L’identifiant sert
seulement à distinguer les instances ; rien d’autre n’en dépend.

Avec une seule instance, laissez `bus` à `none` : les événements restent en mémoire et rien
n’est écrit.

Les backends Redis et NATS ne sont pas encore disponibles. Le bus sur la base de données couvre
toutes les bases de données prises en charge sans rien d’autre à faire tourner.

## Paramètres

```toml title="verdin.toml"
[server]
# How often to read settings that other instances changed; 0 turns it off.
sync_interval_secs = 10

[plugins]
# Run the plugins' scheduled jobs here (true on one instance only).
run_jobs = true

[api]
# Emptied on every instance by the event bus; keep it short without it.
cache_ttl_secs = 60

[cluster]
# Share realtime events, presence, cache invalidation and search updates.
bus = "database"
# MySQL, MariaDB and SQLite: how often to read other instances' events.
poll_interval_ms = 1000
```

Définissez `run_jobs` par instance avec `VERDIN_PLUGINS__RUN_JOBS=false`.

## Connexions à la base de données

Chaque instance ouvre jusqu’à `[database].pool_max` connexions (10 par défaut). Gardez
`instances × pool_max` sous la limite du serveur, avec de la marge pour les migrations, les
sauvegardes et la maintenance. La limite par défaut de PostgreSQL est de 100 connexions. Sur
PostgreSQL, le bus d’événements garde une des connexions de chaque instance pour `LISTEN`.

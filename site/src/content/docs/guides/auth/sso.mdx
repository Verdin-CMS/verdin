Admins can sign in through any OpenID Connect provider: Microsoft Entra ID, Google Workspace,
Okta, Auth0, Keycloak, Authentik, GitLab and others. Each provider gets a button on the
sign-in page, and password sign-in keeps working next to it. This guide registers an
application, configures the provider in Verdin and maps groups to roles.

SSO is an Enterprise feature in Strapi. In Verdin it is part of the open source core.
For your sites' end users, see [OAuth sign-in for end users](/guides/auth/end-users/)
instead.

## Before you start

- Configuring SSO needs **Manage features** (`features.manage`).
- Set `[server].public_url` to the address admins reach Verdin at, such as
  `https://cms.example.com`. The redirect URI is built from it.

## Set it up

<Steps>

1. **Register an application** (a "web" client) at the provider, with this redirect URI:

   ```text
   https://cms.example.com/admin/api/auth/sso/<id>/callback
   ```

   `<id>` is the provider id you choose in step 3, such as `corp`. The admin path follows
   `[admin].path`.

2. **Put the client secret in the environment** and restart Verdin:

   ```sh title=".env"
   VERDIN_SSO_CORP_SECRET=…
   ```

   The variable is `VERDIN_SSO_<ID>_SECRET`, with the id in capitals and dashes as
   underscores. Public clients (PKCE only, no secret) need no variable.

3. **Add the provider.** Turn on **Settings → Features → Single sign-on**, select
   **Configure providers**, then **Add a provider** and fill in:

   - **Id**: lowercase letters, digits and dashes, up to 32 characters.
   - **Button text**: shown on the sign-in page as "Continue with …".
   - **Issuer URL**: Verdin reads `/.well-known/openid-configuration` under it. It must use
     `https`, except on `localhost`.
   - **Client id** and **Scopes** (`openid email profile` by default; `openid` is required).

   The dialog shows the **Redirect URI to register at the provider** and the name of the
   secret variable. Save.

4. **Try it** in a private window: the sign-in page shows **Continue with Corp account**.

</Steps>

## Who may sign in, and with which roles

| Setting | JSON key | Effect |
| --- | --- | --- |
| **Allowed email domains** | `allowedDomains` | Only these email domains may sign in. Empty means any. |
| **Create accounts on first sign-in** | `autoCreate` | Create an admin account the first time someone signs in. Without it, only emails that already have an account may sign in. |
| **Default roles** | `defaultRoles` | Role codes of created accounts when the role mapping gives none. |
| **Role claim** | `roleClaim` | The ID token claim that lists the user's groups, such as `groups` or `roles`. |
| **Role mapping** | `roleMap` | Which role code each claim value gives. |
| **Trust unverified emails** | `trustUnverifiedEmail` | Accept emails the provider does not mark as verified. |
| **The provider enforces MFA** | `providerMfa` | Do not ask admins for their Verdin second factor after this provider. |

- A provider that creates accounts needs default roles or a role mapping.
- Neither can give the Super Admin role; promote admins by hand in **Settings → Users**.
- Roles are only set when the account is created. After that, manage them in
  **Settings → Users**.
- The first and last name of a created account come from the `given_name` and `family_name`
  claims.

The same provider as JSON, as stored by the feature (`PUT /admin/api/features/sso`):

```json
{
  "enabled": true,
  "settings": {
    "providers": [
      {
        "id": "corp",
        "name": "Corp account",
        "issuer": "https://login.microsoftonline.com/<tenant>/v2.0",
        "clientId": "…",
        "scopes": ["openid", "email", "profile"],
        "autoCreate": true,
        "defaultRoles": ["author"],
        "roleClaim": "groups",
        "roleMap": { "<editors group id>": "editor" },
        "allowedDomains": ["corp.example"],
        "trustUnverifiedEmail": true,
        "providerMfa": true
      }
    ]
  }
}
```

## Provider notes

- **Microsoft Entra ID** leaves `email_verified` out of its ID tokens: turn on **Trust
  unverified emails** for it. Add the `groups` claim in the app's token configuration to map
  groups; its values are group ids.
- **Google Workspace**: the issuer is `https://accounts.google.com`. Limit sign-ins to your
  domain with **Allowed email domains**.
- **Keycloak**: the issuer is the realm URL, `https://<host>/realms/<realm>`.

## Two-factor authentication

By default, an admin who has a Verdin [second factor](/guides/auth/two-factor/) is asked
for it after the provider sends them back. When the provider already enforces MFA, turn on
**The provider enforces MFA** so they are not asked twice.

## How it works

<Diagram
  caption="An SSO sign-in"
  code={`sequenceDiagram
  participant B as Browser
  participant V as Verdin
  participant P as Provider
  B->>V: GET /admin/api/auth/sso/corp
  V-->>B: redirect with state and PKCE challenge
  B->>P: sign in
  P-->>B: redirect to callback with code
  B->>V: GET /admin/api/auth/sso/corp/callback
  V->>P: exchange code (TLS)
  V-->>B: session cookie, redirect to /admin/`}
/>

- Verdin uses the authorization code flow with PKCE (S256). The `state` is signed and tied
  to a short-lived `HttpOnly` cookie, and the `nonce` is derived from it.
- It checks the ID token's issuer, audience (and `azp` when there are several), expiry and
  nonce. It needs an `email` claim with `email_verified: true`, unless **Trust unverified
  emails** is on.
- The provider's endpoints must use `https`.
- Every SSO sign-in is recorded in the [audit logs](/guides/content/audit-logs/) as
  `admin.login`, with the provider.

When a sign-in fails, the browser returns to the sign-in page with the reason ("Single
sign-on failed"), and the reason is written to the server log. Common ones:

| Reason | Fix |
| --- | --- |
| the provider did not verify the email | Turn on **Trust unverified emails**, or fix the provider's claim. |
| this email domain may not sign in | Add the domain to **Allowed email domains**. |
| no admin account for this identity | Turn on **Create accounts on first sign-in**, or create the admin first. |
| the sign-in request expired or was not started here | Start again from the sign-in page, in the same browser. |

<Aside type="note">
A deactivated admin cannot sign in through SSO either.
</Aside>

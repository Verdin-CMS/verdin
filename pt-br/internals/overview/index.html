Visão geral da arquitetura

Esta seção é para quem trabalha no próprio Verdin. Ela explica como o servidor e o painel de administração são montados, por que são construídos assim e por onde começar a ler o código. Para usar o Verdin, comece pelo guia de início rápido.

O Verdin é um CMS headless escrito em Rust que segue o Strapi v5: você modela o conteúdo visualmente ou em arquivos JSON e ganha uma API REST e GraphQL, além de um painel de administração. Ele é distribuído como um único binário que contém o servidor, a CLI e o painel de administração em Angular, e roda em PostgreSQL, MySQL, MariaDB e SQLite.

Objetivos

Seção intitulada “Objetivos”
  • Um único binário. O verdin contém o servidor, a CLI e o painel de administração embutido. A produção não precisa de Node.js nem de node_modules.
  • Inicialização rápida, pouco uso de memória.
  • Quatro bancos de dados, uma única suíte de testes. PostgreSQL, MySQL, MariaDB e SQLite são todos de primeira classe e todos cobertos pelos mesmos testes.
  • Schema como código. Os tipos de conteúdo são arquivos JSON que você versiona no git.
  • API REST compatível com o Strapi v5 sempre que razoável, para que os frontends existentes migrem com poucas mudanças.
  • Tudo gratuito. Não existe edição enterprise: SSO, logs de auditoria, fluxos de revisão, lançamentos e todos os outros recursos estão disponíveis para todos.

O que foi entregue versão a versão, e o que vem a seguir, está no roadmap.

Fora dos objetivos

Seção intitulada “Fora dos objetivos”
  • Rodar os plugins JavaScript do Strapi. Os plugins do Verdin são módulos WebAssembly (veja plugins).
  • Ler um banco de dados do Strapi como está. O conteúdo é trazido por um importador (veja migração a partir do Strapi).
  • Renderizar páginas. O Verdin é headless.

Princípios de design

Seção intitulada “Princípios de design”
  1. O schema é a fonte da verdade. As tabelas, a validação, as APIs REST e GraphQL, o documento OpenAPI e os formulários da administração são todos derivados dele.
  2. Nenhum identificador SQL vem de uma requisição. Os nomes de tabelas e colunas vêm apenas do schema validado, e todo valor é um parâmetro vinculado.
  3. Os dialetos são de primeira classe. Nada de “funciona no PostgreSQL, MySQL depois”. Todo recurso é testado nos quatro motores.
  4. Seguro por padrão. A API de conteúdo fica fechada até você conceder permissões, os campos private nunca são expostos e os limites de profundidade e de tamanho das consultas estão sempre ativos.
  5. As operações destrutivas são explícitas. Remover uma coluna ou uma tabela exige a sua aprovação; isso nunca acontece como efeito colateral.
  6. Nenhum estado global. Os serviços são passados pelo state do axum e pelos construtores; não há singletons.

O quadro geral

Seção intitulada “O quadro geral”

Uma requisição entra no binário por uma pequena pilha de camadas compartilhadas, chega a um dos routers da API e termina no Document Service, que monta o SQL para o dialeto conectado. O registro de schemas, carregado de schema/*.json, alimenta cada passo, e o motor de migrações mantém o banco de dados alinhado com ele.

  • API de conteúdo sob [api].prefix (padrão /api): as rotas REST por tipo de conteúdo, os uploads e o documento OpenAPI. Veja a API REST.
  • API de administração sob {admin.path}/api (padrão /admin/api): tudo o que o painel de administração faz. Veja a API de administração.
  • GraphQL em /graphql e MCP em /mcp, quando esses recursos estão ativados. Os argumentos GraphQL são traduzidos para a mesma árvore de parâmetros que o parser REST lê, então as duas APIs compartilham os filtros, a paginação, o populate e as regras de permissões.
  • Painel de administração sob [admin].path (padrão /admin), servido a partir do binário ou de [admin].assets_dir. Veja os detalhes internos do painel de administração.
  • Rotas operacionais: /_health, /_ready e /_metrics quando as métricas estão ativadas. Veja monitoramento.

Toda escrita passa pelo Document Service, qualquer que seja a API de onde veio. Ele valida os dados, grava as linhas e as tabelas de vínculos em uma única transação e depois informa aos listeners (webhooks, índice de busca, histórico, tempo real, log de auditoria) o que mudou.

Quando os recursos são ativados ou desativados, ou quando o construtor de tipos de conteúdo altera o schema no verdin dev, o router inteiro é reconstruído e trocado no lugar (um ArcSwap), sem reiniciar.

Regra de dependências. O verdin-schema e o verdin-db são a base. O verdin-migrate e o verdin-query se apoiam neles, o verdin-content nesses, e o verdin-auth, o verdin-upload, o verdin-search e o verdin-plugins nas camadas abaixo deles. O verdin-api e o verdin-graphql ficam perto do topo, e o binário verdin depende de tudo. O Cargo proíbe ciclos, e o código unsafe é proibido em todo o workspace.

Por onde começar a ler

Seção intitulada “Por onde começar a ler”
Para entender Leia
Como o binário inicia e monta os seus routers crates/verdin/src/cli.rs (start), depois crates/verdin/src/app.rs
O formato do schema e as suas regras de validação crates/verdin-schema/src/raw.rs, validate.rs, naming.rs
Como um schema vira tabelas crates/verdin-migrate/src/derive.rs, depois armazenamento
As migrações crates/verdin-migrate/src/diff.rs, plan.rs, apply.rs e o motor de migrações
Os handlers da API de conteúdo crates/verdin-api/src/handlers.rs e lib.rs
Os parâmetros de consulta crates/verdin-query/src/params.rs (parser), parse.rs (validação), sql.rs (SQL)
As leituras e as escritas crates/verdin-content/src/service.rs e input.rs, e o Document Service
O painel de administração admin/src/app/app.routes.ts, depois features/content/ e os detalhes internos do painel de administração

Navegue pelo código no GitHub. O resto desta seção cobre o armazenamento, a camada de banco de dados, as migrações, o Document Service, o painel de administração, os testes e o registro de decisões.

O comportamento visível para o usuário está documentado em outros lugares: os parâmetros de consulta na API REST, as configurações na referência de configuração, os comandos na referência da CLI e o endurecimento em segurança.

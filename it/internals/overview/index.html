Panoramica dell'architettura

Questa sezione è per chi lavora su Verdin stesso. Spiega come sono messi insieme il server e il pannello di amministrazione, perché sono costruiti così, e da dove iniziare a leggere il codice. Per usare Verdin, parti invece dal quickstart.

Verdin è un CMS headless scritto in Rust che segue Strapi v5: modelli i contenuti in modo visuale o in file JSON, e ottieni un’API REST e GraphQL più un pannello di amministrazione. Viene distribuito come un unico binario che contiene il server, la CLI e il pannello di amministrazione Angular, e gira su PostgreSQL, MySQL, MariaDB e SQLite.

Obiettivi

Sezione intitolata “Obiettivi”
  • Un solo binario. verdin contiene il server, la CLI e il pannello di amministrazione incorporato. In produzione non servono Node.js né node_modules.
  • Avvio rapido, poca memoria.
  • Quattro database, una suite di test. PostgreSQL, MySQL, MariaDB e SQLite sono tutti di prima classe e tutti coperti dagli stessi test.
  • Schema come codice. I tipi di contenuto sono file JSON che versioni in git.
  • API REST compatibile con Strapi v5 ovunque sia ragionevole, così i frontend esistenti migrano con poche modifiche.
  • Tutto gratuito. Non c’è un’edizione enterprise: SSO, log di audit, flussi di revisione, rilasci e ogni altra funzionalità sono disponibili per tutti.

Cosa è uscito release dopo release, e cosa arriverà, è nella roadmap.

Non obiettivi

Sezione intitolata “Non obiettivi”
  • Eseguire i plugin JavaScript di Strapi. I plugin di Verdin sono moduli WebAssembly (vedi plugin).
  • Leggere un database Strapi così com’è. I contenuti migrano tramite un importer (vedi migrare da Strapi).
  • Generare pagine. Verdin è headless.

Principi di progettazione

Sezione intitolata “Principi di progettazione”
  1. Lo schema è la fonte di verità. Tabelle, validazione, API REST e GraphQL, documento OpenAPI e form dell’admin derivano tutti da esso.
  2. Nessun identificatore SQL arriva mai da una richiesta. I nomi di tabelle e colonne arrivano solo dallo schema validato, e ogni valore è un parametro.
  3. I dialetti sono di prima classe. Niente “funziona su PostgreSQL, MySQL più avanti”. Ogni funzionalità è testata su tutti e quattro i motori.
  4. Sicuro di default. La content API è chiusa finché non concedi permessi, i campi private non vengono mai esposti, e i limiti di profondità e dimensione delle query sono sempre attivi.
  5. Le operazioni distruttive sono esplicite. Eliminare una colonna o una tabella richiede la tua approvazione; non succede mai come effetto collaterale.
  6. Nessuno stato globale. I service vengono passati tramite lo state di axum e i costruttori; non ci sono singleton.

Il quadro generale

Sezione intitolata “Il quadro generale”

Una richiesta entra nel binario attraverso una piccola pila di layer condivisi, raggiunge uno dei router delle API, e finisce nel Document Service, che costruisce l’SQL per il dialetto connesso. Il registro dello schema, caricato da schema/*.json, alimenta ogni passaggio, e il motore di migrazione mantiene il database allineato a esso.

  • Content API sotto [api].prefix (default /api): route REST per tipo di contenuto, upload e il documento OpenAPI. Vedi l’API REST.
  • API admin sotto {admin.path}/api (default /admin/api): tutto ciò che fa il pannello di amministrazione. Vedi l’API admin.
  • GraphQL su /graphql e MCP su /mcp, quando quelle funzionalità sono attive. Gli argomenti GraphQL vengono tradotti nello stesso albero di parametri letto dal parser REST, così entrambe le API condividono filtri, paginazione, populate e regole dei permessi.
  • Pannello di amministrazione sotto [admin].path (default /admin), servito dal binario o da [admin].assets_dir. Vedi interni del pannello di amministrazione.
  • Route operative: /_health, /_ready, e /_metrics quando le metriche sono attive. Vedi monitoraggio.

Ogni scrittura passa dal Document Service, da qualunque API provenga. Valida i dati, scrive le righe e le tabelle di link in una sola transazione, e poi comunica ai listener (webhook, indice di ricerca, cronologia, realtime, log di audit) cosa è cambiato.

Quando le funzionalità vengono attivate o disattivate, o quando il costruttore di tipi di contenuto modifica lo schema in verdin dev, l’intero router viene ricostruito e sostituito sul posto (un ArcSwap), senza riavvio.

Struttura del repository

Sezione intitolata “Struttura del repository”
  • Cargo.toml il workspace (versione, edition, profilo di release)
  • Directorycrates/
    • Directoryverdin-schema/ modello dello schema, parser JSON, validazione, regole di naming
      • …
    • Directoryverdin-db/ pool di connessioni, rilevamento di flavor e versione, valori tipizzati
      • …
    • Directoryverdin-migrate/ modello fisico, snapshot, diff, piano, apply con journal, tabelle della piattaforma
      • …
    • Directoryverdin-query/ dai parametri di query a una query tipizzata, e SQL per filtri e ordinamenti
      • …
    • Directoryverdin-content/ Document Service: validazione, bozza e pubblicazione, relazioni, componenti, blocks, eventi
      • …
    • Directoryverdin-auth/ utenti admin, sessioni, due fattori e passkey, token API, RBAC, permessi pubblici
      • …
    • Directoryverdin-upload/ libreria media: provider di storage, metadati dei file, formati delle immagini
      • …
    • Directoryverdin-email/ invio delle email: SMTP, Resend, Postmark e un provider di log
      • …
    • Directoryverdin-search/ indice full-text Tantivy
      • …
    • Directoryverdin-plugins/ plugin WebAssembly (Extism): hook sui documenti, route, job pianificati
      • …
    • Directoryverdin-graphql/ API GraphQL generata dallo schema
      • …
    • Directoryverdin-api/ router axum: content API, API admin, OpenAPI, MCP, realtime, webhook…
      • …
    • Directoryverdin-testkit/ helper per i test (un database nuovo per test); non pubblicato
      • …
    • Directoryverdin/ il binario: configurazione, bootstrap, CLI, metriche, admin incorporato
      • …
  • Directoryadmin/ pannello di amministrazione Angular
    • …
  • Directorypackages/
    • Directoryclient/ @verdin/client, il client TypeScript tipizzato
      • …
  • Directoryexamples/
    • Directoryblog/ progetto di esempio
      • …
  • Directorydocker/ compose.dev.yml (database, RustFS, Mailpit) e l’immagine di release
    • …
  • Directorysite/ questo sito di documentazione
    • …
  • Directorydocs/ roadmap, guida alla traduzione e note di progettazione
    • …

Regola delle dipendenze. verdin-schema e verdin-db sono la base. verdin-migrate e verdin-query si basano su di loro, verdin-content su questi, e verdin-auth, verdin-upload, verdin-search e verdin-plugins sui livelli sottostanti. verdin-api e verdin-graphql stanno vicino alla cima, e il binario verdin dipende da tutto. Cargo vieta i cicli, e il codice unsafe è vietato in tutto il workspace.

Sezione intitolata “Da dove iniziare a leggere”
Per capire Leggi
Come si avvia il binario e assembla i suoi router crates/verdin/src/cli.rs (start), poi crates/verdin/src/app.rs
Il formato dello schema e le sue regole di validazione crates/verdin-schema/src/raw.rs, validate.rs, naming.rs
Come uno schema diventa tabelle crates/verdin-migrate/src/derive.rs, poi storage
Le migrazioni crates/verdin-migrate/src/diff.rs, plan.rs, apply.rs, e motore di migrazione
Gli handler della content API crates/verdin-api/src/handlers.rs e lib.rs
I parametri di query crates/verdin-query/src/params.rs (parser), parse.rs (validazione), sql.rs (SQL)
Letture e scritture crates/verdin-content/src/service.rs e input.rs, e Document Service
Il pannello di amministrazione admin/src/app/app.routes.ts, poi features/content/ e interni del pannello di amministrazione

Sfoglia il codice su GitHub. Il resto di questa sezione copre storage, il livello database, le migrazioni, il Document Service, il pannello di amministrazione, i test e il registro delle decisioni.

Il comportamento visibile agli utenti è documentato altrove: parametri di query nell’API REST, impostazioni nel riferimento della configurazione, comandi nel riferimento della CLI, e rafforzamento in sicurezza.

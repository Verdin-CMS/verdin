Document Service

Document Service (سرویس سند؛ DocumentService در crates/verdin-content/src/service.rs) تنها کدی است که ردیف‌های محتوا را می‌خواند و می‌نویسد. API محتوا، API مدیریت، GraphQL، MCP، افزونه‌ها، درون‌ریزی‌ها و نقشهٔ سایت همگی از آن عبور می‌کنند، بنابراین اعتبارسنجی، پیش‌نویس و انتشار، قاعده‌های روابط و رویدادها، از هر APIای که فراخوانی شده باشند، یکسان رفتار می‌کنند. مانند Document Service در Strapi v5، روی سندها (که با documentId شناسایی می‌شوند) کار می‌کند، نه روی ردیف‌ها.

API

Section titled “API”

متدهای اصلی (ساده‌شده؛ برای نوع‌های دقیق، کد منبع را ببینید):

متد کار
find_many(uid, &Query) -> Page یک صفحه از سندها، با meta به شکل page یا offset
find_one(uid, document_id, &Query) -> Option<Json> یک سند در وضعیت و زبان کوئری
single_document_id(uid) سند یک نوع تکی، اگر وجود داشته باشد
create(uid, &data, WriteOptions) -> String یک سند می‌سازد و documentId آن را برمی‌گرداند
update(uid, document_id, &data, WriteOptions) به‌روزرسانی جزئی پیش‌نویس (یا تنها نسخه)؛ در صورت نیاز یک نسخهٔ زبان جدید می‌سازد
delete(uid, document_id) همهٔ نسخه‌های سند در زبان فعلی را حذف می‌کند
publish(uid, document_id, actor) پیش‌نویس را روی نسخهٔ منتشرشده کپی می‌کند
unpublish(uid, document_id) نسخهٔ منتشرشده را حذف می‌کند
discard_draft(uid, document_id) پیش‌نویس را با نسخهٔ منتشرشده جایگزین می‌کند
uid_availability(…) اینکه یک مقدار uid آزاد است یا نه، همراه با یک پیشنهاد آزاد
document_locales، timeline، usage… ابزارهای کمکی برای پنل مدیریت

WriteOptions دو فیلد دارد: publish (انتشار پس از نوشتن، در نوع‌های دارای پیش‌نویس و انتشار) و actor (مدیری که در created_by_id / updated_by_id ثبت می‌شود).

این سرویس مقداری است که clone کردنش ارزان است و با متدهای builder پیکربندی می‌شود: in_locale(locale) برای نوع‌های بومی‌سازی‌شده، with_listener، with_hook، dry_run() (یک نوشتن را کامل اعتبارسنجی و سپس rollback می‌کند، که اجراهای آزمایشی درون‌ریزی از آن استفاده می‌کنند) و without_plugin_hooks() (برای نوشتن‌هایی که خود افزونه‌ها انجام می‌دهند).

این سرویس نمی‌داند چه کسی آن را فراخوانی می‌کند. مجوزها پیش از فراخوانی توسط لایهٔ API اعمال می‌شوند: کنش‌هایی را که فراخواننده مجوزش را ندارد رد می‌کند، نوع‌هایی را که یک کوئری می‌تواند از طریقشان populate یا فیلتر کند محدود می‌کند، و فیلترهای شرطی را به کوئری اضافه می‌کند (برای مثال شرط «مدخل‌های خودش» در نقش مدیریتی Author به created_by_id = <admin id> تبدیل می‌شود). فیلترها بخشی از SQL هستند، بنابراین صفحه‌بندی و شمارش‌ها دقیق می‌مانند.

آنچه هر نوشتن انجام می‌دهد

Section titled “آنچه هر نوشتن انجام می‌دهد”
  1. هوک‌ها. DocumentHookها ابتدا به ترتیب اجرا می‌شوند: مرحله‌های گردش‌کار بازبینی، سپس افزونه‌ها. یک هوک می‌تواند داده‌ها را جایگزین کند یا نوشتن را رد کند، که به 400 تبدیل می‌شود. از نام‌های lifecycle در Strapi استفاده می‌کنند (beforeCreate، beforeUpdate، beforeDelete، beforePublish، beforeUnpublish، beforeDiscardDraft).
  2. اعتبارسنجی ورودی (input.rs): کلیدهای ناشناخته، فیلدهای سیستمی (id، documentId، مُهرهای زمانی) و سمت‌های معکوس (mappedBy) روابط خطا هستند؛ هر مقدار با نوع ویژگی و قیدهای آن (min، max، minLength، maxLength، regex، مقدارهای enumeration، کاردینالیتی رابطه، allowedTypes رسانه) بررسی می‌شود؛ کامپوننت‌ها و ناحیه‌های پویا به‌صورت بازگشتی اعتبارسنجی می‌شوند؛ مقدارهای password با argon2 هش می‌شوند.
  3. ارجاع‌ها. سندهای مرتبط و فایل‌های رسانه باید وجود داشته باشند، که درون تراکنش بررسی می‌شود.
  4. ردیف‌ها و پیوندها، در یک تراکنش: ردیف درج یا به‌روز می‌شود، سپس جدول‌های پیوند رابطه، چندریختی و رسانهٔ آن بازنویسی می‌شوند (موقعیت‌ها از 1 تا n دوباره شماره‌گذاری می‌شوند). پیوند دادن یک مقصد oneToOne یا oneToMany آن را از سندهای دیگر در همان وضعیت جدا می‌کند.
  5. فیلدها و قاعده‌های الزامی. وقتی یک نسخه منتشر می‌شود، یا در هر نوشتن روی نوع‌های بدون پیش‌نویس و انتشار، ویژگی‌های required (از جمله آن‌هایی که درون کامپوننت‌ها و ناحیه‌های پویا هستند) و قاعده‌های اعتبارسنجی میان‌فیلدی بررسی می‌شوند. یک شکست کل نوشتن را rollback می‌کند.
  6. یکتایی با نمایه‌های یکتای محدودشده اعمال می‌شود. یک نقض به ویژگی خودش نگاشت و به شکل ValidationError گزارش می‌شود، بدون شرایط رقابتی.
  7. commit، سپس رویدادها. پس از commit شدن تراکنش، سرویس هر DocumentListener را با یک DocumentEvent (entry.create، entry.update، entry.publish، entry.unpublish، entry.discard-draft، entry.delete) فراخوانی می‌کند که uid، documentId، زبان و actor را حمل می‌کند.

خطاهای اعتبارسنجی از قالب Strapi استفاده می‌کنند: فهرستی از { path, message, name: "ValidationError" }، که در آن path به درون داده‌ها اشاره می‌کند (["seo", "metaTitle"]، ["blocks", 2, "text"]). پنل مدیریت آن‌ها را روی فیلدهای خودش نگاشت می‌کند.

شنونده‌ها state مشتق را بدون کد مخصوص هر handler با محتوا هماهنگ نگه می‌دارند: وب‌هوک‌ها، تاریخچهٔ محتوا، کش پاسخ، هوک‌های پس از نوشتن افزونه‌ها، گزارش حسابرسی، رویدادهای بلادرنگ، نظرها و وظیفه‌ها، نشانه‌های «دیده‌شده»، پاک‌سازی CDN و نمایهٔ جستجو. شنونده‌ای که شکست بخورد خطای خودش را در لاگ ثبت می‌کند؛ نوشتن از قبل موفق شده است. چون شنونده‌ها پس از commit اجرا می‌شوند، یک اجرای آزمایشی هرگز به آن‌ها نمی‌رسد.

خواندن‌ها

Section titled “خواندن‌ها”

یک خواندن ردیف‌های وضعیت و زبان درخواست‌شده را انتخاب می‌کند، فیلترها و مرتب‌سازی را در SQL اعمال می‌کند و سپس آنچه درخواست شده را populate می‌کند:

  • روابط با کوئری‌های دسته‌ای بارگذاری می‌شوند، یکی برای هر رابطه و سطح (WHERE … IN (…)، در دسته‌های 500 شناسه‌ای)، هرگز با joinهای زنجیره‌ای. این هم از انفجار حاصل‌ضرب دکارتی و هم از کوئری‌های N+1 جلوگیری می‌کند. برای هر مدخل و رابطه حداکثر 1,000 مدخل مرتبط populate می‌شود؛ شمارش‌ها دقیق می‌مانند.
  • مقصدها در همان نسخهٔ مبدأ خوانده می‌شوند: سندهای منتشرشده مقصدهای منتشرشده را می‌بینند و پیش‌نویس‌ها، پیش‌نویس‌ها را.
  • کامپوننت‌ها و ناحیه‌های پویا از ستون JSON خود می‌آیند؛ روابط و رسانهٔ درون آن‌ها با همان کوئری‌های دسته‌ای resolve می‌شوند.
  • جستجوی _q وقتی [search] روشن باشد از نمایهٔ Tantivy استفاده می‌کند، و در غیر این صورت از یک $containsi غیرحساس به بزرگی و کوچکی حروف روی فیلدهای متنی.

شکل خروجی (سندهای تخت، قالب مقدارها، نحو populate، محدودیت‌ها) در REST API مستند شده است.

چرخهٔ عمر یک درخواست API محتوا

Section titled “چرخهٔ عمر یک درخواست API محتوا”
  1. لایه‌های مشترک (بیرونی‌ترین در ابتدا): نشانی کلاینت تعیین می‌شود (با استفاده از X-Forwarded-For فقط از [server].trusted_proxies)، متریک‌ها در صورت فعال بودن درخواست را می‌شمارند، یک شناسهٔ درخواست تنظیم و به شکل x-request-id منتشر می‌شود، tracing یک span باز می‌کند، و CORS وقتی [api].cors_origins تنظیم شده باشد روی API محتوا و GraphQL اعمال می‌شود.
  2. لایه‌های API محتوا: محدودیت‌های نرخ برای هر کلاینت، ETagها و کش اختیاری خواندن‌های ناشناس، محدودیت اندازهٔ بدنه ([server].body_limit) و مهلت درخواست، برچسب‌های کش CDN روی پاسخ‌ها.
  3. مسیریابی. بخش مسیر در میان pluralNameهای نوع‌های محتوا (نوع‌های مجموعه‌ای) و singularNameها (نوع‌های تکی) جستجو می‌شود. نام‌های ناشناخته 404 هستند.
  4. مجوزدهی (verdin-auth). نبود هدر Authorization یعنی نقش عمومی؛ Bearer vd_… یک توکن API است. یک توکن نامعتبر یا منقضی 401 است، هرگز نقش عمومی نیست. کنش مسیر (find، findOne، create، update، delete، publish) باید برای آن نوع مجاز شده باشد، وگرنه پاسخ 403 است.
  5. parse کردن کوئری (verdin-query). رشتهٔ کوئری خام به یک درخت کروشه‌ای parse می‌شود (حداکثر 16 KB، 12 سطح، 1,000 جفت)، سپس به یک Query تایپ‌شده که با فیلدهای نوع اعتبارسنجی می‌شود: فیلدهای ناشناخته و private خطای 400 هستند، و populate، فیلترهای رابطه و مرتب‌سازی‌های رابطه به نوع‌هایی محدود می‌شوند که فراخواننده اجازهٔ خواندنشان را دارد. خواندن ?status=draft به readDrafts هم نیاز دارد.
  6. Document Service. handler یکی از find_many، find_one، create، update، delete یا یک کنش را فراخوانی می‌کند. نوشتن‌های بدون ?status=draft در نوع‌های دارای پیش‌نویس و انتشار منتشر می‌کنند (رفتار Strapi v5) و نسخهٔ نوشته‌شده را برای پاسخ دوباره می‌خوانند.
  7. پاسخ. { "data": …, "meta": … }. خطاها از همین پوشش با data: null و یک شیء error استفاده می‌کنند.

مسیرهای API مدیریت همین مسیر را طی می‌کنند، با یک نشست مدیریت به جای توکن API، RBAC مدیریت به جای مجوزهای API محتوا، و پیش‌فرض‌های پیش‌نویس‌محور: پیش‌نویس‌ها را می‌خوانند و فقط پیش‌نویس می‌نویسند، و انتشار یک کنش صریح است. GraphQL آرگومان‌هایش را پیش از گام 5 به همان درخت پارامتر ترجمه می‌کند، بنابراین parser، محدودیت‌ها و قاعده‌های مجوز را به اشتراک می‌گذارد.

Verdin 업그레이드

이 페이지에서는 프로젝트를 새 Verdin 버전으로 옮기는 방법을 설명하고, 마이너 버전 사이에 바뀐 것을 나열합니다. Verdin은 0.x 방식을 더한 Semantic Versioning을 따릅니다. 1.0 전까지 마이너 릴리스(0.8 → 0.9)는 동작이 바뀔 수 있고, 패치 릴리스(0.9.0 → 0.9.1)는 수정과 보안 강화만 합니다.

업그레이드하기 전에

섹션 제목: “업그레이드하기 전에”
  1. 현재 버전부터 새 버전까지의 changelog를 읽으세요. changelog에 모든 변경이 있고, 아래 참고 사항은 조치가 필요한 것을 요약합니다.
  2. 데이터베이스와 미디어 스토리지를 백업하세요(백업 참고). 이전 버전으로 돌아가려면 그 백업을 복원해야 합니다. 이전 버전은 새 버전이 추가한 테이블과 컬럼을 되돌리지 않습니다.
  3. 참고 사항에 프런트엔드나 편집자가 의존하는 동작이 언급되어 있으면 프로덕션 사본에서 시험해 보세요.

버전을 건너뛸 수 있습니다. 마이그레이션은 릴리스마다 하나씩 재생하는 것이 아니라 데이터베이스와 새 버전이 기대하는 것의 차이로 계산하므로, 0.6 → 0.9도 한 번에 마이그레이션됩니다. 그 사이 모든 버전의 참고 사항을 읽으세요.

업그레이드

섹션 제목: “업그레이드”
  • Docker
  • Binary

  1. Compose 파일, 매니페스트, Dockerfile에서 이미지 태그를 바꿉니다. 예: ghcr.io/verdin-cms/verdin:0.10 → ghcr.io/verdin-cms/verdin:0.11. 마이너 태그(0.10)는 패치 릴리스를 따라갑니다. 패치가 들어오는 시점도 직접 정하려면 전체 버전(0.10.0)을 고정하세요.

  2. 이미지를 받고 재시작합니다.

    이미지의 기본 명령인 start --migrate가 서비스하기 전에 새 버전의 마이그레이션을 적용합니다. 로그에서 applied migrations와 verdin listening을 확인하세요.

  1. 릴리스 페이지에서 플랫폼용 아카이브(예: verdin-v0.10.0-x86_64-unknown-linux-musl.tar.gz)를 내려받고, 릴리스의 SHA256SUMS로 확인합니다.

  2. 서버를 멈추고, verdin 바이너리를 교체하고, 버전을 확인합니다.

  3. 프로젝트 디렉터리에서 마이그레이션을 검토하고 적용합니다.

    또는 safe 단계를 먼저 적용하는 verdin start --migrate로 시작하세요.

  4. 평소처럼 서버를 시작합니다(verdin start).

시작할 때의 마이그레이션

섹션 제목: “시작할 때의 마이그레이션”

새 버전은 흔히 자체 테이블이나 컬럼(세션, 설정, 새 기능)을 추가합니다. verdin start는 데이터베이스를 스키마와 새 버전이 필요로 하는 것과 비교합니다.

  • 일치하면 시작합니다.
  • 대기 중인 단계가 있으면 시작을 거부하고, verdin migrate plan과 verdin migrate apply를 실행하거나 --migrate로 시작하라고 알려 줍니다.
  • --migrate는 safe 단계만 적용합니다. risky나 destructive 단계가 있으면 시작이 실패하며, 플랜을 읽은 뒤 verdin migrate apply --allow risky(또는 destructive)로 직접 적용합니다.
  • 스키마 변경을 트랜잭션에서 실행할 수 없는 MySQL과 MariaDB에서는 중단된 마이그레이션이 다음 verdin migrate apply에서 실패한 단계부터 재개됩니다.

인스턴스가 여러 개면 롤링 업그레이드가 동작합니다. 첫 새 인스턴스가 마이그레이션 잠금을 잡고 마이그레이션하며, 나머지는 기다렸다가 할 일이 남지 않은 것을 확인합니다. 여러 인스턴스 실행을 참고하세요.

주의

프로젝트 전체를 한 버전으로 업그레이드하세요. 두 마이너 버전의 인스턴스를 롤링 배포에 걸리는 시간보다 오래 나란히 실행하지 마세요.

업그레이드 참고 사항

섹션 제목: “업그레이드 참고 사항”

버전별 주요 변경과 호환성을 깨는 변경이며, 오래된 것이 마지막입니다. 전체 목록은 changelog에 있습니다.

0.10 → 0.11

섹션 제목: “0.10 → 0.11”

시작할 때 실행되는 마이그레이션은 테이블 하나, vd_cluster_events를 추가하며, [cluster] bus = "database"일 때만 쓰입니다.

  • Decimal: 정수인 decimal 값은 Strapi처럼 JSON 정수(25, 25.0이 아님)로 반환됩니다. JSON 타입을 엄격하게 검사하는 클라이언트는 차이를 느낄 수 있습니다. [api] decimal_as_string은 그대로입니다. SQLite에서 decimal의 sort와 $gt/$lt/$between은 이제 텍스트가 아니라 숫자를 비교하므로, 예전의(잘못된) 순서에 의존하던 결과는 바뀝니다.
  • **로컬라이즈된 타입의 populate=***는 Strapi v5처럼 문서의 다른 로케일 버전인 localizations도 반환합니다. 스키마에 localizations라는 속성이 있다면 그 의미가 유지됩니다.
  • 플러그인: 플러그인 자신의 쓰기로 발생한 after 훅은 쓰기 안이 아니라 플러그인의 호출이 반환된 뒤 실행되며, 쓰는 훅은 최대 4단계까지 중첩됩니다. 호스트 함수는 호출의 시간 제한에서 멈춥니다.
  • 여러 인스턴스: 모든 인스턴스에 [cluster] bus = "database"를 설정해 실시간 스트림, 프레즌스, 응답 캐시, 검색 인덱스가 다른 인스턴스에서 생긴 변경을 따라가게 하세요(확장 참고).
  • 관리자 목록을 읽는 스크립트: GET /admin/api/users, /roles, /api-tokens, /webhooks, /releases, /site/redirects, /site/menus, /site/forms, /deploy/targets는 pageSize(최대 100)를 넘기지 않으면 25개 행을 반환하며, 이미 페이지로 나뉘던 목록처럼 meta.pagination이 붙습니다. page가 meta.pagination.pageCount에 이를 때까지 ?page=로 페이지를 넘기세요. /deploy/deployments는 최신 50개를 반환하는 대신 같은 방식으로 페이지를 나누며, limit은 pageSize의 지원 중단된 별칭으로 계속 동작합니다. 목록을 참고하세요.

0.9.1 → 0.10

섹션 제목: “0.9.1 → 0.10”

데이터베이스 마이그레이션은 없습니다. 문서가 docs/에서 이 사이트로 옮겨졌습니다.

  • review-workflows.updateEntryStage 웹훅 수신자: model은 이제 항목 이벤트처럼 단수 이름(article)이고, uid는 uid로 옮겨졌습니다. model을 쓰던 곳에서는 uid를 읽으세요.
  • TypeScript 타입을 다시 생성하세요(verdin types). Collections와 Singles가 이제 타입 별칭이며, createClient<VerdinSchema>에 이것이 필요합니다.
  • Docker: 이미지는 변환 캐시와 검색 인덱스를 /data에 두고 /app/public/uploads를 /data/uploads로 링크합니다. 읽기 전용 /app을 피하려고만 VERDIN_UPLOAD__TRANSFORMS__CACHE_DIR나 VERDIN_SEARCH__DIR를 설정했다면 지워도 됩니다. 이미지에 HEALTHCHECK가 있습니다.
  • CDN: 응답에 populate할 수 있는 타입의 태그가 붙으므로, 퍼지가 전보다 더 많은 캐시를 새로 고칩니다. 바꿀 것은 없습니다.
  • 관리자 패널의 관계 필드는 인라인 검색 상자 대신 대화 상자(항목 연결)로 항목을 연결합니다.

0.9.0 → 0.9.1

섹션 제목: “0.9.0 → 0.9.1”

보안 강화 릴리스이며, 모든 설치에서 업그레이드를 권장합니다. 마이그레이션(새 테이블 하나, 새 컬럼 두 개)은 시작할 때 실행됩니다.

  • 리버스 프록시 뒤에서는 [server].trusted_proxies를 설정하세요. 나열한 프록시의 X-Forwarded-For만 클라이언트 주소로 씁니다. 그러지 않으면 프록시 뒤의 모든 클라이언트가 요청 한도와 감사 로그에서 주소 하나를 공유합니다.
  • 다른 출처의 브라우저 프런트엔드에는 [api].cors_origins가 필요합니다. 0.9.1이 콘텐츠 API와 GraphQL에 CORS를 추가했습니다. 이전에는 CORS 지원이 없었습니다.
  • 관계를 통한 읽기가 권한을 따릅니다. populate, 관계 필터, 관계 정렬은 모든 API에서 호출자가 읽을 수 있는 타입과 필드에만 닿습니다. find 권한이 없는 타입을 populate하던 공개 요청과 토큰 요청은 이제 더 적은 데이터를 받습니다. 빠진 권한을 허용하세요.
  • SSO가 더 엄격해졌습니다. 설정에는 Super Admin이 필요하고, defaultRoles와 roleMap은 Super Admin을 줄 수 없으며, 제공업체의 email_verified 클레임이 true여야 하고(trustUnverifiedEmail이 아니면), 제공업체를 신뢰하지 않으면 (providerMfa) 관리자의 두 번째 인증 수단이 적용되며, 발급자와 토큰 엔드포인트는 공개 https URL이어야 합니다. 업그레이드 후 SSO 로그인을 확인하세요.
  • Super Admin은 다른 Super Admin만 생성, 편집, 삭제, 재초대, 재설정할 수 있습니다.
  • 최종 사용자 계정은 관리자 계정처럼 비밀번호를 반복해서 틀리면 잠깁니다.
  • populate한 관계는 항목과 관계당 최대 1,000개 항목을 반환합니다.
  • 검색 인덱스는 첫 시작에서 다시 만들어집니다(private 컴포넌트 필드는 더 이상 인덱싱하지 않음).

0.8 → 0.9

섹션 제목: “0.8 → 0.9”
  • 관리자 목록의 검색 상자가 제목 대신 모든 텍스트 필드를 검색합니다(_q).
  • 새 관리자 권한 deploy.manage, deploy.trigger, site.manage. Editor는 deploy.trigger와 site.manage를 받습니다.
  • 새 선택 기능(실시간, 댓글과 작업, AI 기능, SEO와 사이트맵, 리디렉션, 메뉴, 폼)은 켜기 전까지 꺼져 있습니다. 메트릭에는 [metrics].enabled = true가 필요합니다.

0.7 → 0.8

섹션 제목: “0.7 → 0.8”
  • 조건부 필드가 적용됩니다. conditions로 숨겨진 필드는 더 이상 필수가 아닙니다. 그런 필드가 필수라는 데 의존하던 콘텐츠는 이제 그 필드 없이 저장될 수 있습니다.
  • 새 password 속성 타입. verdin import strapi가 이제 Strapi의 비밀번호 필드를 가져옵니다.

0.7.0 → 0.7.1

섹션 제목: “0.7.0 → 0.7.1”
  • 플러그인 런타임이 Wasmtime 48로 옮겨 갑니다. 기존 플러그인은 다시 빌드하지 않아도 계속 동작합니다.
  • 소스에서 빌드하려면 Rust 1.95 이상이 필요합니다.

0.6 → 0.7

섹션 제목: “0.6 → 0.7”
  • 여러 인스턴스: 각 인스턴스가 다른 인스턴스가 바꾼 설정을 [server].sync_interval_secs(10초)마다 읽습니다. 두 개 이상 실행한다면 하나를 뺀 모든 인스턴스에 [plugins].run_jobs = false를 설정하세요.

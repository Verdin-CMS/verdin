Permissions reference

Bu içerik henüz dilinizde mevcut değil.

This page lists every permission Verdin checks. It is generated from crates/verdin-auth/src/permissions.rs on every build, so it matches the server. For how roles, tokens and the public role fit together, see Permissions.

Verdin has two separate permission systems:

  • Admin permissions decide what an admin user can do in the admin panel and the admin API. They belong to roles, edited in Settings → Roles; a user has the union of their roles’ permissions.
  • Content API actions decide what a caller of /api and /graphql can do: anyone without a token (Settings → Public access), an API token (Settings → API tokens) or a signed-in end user (their role in Settings → End users).

Admin permissions

Section titled “Admin permissions”

An admin permission is an action, plus, depending on the kind of action:

  • Content actions take a subject: one content type (api::article) or all of them (*, All content types). They can be limited further:
    • to the documents the user created (the is-creator condition, shown as Own);
    • on content.read, content.create and content.update, to some fields (Fields). Other fields are hidden from reads and rejected on writes;
    • on localized types, to some locales.
  • Media library actions take no subject. is-creator limits them to the user’s own files (Own files).
  • Settings actions take no subject and no conditions: the user has them or not.

Super Admin is allowed everything by code and has no permission rows. Some operations are reserved to Super Admins whatever the permissions: managing Super Admin accounts, giving the Super Admin role, and switching single sign-on.

Built-in roles

Section titled “Built-in roles”
Role Permissions
Super Admin Everything.
Editor Every content action on all content types, every media library action, deploy.trigger and site.manage.
Author content.read, content.create, content.update and content.delete on their own entries (no publishing); media.read and media.create, media.update and media.delete on their own files.

Existing installations receive the permissions added to the built-in roles in later versions once, on upgrade.

Content

Section titled “Content”
Action Label in Roles Allows
content.read Read See entries of the type in the admin panel.
content.create Create Create entries, clone them and import them.
content.update Update Edit entries, restore versions from their history and move them between review stages.
content.delete Delete Delete entries.
content.publish Publish Publish and unpublish entries, discard drafts, and publish the entries of a release.

Media library

Section titled “Media library”
Action Label in Roles Allows
media.read Read files Browse the Media library and pick files in entries.
media.create Upload files Upload files (also from a URL) and create folders.
media.update Edit files Edit file details and replace files. Renaming and moving folders needs it on all files.
media.delete Delete files Delete files. Deleting folders needs it on all files.

Users and access

Section titled “Users and access”
Action Label in Roles Allows
users.manage Manage users Invite, edit, deactivate and delete admin users, and reset their second factors. Only a Super Admin can manage Super Admins or give that role.
roles.manage Manage roles Create, edit and delete admin roles, and edit Public access (what the content API allows without a token).
tokens.manage Manage API tokens Create, regenerate and delete API tokens.
endusers.manage Manage end users Manage End users: their accounts and their roles on the content API.

Content model and editing

Section titled “Content model and editing”
Action Label in Roles Allows
schema.manage Manage content types Use the Content-type builder (it edits schema files, so only in verdin dev).
locales.manage Manage locales Add, edit and remove locales in Internationalization.
views.manage Configure entry editors Configure the entry editor of each content type (field order, sizes, labels). Anyone who can read a type sees its layout.

Publishing workflows

Section titled “Publishing workflows”
Action Label in Roles Allows
releases.manage Manage releases Create, edit, publish and delete Releases, and add entries to them.
workflows.manage Manage review workflows Create, edit and delete Review workflows, and move entries to any stage (others only reach the stages open to their roles).

Platform

Section titled “Platform”
Action Label in Roles Allows
features.manage Manage features Switch features on and off in Features and edit their settings, and send a test email. Switching single sign-on is reserved to Super Admins.
webhooks.manage Manage webhooks Create, edit and delete Webhooks, rotate their secrets, trigger them and retry deliveries.
plugins.manage Manage plugins See installed Plugins, switch them on and off, edit their settings and read their logs.
audit.read Read audit logs Read the Audit logs.

Site and delivery

Section titled “Site and delivery”
Action Label in Roles Allows
deploy.manage Manage deploy targets and the CDN Manage deploy targets in Deployments and purge the CDN; includes triggering deploys.
deploy.trigger Trigger deploys Trigger deploys of the configured targets.
site.manage Manage SEO, redirects, menus and forms Manage SEO and sitemap settings, Redirects, Menus, Forms and their submissions.

Content API actions

Section titled “Content API actions”

The public role, API tokens with the Custom type and end-user roles grant these actions per content type. The media library (plugin::upload), the end-user accounts of /api/users (plugin::users-permissions.user) and the list of locales at /api/i18n/locales (plugin::i18n.locale) have rows of their own in the same grid. Everything is closed by default.

Action Label Allows
find Find GET /api/{pluralName} (and single types’ GET), GraphQL list queries.
findOne Find one GET /api/{pluralName}/{documentId}, GraphQL single queries.
create Create POST: create entries.
update Update PUT: update entries.
delete Delete DELETE: delete entries.
publish Publish POST /api/{pluralName}/{documentId}/actions/publish (also unpublish and discard-draft).
readDrafts Read drafts Reading ?status=draft.

publish and readDrafts do not apply to the media library and users rows. The locales row takes find only, as Strapi’s i18n plugin does. Reading drafts needs readDrafts on top of find or findOne.

API token types

Section titled “API token types”
Type Label Allows
read-only Read-only find and findOne on every type (no drafts).
full-access Full access Every action on every type.
custom Custom Only the listed grants.

Plugin routes and plugin GraphQL fields do their own access checks: the content API actions above do not apply to them (see Plugin reference).

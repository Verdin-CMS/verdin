Огляд архітектури

Цей розділ — для тих, хто працює над самим Verdin. У ньому пояснено, як зібрано сервер і адмін-панель, чому їх побудовано саме так і з чого починати читати код. Щоб користуватися Verdin, почніть натомість зі швидкого старту.

Verdin — headless CMS, написана на Rust, що наслідує Strapi v5: ви моделюєте вміст візуально або в JSON-файлах і отримуєте REST і GraphQL API та адмін-панель. Вона постачається як один бінарник, що містить сервер, CLI й адмін-панель на Angular, і працює з PostgreSQL, MySQL, MariaDB і SQLite.

Цілі

Section titled “Цілі”
  • Один бінарник. verdin містить сервер, CLI і вбудовану адмін-панель. Production не потребує ні Node.js, ні node_modules.
  • Швидкий запуск, невелике споживання пам’яті.
  • Чотири бази даних, один набір тестів. PostgreSQL, MySQL, MariaDB і SQLite — усі повноцінні й усі покриті тими самими тестами.
  • Схема як код. Типи вмісту — це JSON-файли, які ви версіонуєте в git.
  • REST API, сумісний зі Strapi v5, скрізь, де це розумно, щоб наявні фронтенди переходили з мінімумом змін.
  • Усе безкоштовно. Enterprise-версії немає: SSO, журнали аудиту, процеси перевірки, релізи та всі інші функції доступні всім.

Що вийшло в кожному релізі і що буде далі, описано в дорожній карті.

Що не є цілями

Section titled “Що не є цілями”
  • Запуск JavaScript-плагінів Strapi. Плагіни Verdin — це модулі WebAssembly (див. плагіни).
  • Читання бази даних Strapi як є. Вміст переноситься через імпортер (див. міграцію зі Strapi).
  • Рендеринг сторінок. Verdin — headless.

Принципи проєктування

Section titled “Принципи проєктування”
  1. Схема — джерело істини. Таблиці, валідація, REST і GraphQL API, документ OpenAPI та форми адмінки — усе виводиться з неї.
  2. Жоден SQL-ідентифікатор ніколи не береться із запиту. Назви таблиць і колонок беруться лише з перевіреної схеми, а кожне значення — прив’язаний параметр.
  3. Діалекти — повноцінні. Ніякого «працює на PostgreSQL, MySQL пізніше». Кожну функцію тестують на всіх чотирьох рушіях.
  4. Безпечно за замовчуванням. API вмісту закритий, доки ви не надасте дозволи, поля private ніколи не розкриваються, а обмеження глибини й розміру запитів завжди ввімкнені.
  5. Деструктивні операції — явні. Видалення колонки чи таблиці потребує вашого схвалення; воно ніколи не стається як побічний ефект.
  6. Жодного глобального стану. Сервіси передаються через стан axum і конструктори; синглтонів немає.

Загальна картина

Section titled “Загальна картина”

Запит потрапляє в бінарник через невеликий стек спільних шарів, доходить до одного з маршрутизаторів API і завершується в Document Service, що будує SQL для підключеного діалекту. Реєстр схеми, завантажений із schema/*.json, живить кожен крок, а рушій міграцій тримає базу даних у відповідності з ним.

  • API вмісту під [api].prefix (типово /api): REST-маршрути для кожного типу вмісту, завантаження й документ OpenAPI. Див. REST API.
  • Admin API під {admin.path}/api (типово /admin/api): усе, що робить адмін-панель. Див. admin API.
  • GraphQL на /graphql і MCP на /mcp, коли ці функції ввімкнено. Аргументи GraphQL перетворюються на те саме дерево параметрів, яке читає REST-парсер, тож обидва API мають спільні фільтри, пагінацію, populate і правила дозволів.
  • Адмін-панель під [admin].path (типово /admin), що віддається з бінарника або з [admin].assets_dir. Див. внутрішню будову адмін-панелі.
  • Службові маршрути: /_health, /_ready і /_metrics, коли метрики ввімкнено. Див. моніторинг.

Кожен запис проходить через Document Service, хоч би з якого API він надійшов. Він перевіряє дані, записує рядки й таблиці зв’язків в одній транзакції, а потім повідомляє слухачам (вебхуки, пошуковий індекс, історія, реальний час, журнал аудиту), що змінилося.

Коли функції вмикаються чи вимикаються або коли конструктор типів вмісту змінює схему у verdin dev, увесь маршрутизатор перебудовується й підміняється на місці (ArcSwap) без перезапуску.

Правило залежностей. verdin-schema і verdin-db — основа. verdin-migrate і verdin-query будуються на них, verdin-content — на цих, а verdin-auth, verdin-upload, verdin-search і verdin-plugins — на шарах під ними. verdin-api і verdin-graphql розташовані близько до вершини, а бінарник verdin залежить від усього. Cargo забороняє цикли, а код unsafe заборонено в усьому workspace.

З чого почати читати

Section titled “З чого почати читати”
Щоб зрозуміти Читайте
Як бінарник запускається й збирає маршрутизатори crates/verdin/src/cli.rs (start), потім crates/verdin/src/app.rs
Формат схеми та її правила валідації crates/verdin-schema/src/raw.rs, validate.rs, naming.rs
Як схема стає таблицями crates/verdin-migrate/src/derive.rs, потім сховище
Міграції crates/verdin-migrate/src/diff.rs, plan.rs, apply.rs і рушій міграцій
Обробники API вмісту crates/verdin-api/src/handlers.rs і lib.rs
Параметри запиту crates/verdin-query/src/params.rs (парсер), parse.rs (валідація), sql.rs (SQL)
Читання й запис crates/verdin-content/src/service.rs і input.rs, а також Document Service
Адмін-панель admin/src/app/app.routes.ts, потім features/content/ і внутрішня будова адмін-панелі

Переглядайте код на GitHub. Решта цього розділу охоплює сховище, шар бази даних, міграції, Document Service, адмін-панель, тестування і журнал рішень.

Поведінку для користувачів описано в інших місцях: параметри запиту — у REST API, налаштування — у довіднику конфігурації, команди — у довіднику CLI, а посилення захисту — у безпеці.

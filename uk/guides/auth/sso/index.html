Єдиний вхід

Адміністратори можуть входити через будь-якого провайдера OpenID Connect: Microsoft Entra ID, Google Workspace, Okta, Auth0, Keycloak, Authentik, GitLab та інших. Кожен провайдер отримує кнопку на сторінці входу, а вхід за паролем працює поруч із нею. У цьому посібнику ви зареєструєте застосунок, налаштуєте провайдера у Verdin і зіставите групи з ролями.

У Strapi SSO — функція Enterprise. У Verdin вона є частиною ядра з відкритим кодом. Для кінцевих користувачів ваших сайтів див. натомість вхід через OAuth для кінцевих користувачів.

Перш ніж почати

Section titled “Перш ніж почати”
  • Налаштування SSO потребує Керування функціями (features.manage).
  • Задайте [server].public_url — адресу, за якою адміністратори відкривають Verdin, наприклад https://cms.example.com. З неї будується URI перенаправлення.

Налаштування

Section titled “Налаштування”

  1. Зареєструйте застосунок (клієнт типу «web») у провайдера з таким URI перенаправлення:

    <id> — id провайдера, який ви виберете на кроці 3, наприклад corp. Шлях адмінки відповідає [admin].path.

  2. Покладіть секрет клієнта в середовище й перезапустіть Verdin:

    Змінна називається VERDIN_SSO_<ID>_SECRET, з id великими літерами й дефісами, заміненими на підкреслення. Публічні клієнти (лише PKCE, без секрету) змінної не потребують.

  3. Додайте провайдера. Увімкніть Налаштування → Функції → Єдиний вхід, виберіть Налаштувати провайдерів, потім Додати провайдера й заповніть:

    • ID: малі літери, цифри й дефіси, до 32 символів.
    • Текст кнопки: показується на сторінці входу як «Продовжити через …».
    • URL видавця: Verdin читає /.well-known/openid-configuration за цією адресою. Вона має використовувати https, окрім localhost.
    • ID клієнта та Області (scopes) (типово openid email profile; openid обов’язковий).

    Діалог показує URI перенаправлення для реєстрації в провайдера і назву змінної секрету. Збережіть.

  4. Спробуйте у приватному вікні: сторінка входу показує Продовжити через Corp account.

Хто може входити і з якими ролями

Section titled “Хто може входити і з якими ролями”
Налаштування Ключ JSON Дія
Дозволені домени ел. пошти allowedDomains Входити можуть лише ці домени ел. пошти. Порожньо — будь-які.
Створювати облікові записи під час першого входу autoCreate Створювати обліковий запис адміністратора, коли хтось входить уперше. Без цього входити можуть лише адреси, які вже мають обліковий запис.
Ролі за замовчуванням defaultRoles Коди ролей створених облікових записів, коли зіставлення ролей нічого не дає.
Claim ролі roleClaim Claim в ID token, що перелічує групи користувача, наприклад groups або roles.
Зіставлення ролей roleMap Який код ролі дає кожне значення claim.
Довіряти непідтвердженим адресам trustUnverifiedEmail Приймати адреси, які провайдер не позначає як підтверджені.
Провайдер вимагає MFA providerMfa Не запитувати в адміністраторів другий фактор Verdin після цього провайдера.
  • Провайдер, що створює облікові записи, потребує ролей за замовчуванням або зіставлення ролей.
  • Ні те, ні інше не може надати роль Super Admin; підвищуйте адміністраторів вручну в Налаштування → Користувачі.
  • Ролі задаються лише під час створення облікового запису. Після цього керуйте ними в Налаштування → Користувачі.
  • Ім’я та прізвище створеного облікового запису беруться з claims given_name і family_name.

Примітки щодо провайдерів

Section titled “Примітки щодо провайдерів”
  • Microsoft Entra ID не включає email_verified у свої ID tokens: увімкніть для нього Довіряти непідтвердженим адресам. Щоб зіставляти групи, додайте claim groups у конфігурації токенів застосунку; його значення — id груп.
  • Google Workspace: видавець — https://accounts.google.com. Обмежте вхід своїм доменом через Дозволені домени ел. пошти.
  • Keycloak: видавець — URL realm, https://<host>/realms/<realm>.

Двофакторна автентифікація

Section titled “Двофакторна автентифікація”

Типово в адміністратора, який має другий фактор Verdin, його запитують після повернення від провайдера. Коли провайдер уже вимагає MFA, увімкніть Провайдер вимагає MFA, щоб не запитувати двічі.

Як це працює

Section titled “Як це працює”
  • Verdin використовує authorization code flow з PKCE (S256). state підписаний і прив’язаний до короткочасної cookie HttpOnly, а nonce виводиться з нього.
  • Він перевіряє видавця ID token, аудиторію (і azp, коли їх кілька), термін дії та nonce. Потрібен claim email з email_verified: true, якщо не ввімкнено Довіряти непідтвердженим адресам.
  • Ендпоінти провайдера мають використовувати https.
  • Кожен вхід через SSO записується в журнали аудиту як admin.login із зазначенням провайдера.

Коли вхід не вдається, браузер повертається на сторінку входу з причиною («Не вдалося виконати єдиний вхід»), а причина записується в журнал сервера. Поширені причини:

Причина Виправлення
the provider did not verify the email Увімкніть Довіряти непідтвердженим адресам або виправте claim у провайдера.
this email domain may not sign in Додайте домен до Дозволені домени ел. пошти.
no admin account for this identity Увімкніть Створювати облікові записи під час першого входу або спершу створіть адміністратора.
the sign-in request expired or was not started here Почніть знову зі сторінки входу в тому самому браузері.

Заувага

Деактивований адміністратор також не може увійти через SSO.

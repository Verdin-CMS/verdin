権限

Verdin は 2 種類の利用者を別々に制御します。管理パネルにログインする管理者と、サイトやアプリからコンテンツを読み書きするコンテンツ API の呼び出し元です。このページでは、それぞれがどのように認可されるか、そして各要素がどう組み合わさるかを説明します。アクションの完全な一覧は権限のリファレンスにあります。

誰が 認証方法 権限の出どころ 適用先
管理者 メールアドレスとパスワード（さらに第二要素または SSO） その管理者のロール 管理パネルと Admin API
匿名の呼び出し元 Authorization ヘッダーなし 公開アクセス REST、GraphQL、リアルタイム
サーバーやビルド Authorization: Bearer vd_… API トークンの種類 REST、GraphQL、リアルタイム
ログイン済みのエンドユーザー Authorization: Bearer <JWT> そのエンドユーザーのロール REST、GraphQL、リアルタイム

デフォルトではすべてが閉じています。アクセスを許可するまでコンテンツ API は 403 を返し、管理者はロールで許可されたことしかできません。

管理者のロール

Section titled “管理者のロール”

管理者は 1 つ以上のロールを持ち、その権限は合算されます。組み込みのロールは 3 つです。

ロール できること
Super Admin ユーザー、ロール、API トークンを含むすべて。編集できません。
Editor すべてのコンテンツの閲覧、作成、更新、削除、公開。メディアライブラリの利用、デプロイの実行、SEO、リダイレクト、メニュー、フォームの管理。
Author コンテンツの作成と、自分が作成したエントリーだけの閲覧、更新、削除。公開はできません。ファイルをアップロードでき、編集・削除できるのは自分のファイルだけです。

その他のロールは設定 → ロール（権限 roles.manage）で作成します。最後の有効な Super Admin は無効化、削除、降格ができないので、インスタンスから締め出されることはありません。ロールでメンバーに二段階認証の設定を必須にすることもできます。設定するまで、メンバーは自分のプロフィールにしかアクセスできません。

権限とは

Section titled “権限とは”

権限は、アクション、コンテンツのアクションの場合は対象、そして任意の条件からなります。

  • コンテンツのアクション: 1 つのコンテンツタイプ（api::article）またはすべてのコンテンツタイプ（*）に対する content.read、content.create、content.update、content.delete、content.publish。
  • メディアのアクション: メディアライブラリに対する media.read、media.create、media.update、media.delete。
  • 設定のアクション: users.manage、tokens.manage、webhooks.manage、features.manage など。設定の対応するページを開けるようにします。
  • 条件: is-creator は、コンテンツやメディアの権限を、その管理者が作成したものに限定します。Author ロールはこの仕組みで動いています。

条件はデータベースのクエリの一部になります。is-creator で絞り込んだ一覧は、後から行を隠すのではないので、件数とページが正しくなります。

フィールドとロケールの権限

Section titled “フィールドとロケールの権限”

コンテンツの権限はさらに絞り込めます。

  • フィールド。 content.read、content.create、content.update では、対象とする属性を列挙できます。リストにないフィールドは読み取り（検索、フィルター、ソート、関連エントリーを含む）で隠され、書き込みでは拒否されます。
  • ロケール。 多言語化された型では、コンテンツの権限が対象とするロケールを列挙できます。他のロケールのバージョンは読むことも変更することもできません。

どちらも、ロールのエディターでコンテンツタイプごとに、フィールドと言語で設定します。

コンテンツ API

Section titled “コンテンツ API”

コンテンツ API の呼び出し元は、許可と照合されます。許可とは、対象に対するアクションです。

アクション 許可されること
find ドキュメントの一覧（GET /api/articles）、またはシングルタイプの読み取り。
findOne 1 件のドキュメントの読み取り（GET /api/articles/{documentId}）。
create POST
update PUT
delete DELETE
publish actions/publish、actions/unpublish、actions/discard-draft のルート。
readDrafts status=draft での読み取り。

対象は、コンテンツタイプ、メディアライブラリ（plugin::upload）、そしてエンドユーザーがオンの場合はエンドユーザーのアカウント（plugin::users-permissions.user）です。

どの呼び出し元にも当てはまるルールがいくつかあります。

  • 下書きを読むには、find または findOne に加えて readDrafts が必要です。サイトのコンテンツを読む許可で、未公開の作業を誤って読むことはありません。
  • リレーションを介した populate、フィルター、ソートには、その対象の型への読み取り権限が必要です。
  • private なフィールドは、許可にかかわらず返されません。
  • 書き込みは、Strapi と同様に、find がなくても書き込んだドキュメントを返します。
  • 同じ許可が GraphQL とリアルタイムストリームにも適用されます。

公開アクセス

Section titled “公開アクセス”

Authorization ヘッダーのないリクエストには、設定 → 公開アクセスの許可が与えられます。デフォルトでは何も許可されていません。サイトが表示する型に find と findOne を許可するのが一般的です。

API トークン

Section titled “API トークン”

API トークンは、サーバー、ビルドの工程、スクリプトのためのものです。設定 → APIトークン（権限 tokens.manage）で作成します。

種類 許可
読み取り専用 すべての型に対する find と findOne。下書きは読みません。
フルアクセス すべての型に対するすべてのアクション。下書きを含みます。
カスタム 公開アクセスと同様に、選んだ許可。
  • トークンは vd_ で始まります。シークレットは作成時と再生成時に一度だけ表示されます。Verdin はその鍵付きハッシュだけを保存します。
  • トークンには有効期限を設定できます。不明なトークン、期限切れのトークン、不正な形式のトークンは 401 になり、公開アクセスにフォールバックすることはありません。
  • ドキュメントを公開しない限り、有効なトークンならどれでも /api/_openapi.json の OpenAPI ドキュメントを読めます。

作成とローテーションについては API トークンを参照してください。

エンドユーザー

Section titled “エンドユーザー”

エンドユーザーは、Strapi の users-permissions プラグインと同様に、サイトやアプリにログインする人々です。この機能はデフォルトでオフです。各アカウントは 1 つのロールを持ちます。

  • Public はトークンのないリクエストのロールで、その許可は設定 → 公開アクセスのものです。
  • Authenticated は、デフォルトで新しいアカウントに与えられます。
  • カスタムロールは、上と同じアクションで任意の許可の組み合わせを持ちます。

エンドユーザーは、ログイン時に得た JWT を Authorization: Bearer <jwt> として送ります。Verdin は vd_ プレフィックスによって API トークンと区別します。エンドユーザーを参照してください。

Strapi との比較

Section titled “Strapi との比較”

モデルは Strapi v5 に従っています。is-creator 条件付きの管理者の RBAC と、公開アクセス、API トークン、users-permissions のロールを持つコンテンツ API です。違いは次のとおりです。

  • カスタムロール、フィールドとロケールの権限、SSO、監査ログなど、すべての機能をすべてのプロジェクトで使えます。
  • コンテンツ API で下書きを読むことは、独立した許可 readDrafts です。
  • REST での公開には、独立した許可 publish と専用のルートがあります。

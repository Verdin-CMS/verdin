デプロイと CDN

Verdin が提供するものをキャッシュするサイトのための、2 つの仕組みです。

  • デプロイは、管理画面のヘッダーにデプロイボタンを置きます。ボタンはサイトのビルドフック（Netlify、Vercel、Cloudflare Pages、または任意の CI）を呼び出し、プロバイダーがビルドの進み具合を報告します。
  • CDN のパージは、コンテンツ API のレスポンスにコンテンツタイプごとのタグを付け、コンテンツが公開の範囲で変わったときに、Cloudflare、Fastly、または独自のエンドポイントでそのタグをパージします。

どちらもコアの一部で、機能の切り替えはありません。デプロイは設定 → デプロイで、CDN は verdin.toml で設定します。

デプロイ

Section titled “デプロイ”

ターゲットを追加する

Section titled “ターゲットを追加する”
  1. プロバイダーで、サイトのビルドフックを作成してその URL をコピーします（Netlify: Build hooks、Vercel: Deploy Hooks、Cloudflare Pages: Deploy hooks、CI: POST でパイプラインを開始する任意の URL）。
  2. Verdin で設定 → デプロイに移動し、ターゲットを追加を選びます。
  3. 名前（本番サイトなど）を付け、ビルドフックURLを貼り付けます。
  4. 保存します。フックの URL はシークレットなので、以後はそのホストだけが表示されます。ターゲットを別のフックに向けるには、URLを置き換えるを使います。

デプロイできる管理者のヘッダーに、デプロイが表示されるようになります。ターゲットが複数ある場合は、デプロイ先のメニューが開きます。確認後、Verdin は次を送ります。

1 つのターゲットのデプロイは最大で 10 秒に 1 回なので、ダブルクリックしてもビルドが 2 回始まることはありません。リクエストは 15 秒でタイムアウトし、リダイレクトは追いかけません。2xx 以外で応答したフックは拒否として記録されます。

ビルドの状態を報告させる

Section titled “ビルドの状態を報告させる”

コールバックがない場合、デプロイは開始済みのままです。管理画面でビルド中、完了、エラーと、デプロイされたサイトへのリンクを表示するには、プロバイダーにターゲットのコールバック URL を渡します。ターゲットのコールバックURLボタンを選び、コピーしてください。

  • Netlify
  • Vercel
  • Other CI

Site configuration → Build & deploy → Deploy notifications で、Deploy started、Deploy succeeded、Deploy failed 用の送信 Webhook を、コールバック URL で追加します。

Team settings → Webhooks で、deployment.created、deployment.succeeded、deployment.error のイベント用の Webhook を、コールバック URL で作成します。

status（building、ready、error のいずれか）と、任意でデプロイされた url と message を含む JSON を POST します。

Verdin は Netlify の state、Vercel の type、そして素の status を理解し、ターゲットの最新のデプロイを更新します。204 を返し、URL が誤っていれば 404 を返します。コールバック URL は {public_url}{admin path}/api/deploy/callback/{id}/{secret} なので、[server].public_url をプロバイダーが到達できるアドレスに設定してください。

注意

コールバック URL にはシークレットが含まれています。それを持つ人は誰でも、そのターゲットのデプロイの状態を報告できます。デプロイを開始したり、何かを読んだりすることはできません。

デプロイ履歴には、直近の 50 件のデプロイが新しい順に、ターゲット、開始時刻、状態、フックの HTTP ステータス、プロバイダーのメッセージとともに一覧されます。ターゲットを削除すると、その履歴は削除されますが、ビルドフックは削除されません。

権限

Section titled “権限”
権限 許可されること
デプロイの実行（deploy.trigger） ヘッダーのデプロイボタン。組み込みの Editor ロールが持っています。
デプロイターゲットとCDNの管理（deploy.manage） 設定 → デプロイ: ターゲット、コールバック URL、CDN のパージ。

権限を参照してください。ビルドフックの URL は Webhook と同じアドレスの規則に従います。verdin start では、[webhooks].allow_private_networks で許可しない限り、プライベートなネットワークを指すことはできません。

変更のたびにデプロイする

Section titled “変更のたびにデプロイする”

ボタンは、必要なときに再ビルドするサイトに向いています。公開のたびに再ビルドするには、ビルドフックを URL にした entry.publish と entry.unpublish の Webhook を作成します。予定した変更のまとまりには、リリースで公開し、Webhook を releases.publish につなぎます。

CDN のパージ

Section titled “CDN のパージ”

CDN がコンテンツ API をキャッシュしていると、キャッシュの期限が切れるまで古いコンテンツを提供します。[cdn] を設定すると、Verdin はレスポンスにタグを付け、コンテンツが変わるたびに適切なタグをパージするので、長い時間キャッシュできます。

タグ付けの仕組み

Section titled “タグ付けの仕組み”

コンテンツ API の成功した GET にはすべて、vd（すべて）、vd-<singularName>（コンテンツタイプ）、そしてそのドキュメントが populate できるすべての型のタグが付きます。リレーションの対象で、コンポーネントやダイナミックゾーンの中も含み、さらにその先のリレーションもたどります。ブログのサンプルの記事では、両方のヘッダー形式で次のようになります。

ポリモーフィックリレーションを持つ型はどの型にも到達しうるので、そのレスポンスにはすべての型のタグが付きます。

Cloudflare は Cache-Tag を、Fastly は Surrogate-Key を読みます。コンテンツが公開の範囲で変わると、Verdin はその型のタグをパージします。

  • エントリーの公開、非公開、削除。
  • 下書きと公開を使わない型への書き込み（その書き込みはすぐに公開されるため）。

下書きは公開されないので、下書きを保存しても何もパージされません。1 秒以内（debounce_ms）の変更は 1 回のパージにまとめられ、失敗したパージは 2 回再試行されます。

設定する

Section titled “設定する”
  • Cloudflare
  • Fastly
  • Webhook

VERDIN_CDN_TOKEN は、そのゾーンに Cache Purge の権限を持つ API トークンです。

VERDIN_CDN_TOKEN は、そのサービスをパージできる Fastly の API トークンです。

Verdin は POST { "tags": ["vd-article"] } を送り、トークンが設定されていれば Authorization: Bearer <VERDIN_CDN_TOKEN> を付けます。別の CDN、リバースプロキシ、フレームワークの再検証 API に使ってください。

Verdin は起動時にこのセクションを確認し、プロバイダーが必要とする zone_id、service_id、url、トークンがなければ実行を拒否します。[cdn] を参照してください。

何をキャッシュするかを決めるのは引き続き CDN です。API のパス（たとえば匿名の GET での /api/*）に、エッジの TTL が長いキャッシュルールを設定してください。認証付きのリクエスト、プレビューの読み取り、/api/_events はキャッシュの対象外にします。

確認と手動のパージ

Section titled “確認と手動のパージ”

設定 → デプロイの CDN のセクションには、プロバイダーと最近のパージ（タグ付きでパージ済みまたは失敗）が表示されます。すべてパージは、vd のタグが付いたすべてのレスポンスを破棄します。

レスポンスには populate できる型のタグが付くので、カテゴリーの名前を変えると、リクエストが populate を求めたかどうかにかかわらず、そのカテゴリーを含みうるキャッシュ済みの記事の一覧もパージされます。

Verdin 自身のメモリ内キャッシュ（[api].cache_ttl_secs）は別のもので、変更のたびに空になります。
